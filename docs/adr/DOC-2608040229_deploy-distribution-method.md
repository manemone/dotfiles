# DOC-2608040229: dotfiles の配布方式（作業ツリー直リンクからの脱却）

- **Status**: Accepted
- **Date**: 2026-08-04
- **Decision by**: 傘 `ai/deploy-stability` の調査フェーズ（現行コードの網羅読解 + 実 `$HOME` の状態確認 + シンボリックリンク差し替え手法の実測）

> これは ADR（Architecture Decision Record）である。実測・調査に基づいて確定した技術的決定の記録であり、
> 原則として変更しない（新しい決定は新しい ADR を追加する）。

## 1. Context

### 1.1 現行方式

`deploy-all.sh` は各 `<tool>/deploy.sh` を呼び、`shared/helpers.sh` の `symlink_backup` を使って
**リポジトリの作業ツリー内のファイルへ `$HOME` から直接シンボリックリンクを張る**。

配布物の全量は次のとおり（調査で網羅的に確認した）。

| ツール | 配布先 | 方式 |
|---|---|---|
| `zsh` | `~/.zshrc`, `~/.zsh_plugins.txt` | symlink |
| `nvim` | `${XDG_CONFIG_HOME:-~/.config}/nvim/init.lua`, `.../lua`, `.../lazy-lock.json` | symlink（`lua` はディレクトリごと1本） |
| `tmux` | `~/.tmux.conf` | symlink |
| `bin` | `~/bin/ocw`, `~/bin/claude-ds`, `~/bin/ocw-meter` | symlink |
| `claude` | `~/.claude/CLAUDE.md` | symlink |
| `claude` | `~/.claude/settings.json` | **実ファイル生成**（`claude/settings.json` と非追跡の `claude/settings.machine.json` を python3 でマージ） |
| `claude` | `~/.claude/skills/<skill 名>` | **スキルごとに個別 symlink**。退避先も専用の `~/.claude/skills-backup/<名前>.<日時>.<PID>` |

### 1.2 解きたい3つの不安定さ

1. **配布物と作業ツリーが同一。** deploy 後にリポジトリ側のファイルを編集すると、コミットもしていない
   編集途中の状態がそのまま `$HOME` の設定として有効になる。壊れた中間状態が即座に本番になり、
   シェルや nvim が起動しなくなり得る。
2. **ワークツリーからデプロイすると寿命が違う。** `git worktree` を消した時点で `$HOME` 側の
   symlink が全部リンク切れになる。このリポジトリは `ocw` / 傘ブランチ運用でワークツリーを日常的に
   作っては消すため、現実に踏む。
3. **どこからデプロイされたか追跡できない。** 今 `$HOME` に効いている設定がどのツリーのどのコミット
   由来なのかを、リンク先パスを読む以外に知る手段がない。

## 2. 調査で確定した事実

決定の前提になった事実を記録する。いずれも本 ADR を書いた時点で実物を確認したものである。

### 2.1 「警告するだけ」は既に実装済み

`shared/helpers.sh` の `is_linked_worktree` / `warn_if_linked_worktree` が、リンクされた
git ワークツリーからの deploy を検出して警告する（PR #33 で導入。ルート `README.md` の
「Deploying from a git worktree」節も対応済み）。**したがって「現行方式を維持し警告するだけ」の
最小案は、既に取り込み済みの現状そのものである。** 追加できる価値は「拒否」「由来の可視化」
「リンク切れの検出」に限られ、問題1（編集途中が即本番）には原理的に手が届かない。

### 2.2 symlink の「即時反映」は既存ファイルの中身にしか効かない

実 `$HOME` の状態を確認したところ、全リンクが `dotfiles/master`（メインワークツリー）を指していた。
一方 `~/.claude/skills/` には `pr-review-loop` と `umbrella-orchestrator` しかなく、master に既に
存在する `repo-baseline` スキルは配布されていなかった。

つまり現行方式でも、**ファイルの追加・削除・リネームは再デプロイしないと反映されない**。
「即時反映」の利益は「既に配布済みのファイルの中身を書き換えたとき」に限定される。

### 2.3 配布物は単ファイルでは自己完結しない

`zsh/.zshrc` は自分自身のパスを `${(%):-%x}:A`（realpath 展開）で解決し、そこから
`DOTFILES_DIR` を逆算して `$DOTFILES_DIR/shared/helpers.sh` を source する。
`bin/ocw-meter` は自分のディレクトリ相対で価格表 `bin/prices/*.json` を探す。

**配布実体は「ツリーごと」でなければ成立しない。** 個別ファイルを `$HOME` へコピーする方式は、
これらの相対参照を壊す。

### 2.4 非追跡ファイルが配布経路に乗っている

`claude/settings.machine.json`（マシン固有設定・`.gitignore` 済み）は `claude/deploy.sh` の
マージ入力である。配布実体を `git archive` で作ると**この設定が黙って落ちる**。
配布実体の生成は「作業ツリーのファイルコピー」でなければならない。

### 2.5 `current` シンボリックリンクの差し替え手法（実測）

Linux（GNU coreutils）の一時ディレクトリで実測した結果:

| 手法 | 結果 |
|---|---|
| `ln -sfn <新> current` | ✅ `current` が新しい先を指す。ただし unlink → symlink の2手であり原子的ではない |
| `mv -f <新リンク> current` | ❌ **`current/` の中へ移動してしまった**（`current` がディレクトリへの symlink のため） |
| `mv -T <新リンク> current` | ✅ 原子的に差し替わる。ただし **`-T` は GNU 専用**（BSD/macOS には無く `-h` が必要） |

### 2.6 隣接する既存バグを2件検出した

- `uninstall.sh` の `KNOWN_LINKS_bin` に **`ocw-meter` が無い**。`bin/deploy.sh` は張っているため、
  uninstall しても `~/bin/ocw-meter` が残る。
- `bin/ocw-meter` は `OCW_METER_SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"` で
  価格表の位置を決めるが、**`BASH_SOURCE[0]` の symlink を解決していない**。`~/bin/ocw-meter`
  経由で起動すると `~/bin/prices` を探して外す。symlink 配布に特有の壊れ方である。

## 4. 採用案（C）: 世代ディレクトリ + `current` シンボリックリンク

### 4.1 構造

```
${XDG_DATA_HOME:-$HOME/.local/share}/dotfiles/
├── generations/
│   ├── 20260804T091500-fab7694/     ← 世代ディレクトリ（配布実体）
│   │   ├── .dotfiles-manifest       ← 由来の記録
│   │   ├── shared/
│   │   └── zsh/  nvim/  tmux/  bin/  claude/
│   ├── 20260804T101200-25e1430/
│   └── 20260804T113000-fab7694/
└── current -> generations/20260804T113000-fab7694
```

`$HOME` 側のシンボリックリンクは**必ず `current` を経由するパス**を指す
（例: `~/.zshrc -> ~/.local/share/dotfiles/current/zsh/.zshrc`）。
世代ディレクトリを直接指さない。**これが世代方式の要**であり、`current` を1本付け替えるだけで
全リンクの向き先が一斉に切り替わる（＝ロールバックが1手で済む）。

### 4.2 デプロイの流れ

1. 作業ツリーから新しい世代ディレクトリへツリーをコピーする
2. `.dotfiles-manifest` を世代ディレクトリ内に書く
3. `current` を新世代へ付け替える
4. 各 `<tool>/deploy.sh` が `$HOME` から `current` 経由のパスへ symlink を張る
5. 保持数（3）を超えた古い世代を削除する

### 4.3 世代の中身は常に全ツール分にする

`--only <tools>` は「`$HOME` のどのリンクを張り直すか」だけを制御し、**世代ディレクトリの内容には
影響させない**。

理由: `--only zsh` のときに zsh だけをコピーした世代を作ると、`current` を切り替えた瞬間に
`~/bin/ocw` など他ツールのリンクが**新世代に存在しないパスを指してリンク切れになる**。
`current` が全リンクの共通の起点である以上、世代は常に完全な集合でなければならない。

### 4.4 `.dotfiles-manifest` の内容（問題3への回答）

世代ディレクトリ直下に平文で置く。少なくとも次を記録する。

- デプロイ日時
- ソースツリーの絶対パス
- コミット SHA / ブランチ名
- 作業ツリーが dirty だったか
- リンクされた git ワークツリーからのデプロイだったか
- モード（世代モード / dev モード）
- デプロイしたホスト名

### 4.5 dev モード（即時反映を捨てない）

`current` を世代ディレクトリではなく**作業ツリーそのもの**へ向けるモードを用意する。
このとき世代は作らない。挙動は現行方式と等価で、リポジトリを編集すれば即 `$HOME` に反映される。

- 既定は世代モード。dev モードは明示的な指定でのみ有効になる
- dev モード中であることは状態表示コマンドで必ず可視化する
- dev モードで**リンクされたワークツリー**を指した場合は、既存の `warn_if_linked_worktree` と
  同じ趣旨の警告を出す（そのワークツリーを消せば全リンクが切れるため）

これにより「設定を試行錯誤しやすい」という現行方式の利点は、失われるのではなく
**既定から外れて明示的な選択になる**。2.2 のとおり即時反映の実効範囲はもともと
「既存ファイルの中身の書き換え」に限られており、通常運用では再デプロイ（コピーのみで一瞬）で足りる。

### 4.6 保持世代数は3

理由:

- **走行中プロセスの足元を残す。** nvim の lazy.nvim は起動後もランタイムに `lua/` を遅延読み込みする。
  旧世代を即削除すると、nvim を開いたまま再デプロイした後の遅延ロードが失敗する。
- **直前へのロールバックが `current` の付け替えだけで済む。** シェルが起動しなくなった状態からの
  復旧手段として、git の操作（stash → checkout → 再デプロイ）より確実で短い。
- コストは GC 処理と数十 MB のディスクのみ。

GC は「`current` が指す世代は決して削除しない」「dev モード中は世代の削除を行わない」を不変条件とする。

### 4.7 移植性の判断

- **`current` の差し替えは `ln -sfn` を使い、原子性は追わない。**
  `mv -T`（GNU）/ `mv -h`（BSD）で分岐すれば原子的にできるが、**macOS の実機で検証できない
  コードパスを macOS 側にだけ置くことになる**。差し替えの窓は unlink から symlink までの
  数マイクロ秒であり、その瞬間にシェルが起動する確率は、検証されない分岐を抱えるリスクに見合わない。
  `ln -sfn` は GNU / BSD の双方で広く使われるイディオムである。
- **コピーは `cp -a` を使う。** `rsync` に依存しない（最小構成の Linux に無いことがある）。
  `-a` は GNU / BSD 双方にある。
- `date` はオプション無しの `date +FORMAT` のみを使う（BSD/GNU 共通で安全。
  シェルスクリプトコーディング方針 DOC-2608020715-a の第7節に従う）。

### 4.8 既存の例外（`claude/`）の扱い

- **`~/.claude/settings.json`（実ファイル生成）**: マージ元を `current/claude/settings.json` と
  `current/claude/settings.machine.json` に変更する。生成物が実ファイルであること自体は変えない。
  非追跡の `settings.machine.json` は 2.4 のとおり `cp -a` でコピーされるため世代内に入る。
- **`~/.claude/skills/<name>`（個別 symlink）**: リンク先を `current/claude/skills/<name>` に変更する。
  `uninstall.sh` の「リポジトリ由来の symlink か」の判定（現行は `$SCRIPT_DIR/claude/skills` 前方一致）は、
  **canonical prefix 配下と旧方式の作業ツリー配下の両方**を認識するようにする（移行のため）。

### 4.9 状態ファイル（$HOME 側からの書き戻し）の扱い

`~/.config/nvim/lazy-lock.json` は `current/nvim/lazy-lock.json` への symlink であり、実体は
**世代ディレクトリ内のコピー**である（4.1 の原則どおり）。lazy.nvim は `:Lazy update` / `:Lazy sync`
でこのファイルを symlink 経由で**書き戻す**。書き込み先は世代ディレクトリ内のため、リポジトリの
`nvim/lazy-lock.json` には反映されず `git status` にも出ない。結果、ロック更新は次の
`create_generation`（作業ツリーからの `cp -a`）で作られる新世代に**引き継がれず消える**。

作業ツリー直リンク方式（8b944bb 以前）ではこの書き戻しがそのまま `git status` に出ていたため、
これは世代方式移行で新たに生まれた回帰である。同種の書き戻しファイルは
`nvim/lazy-lock.json` の他に無いことを確認済み（`zsh/.zsh_plugins.txt` は antidote の
**入力**ファイルで人間が編集する側、ツールは書かない。`claude/settings.json` は §4.8 の
既存の実ファイル生成であり別問題）。

**採用した対処: デプロイ時に検知＋取り込み。symlink 配布は維持する。**

`$HOME` はリポジトリを知らないという本 ADR の設計思想を壊さず、失われる情報をゼロにできること、
将来ほかの書き戻しファイルが増えても同じ経路で拾えることが採用理由。却下した案:
`lazy-lock.json` を配布物から外し nvim 所有の実ファイルにする案、`lazy-lock.json` だけ
ソースツリー直リンクの例外にする案（symlink 配布の一貫性を崩す）、運用ルールのみで済ませる案
（見落としを防げない）。

- `shared/helpers.sh` の `state_files_for_tool()` が、ツールごとの状態ファイル（ツール相対パス）
  の一覧を返す。`links_for_tool()` と同じ「一元化して二重管理を避ける」作法に従う。現時点の中身は
  `nvim` の `lazy-lock.json` のみ
- `shared/helpers.sh` の `detect_state_writeback()` が、`current` が指す世代とソースツリーの間で
  状態ファイルを `cmp -s` で比較する（`diff` は最小構成の Linux に無いことがあるため使わない —
  §4.7 が `rsync` を避けたのと同じ理屈）
- `deploy-all.sh` は `create_generation` を呼ぶ直前にこの検知を挟む。差分があれば警告して停止し、
  取り込み方（`--adopt-state`）を案内する。`--force` で続行（＝破棄）できる
- `--adopt-state`: `current` が指す世代の状態ファイルをソースツリーへ**コピーバックするだけ**で
  終了する（`git status` で確認・コミットしたうえで、改めて通常の deploy を実行してもらう
  2段階のフローを意図している）。世代を作らず `current` も `$HOME` symlink も一切触らない
- `--dev` 中は検知をスキップする。dev モードでは `current` がソースツリー自身を指すため差分が
  常にゼロで、検知が空回りするため
- `--dry-run` でも検知は走らせる（report-only）。プレビューの意味がなくなるため
- `--status` は既存の副作用ゼロの原則を保ったまま、未取り込みの状態ファイルがあれば表示する
  （検知結果を理由に非0終了にはしない。取れる対応が `--adopt-state` であって `--status` 自体が
  壊れているわけではないため）

**残された穴（rollback）**: `--rollback` で `current` が旧世代へ切り替わると、その世代は
`gc_generations` の「`current` が指す世代は削除しない」という保護を失う。書き戻しが入ったまま
`--adopt-state` されていない世代は、その後の通常デプロイの GC で削除され得る。GC 側に
「ソースツリーと差分がある世代は保護する」という不変条件を追加することも検討したが、
複数回の rollback を経ると「どの世代の書き戻しを保護すべきか」の判定が複雑になり、
複雑さに見合わないと判断して却下した。代わりに `cmd_rollback` が、切り替え前に
`current` が指す世代の未取り込み差分を検知して警告する（ブロックはしない — rollback は
緊急復旧のためのコマンドであり、ここで止めるのは本末転倒なため）。この穴は自動では塞がれない、
運用でカバーする既知のギャップとして記録する。

### 4.10 移行パス

既存マシンは新方式で `./deploy-all.sh` を実行するだけでよい。ただし1点、現行の `symlink_backup` は
「dst に既存のものがあれば `.backup` へ退避」するため、**旧方式の symlink がそのまま `.backup` として
残ってしまう**（`~/.zshrc.backup` が古い symlink になり、後日 `uninstall.sh` がそれを「ユーザーの元設定」
として復元する）。

したがって `symlink_backup` に「dst が既に**このリポジトリ由来の** symlink であれば、退避せずに
張り替える」判定を加える。判定基準は「リンク先が canonical prefix 配下、またはソースツリー配下であること」。

## 5. 却下した案と理由

### 案A / 案F: 現状維持・やらない

**却下。** 2.1 のとおり、警告はもう入っている。問題1は運用（「メインワークツリーでは編集しない」）でしか
回避できず、傘ブランチのマージ後にメインワークツリーへ戻って作業する場面は現に存在する。
問題3に至っては手段が `readlink` しかない。3つの問題のうち2つが未解決のまま残る。

### 案B: ガード強化のみ（worktree からの deploy を拒否 + 状態表示）

**却下。** 問題2・3には有効で、コストも小さい。しかし**問題1に原理的に手が届かない**。
配布物と作業ツリーが同一である限り、編集途中の状態が本番になる性質は消えない。
なお本案の要素（状態表示・リンク切れ検出）は、採用案の中に運用コマンドとして取り込む。

### 案D: `$HOME` へ実体をコピーする（symlink 廃止）

**却下。** 3つの問題は解決するが、コストが釣り合わない。

- `symlink_restore` は「dst が実ファイルならユーザーデータとみなしてスキップ」する設計であり、
  配布物が実ファイルになると**「ユーザーが編集したのか deploy が置いたのか」を判定できなくなる**。
  正しく作るには全配布ファイルのハッシュ台帳が必要になる。
- `nvim/lua/` のようなディレクトリ配布で、削除されたファイルの掃除を自前で実装する必要がある。
- 即時反映を完全に失い、dev モードのような逃げ道も作れない。

1人の開発者の dotfiles に対して明確に過剰である。

### 案E: `current` のみ（世代を保持しない）

**却下（ただし僅差）。** 検討の結果、安全に実装しようとすると案E は「一時ディレクトリへ同期 →
`current` を差し替え → 旧実体を削除」となり、**世代を1つだけ持つ案C と実装がほぼ同じ**になる
（単一ディレクトリへ直接同期すると、同期中の中間状態がそのまま本番になり問題1が形を変えて再発する）。
実装差分は GC 処理のみであるにもかかわらず、4.6 の2つの利益（走行中プロセスの保護・
ロールバックの容易さ）を失う。差が小さいなら得るほうを選ぶ。

### `mv -T` / `mv -h` による原子的な `current` 差し替え

**却下。** 4.7 のとおり、macOS 実機で検証できない分岐を抱えるコストが、数マイクロ秒の窓を
閉じる利益を上回る。

### 配布実体を `git archive` で作る

**却下。** 2.4 のとおり、非追跡の `claude/settings.machine.json` が落ちる。

### ファイル監視による自動再同期（watch）

**却下。** クロスプラットフォームで監視ツール（`fswatch` / `inotifywait`）への依存が増える。
dev モードがあれば同じ用途を依存ゼロで満たせる。

## 6. 検証方法

`tests/deploy_smoke.sh`（`HOME` を一時ディレクトリへ差し替えたサンドボックス。対象は既定どおり
`bin,claude`）に、本 ADR の性質を直接検証するシナリオを追加する。テスト方針 DOC-2608020715-b の
分類（副作用が `$HOME` の外やネットワークに及ぶ `zsh` `tmux` `nvim` はサンドボックス対象外）は変更しない。

- **ソースツリー消失耐性（問題2の回帰テスト）**: サンドボックス内にリポジトリのコピーを作り、
  そこから deploy → コピーを削除 → `$HOME` 側の配布物がまだ読めること
- **編集分離（問題1の回帰テスト）**: deploy 後にソースツリーのファイルを書き換え →
  `$HOME` 側から読める内容が変わらないこと
- **世代と GC**: 再デプロイで世代が増え `current` が新世代を指すこと。保持数を超えた古い世代が
  削除され、`current` が指す世代は削除されないこと
- **ロールバック**: `current` が直前の世代へ戻り、`$HOME` 側のリンクを張り直さずに内容が戻ること
- **dev モード**: `current` がソースツリーを指し、編集が即反映されること
- **移行**: 旧方式のリンクが張られた状態で deploy すると張り替わり、`.backup` に旧 symlink が
  残らないこと
- **uninstall**: canonical prefix が片付き、**dev モード時にソースツリーが削除されないこと**

## 7. この決定で変わらないこと

- `$HOME` 側の配布先パスの集合（`uninstall.sh` の `KNOWN_LINKS_*` / `KNOWN_GENERATED_*` の枠組み）
- `~/.claude/settings.json` が symlink ではなく生成された実ファイルであること
- `claude/skills/` をスキルごとに個別 symlink すること（ディレクトリ丸ごとの symlink 禁止）
- `.backup` による退避と `symlink_restore` による復元という uninstall の基本方針
- POSIX sh（`shared/helpers.sh` / `deploy-all.sh` / `uninstall.sh` / `*/deploy.sh`）という方言の制約
