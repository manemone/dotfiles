# ADR: 実装の孫に自己 compact の判断を思い出させるフック

## ステータス

決定（2026-10-15）。傘 `context-bloat`（計画書 DOC-2610142332）の孫3 で決めた。ADR
DOC-2610142337（実装途中の自己 compact）が決めた区切り・閾値・回数の上限を引き継ぎ、それを
**思い出させる**仕組みだけを足す。DOC-2610142337 と DOC-2610131214 は書き換えない。

## 1. 背景

実装の孫が compact を判断する機会は、スキル本文に書いた区切りの箇所に限られる。その本文は文脈の
ずっと前に読んだもので、作業に没頭すると判断自体が起きない（司令官側でも ADR DOC-2610140044 で
同じ形の取りこぼしが観測済み）。区切りの追加（DOC-2610142337）だけでは、追加した区切りも同じ理由で
見落とされる。

## 2. 決定

1. **フックは compact を打たず、判断を促す一文を差し込むだけ。** コマンドを実行しない。判断（区切りか・
   回数の上限・復帰メモ）は DOC-2610142337 のとおり孫が行う
2. **`OCW_ROLE=implementer` のときだけ働く。** `ocw -H` が各ペインに渡す環境変数で絞る。司令官
   （DOC-2610130913・DOC-2610140044）、レビュワー、`OCW_ROLE` を持たないセッションには何も言わない。`ocw -H --no-commander` で作る
   `task-intake` の軽いハンドオフの実装AIも `OCW_ROLE=implementer` を持つので対象に含まれる
   （自動付与指示は受け取らず、差し込みが入口になる。復帰メモにはブリーフのパスと最初の指示を残す。
   `pr-review-loop` の (3) に書いた）。絞りは
   シェルの先頭で行い、対象外の呼び出しでは python3 を起動しない（全ツール呼び出しで走るため）
   **サブエージェントのツール呼び出し（入力に `agent_id` がある）も黙る。** 環境変数は
   サブエージェントにも受け継がれるが、通知が親の孫に届かず、サブエージェントが親のペインを
   区切りでない時点で compact しうるため
3. **種類は PostToolUse（matcher なし）。** 実装の孫は長い 1 ターンで走り続けるので、ターンの終わりに
   しか来ない Stop では届きにくい。返し方は `hookSpecificOutput.additionalContext`
4. **文脈の測り方は transcript の末尾 1 MiB だけを読み、直近の assistant の `usage` の入力・
   キャッシュ読み・キャッシュ書き込みの合計を取る。** スキル本文の測り方（手順1のコマンド）と同じ量。
   実機の 330 MB の transcript でも約 80 ms（全体を読まない）
5. **閾値は 200,000 超（DOC-2610142337 §2.2 と同じ）。間引き: 超えた最初の 1 回、その後は前回の
   差し込みから 50,000 増えるごと。** 毎回差し込むと文脈を太らせ、無視されるようにもなる。
   文脈が閾値以下に戻ったら（compact した）状態を消し、次に超えたとき最初の 1 回から差し込む
6. **状態はセッション ID ごとのファイル**（`${XDG_STATE_HOME:-~/.local/state}/dotfiles/compact-reminder/`。
   リポの外）に、最後に差し込んだ文脈の大きさだけを書く。古いセッションのファイルは掃除しない
   （1 ファイル数バイトで、掃除の仕組みのほうが重い）
7. **判定できないときは黙る。** `OCW_ROLE` 以外、python3 が無い・入力が壊れている・transcript が
   読めない・usage が取れない・session_id が不正（パス区切りを含む）、のいずれも出力なしで exit 0。
   エージェントを止めない（`git-guard.sh` と同じ方針）
8. **言語は POSIX sh + python3**（`git-guard.sh` と同じ。JSON を扱うため python3 が要る）。
   ただしペイロードは `git-guard.sh` と違い stdin のまま渡し、python のコードを `-c` で渡す。
   matcher なしの PostToolUse には `tool_response`（ツール出力全体）が入り、引数1つで渡すと
   128 KiB（`MAX_ARG_STRLEN`）超で exec が失敗するため
9. **差し込む文面は短くし、手順の本文を持たない。** 「区切りなら `ocw self-compact` を判断」と、
   区切りの定義・WIP と指摘対応の修正の途中を除くことを一言で示し、手順は §3.2 の自動付与指示と
   `pr-review-loop` へ誘導する。実装中の孫に届く場所の本文（自動付与指示）にはフックへの言及を
   足さない: 文面自身が手順の場所を指すので言及が無くても動き、毎回読まれる場所を太らせない
   ことを優先した

## 3. 却下した案

- **Stop フック**: 長い 1 ターンの途中では発火せず、届かない
- **毎呼び出しで差し込む**: 文脈を太らせ、無視されるようになる
- **フックから `ocw self-compact` を打つ**: 区切りでない時点で compact すると作業中の判断が落ちる。
  DOC-2610142337 §6 の「区切りに関係なく即 compact」と同じ形になる
- **司令官・レビュワーにも効かせる**: 司令官は自分の手順で判断済み、レビュワーは 200k に届かない
  （DOC-2610131214 §2.1）。計画書 スコープ外
- **transcript 全体を読む**: 数十〜数百 MB になりうる。毎呼び出しで読めない
- **間引きを呼び出し回数で数える**: 回数は文脈の増え方と対応しない。増分のほうが「前回から状況が変わった」
  を表す

## 4. 未検証

- **実機で `additionalContext` が実装の孫の文脈に届くか。** デプロイは人間の指示が要り（AGENTS.md
  「最重要ルール」）、新しいエージェントを起動して試すことは auto mode の分類器に拒否される
  （計画書 DOC-2610122205 進行記録）ため、この PR では試していない。確かめるテスト（入力 JSON → 出力）は
  出力の形が Claude Code の PostToolUse の仕様どおりであることまでしか保証しない。デプロイ後に実装の孫が
  200k を超えたとき `[compact-reminder]` で始まる一文が見えるかを、人間か次の傘の司令官が確かめる
- 差し込みが孫の振る舞い（区切りでの compact の実施率）を実際に変えるか。DOC-2610142337 §4 の測定と
  同じ枠で、`quality.py` / `commits.py` に加え、compact 回数の増減で見る

## 追記（2026-10-20）: 区切りのツール呼び出しで再掲する

傘 `token-levers`（計画書 DOC-2610200214）の孫2 で決めた。§2 の決定 5 と 9 を次のとおり拡張する
（ほかの決定は変えない。閾値・回数の上限も DOC-2610142337 のまま）。

### 根拠

実測（2026-10-16〜19）で、pixidex の実装の孫 1 本がフックのリマインドを 200k〜454k の間に 6 回受けたのに、
一度も compact を判断しなかった。区切り（コミット・PR 作成・レビュー依頼・再レビュー依頼）は 10 回以上あったが、
リマインドが区切りと重なったのは 6 回中 1 回だけで、残りは修正やコンフリクト解消の途中に届いた。逆に、
リマインドが区切りの近くに届いた孫は、その場で compact を判断していた。つまり**判断が起きるかは、リマインドが
区切りに届くかで決まる**。50k ごとの間引きは区切りと無関係なので、これだけでは素通りされる。

### 決定

1. **区切りに当たるツール呼び出しで、閾値超えならリマインドを出す（50k の間引きとは別枠）。** 区切りは
   PostToolUse の入力から見分ける: `tool_name` が `SendMessage`、または `Bash` で `tool_input.command` が
   `git commit` / `git push` / `gh pr create` / `herdr agent prompt` に当たる。区切りの定義は DOC-2610142337 と
   `pr-review-loop`「区切りでの自己 compact」に合わせる。WIP のコミットと指摘対応の修正の途中はフックでは
   見分けられないので、従来どおり文面で除外を伝え、孫に見送らせる。承認後の報告（Phase 7）は
   `herdr agent prompt` / `SendMessage` を使うが区切りでない（`pr-review-loop`・DOC-2610131214）ので、文面で除外に挙げる
2. **1区切り1回。** 区切りを2種類に分け、種類ごとに直前のリマインドから 5 分は同じ種類で出さない。
   コミット系（`git commit` / `git push` / `gh pr create`。一続きを1区切りとして扱う）と、依頼系
   （`herdr agent prompt` / `SendMessage`）で、互いのクールダウンを消費しない。1つの共通のクールダウン
   にすると、指摘対応のコミットの直後 5 分以内に来る再レビュー依頼（実測では 3k 文脈が増える間）が
   黙り、本命の区切りに届かないため（レビューで指摘され修正した）。状態ファイルは 1 行目が文脈の大きさ
   （従来どおり）、2・3 行目がコミット系・依頼系の直前のリマインドの時刻（無ければ 0 または行なし）。
   文脈の増分で数える案は、一続きの操作で文脈がほとんど増えず、逆に区切りの間隔が空いても増えない
   場合があるため退け、時刻にした
3. **区切りでない呼び出しの 50k ごとの再掲は残す。** 区切りに届く前に 200k を大きく超える孫でも、
   最初の 1 回は届く。区切りのリマインドも「前回の差し込みの文脈」を更新するので、合わせた頻度が
   過剰にならない（区切りで出した直後の 50k 間は区切りでない呼び出しでは出ない）
4. **文面を変える。** 区切りのリマインドは「次のターンの冒頭で、compact するか見送るかを1行書くこと
   （見送るなら理由も）」とする。判断を言葉にさせて素通りを減らすため。区切りでない呼び出しの文面は従来のまま
5. **対象外の役割は python3 を起動しない（決定 2 のとおり）。** 区切りの判定は python3 の中で行い、
   シェルの先頭の役割の絞りより前には何も足していない。テストで固定した
   （`tests/compact_reminder_test.sh`。fake の python3 が呼ばれないことを確かめる）
6. サブエージェント（`agent_id` あり）では、区切りでも黙る

### 未検証

- 実機の PostToolUse で `SendMessage` が `tool_name` として入ること（ツール名どおりの想定。テストは
  合成の入力で確かめた）。デプロイ後に孫が 200k を超えたとき、区切りで出ることを人間か司令官が確かめる
- 区切りでの再掲が compact の実施率を変えるか（DOC-2610142337 §4 と同じ枠で、compact 回数の増減で見る）
