# ADR: 再レビューのたびにレビュワーの会話を新しくする

## ステータス

決定（2026-10-20）。傘 `token-levers`（計画書 DOC-2610200214）の孫1 で決めた。実機での確認結果は §5 に書く。
並走する傘 `review-tiering`（PR #164、レビューの形を段階的にする決定）とは変える対象が違う
（#164 は「何を指摘するか」、本 ADR は「レビュワーの会話をいつ作り直すか」と「どう読むか」）。

## 1. 背景

実測（pixidex のレビュワー64本、Opus）で、レビュワーの文脈は最初の1周で約145k に達し（開始時 約58k ＋ 開始直後 約19k ＋
ラウンド1の増分 中央値 約86k）、その後は再レビュー1回ごとに中央値 +8〜14k ずつ増える。ピーク中央値は 185k、最大 477k。
compact は64本すべてでゼロで、`claude/hooks/compact-reminder.sh` は実装の孫専用なので、レビュワーには膨張対策が一切無い。
ラウンドが進むほど、毎回の呼び出しで払う cache read が大きくなる。

## 2. 決定

1. **再レビューのたびに、レビュワーのエージェントを終了して起動し直す（既定）。** ラウンド2以降の頭だけで、
   初回のレビューには要らない。条件付き（文脈が一定以上のときだけ）にはしない。条件の閾値を決める実測が無く、
   「一定以上」の判定に手順が増えるほど、無人運用で壊れる箇所が増えるため。前ラウンドの指摘と返信は PR のコメントに
   残っているので、会話を捨てて失うものは少ない
2. **終了は `/exit` を `herdr pane send-text` で送り、`Enter` で確定する。** Claude Code / Codex / OpenCode が共通で持つ
   終了コマンドで、`pr-review-loop` が AI 不問であることを保てる。エージェントが消えない（最大15秒）ときは、
   強制的に閉じず（`herdr pane close` はペインごと消え `reviewer` ラベルが失われる）、従来どおり同じ会話に再依頼する
3. **起動し直しは Phase 2 Step 2 の既存の手順を使う**（`ocw agent` → `herdr agent start` → `pane run`）。新しい手順を
   増やさない。起動後に `$REVIEWER_AGENT` を読み直すところまで Step 2 が受け持つ
4. **新しいレビュワーへの最初の依頼は、Phase 2 Step 3 と同じ文言（「以下を読んでPRレビューを実行してください」）で始める。**
   使用量の集計（`by_unit.py` など）は、会話の最初の発話にこの文言があるかでレビュワーのセッションを見分ける。
   「再レビュー依頼」で始めると、新しい会話が実装のセッションに数えられる
5. **新しいレビュワーに渡すものを1つ足す: 何ラウンド目か。** レビュー指示ファイルのパスと前回レビュー対象 SHA は
   既に渡している。ラウンド数は「後続ラウンド（ラウンド2以降）の新規 finding 閾値」を新しい会話にも効かせるために要る
6. **読み方の作法をレビュー指示テンプレートに4行足す（C 案）。** persisted-output を Read で全文読み直さない・旧版を
   `git show | cat -n` で取り直さず `git diff <前回SHA>..HEAD` で読む・規約文書を全文 cat しない・ラウンド2以降は
   最新のレビュー1件と未解決スレッドだけ読む。グローバルの `claude/CLAUDE.md` にある「大きい出力を文脈へ流し込まない」は
   レビュワーにも載っているが効いていない（増分の約11%が二重取り込み）ため、毎ラウンド読まれるテンプレートに置く。
   `claude/CLAUDE.md` は触らない

## 3. 却下した案

- **B 案: レビュワーにも区切りの compact を入れる。** ピーク中央値 185k → 130〜150k の見込みで、A 案（長尺のピーク
  240〜480k → 100〜150k）より小さい。compact は要約の書き直しに費用がかかり、要約を経ると読んだ内容が欠けて基準
  （レビュー指示ファイル）が薄まる。A 案は基準をファイルから読み直すので欠けない。フックの対象を広げる変更も要る
- **`/clear` を送る。** Claude Code にしか効かない。Codex / OpenCode のレビュワーで壊れる
- **条件付きで新しくする。** 上記 §2.1

## 4. 見込みの効果と、効果の測り方

費用の比較: 作り直しで払うのは、開始時の固定分（約58k ＋ 読み直しの約19k）。続けた場合は、ラウンド2の時点で
中央値 約147k の cache read を毎呼び出しで払い、以後増える。再レビュー4回以上の長尺（約20本が費用上位）で
ピークが 240〜480k から 100〜150k へ下がる見込み。1回で終わるレビュー（再レビュー0回）には影響しない。

デプロイ後に、再レビュー回数別のレビュワーのピークを背景の実測と同じ方法で比べる。**`review-tiering`（#164）の変更も
レビュワーの費用を動かすので、本件の効果とは切り分けられない。** 比べるときは #164 が入った日を境目に記録する。

計測の整合: レビュワーのセッション ID がラウンドごとに変わる。ocw-meter の役割は、ペインのシェルが持つ `OCW_ROLE` を
起動し直したエージェントが受け継ぐ（`ocw agent reviewer` も同じペインで走る）ので、新しい会話も `reviewer` に解決される。
`by_unit.py` はセッションごとに費用を足し上げるので、1 PR に複数のレビュワーのセッションがあっても合算される
（§2.4 の文言を守る限り）。`bin/ocw-meter` の改修は要らない。
