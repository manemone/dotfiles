# ADR: claude-ds の自動 compact の位置を 786432 から 233000 へ下げる

## ステータス

決定（2026-11-03）。傘 `ds-cost-down`（計画書 DOC-2611032048）の孫1 で決めた。実装は `bin/claude-ds` の
`CLAUDE_CODE_AUTO_COMPACT_WINDOW`、使い方の説明は [bin/README.md](../../bin/README.md) §3.2。

## 1. 以前の判断と、覆す理由

以前は「DeepSeek はキャッシュヒットがミスの約1/50と安く、長い文脈のコストが響きにくいため、公式推奨値 786432 をそのまま採る」
としていた。2026-11-03 の実測（ocw-meter のストアと会話ログ。費用は価格表からの見積もりで請求額ではない）はこれを覆した。

- 費用の約8割が、文脈 10万超の呼び出しから出ている
- 種類別ではキャッシュ読み直しが 53%。1回の呼び出しは安くても、大きい文脈のまま何百回も呼ぶと回数で効く
- self-compact を取りこぼした会話は 30〜48万まで伸び、サブエージェントも 48万まで一度も圧縮されなかった

## 2. 決定

`CLAUDE_CODE_AUTO_COMPACT_WINDOW` を **233000** にする。実際の発火位置は約 **200,000** トークン。

- 値の意味: この値は compact が始まる位置そのものではなく、**窓の大きさ**として扱われる。発火位置は
  「窓 − `min(maxOutputTokens, 20000)` − 13000」である。根拠は3つ。
  - 公式の文書: model-config に「1M の窓のモデルは既定で約 967K で compact する」（1,000,000 − 20,000 − 13,000 = 967,000 と一致）、
    env-vars の `CLAUDE_CODE_MAX_OUTPUT_TOKENS` に「上げると auto-compaction が始まるまでの実効ウィンドウが減る」とある
  - 手元の会話ログ: 既定の 1M モデルの自動 compact の `preTokens` は 966,936〜969,778
  - Claude Code 2.1.317 の実装（レビューでの確認）: 窓 = min(モデルの文脈上限, この値)。未知のモデル ID
    （`deepseek-flash[1m]` が該当）の `maxOutputTokens` 既定は 32000 なので予約は 20000。よって 233000 − 20000 − 13000 = 200,000
  - 環境変数は `/autocompact` やフラグ、`autoCompactWindow` 設定より優先される。受け付ける範囲は 100K〜1M
- 位置の考え方: 自動 compact は self-compact（`claude/hooks/compact-reminder.sh` の `THRESHOLD`。孫2 で 200k から 150k に決まった。
  ADR DOC-2611032102）より**後に来る安全網**。フックは 150k を超えても、区切り（検証が通ったコミットの直後・レビュー依頼の直後）でなければ
  続けてよいとし、区切りを待つ間 50k 増えるごとに再掲する（`STEP = 50000`）。self-compact は「150k を超えてから次の区切りまで」の幅で
  起きる前提なので、発火は 150k にその幅（50k）を足した約 200k に置く。157k 付近だと幅が約 7k しかなく、ファイル1本の Read や
  テスト出力1回で埋まり、区切りに届く前に作業の途中で自動 compact が走って self-compact の規則が死ぬ。
  窓の値 233000 は、計画書 背景2 の1（人間の確定事項）の「20〜25万程度」にも収まる。
  経緯: 初版の 220000 は発火が約 187k で当時の閾値 200k より手前だったため 240000（約 207k）に直し、孫2 のマージで閾値が 150k に
  なったあと 190000（約 157k）にしたが、上の理由で 233000（約 200k）にした。
  **`compact-reminder.sh` の `THRESHOLD` や `STEP` を変えるときは、変える側がこの値も見直す**（自動 compact の発火が
  self-compact の閾値＋区切りを待つ幅より手前に取り残されると、self-compact が一切起きなくなる）
- 比べた値（計画書 背景4 の試算。圧縮後 55k に戻り要約出力 8k を加算する単純モデルで、圧縮後の読み直しの増加は含まないので甘い）:
  今のまま $9.53 に対し、発火 250k で $8.51（11%減）、200k で $8.09（15%減）、150k で $7.63（20%減）。発火 約200k なので約 15%減の見込み。
  窓の値ではなく実際の発火位置で比べている。費用の主な削減は self-compact の 150k が担い、自動 compact は取りこぼしの安全網なので、
  200k と 150k の差（15% と 20%）は安全網の位置としては小さい
- 発火をさらに 150k 側へ下げる案は採らない（上の区切りを待つ幅の理由）。200k より上げる案も採らない。取りこぼした会話が
  伸びる幅（30〜48万）を抑えるのが目的で、250k では削減が 11% に減る

## 3. サブエージェントに効くか: 未確認

公式の文書（env-vars、model-config、sub-agents）を読んだ範囲では、`CLAUDE_CODE_AUTO_COMPACT_WINDOW` がサブエージェントに効くかは
書かれていない（`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` は「メインの会話とサブエージェントの両方」と明記されているが、別の変数）。
サブエージェント個別には、フロントマターの `autoCompactWindow`（100000〜1000000、下げる方向のみ）がある。

配布後に会話ログで確かめる手順:

1. マージ後に人間が `deploy-all.sh` で配り、`claude-ds` で実際に長いサブエージェントを走らせる
2. 該当セッションの `~/.claude/projects/*/<session>/subagents/*.jsonl` で、1回の呼び出しの文脈（`usage` の入力 + キャッシュ読み）が
   20万を超えて伸び続けていないかを見る。約 20万付近で文脈が大きく縮む箇所（圧縮）があれば効いている
3. 圧縮が見当たらず 20万を超えて伸びるなら効いていない。その場合はサブエージェントの定義側の `autoCompactWindow` で下げる案を、
   別の変更として検討する

注意: サブエージェントのモデル ID が `[1m]` なしの `deepseek-flash` のとき、未知のモデルとして文脈上限 200K と見なされ
（model-config「Correct the window for a gateway or custom model ID」）、窓は min(200000, 233000) = 200000、発火 約 167,000 になる。
この環境変数が無い場合も窓は 200000 なので発火位置は同じで、**環境変数の有無では観測結果が変わらない**。
したがって手順2の判定は `[1m]` 付きのモデル（`deepseek-flash[1m]`。効いていれば約 200,000、効いていなければ約 967,000 まで伸びる）で
動いたサブエージェントのログだけを使う。モデル ID は assistant 行のトップレベルの `requestedModel` で確かめる
（`message.model` は API の応答が返すモデル名で `[1m]` が残らないため、見分けに使えない）。`[1m]` なしのサブエージェントが
約 16.7万で縮んでいても、「効いている」の根拠にしない

## 4. Claude の会話への影響

**効かない。** この環境変数は `bin/claude-ds` の `exec env` の中にしか無く、通常の `claude` の会話には影響しない
（`claude/` 配布物や `settings.machine.json` にも無い）。

## 5. 配布

deploy はしない。マージ後に人間が `deploy-all.sh` で配ると効く。
