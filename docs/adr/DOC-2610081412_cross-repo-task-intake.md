# ADR: 複数リポにまたがる作業の入口スキル `task-intake` と、複数リポ対応の傘

## ステータス

確定（2026-10-08）

## 1. 背景

「こういうことをやりたい」と思いついた会話から、専用の会話（herdr のペイン）へ引き継ぎ、
個別のトピックは孫にやらせる——という流れを人間は頻繁に回しており、そのたびに進め方を
迷っていた。特に、製品リポ（ツール本体がある側。`kenko` 等）と分析リポ（`analysis`。
実験・分析の記録がある側）の両方にまたがる作業の扱いが決まっていなかった。人間の発言
（傘 `cross-repo-workflow` 計画書
[DOC-2610081409](../planning/DOC-2610081409_cross-repo-workflow_計画.md) 背景1.1）:

> こういうこと非常によくやり、そのたびにどう進めようか迷いたくないから

このとき dotfiles と分析リポには次の穴があった（計画書 背景3）。

- **傘が1リポ前提で、複数リポの孫を同じ司令官の下に置けない。**
  `umbrella-orchestrator` は孫を傘ブランチから切り（同じリポの中）、マージ検出も同じリポの
  `gh pr list` しか見ない。`umbrella-handoff` / `umbrella-orchestrator` に複数リポへの言及は
  0件だった
- **PR 1本規模の軽いハンドオフが無い。** `umbrella-handoff` は傘ブランチを作ることが前提で、
  1本で済む件は相談AIが毎回やり方を即興で決めていた
- **入口の判断がどこにも書かれていない。** 配布物 `claude/CLAUDE.md`「傘ブランチへの
  引き継ぎ判断」は「複数の PR に分かれる規模なら `umbrella-handoff` を提案」だけで、
  1本規模のとき・複数リポにまたがるときの扱いが無い
- **分析リポ側に、他リポのツールで回した実験の記録規約が無い。** 散らかりの実例として、
  分析リポの中で同じバッチ投入スクリプトが3か所に複製されていた

直近の具体例2件が設計の検証題材になった（計画書 背景1.2）:

- **例1（PR 1本規模）**: 直前の実験と同じ栄養推定を別の写真データに当て、分析リポで
  スライドにまとめるところまでを「まずトライ」としてクイックにやる依頼。`umbrella-handoff`
  は使わず、相談AIが Markdown のブリーフを手書きして別の会話に渡し、受けた会話が分析リポに
  PR を1本立てた
- **例2（両リポにまたがる見込み）**: 製品の AI 解析で使っている旧モデルの廃止に備え、
  新モデルに乗り換えた場合の評価をしたい。製品リポでモデルを差し替え、分析リポで評価・
  記録する形になる見込み

## 2. 決定

本 ADR の決定はすべて計画書 DOC-2610081409（背景2・設計1〜3）で人間と司令官が確定させた
ものの記録である。

### 2.1 ワークフロー本体は dotfiles に置き、分析リポには記録規約だけを置く

入口スキル・軽いハンドオフ・複数リポの傘の手順は dotfiles の `skills/` に置く。分析リポには
「製品側のツールで回した実験を分析リポにどう記録するか」だけを、分析リポの
`adhoc-analysis` スキルの `references/` に1枚足す形で置く。理由:

1. 分析リポの `.claude/skills/` に置くと、分析リポで開いた会話でしか読み込まれない。
   「こういうことやりたい」と思いつく会話は製品リポで作業中かもしれないし雑談かもしれない
2. 土台（`umbrella-handoff` / `umbrella-orchestrator` / `ocw` / `pr-group-*`、herdr 前提の
   道具）がすべて dotfiles の `skills/` にあり、新しいスキルはそれらを組み合わせて使う側である
3. 分析リポの `AGENTS.md`「道具の置き場の決め方」は「分析リポの構造に依存するか」で
   置き場を決める。ハンドオフ・herdr・孫の回し方は分析リポの構造に依存しない

### 2.2 入口スキル `task-intake`: 判断の3軸と振り分け

`umbrella-handoff` の手前に立つ入口として `skills/task-intake/SKILL.md` を新設する
（計画書 設計1.1）。

- 「こういうことをやりたい」が固まった会話（相談AI）が使う。**相談AIは実装も計画書執筆も
  しない**（`umbrella-handoff` と同じ線引き）
- 自動発動はしない。人間が `/task-intake` で起動するか、相談AIが提案して人間が同意したら使う
- AI 不問（Claude Code / Codex / OpenCode）。Claude Code 固有の送信手段は
  `umbrella-orchestrator` §5「AI間送信手順（二段構え）」を参照して使い、それに依存しきらない

相談AIは次の順で判断し、**判断結果と根拠を人間に1回見せて確認を取ってから**振り分ける
（計画書 設計1.2）。

1. **どのリポにまたがるか**: 製品だけ／分析だけ／両方（その他のリポも同じ扱い）。
   「ツール本体を変えるか」「実行履歴を残すか」を 2.4 の役割分担表に当てて決める
2. **規模**: PR 1本か複数か。目安は `task-intake` §3.2 の3つ（独立にレビュー・マージできる
   単位に分かれる／関心事が分離できる／複数セッション・複数日にまたがる）。もとは配布物
   `claude/CLAUDE.md`「傘ブランチへの引き継ぎ判断」にあったもので、2.8 の書き換え
   （孫5、#123）で二重管理を避けるため `task-intake` 側へ一本化した。
   **両リポにまたがる時点で PR は最低2本**（リポごとに1本）になる
3. **司令官をどのリポに置くか**（複数のときだけ）: 2.3 の規則に従う

振り分け:

| リポ | 規模 | 行き先 |
|---|---|---|
| 1つ | 1本 | 軽いハンドオフ（2.5） |
| 1つ | 複数 | `umbrella-handoff`（従来どおり） |
| 両方 | 各リポ1本ずつ程度 | `umbrella-handoff`。司令官を 3. で決めたリポに置き、もう一方のリポの PR を「他リポの孫」とする（2.6） |
| 両方 | 複数 | 同上 |

### 2.3 司令官は「問いと結論が載るほうのリポ」に置く

両リポにまたがるとき、傘ブランチ・計画書・司令官ワークスペースは、問いと結論が載るほうの
リポに置く。評価が目的なら分析リポ、製品の変更が主目的で評価が確認にすぎないなら製品リポ。

### 2.4 リポ間の役割分担と双方向リンク

散らばること自体は問題にせず、**同じものが2か所にあることと、片方から辿れないこと**を
問題にする（計画書 背景2・設計3）。

| 何を | どこに |
|---|---|
| ツール本体（プロンプト・推論コード） | 製品リポ（`kenko` 等）。分析リポにコピーしない |
| 実行履歴（どの版で・何に・どう流して・何が出たか） | 分析リポ。製品リポのコミット SHA・PR 番号・実行コマンドを残す |
| 結論・意思決定 | Notion（分析リポの既存規約どおり） |

- 製品リポのツールを分析の都合で変えたくなったら、分析リポにコピーして直すのではなく
  製品リポに PR を出す
- 製品リポの PR 本文から分析リポの分析ディレクトリへリンクを貼り、分析側の記録からは
  製品リポのコミット SHA・PR 番号を辿れるようにする（双方向）
- 分析リポ側の具体的な記録規約（`README.md` 等に何を残すか）は、分析リポの
  `adhoc-analysis` の reference が正典である（dotfiles には書かない）

### 2.5 軽いハンドオフは `task-intake` に含める

PR 1本規模（1リポ × 1本）の引き継ぎ手順を `task-intake` の中に含め、別スキルにしない
（計画書 設計1.3）。手順:

1. **ブリーフを書く。** 置き場は**作るワークツリーの外**、対象リポの `{repo_parent}`
   （Pattern A なら `~/work/<repo>/handoff_<slug>.md`）。ワークツリーの中に置くと誤って
   コミットされる。節立ては例1 で実際に使われたブリーフを一般化したもの:
   依頼（原文）／位置づけ／再利用できる資産／先に潰すべき前提／作業の骨子／
   成果物の文体・用語で毎回指摘される点／引き継ぎ元に残っている未処理
2. 対象リポのメインワークツリーで `ocw -H --no-commander <ブランチ名> origin/<既定ブランチ>`
   を叩く（2ペイン。1本規模に司令官は要らない）。ブランチ名は対象リポの規約に従う
3. ワークスペースを日本語ラベル（`<repo> :: <説明>`）へ改名する
4. implementer に**ブリーフの絶対パスだけ**を送る（`umbrella-orchestrator` §5 の二段構え）。
   末尾に「PR 作成後は `/pr-review-loop` を回す。マージは人間」の1文を付ける
5. 相談AIはそこで手を引く。ブリーフは一時ファイルであり、実装AIが PR 本文に必要な内容を
   転記したあとは消してよい（消すのは実装AIではなく人間か相談AI。勝手に消さない）

### 2.6 複数リポの傘

計画書 設計2 のとおり、`umbrella-handoff` / `umbrella-orchestrator` を次の形で複数リポに
対応させる。

- **傘は司令官のリポにだけ立てる。** 傘ブランチ・計画書・司令官ワークスペースは 2.3 で
  決めたリポにだけ置く。`umbrella-handoff` は今と同じく1リポにだけ傘を作る。ブリーフ雛形に
  「関係するリポ」節と「司令官をこのリポに置く理由」を足す
- **他リポの孫は、そのリポの既定ブランチ（`origin/<既定ブランチ>`）から切り、既定ブランチへ
  PR を出す。** spawn は関係するリポのメインワークツリーへ `cd` して
  `ocw -H --no-commander <孫ブランチ> origin/<既定ブランチ>`。base-ref は省略しない
- **他リポの孫の PR は、承認されても AI はマージしない（人間の仕事）。** base が既定ブランチ
  だからであり、`umbrella-orchestrator` §2.4 の「base がこのリポジトリの既定ブランチでない」
  条件がそのまま効く。既定ブランチの判定は**そのリポで** `gh repo view` する。承認済みで
  人間のマージを待つ状態を、進捗の状況値 `⏳ 人間のマージ待ち (PR <owner/name>#XX)` で表す
- **副傘は立てないのが既定で、例外として認める。** 他リポの孫は通常1〜2本で、副傘を立てても
  「副傘→既定ブランチ」の最終 PR が1本増えるだけになる。他リポ側にも独立にマージしたい孫が
  3本以上あるなど、副傘を立てたほうが安い規模なら、計画書にそう書いて副傘を立ててよい
- **進捗テーブルに「リポ」列を足す（後方互換）。** 列順は `| 孫 | リポ | ブランチ | 内容 | 状況 |`。
  **「リポ」列が無い計画書は、全孫が傘と同じリポとして扱う**（既存の計画書を書き換えない）。
  列の値はリポの短い名前で、計画書の別の節（例: `## 関係するリポ`）に名前→メインワークツリーの
  絶対パス・`owner/name`・既定ブランチの対応表を置く。司令官はそこから `cd` 先と `gh -R` の
  引数を引く
- **マージ検出**は `gh pr list -R <owner/name> --head <孫ブランチ> --state merged`
- **他リポの孫の検証（lint / test）を司令官はしない。** 司令官が他リポのメインワークツリーで
  `git checkout` すると、人間の作業ツリー（dirty なことがある）を触ることになる。検証は
  その孫自身の `pr-review-loop`（そのリポの `.claude/pr-review.yml`）と CI に委ね、司令官は
  マージ検出だけを行う
- **後片付け**の `ocw rm` は他リポのメインワークツリーへ `cd` して叩く。base-ref が既定ブランチ
  なので、通常は `--force` なしで通る
- **継ぎ目**: 他リポの孫の PR 本文と、司令官のリポ側の計画書・対応する PR の間に双方向リンクを
  貼る（2.4 と同じ考え方）。複数リポの PR 群をまとめてレビュー依頼するときは
  `pr-group-request` を使い、進捗テーブルの「リポ」列から PR 群の地図を作る

### 2.7 `ocw` は変えない

`bin/ocw` の `init_repo_context` は対象リポを**カレントディレクトリ**から
`git worktree list --porcelain` で解決する。したがって司令官が
`cd <別リポのメインワークツリー> && ocw -H --no-commander <孫> <base-ref>` の形で叩けば、
そのリポにワークツリーと herdr ワークスペースができる。ワークツリーの置き場はそのリポの
`ocw.worktreeDir`（既定 `{repo_parent}/{name}`）に従い、Pattern A の配置と一致する
（計画書 背景4）。

**この根拠はコードを読んで確かめたものであり、本 ADR の時点では実行していない。** 傘の
孫2 が捨ててよい合成リポジトリで1度叩いて確かめる。変更が要ると判明した場合は孫2 で
実装せず司令官に報告する（計画書 スコープ外）。

### 2.8 配布物 `claude/CLAUDE.md` の書き換えは人間の承認後に行う

「傘ブランチへの引き継ぎ判断」節を `task-intake` への誘導に書き換えることは決めたが、
実施は人間の承認を得てからとする（傘の孫5）。このファイルは指示が無い限り編集しない配布物で
あり（`AGENTS.md`「3つの領域」）、symlink / 生成物を通じて Codex・OpenCode にも効くため。
司令官は `task-intake` を作る孫がマージされた時点で人間に承認を求め、得られたら計画書
DOC-2610081409 の背景5 に日付と文言を記録してから spawn する。

## 3. 決定の検証: 例2 を 2.2 に当てはめる

例2（製品のモデル乗り換え評価）を判断の3軸に当てると:

1. **リポ**: 両方。製品リポでモデルを差し替え（ツール本体の変更）、分析リポで評価結果を
   残す（実行履歴）
2. **規模**: 最低2本（製品側の差し替え PR と、分析側の評価・記録 PR）
3. **司令官**: 目的は「新モデルに乗り換えてよいか」の判断＝評価なので、分析リポ

→ 振り分けは `umbrella-handoff`。傘・計画書・司令官は分析リポに置き、製品リポの差し替え PR は
他リポの孫として製品リポの既定ブランチから切る。その PR のマージは人間が行い、PR 本文から
分析リポの分析ディレクトリへリンクを貼る。2本の軽いハンドオフに分けた場合に起きる
「片方から辿れない」状態にならず、2.4 の役割分担と矛盾しない。

例1（PR 1本規模の分析）は、分析リポだけ・1本なので軽いハンドオフになる。実際に相談AIが
即興でやった手順（ブリーフを書いて別の会話に渡し、受けた会話が PR を1本立てる）を 2.5 が
そのまま手順として固定する形になり、こちらも矛盾しない。

## 4. 却下した案

### 4.1 ワークフロー本体を分析リポに置く

人間の最初の発言は「分析リポに置くか？」だった。2.1 の3つの理由（分析リポで開いた会話でしか
読み込まれない／土台がすべて dotfiles にある／分析リポの置き場の基準「構造に依存するか」に
当てはまらない）により却下し、人間が同意した。

### 4.2 軽いハンドオフを別スキルにする

判断の直後にしか使わず、単独で起動する場面が無いため却下した（計画書 設計1.3）。

### 4.3 両リポにまたがる件で軽いハンドオフを2本別々に立てる

各リポ1本ずつなら傘は大げさに見えるが、2本を別々の会話に渡すと、互いを知る場所が無くなり
片方から辿れなくなる。2.4 の役割分担が問題にしているのはまさにこの状態なので却下した。
司令官を1か所に置き、もう一方を他リポの孫にする（2.6）。

### 4.4 他リポにも常に副傘を立てる

他リポの孫は通常1〜2本で、副傘を立てても「副傘→既定ブランチ」の最終 PR が1本増え、
人間のマージが1回増えるだけになるため、既定としては却下した。孫が多い規模に限って
例外として認める（2.6）。

### 4.5 `ocw` に `-C <repo>` を足す

`ocw` は対象リポをカレントディレクトリから解決するため、`cd` してから叩けば別リポに
ワークツリーを作れる（2.7）。オプションを足しても得られるものが無く、`bin/ocw` の変更と
テストのコストだけが増えるため却下した。
