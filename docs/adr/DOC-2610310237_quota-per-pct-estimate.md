# ADR: 週の上限の 1% あたりのトークンを推定する方法

## ステータス

決定（2026-10-31）。傘 `meter-subagent-quota`（計画書 DOC-2610310205）の孫2 で決めた。実装は `bin/ocw-meter` の
`report --quota-per-pct`、使い方は [bin/README.md](../../bin/README.md)。

## 1. 背景

サブスクの週の上限（`seven_day_used_pct`）はトークン数で公開されておらず、「この作業は週の何 % か」を後から答えられなかった。
一方 ocw-meter は `quota.sample`（週の % の時系列）と `usage.message`（モデル別のトークン）の両方を持つので、突き合わせて
推定できる。傘の司令官が 10 月分を手で突き合わせ、Opus は区切りを変えても安定して 1% あたり重み付き約 1,000 万になることを
確かめている（計画書 背景4.1）。本 ADR はその手順を `report` に載せたときの決定を残す。

## 2. 決定

1. **推定は「週の期間の中の、区切りごとの % の増え」を「区切りごとの系統別の重み付きトークン」に当てる回帰にする。**
   `seven_day_resets_at` が同じ記録を 1 つの期間とし、期間の中で 3・6・12 時間の区切り（epoch 基準）を取る。区切りの終わりの %
   は、その時点までの `quota.sample` の % の最大値（セッションをまたいで統合。% はアカウント共通で期間の中では減らないため、累積最大にする。しばらく API を呼んでいないセッションの statusLine は、そのセッションが最後に受け取った古い（小さい）% を後から書くので、「最後の sample」だと終わりの % が下がる。実データでは 10 月の直近 2 期間で約 7% の sample がこれに当たり、全て別セッションへの切り替わりだった）。区切り k の増え = 終わりの %(k) − 終わりの %(k−1)。
   最初の区切りは基準が無いので捨て、トークンの無い区切りと増えが負の区切りも行に入れない
2. **重みは `input + 1.25×cache_creation + 0.1×cache_read + 5×output`。** Anthropic の API 価格の比（入力を 1 とした倍率）で、
   手計算で Opus が安定した重みをそのまま使う。生のトークン（4 項の単純和）も併せて出すが、これは推定した重み付きの値に、期間中の
   その系統の生/重み付きの比を掛けた換算値で、直接フィットした値ではない
3. **系統は `opus` `sonnet` `haiku` `fable` の 4 つ。** モデル名が `claude-` で始まり、名前にその語を含むものだけを数える。
   `claude-ds` の DeepSeek と `<synthetic>` は週の上限に数えられないので除く
4. **係数は非負の最小二乗（標準ライブラリだけ）。** 変数は高々 4 つなので、全ての部分集合について正規方程式を解き、全係数が 0 以上の
   解のうち残差が最小のものを採る（最適解はそれ自身の台での無制約の解なので厳密）。新しい依存は足さない
5. **「測れない」の基準（誤った数字を自信ありげに出さないため）。** 次のどれかなら数字を出さず理由を出す:
   (a) 使用のあった区切りが 12 時間区切りで 6 個未満（使用が無いのも含む）、
   (b) 3・6・12 時間のどれかで推定が 0 になる（他の系統で説明されて分離できない）、
   (c) 回帰がその系統に帰属させる週の % が、区切りの長さのどれかで 3% 未満（% の刻みに埋もれる）、
   (d) 区切りの長さによる値の最大/最小が 1.5 を超える（ぶれが大きい）。
   出す値は 3 つの区切りの中央値。閾値は実データ（Opus は区切りで ±5%、Sonnet は期間数によって 1,300 万〜2,300 万で動く）の
   観察から置いた経験値であり、固定の理論値ではない
6. **使う期間は `--periods <n>`（最新の n 個の 7 日の期間、既定 2）。** 実在しない期間は除く（`seven_day_resets_at` が記録時刻の
   −1 時間〜+7 日＋1 時間に入らないもの。テストの値などで混ざる）。現在進行中の期間は途中まで使う
7. **範囲の report（`--since`/`--until` のモデル別表）には `estimated_weekly_pct` を足す。** その行の重み付きトークンを、系統の
   「1% あたりの重み付きトークン」で割る。推定は範囲の中だけでなくストア全体から出し、測れない系統とモデルが系統に当たらない行は
   null（text では空欄）。ロール別の表には足さない（行が複数モデルの混ざりで、系統を決められないため）
8. **見積もりとしてだけ使う。** 止める・モデルを替えるなどの自動の制御には使わない（傘のスコープ外）

## 3. 却下した案

- **区切りごとの「増えた % ÷ トークン」の単純な比を平均・合計する案。** 区切りに複数の系統が混ざると、比がどの系統のものか決まらず、
  トークンの少ない区切りの比が支配的になる。回帰なら混ざりを分離でき、トークンの多い区切りが自然に重く効く
- **変数の制約を付けない最小二乗。** 小さい系統で負の係数が出ることがあり（負の「1% あたり」は意味が無い）、他の系統の係数まで歪む
- **系統ごとに別々に割る案（その系統の使用だけの区切りを探す）。** 並行して複数の系統を使うのが普通で、純粋な区切りがほとんど無い
- **閾値を理論的に導く案。** `quota.sample` の記録間隔と % の刻みが一定でなく、導けない。実データで見て置く方を採った

## 4. 誤差の要因（見積もりとして読むこと）

- **`seven_day_used_pct` の刻み。** 整数の刻みで来る（10 月の 35,070 件は全て整数）ので、短い区切りでは増えが 0 か 1 に量子化される。3% の基準と
  3・6・12 時間の突き合わせで影響を抑えるが、消えはしない
- **このマシン以外の使用。** 週の % は全マシン・全クライアントの合計だが、ocw-meter はこのマシンの記録しか持たない。他で使った分は
  係数を小さく見せる（1% あたりのトークンを少なく見積もる）。持ち主はほぼこのマシンだけで使っているので許容する
- **`quota.sample` の記録間隔。** statusLine の描画に連動して記録されるため、操作の無い時間は記録が空く。区切りの終わりの %
  が古い値になり、増えが次の区切りへずれる（長い区切りほど影響が小さい）。別セッションの古い値は累積最大で除くが、記録が空いている間の遅れは除けない
- **キャッシュの TTL・サブエージェントなどの数え方。** 重みは目安であり、課金の実態が週の上限の計算に完全に一致する保証は無い。
  サブエージェントの記録は孫1 で数えるようになったが、それ以前に ingest された期間には入っていない（`ingest` をやり直すと入る）
- **期間数への感度。** 同じ系統でも `--periods` を変えると値が動く（実データで Sonnet は 2 期間で約 1,400 万、4 期間で約 2,300 万）。
  Opus はどちらでも 860〜1,030 万に収まった。`--periods` を変えて安定するかを見るのが確かめ方になる
