# ADR: self-compact の閾値を 150k に下げ、回数の上限を増分制に置き換える

## ステータス

決定（2026-11-03）。傘 `ds-cost-down`（計画書 DOC-2611032048）の孫2 で決めた。ADR DOC-2610142337 の
§2.2（閾値 200,000）と §2.3（1 PR につき多くて 3 回）を置き換える。それ以外（区切りの種類・`ocw self-compact`・
復帰メモ・使えないときは何もしない）は引き継ぐ。ADR DOC-2610131214・DOC-2610142337・DOC-2610142359 は
書き換えない。

## 1. 背景

claude-ds（DeepSeek で動く Claude Code）の費用の約8割は文脈 10万超の呼び出しから出ている（計画書 背景4）。
ADR DOC-2610142337 §2.3 の「多くて 3 回」は、「compact 後は 60〜90k で、次に 200k を超えるまで間があくため
通常は 3 回に届かない」という Claude のログからの見立てが前提だった。DeepSeek は 5万→35万へ 30〜60 分で
戻るため、この前提が崩れている。さらに実運用で「3 回」を、数えるはずの区間（実装途中の (3) だけ）より広く
読んで見送る例が出た。

## 2. 測り方と結果

付録A の `sim.py` を土台に、2026-11-03 の DeepSeek の実装役 23 セッション（メインとサブエージェント）で、
「文脈が閾値を超えたら 55k に戻り、要約の出力 8k を足す」単純モデルの費用を出した（圧縮後の読み直しは
含めないので甘い見積もり）。回数の扱いは、上限なしと「1 会話につき 3 回まで」を比べた。ベースは $9.83。

| 閾値 | 上限なし: 削減・回数・最大/会話 | 3 回上限: 削減・回数 |
|---|---|---|
| 250k | 11%・21 回・5 | 10%・19 回 |
| 200k | 15%・43 回・7 | 13%・38 回 |
| 150k | 20%・73 回・12 | 16%・54 回 |
| 120k | 21%・121 回・16 | 14%・67 回 |

- 上限が 3 回だと閾値を下げても得が伸びない（150k で 20%→16%、120k で 21%→14%）。上限が足かせになる
- 120k は 150k より削減が 1 ポイントしか増えず、回数が 1.7 倍になる（そのたびに復帰メモのコストが掛かる）
- Claude（Sonnet）の会話は、ドルでなく週の上限への効きで見る（背景2）。この試算では出していない。
  Claude のログでの測り直しは行っていない（未検証。§6）

## 3. 決定（人間の確認済み）

1. **閾値を 200,000 から 150,000 にする。** フック `claude/hooks/compact-reminder.sh`、
   `pr-review-loop`「区切りでの自己 compact」、`umbrella-orchestrator` §3.2 の自動付与指示で揃える
2. **回数の上限をやめ、増分で止める。** 実装途中の区切り (3) の compact は、前回の compact から文脈が
   100,000 以上増えていなければ見送る（初回は不要。起点は復帰直後に測った値で、compact の前に書く復帰メモには書かない）。この増分は (3) だけの条件で、(1)(2) の区切りには掛けない。
   暴走して compact を繰り返す事態への安全弁という上限の役割は、増分が引き継ぐ。回数は復帰メモに
   残さない。「多くて 3 回」の文言は書き写し先すべて（`pr-review-loop`、`umbrella-orchestrator` §3.2 の
   2 か所、フックの文面）から消す
3. **区切りの明確化。** 承認後に追加の直しが入り、push して再レビューを依頼した直後を、(2)（指摘対応を
   push して再レビューを依頼した直後）に含むと明記する。承認後の完了報告は引き続き区切りでない
4. **Claude の会話にも効くのは 2（回数の上限をやめて増分にする）だけ。** 1 の閾値 150,000 は claude-ds
   （DeepSeek）のときだけで、それ以外の Claude は 200,000 のまま。見分け方は `ANTHROPIC_BASE_URL` に
   `deepseek` を含むか（フックは `bin/claude-ds` が渡す環境変数を受け継ぐ）。人間の決定である
   （当初は全部を Claude にも効かせると書いたが、人間が全体に効かせてよいとしたのは回数の上限だけだったので直した）

## 4. 他の ADR との関係

| 項目 | 旧 | この ADR |
|---|---|---|
| 閾値（DOC-2610142337 §2.2・DOC-2610142359） | 200,000 | 150,000 |
| 実装途中の回数（DOC-2610142337 §2.3） | 1 PR につき多くて 3 回 | 上限なし。前回から +100,000 の増分 |
| 区切りの種類（DOC-2610131214・DOC-2610142337） | 3 つ | 変わらない。(2) に承認後の追加の直しの再レビュー依頼を含むと明記 |
| DOC-2610142337 §6「閾値を 150k に下げる」を却下 | 孫1 の調査と実運用を見てから再考 | DeepSeek の実測（§2）で再考し、採った |

自動圧縮（`CLAUDE_CODE_AUTO_COMPACT_WINDOW`、`bin/claude-ds`）は self-compact を取りこぼしたときの安全網で、
self-compact の閾値より上に置く。値は同じ傘の孫1 が決める。

## 5. 却下した案

- **閾値 120k**: 削減の上乗せが 1 ポイントで、回数が 1.7 倍になる（§2）
- **閾値 200k 据え置き＋増分制のみ**: 削減が 15% で、150k の 20% に届かない
- **全部を DeepSeek のときだけ変える**: 人間が回数の上限は Claude にも効かせると決めた

## 6. 未検証

- Claude の会話で、閾値 150k と上限なしが週の上限をどう動かすか。ADR DOC-2610142337 §4 の品質低下の
  測定（midway 有りの PR が 10 本たまったら）で合わせて見る
- 増分 100,000 が適切か。compact 後は 55k 前後に戻るので、実質は 150k 付近でまた区切りに届く。
  増分は暴走の安全弁としてだけ働く想定であり、実運用で compact が連続するようなら見直す
