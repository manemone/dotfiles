# ADR: 実装の孫は実装の途中の区切りでも自分を compact する

## ステータス

決定（2026-10-14）。傘 `context-bloat`（計画書 DOC-2610142332）の孫2 で決めた。ADR
DOC-2610131214 §2.1 の「実装・修正の途中では行わない」を覆す。それ以外（閾値 200,000・
`ocw self-compact` の使い方・使えないときは何もしない）は引き継ぐ。ADR DOC-2610131214 は
書き換えない。

## 1. 背景

ADR DOC-2610131214 は、実装の孫の compact の区切りを「レビューを依頼した直後」の2つに絞った。
実装の途中で compact すると作業中の判断が落ちる、という理由だった。

自己 compact は本番で効いた（計画書 DOC-2610142332 背景4.1・4.2: 約33時間で差し引き約 $72）。
一方、実装の孫は最初の PR を出す前に文脈が 300〜430k まで膨らみ、呼び出しの 52% が 200k 超だった
（背景4.3）。その 200k 超の呼び出しで 80k を超えていた分の費用は約 $118、今の区切りで回収できたのは
約 $30 で、残りは最初の PR を出す前に使われている。

人間は、レビューでの指摘が増える（途中の compact で判断が落ちて品質が下がる）なら区切りを再考する
という条件を承知のうえで、実装の途中にも区切りを足すと決めた（計画書 背景2）。

## 2. 決定

1. **区切りを1つ足す: 「検証が通ってコミットした直後」。** コミットが作業単位の区切りでない
   （WIP・チェックポイント・「あとで直す」つもりのもの）ときは区切りとみなさない。判断は孫に任せる
   （機械的に決められないため）。ADR DOC-2610131214 の既存の2つ（レビュー依頼の直後、再レビュー依頼の
   直後）はそのまま残す。コミットを伴わない作業を区切りに含めることはしない（§5・§6）
2. **閾値は 200,000 トークンのまま。** 文脈がこれを超えているときだけ行う。測り方も同じ
3. **1本の PR（作業）につき、実装途中の compact は多くて 3 回まで。** compact 後の文脈は 60〜90k
   （計画書 背景4.1）で、次に 200k を超えるまで間があくため、通常は 3 回に届かない。上限は、
   区切りの判断が暴走して compact を繰り返し、そのたびに復帰メモを書き直して逆にコストが
   増える事態への安全弁。数えるのは復帰メモに残す（§3）
4. **指摘対応の修正の途中は対象に含めない。** 修正は小さく、復帰メモに書くべき判断も少ない。
   再レビュー依頼の直後の区切り（ADR DOC-2610131214）で足りる。PR を出す前の実装だけを対象にする
5. **復帰メモは実装途中用の形にする。** 既存のメモ（レビュー待ちに戻る用）とは中身が違う。
   「作業中に下した判断とその理由」が要約で一番落ちやすいので、必ず書く。書く項目: 計画書のパスと
   孫N の節、ここまでに済んだこと（コミットの一覧）、作業中に下した判断とその理由、まだ残っていること、
   次に打つ一手、検証に使うコマンド、実装途中の compact をした回数。先頭は「計画書の続きから実装を
   再開する。レビュー待ちではない」
6. **置き場は実装中の孫に届く場所。** `pr-review-loop` は実装が終わってから起動されるため、そこに
   書くだけでは実装中の孫に届かない。`umbrella-orchestrator` §3.2 の自動付与指示（同じリポの孫用・
   他リポの孫用）に短い段落を入れ、詳細（測り方・復帰メモ・コマンド）は `pr-review-loop` の
   「区切りでの自己 compact（実装側のみ）」に置く。段落は詳細へ誘導するだけにし、毎回読まれる場所を太らせない
   （実装中の孫が `pr-review-loop` を読むのは PR を出す段階なので、段落自身に最低限の手順〔閾値・
   メモ・コマンド・使えないとき〕を書く）
7. **コマンドと落とし方は変えない。** `ocw self-compact`、続きを促す固定文、allow ルール
   `Bash(ocw self-compact *)`、「使えない・拒否・失敗・Claude Code 以外なら何もしない（人間へ提案も通知も
   しない）」は ADR DOC-2610130913・DOC-2610131214 §2.4・§2.5 のまま

## 3. ADR DOC-2610131214 との関係

| 項目 | DOC-2610131214 | この ADR |
|---|---|---|
| 区切り | レビュー依頼の直後、再レビュー依頼の直後 | 左の2つ + 実装途中の「検証が通ってコミットした直後」 |
| 実装途中 | 行わない | 閾値超えなら行う（1 PR につき多くて 3 回） |
| 指摘対応の修正の途中 | 行わない | 行わない（変わらない） |
| 閾値・コマンド・落とし方 | 200,000・`ocw self-compact`・何もしない | 変わらない |
| 復帰メモ | レビュー待ちに戻る用 | 実装途中用を足す（レビュー待ち用はそのまま） |

覆したのは「実装・修正の途中では行わない」のうち、PR を出す前の実装の途中だけである。覆す根拠は、
その間に大きなコストが集中していること（§1）と、復帰メモで判断を残す形が決められること（§2.5）。

## 4. 品質低下の検知（様子見の約束）

人間の条件は「レビューでの指摘が増えるなら区切りを再考する」である。次の方法で測る。

- **何を比べるか**: 実装の孫の PR ごとに、(a) 最初の PR より前に自己 compact をしたか（実装ログの
  `compact_boundary` で trigger が manual、かつ最初の `gh pr create` より前）、(b) レビューの投稿数
  （ラウンド数の代わり。レビュワーの投稿は状態が COMMENT なので状態では数えられない）、
  (c) インラインの指摘数。(a) が有る PR と無い PR で (b)(c) を比べる。PR の規模や分野に差があるので、
  平均の差ではなく、分野（分析・実装・UI など）を揃えた比較か、差が大きいときの個別の確認で見る
- **測る道具**: `docs/adr/probes/context-bloat/quality.py`（出力は表。大きくなりうるのでファイルに書いてから見る）。
  どこでコミットが来るかは `commits.py`
- **いつ・誰が**: 実装途中の compact をした PR が **10 本**たまったら、次の傘の司令官（または人間の
  依頼を受けた相談 AI）が測る。比較は、compact をした PR と、しなかった PR のうち同じ分野のもの。
  現時点（配布直後）は midway 有りの PR が 1 本しかなく、比較できない
- **再考の目安**: midway 有りの PR のほうが、レビューの投稿数またはインラインの指摘数が目に見えて
  多い（同じ分野で一貫して 1.5 倍以上）なら、区切りを狭める（回数の上限を下げる・閾値を上げる・
  コミットを伴う場合だけにする）か、取りやめる。目安は暫定であり、司令官が人間に諮って決める
- 品質は指摘数だけでは測れない（要約で落ちた判断が、指摘にならず黙って間違いになる場合がある）。
  数字に出ない劣化は、人間が PR を見て気づいたときに申告してもらう

## 5. 実ログから分かったこと（commits.py）

2026-10-13 以降の実装の孫（ワークツリー名に `-NN-` を含む 30 呼び出し以上のセッション。レビュワーは
`miss.py` と同じ判定で除く）で、最初の `gh pr create` より前の `git commit` の回数と、そのとき文脈が
200k 超だった回数を数えた。PR を作った孫 25 本について:

- 全員が最初の PR までに 1 回以上コミットしている（0 回の孫はいない）。1 回だけの孫は、`git commit` と
  `gh pr create` を同じ呼び出しで打っているものが多く、途中の区切りにならない
- 200k 超でコミットしたのは 15 本。そのうち最初の超過コミットが PR 作成より 20 呼び出し以上前なのは
  10 本で、途中の区切りで回収できる見込みがある。残りは PR 作成の直前で、回収しにくい
- 同じ 25 本のうち、コミット直後の区切りでは回収できないのは、200k 超が PR より後（または PR 直前）の
  孫と、超えない孫

したがって、これは回収額の一部（10 本分）を取れる見込みであり、約 $118 のうち取り戻せる割合は運用で見る。
初版はコミットを伴わない作業単位も区切りにしたが、実ログにはその根拠がなかったため（レビューで
指摘され）コミット直後に絞った。調査・生成が主の孫が今後増えて取りこぼしが見えたら、区切りを広げる
（§4 の測定と同じ枠で再考する）。

## 6. 却下した案

- **閾値を超えたら区切りに関係なく即 compact する**: 作業中の判断が落ちる。ADR DOC-2610131214 が
  避けた形そのもの。区切りに寄せることで、メモに書ける状態で compact する
- **コミットを伴わない作業単位も区切りにする**: 初版で採ったが、実ログにコミットのない孫はおらず根拠がない（§5）。判断が曖昧になり、復帰メモに書けない状態での compact を招くおそれもある
- **autocompact の閾値を下げる**: 発動のタイミングと残す内容を選べない（ADR DOC-2610130834 §3）
- **閾値を 150k に下げる**: 回数が増えて1回あたりの得が薄い（ADR DOC-2610131214 §3）。孫1 の
  調査結果と実運用を見てから再考する
- **指摘対応の修正の途中も対象に含める**: 修正は小さく、得より復帰メモのコストが大きい（§2.4）

## 7. 未検証

- 実装途中の compact が品質を落とすか（§4 で運用の中で測る）
- 復帰メモの形（§2.5）が、実装途中の判断を実際に保てるか。復帰後に孫が同じ調査をやり直す、
  決めたことを覆すなどが見えたら、メモの項目を増やす
- 孫のペインで `Bash(ocw self-compact *)` が分類器に止められないか（ADR DOC-2610131214 §5。
  実装の孫でも通ることは、計画書 背景4.1 の全 14 回が `queued` で通ったことから確認済みだが、
  実装途中の経路では未観測）
