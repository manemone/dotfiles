# ADR: `ocw -H` のワークスペースを Herdr のワークツリーグループに乗せる方式

## ステータス

採用（2026-10-11）

方式 A＋C を人間が選んだ（計画書 DOC-2610111927 設計2: 「そうするしかないよな、残念だが」）。
実装は孫3（`bin/ocw` の `-H`）。§4 で「実装する孫が決める」としていた点の決定は §4.1 に記す。

## 1. 背景

`ocw -H` は `herdr workspace create --cwd <ワークツリー> ...` で Herdr のワークスペースを作る。
この作り方だと、Herdr からはどのリポのどのワークツリーとも結び付かない独立したワークスペースに
なり、サイドバーには傘・孫・他リポのワークスペースが平らに並ぶ。傘は3ペイン、孫は2ペインを
開くので、数が増えると雑然とする。人間の要望は、手で並べ替えなくても「傘ブランチとその孫」の
単位で自動でまとまることである（計画書 DOC-2610111927「herdr のサイドバーで傘と孫のワークスペースを
自動でまとめる」の背景1〜3）。

Herdr 本体には、リポのメインのチェックアウトを親にして、リンクされたワークツリーの
ワークスペースを子としてインデントして並べるグループ表示がある。本 ADR は、これに乗せたときの
実際の動きを実測し、傘単位に寄せられるか、どの方式を採るかをまとめる。

## 2. 実測

### 2.1 条件と作法

- Herdr は手元のクライアント・サーバーとも 0.9.0（`herdr status`）。設定リファレンスにある 0.9.3 では試していない
- 人間が使っているセッション（`default`）には触れず、名前付きの別セッション `hwgprobe` を
  `herdr --session hwgprobe server` で起こして実験した。CLI は `HERDR_SOCKET_PATH` をそのセッションの
  ソケット（`~/.config/herdr/sessions/hwgprobe/herdr.sock`）に向けて叩いた
- 実験用のリポは `mktemp -d` の使い捨て。`main`（メインのチェックアウト）と、そこから
  `git worktree add` した `umb`（傘役）・`g1` `g2` `g3`（孫役）の4つ。別リポ（`main` と `o1`）も1組作った
- サイドバーの見た目は、別セッションに `tmux` 内で `herdr --session hwgprobe` を接続し、
  `tmux capture-pane -p` でテキストとして読み取って確かめた（人間の目視ではない。8節に見てほしい点を残す）

### 2.2 未確認の点ごとの結果

計画書 背景4.4 の番号に対応する。

1. **親子関係の決まり方**
   - `herdr worktree open --cwd <メイン> --path <ワークツリー>` で、メインのチェックアウトを親、
     指定したワークツリーを子とするグループになる。判定は `worktree.repo_key`（`.git` の場所）で、
     リポ単位である
   - **リンクされたワークツリーのワークスペースは親になれない。** `--workspace <umbのID>` で
     `worktree open` を叩くと `linked_worktree_source`
     （「New and open worktree actions start from the repo parent workspace.」）で拒否された。
     孫を傘の子にする（方式 B）はできない
   - グループ内の並びは**作成順**。ラベルを `A-G1-last` のように辞書順で先頭にしても、最後に開いた
     ものは末尾に並んだ。作成後の `workspace rename` で並びは変わらなかった。
     並べ替えのコマンドも無い
2. **親が開いていないとき**: エラーにならず、メインのチェックアウトのワークスペースが自動で作られる
   （実験では `w1`）。そのペインはメインの cwd で開く 1 ペイン。親は最初に開いた子より上に並ぶ。
   作成直後の `workspace list` では親のラベルが一時ディレクトリ名（`tmp.…`）で、
   後の `list` では `main`（チェックアウト名）になっていた。ラベルが決まる仕組みは未確認
   - **メインのチェックアウトに `workspace create --cwd <メイン>` で作った普通のワークスペースが
     既に開いているとき**は、`worktree open --cwd <メイン>` はそれをそのまま親にした
     （親を別に作らず、元のラベル `plain-main` のまま子 `C1` がインデントされて並んだ。
     サイドバーで確認）。人間の実環境のように親が普通のワークスペースで開いている場合、
     重複せずグループに入る
3. **ペイン構成と環境変数**
   - `worktree open` が作るのはルートペイン 1 つ。ペインの追加は `pane split` で今までどおりできる
   - **`worktree open` に `--env` は無い**（ルートペインに環境変数を渡せない）。一方、
     `pane split --env KEY=VALUE` は効いた（分割したペインで `OCW_ROLE=implementer` が見えた）。
     ルートペインには `pane run <ペイン> 'env OCW_ROLE=… <コマンド>'` で、起動するコマンドにだけ
     環境変数を渡せた。ルートペインのシェル自体には環境変数が入らない
   - 実際の `claude` / `opencode` 等の起動と `ocw-meter` への影響は、実験では確かめていない
4. **`--trust-repository`**: 実験したどの操作でも要らなかった。要る場面は見つけていない
   （自分が所有するリポジトリのみ。他人所有のリポジトリは試していない）。
   要る場合は人間がリポを確認する手順として扱い、エラー回避のためには付けない
5. **片付け**
   - 子のワークスペースの `workspace close` は成功する。**親の `workspace close` は、
     子が開いていると `workspace_group_close_required` で失敗する**（`--group` が要る）。
     `ocw rm` が閉じるのは孫（子）のワークスペースなので、この制限は当たらない。
     親（メインのチェックアウトのワークスペース）は閉じる対象にしないのが安全
   - **`herdr worktree remove --workspace <子>` は、ワークスペースを閉じるだけでなく
     ワークツリーのチェックアウトのディレクトリごと削除する**（ブランチは残る）。未コミットの
     変更があると `dirty_worktree_requires_force`。`ocw rm` は git 側の削除を自分で行うので、
     二重に消さないよう `worktree remove` は使わず `workspace close` を使う
6. **移行前のワークスペース**: 既存のワークスペース（`workspace create --cwd <ワークツリー>` で
   作ったもの）がそのパスで開いていると、同じパスへの `worktree open` は新規作成せず
   `already_open: true` でそのワークスペースを返し、**グループに加えたうえでラベルを `--label` の値に
   書き換えた**。移行前のものを一括で作り直す必要は無く、開き直せばグループに入る
   （自動では入らない。ocw で作ったままのものは平らなまま）
7. **0.9.0 での成否**: 上記は全て 0.9.0 で成り立った。設定リファレンスの `row_gap` 等は試していない
   （0.9.3 への更新が必要かは、この実験の範囲では不要）
8. **`ocw.worktreeDir` が Herdr の `worktrees.directory` 以外のとき**: 実験のワークツリーは
   `/tmp/…` で `~/.herdr/worktrees` の外だったが、`worktree open --path` で問題なくグループに
   入った。`ocw.worktreeDir` のレイアウトを尊重できる
9. **他リポの孫**: 別リポのワークスペースはそのリポ自身のグループに入り、最初のリポのグループには
   混ざらない。見込みどおりで、他リポの孫は傘のグループに入らない

## 3. 方式の比較

| 方式 | 内容 | 可否と限界 |
|---|---|---|
| A. リポ単位のグループ | `worktree open --cwd <メイン> --path <ワークツリー>` | 成り立つ。傘と孫が同じリポの親の下に並ぶ。同じリポで傘を2本回すと混ざる |
| B. 傘単位のグループ | 孫を傘のワークスペースの子にする | **不可**。リンクされたワークツリーは親になれない（`linked_worktree_source`） |
| C. A ＋ 並びの工夫 | 並びは作成順なので、傘の次にその孫を開く。ラベルの接頭辞で傘を区別する | 1本の傘だけなら傘→孫の順で隣り合う。傘を複数本回すと、孫を後から足すたびに別の傘の孫の後ろに入り、隣り合わなくなる |
| D. 現状維持 | `workspace create` のまま | 何も変わらない（比較対象） |

## 4. 推奨

**方式 A に C のラベルの工夫を足す。** 傘単位に完全に寄せることはできない（B は不可、並べ替え手段も無い）が、
リポ単位のグループだけで「無関係な平らな列」は解消し、1本の傘を回している間は傘→孫の順で自然に
隣り合う。複数の傘を同時に回すときは、ラベルの接頭辞（現行どおり `<リポ> :: <傘名> 孫N …`）が
区別の手がかりになる。

`ocw -H` の変更（実装は別の孫の仕事）:

- ワークツリーは今までどおり `ocw` が作る（`ocw.worktreeDir` を尊重）
- ワークスペースは `workspace create` の代わりに `worktree open --cwd <メインのワークツリー>
  --path <作ったワークツリー> --label … --no-focus` で作る
- 環境変数（`OCW_ROLE` / `OCW_RUN_ID`）は、ルートペインには渡せないので、`pane split --env` で
  作るペインに渡す。ルートペインは `pane run` で `env OCW_ROLE=… OCW_RUN_ID=… <コマンド>` として
  起動するか、ルートペインを使わない構成にする。どちらにするかは `ocw-meter` が環境変数を
  どう読むかとの突き合わせが要る（決定済み。§4.1 の「ルートペインの環境変数」に従う）
- `ocw rm` とロールバックは `workspace close <ID>` のまま。`worktree remove` は使わない
  （チェックアウトを消してしまうため）。親のワークスペースは閉じない
- `worktree-cleanup` の孤児の判定も `workspace close` のまま。ただし対象に親（メインの
  チェックアウトのワークスペース）が入らないことを確認する
- 親が自動で作られた場合（メインのチェックアウトのワークスペースが開いていなかったとき）、
  その親は `ocw rm` でも、`ocw -H` の途中失敗時のロールバックでも閉じない（子の ID だけを閉じる）。
  1 ペインのワークスペースがサイドバーに残るので、閉じるのは人間に任せる
- 移行前のワークスペースは `ocw rm` で閉じるまで平らなまま残る（`ocw` には既存のワークツリーを
  開き直す経路が無い）。グループに入れたければ人間が `herdr worktree open --cwd <メイン>
  --path <ワークツリー>` で開き直す（2.2 の 6）。放置してよい。一括の作り直しは本傘のスコープ外

### 4.1 実装での決定（孫3）

- **ルートペインの環境変数**: `ocw-meter` は `os.environ` の `OCW_RUN_ID` / `OCW_ROLE` を
  読む。ルートペインのシェルは herdr **サーバー**の環境を継ぐだけで、クライアント側で環境変数を
  付けても届かない（レビューでの実測）。起動コマンドへの `VAR=値` 前置では、その1回のプロセスにしか
  効かず、エージェントを起動し直すと帰属が落ちる。そこで起動コマンドの前に
  **`export OCW_ROLE=… OCW_RUN_ID=…; ` をシェルへ打ち込み**、シェル自体に入れる（以前の `--env` と
  同じ状態。`&&` 複合コマンドにも効く）。ルートペインを使わない構成にはしない（3/2 ペインの外部契約を
  保つ）。`--name` の判定には export を足す前のコマンドを渡すので孫2 の claude 判定と両立する。
  分割で作るペインは従来どおり `pane split --env`。本物の herdr（0.9.0）で各ペインに正しい
  `OCW_ROLE` が届くことを確かめた
- **`already_open: true`**: エラーにして止める。既存のワークスペースにペインを重ねない。
  このとき `ocw` は ID を保持しないので、ロールバックは ocw が作っていない既存のワークスペースを
  閉じず、作ったワークツリーとブランチだけを消す
- **`--trust-repository`**: 付けない。実測で要らなかった

## 5. 却下した案

- **B（傘単位）**: Herdr が許さない（2.2 の 1）
- **`ocw` が `herdr worktree create` でワークツリーを作る**: `ocw.worktreeDir` のレイアウト・
  `ocw-base-ref` の永続化・ブランチ命名を `ocw` が握っている前提が崩れる。`worktree open --path` が
  任意の場所のワークツリーを開けると分かった（2.2 の 8）ので、任せる理由が無い
- **`worktree remove` で片付ける**: チェックアウトごと消える（2.2 の 5）。git 側の削除は `ocw rm` の責務
- **`--group` で親ごと閉じる**: 人間が使っているメインのチェックアウトのワークスペースまで巻き込む
- **D（現状維持）**: 問題が解消しない

## 6. 残る不確かさ

- 親のラベルが一時的に一時ディレクトリ名になる理由（2 の2）
- ~~ルートペインの環境変数の渡し方と `ocw-meter` との整合（2 の3）~~ → §4.1 で決定済み（シェルへ `export` を打ち込む）
- 他人所有のリポジトリでの `--trust-repository`（2 の4）
- Herdr 0.9.3 での挙動の違い（2 の7）
- 実際の運用での 3 ペイン構成のグループ表示

## 7. 後片付けの確認

実験で作った別セッション `hwgprobe` は `herdr session stop` → `herdr session delete` で消し、
一時リポジトリ（2 つ）と `tmux` の接続用サーバーも削除した。`herdr session list` には `default` のみが
残る。実験の前後で人間のセッションの `herdr workspace list` を比べ、既存のワークスペースの
ID・ラベルに変化が無いことを確かめた（実験中に別の作業が新しいワークスペースを 1 つ作っていたが、
これは本実験とは無関係）。

## 8. 人間に判断・確認してほしい点

- 方式の選択: 推奨の A＋C でよいか。傘単位のまとまり（B）は Herdr の仕様上できないと分かった。
  「リポ単位のグループ＋ラベル接頭辞」で足りるか
- 複数の傘を同じリポで同時に回すと並びが混ざる。許容できるか
- 見た目の確認: 実験はテキスト出力で読み取った。実際のサイドバー（`row_gap` や色など）で
  グループが期待どおりに見えるかは、人間の目で確かめてほしい
- Herdr を 0.9.3 に更新するかは人間の判断（0.9.0 で足りることは確認した）
