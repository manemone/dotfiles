# ADR: 複数リポにまたがる PR 群のレビュー作法を 2 つのスキルに分ける（`pr-group-review` / `pr-group-request`）

## ステータス

確定（2026-09-27）

## 1. 背景

他人が出した、複数リポにまたがる PR 群（9 リポ 18 本）を、人間が AI にまとめて
レビューさせた。作者自身も「個々の PR より PR 群の構造のレビューを受けたい」という
趣旨で、PR 群の構造をまとめた文書を自作していた。このとき dotfiles には次の穴があった
（傘 `multi-repo-pr-review` 計画書
[DOC-2609270342](../planning/DOC-2609270342_multi-repo-pr-review_計画.md) 背景3）。

- 既存の `pr-review-loop` はレビュイー（自分の PR を直す側）から起動するスキルであり、
  Herdr の reviewer ペインを通して相手を待つ。相手が他人のときには使えず、
  **レビュワーとして他人の PR にコメントし、返信を待って追いレビューする工程を担当する
  スキルが無い**
- 複数リポにまたがる PR 群の「地図」（グループ、依存、積んでいる PR、マージと適用の順序、
  手作業の工程、未決の ADR、リポ間の照合表、ロールバック）を**作る、または検証する手順が
  どのスキルにも無い**
- 逆に、自分の PR 群のレビューを他人に頼むときに、地図と依頼文を用意する手順も無い
- 傘ブランチの計画書には孫の PR の並びがあるが、それをレビュー依頼用の地図に変える手順が無い

レビューの途中で次の 2 つの失敗が起き、どちらも本 ADR の決定の直接の根拠になった
（計画書 背景1）。

- AI が他人の PR に修正コミットを作り、push してよいか尋ねた。人間の返答:
  「修正じゃなくてレビューをしてほしいんだが。これは僕のPRじゃないので。」
- AI が GitHub への投稿を権限の仕組みに止められ、投稿スクリプトを人間に渡して
  「自分で実行してください」とした。人間の返答:「なんでや！やってくれ！」

そのレビューで測った実測値のうち、決定に効いたもの（計画書 背景4.1）:

- **対象 PR の列挙は 1 つの情報源だけでは漏れた。** チャットに共有されたリストには 15 本しか
  無く、ADR の PR 3 本は作者の自作文書にだけ載っていた
- 手元の clone の状態はばらばらで、別の作業ブランチが dirty のまま checkout されているものも
  あった。各 PR の head を `git fetch origin pull/N/head:refs/review/pr-N` で取り、一時的な
  場所へ detached worktree として展開して、**人間の作業ツリーには触れずに**読んだ
- 指摘 62 件を反証した結果、confirmed 41 / plausible 6 / refuted 3 / duplicate 12。
  ブロッカー 0、重大 8。**重大 8 件のうち 6 件はコードではなく「順序と手作業」**
  （DB スキーマ管理ツールの適用順、submodule が古い系統を指す、デプロイツールの前提、
  ブランチから apply 済みのインフラ）だった。リポ間の照合（ペイロード↔スキーマ↔受信、
  API 契約↔実装、インフラ名↔ENV 等）は全部一致していた
- 投稿では COMMENT レビュー 17 件とインラインコメント 47 件を出した。**インラインコメントの
  行が diff の hunk 内にあるかを投稿前に検証し、レビュー後に head が動いていないかを投稿直前に
  確認した**
- auto mode の分類器に 2 回止められた（ローカルのテスト DB を使うテストの実行、GitHub への投稿）。
  後者は人間が「やってくれ」と言ったあと、auto mode を抜けて実行できた

本 ADR は、この経験から人間と司令官が確定させた 2 スキルの外形を記録する
（計画書 背景2・背景5・設計1）。スキル本体は後続の孫が本 ADR に従って書く。

## 2. 決定

### 2.1 スキルを 2 つに分け、`pr-review-loop` とは別物にする

| スキル | 役割 | 起動 | 外部への書き込み |
|---|---|---|---|
| `pr-group-review` | 他人の PR 群を**レビュワーとして**レビューする。追いレビューも同じスキルで行う | 手動（`/pr-group-review`。自動発動しない） | GitHub への **COMMENT レビュー投稿のみ**（人間の確認後） |
| `pr-group-request` | 自分の PR 群のレビューを他人に頼む準備をする（地図・継ぎ目の自己チェック・各 PR の本文・依頼文） | 手動（`/pr-group-request`。自動発動しない） | 自分の PR の本文の更新（人間の確認後）。チャット用の依頼文は**下書きを渡すだけ**で、投稿は人間 |

- どちらも **AI 不問**（Claude Code / Codex / OpenCode）。既存スキルと同じく YAML frontmatter
  を除き自然言語で完結させ、**実行可能なスクリプトは同梱しない**（手順中のコマンド例や
  コード断片は可）。スキルは `skills/` から全エージェントへ配られる（ADR
  [DOC-2608272128](DOC-2608272128_skills-multi-agent-distribution.md)）
- **レビュワーはレビューだけをする。** `pr-group-review` は次を明示的な禁止として持つ:
  他人の PR への修正コミットの作成・push、PR 本文の書き換え、`APPROVE` / `REQUEST_CHANGES`
  の投稿。指摘も「マージ前の前提」も、すべてレビューコメントで返す
- **`pr-review-loop` は改修しない。** 依頼者側で返ってきた指摘への対応は、PR ごとに
  `pr-review-loop` で回すと `pr-group-request` から接続を説明する。両スキルと
  `pr-review-loop` の間には相互参照を 1〜2 行ずつ足すだけにする

`pr-review-loop` と別物にする理由: `pr-review-loop` は「自分の PR を直す側」が起動し、
Herdr の reviewer ペインと往復して承認→マージまで進む。今回欲しいのは起動する側が
**レビュワー**で、相手は Herdr のペインの向こうではなく GitHub の向こうにいる他人（背後に
AI がいる）であり、ゴールもマージではなく「コメントを返して相手の返信を待つ」ことである。
起動者・相手の居場所・ゴールがすべて違うため、同じスキルに分岐を足すと両方の手順が読みにくくなる。

レビュワー用と依頼者用を分ける理由: 両者は外部へ書き込めるものが根本的に違う（他人の PR には
COMMENT しか出せない／自分の PR は本文を書き換えてよい）。禁止事項をスキル単位で持たせると、
レビュワーとして動いているときに依頼者側の「本文を更新する」手順が紛れ込む余地が無くなる。

### 2.2 レビュー状態の置き場所: どのリポにも置かず、`PR_GROUP_REVIEW_DIR` 配下に `git init`

- ベースディレクトリは環境変数 `PR_GROUP_REVIEW_DIR` で上書き可能とし、既定を
  `$HOME/work/reviews` にする
- レビュー 1 件（1 つの PR 群）につき `$PR_GROUP_REVIEW_DIR/<YYYY-MM-DD>-<テーマ>/` を作り、
  そこで `git init` する。ラウンドごとにコミットして履歴を残す
- **レビュワー用・依頼者用の両方がこの置き場を使う。** どちらの用途かは状態ファイル内に記録する
- 中身: 状態ファイル（JSON。対象 PR の一覧〈リポ・番号・URL・レビュー時の head SHA〉、PR 群の
  地図、ラウンドごとの指摘〈ID・重要度・blocking か・状態〉、投稿済みレビューの ID）、投稿用の
  下書き、まとめの HTML。形式の詳細は `pr-group-review` の参照文書で定める

ここでいう「状態」は、コードを読むための worktree ではなく、**レビューという仕事の記録**で
ある（人間が「そういう意味の状態だよね？」と確認し、AI がそのとおりだと答えた）。コードを
読むための取得は次のとおり別に扱い、状態ディレクトリには置かない。

- clone は「リポ名の下にメインブランチのディレクトリ」の形（例: `~/work/<repo>/<default-branch>`）。
  無ければその形で clone する（ワークツリーを使うため）
- **人間の作業ツリーに一切触れない。** 各 PR の head を `git fetch origin pull/N/head:refs/review/pr-N`
  で取り、scratchpad などの一時的な場所に detached worktree として展開して読む
- レビュー時点の head SHA を状態ファイルに記録する（追いレビューの差分の起点、投稿直前の確認に使う）

### 2.3 単体 PR は「1 本だけの PR 群」として同じスキルで扱う

単体リポの PR 1 本も、同じ `pr-group-review` / `pr-group-request` で扱う。地図は「1 本だけの表」、
継ぎ目チェックは該当する項目だけ、というように PR 群の規模に応じて縮退させ、同じフローで回す。
単体 PR 用のスキルは増やさない。

### 2.4 まとめ文書は自己完結 HTML にし、状態ディレクトリに置いて人間が共有する

- まとめ文書は Claude の artifact にせず、**外部 CDN に依存しない自己完結した HTML ファイル**で作る
- HTML は 2.2 の状態ディレクトリ内に生成する
- 共有は**人間がチャット（Slack）に添付する。AI はチャットへ投稿しない**
- Notion へのアップロードは、人間が求めたときだけの任意の追加手段としてスキルに記載する

### 2.5 外部への書き込みの扱い

- 流れは **下書き → 人間の確認 → 投稿**。人間の明示的な了承なしに投稿しない
- 他人の PR へ投稿するのは **COMMENT だけ**。承認と変更要求は人間が判断する
- **2 段の投稿を既定にする。** 1 段目で構造・順序・blocking の指摘を返し、細かい指摘は 2 段目で
  返す（Google eng-practices「Navigating a CL in review」: 設計の指摘は手戻りが大きいため
  すぐに返す）。人間が確認の時点で「一度に出す」を選んだらそれに従う（人間はこの点を明言して
  いないため、人間が選べる形にした）
- 投稿の直前に次を確認する:
  1. PR の head が状態ファイルに記録した SHA から動いていないか。動いていたら投稿せず人間に報告する
  2. インラインコメントの行が diff の hunk 内にあるか
- **権限の仕組み（auto mode の分類器など）に投稿を止められたら、スクリプトを人間に渡して
  「自分で実行してください」とはしない。** 止められたことと理由を人間に伝え、許可（auto mode を
  抜ける等）を得たうえで AI 自身が投稿する。ローカルの共有リソース（テスト DB 等）を使う操作を
  止められた場合も同様に、人間の判断を仰ぐ

### 2.6 blocking の表示とコメント書式は投稿先のルールに委ねる

- コメントの書式（接頭辞・分類タグ・文体など）は、**投稿先のリポのルール（AGENTS.md や docs 配下の
  レビュー規約）を読んで従う。** スキルに特定組織の書式を直接書き込まない。例として載せる場合も、
  特定組織の規則だと分かる書き方にし、組織名・リポ名は書かない
- ラベル・タグは投稿先のルールに従い、それを崩さない（例: タグを 1 つしか付けられないルールなら、
  blocking を示すためにタグを足さない）
- blocking であることは、**コメント本文の定型文**（例:「マージ前に対応が必要です」）と、
  **レビューサマリの先頭での列挙**で示す
- 投稿先にルールが無いリポでは、Conventional Comments の `(blocking)` / `(non-blocking)` を使う

### 2.7 共通の参照文書は `pr-group-review` 側に置き、`pr-group-request` から相対パスで参照する

地図テンプレート（HTML の雛形を含む）・リポ間の継ぎ目チェックリスト・状態ファイルの形式は
`skills/pr-group-review/` の中（例: `skills/pr-group-review/references/`）に置く。
`pr-group-request` は同じものを兄弟ディレクトリへの相対パス（`../pr-group-review/references/...`）で
参照し、**内容を 2 つのスキルに重複して持たない。** スキルは全エージェントへスキル単位の
symlink で配られ、配布先でも兄弟として並ぶため、相対パスで届く。参照される側のファイル名は
安定させる。

継ぎ目チェックリストには、1 章の実測（重大指摘の大半は照合ではなく順序と手作業の側にあった）を
冒頭の注意として書き、項目には **PR 群に入っていない利用者**（変更に依存しているが PR 群の外にある
コード・サービス）を含める（Qodo の cross-repo code review が、影響を両方向に追うことを勧めている）。

### 2.8 追いレビューは手動で起動する

- 相手（背後に AI がいる他人）の返信を待ち、人間が `/pr-group-review` を再び起動したら、
  状態ディレクトリから前回のラウンドを読み込んで次のラウンドを返す
- 前回の SHA から差分を取る。force-push / rebase されていたら `git range-diff` で取り直す
  （GitHub の「前回のレビュー以降の変更」は rebase / force-push で壊れるため）
- スレッドごとに「解決 / 未解決 / 新規」を判定し、状態ファイルに記録してコミットする
- 定期的に確認する仕組み・自動の追いレビューは入れない

## 3. 却下した案

### 3.1 `pr-review-loop` を拡張してレビュワー側も扱う

2.1 のとおり、起動者（レビュイー／レビュワー）・相手の居場所（Herdr のペイン／GitHub の向こうの
他人）・ゴール（承認→マージ／コメントして返信待ち）がすべて違う。分岐を足すと、レビュワーとして
動いているときに「修正して push する」手順が同じ文書に並び、まさに 1 章の失敗（他人の PR に修正
コミットを作ろうとした）を誘う。

### 3.2 1 つのスキルでレビュワー用・依頼者用の両方を扱う

外部へ書き込めるもの（COMMENT のみ／自分の PR の本文の更新）が違い、禁止事項もスキル単位で
持たせたい（2.1）。共通部分は参照文書として共有する（2.7）ことで、分けても重複は生じない。

### 3.3 レビュー状態を対象リポのどれかに置く

複数リポにまたがる PR 群では、どのリポにも属さない情報（リポ間の照合表、マージと適用の順序）が
主役になる。特定のリポに置くとそのリポだけが特別扱いになり、他人のリポに自分のレビュー記録を
置くことにもなる。さらに 1 章の実測では手元の clone が dirty な作業ブランチを checkout している
ことがあり、状態の置き場として触ると人間の作業ツリーを汚す。

### 3.4 まとめを Claude の artifact で作る

人間が「脆い」として却下した（計画書 背景2）。artifact は特定の製品・アカウントに依存し、
AI 不問（2.1）とも整合しない。自己完結 HTML なら状態ディレクトリに履歴ごと残り、チャットに
添付するだけで誰でも開ける。

### 3.5 自動で（定期的に）追いレビューする

人間が手動起動に決めた（計画書 背景2）。相手の返信のタイミングは読めず、定期確認は空振りの
コストがかかるうえ、外部への書き込み（2.5）を人間の確認なしに繰り返す経路を作ることになる。

### 3.6 AI が `APPROVE` / `REQUEST_CHANGES` まで出す

承認と変更要求はマージの可否に直結する判断であり、人間が行う。AI が出すのは COMMENT だけに
することで、AI の指摘が誤っていても PR の状態は変わらない（1 章の実測でも、反証で 3 件が
refuted、12 件が duplicate になった）。

### 3.7 権限に止められたら投稿スクリプトを人間に渡して実行させる

1 章の失敗そのもの。人間は「なんでや！やってくれ！」と返した。人間が求めているのは投稿という
作業を AI にやってもらうことであり、権限の仕組みが止めたのは「人間の了承なしに外部へ書き込む
こと」である。したがって正しい対応は、止められたことを伝えて了承（auto mode を抜ける等）を
得たうえで AI が投稿することで、作業を人間に押し戻すことではない（2.5）。

### 3.8 対象 PR の列挙を人間が示したリストだけで行う

1 章の実測で、チャットのリストに無い ADR の PR 3 本が作者の自作文書にだけ載っていた。列挙は
人間が示したリスト・作者の地図・各 PR の本文のリンク・同じブランチ名や関連 issue など複数の
情報源から行い、突き合わせたうえで人間に一覧を確認する。
