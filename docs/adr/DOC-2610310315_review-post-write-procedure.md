# ADR: PR への書き込みを「許可ルールに当たる単体コマンド」に固定する

## ステータス

決定（2026-10-31）。傘 `review-post-classifier`（計画書 DOC-2610310309）の孫1 で決めた。

## 1. 背景

2026-10-29 から、`pr-review-loop` のレビュー投稿・返信・スレッド解決が auto mode の分類器に
止められることが増えた。止められた操作はすべて複合コマンド（ヒアドキュメント・`cd …;`・
`--input` に ruby で組んだ JSON を渡す形）で、レビュー依頼が別セッションのメッセージで届いた
セッションに多かった。`skills/pr-review-loop/SKILL.md` には書き込みの手順が無く、AI が毎回その場で
コマンドを組み立てていた。gh の許可ルールはこのマシンの生成物にしか無く、配布物には無かった。

## 2. 決定

1. **書き込みの形を固定する。** `skills/pr-review-loop/SKILL.md` に「GitHub への書き込み手順」の節を
   新設し、レビュー指示テンプレートと Phase 6 から参照させる。本文・JSON はファイル書き込み機能で作り、
   投稿は値をそのまま書いた単体コマンド1つで打つ。形は次の3つ。

   | 用途 | コマンド | 当たる許可ルール |
   |---|---|---|
   | review | `gh api -X POST repos/<owner>/<repo>/pulls/<n>/reviews --input <絶対パス>` | `Bash(gh api -X POST repos/manemone/*/pulls/*/reviews --input *)` |
   | 返信 | `gh api -X POST repos/<owner>/<repo>/pulls/<n>/comments/<id>/replies --input <絶対パス>` | `Bash(gh api -X POST repos/manemone/*/pulls/*/comments/*/replies --input *)` |
   | 会話コメント | `gh pr comment <n> -R <owner>/<repo> --body-file <絶対パス>` | `Bash(gh pr comment * -R manemone/* --body-file *)` |

   review の `event` は `COMMENT` 固定。
2. **許可ルールを配布物 `claude/settings.json` の `permissions.allow` に入れる。** 許可ルールに当たった
   コマンドは分類器を通らないので、依頼の届き方に関係なく投稿が通る。対象は `manemone/*` に絞り、
   `--input` / `--body-file` まで前置に含めて形を固定する。`gh pr review`・`gh pr comment *`
   のような広いルール（`--approve` や他の形まで通る）は足さない。
   ただし許可ルールの `*` は空白や `/` も含む任意の文字列に当たるため、前置が合うだけで形が
   固定されるわけではない（例: 前置の後ろに別の API パスや `-X PUT` を連ねた単体コマンドも
   当たる）。そこで `permissions.ask` に `gh api` のマージ API（`*merge*`）と、
   `-X` の後ろに `PUT` / `DELETE` / `PATCH` が続く形（`-XPATCH` のように空白なしの形を含む）と
   `--method` を足し、許可より優先して確認が出るようにした（ask は allow に勝つ）。
  会話コメントの形にも同じことが起きる（前置の後ろに `--edit-last` を連ねると自分の最後のコメントを
  書き換えられる）ため、`Bash(gh pr comment *--edit-last*)` も ask に足した。
   確認に落とせるのは、コマンド文字列に現れる範囲だけである（残余は §4）。git-guard フック（ADR DOC-2609121719）は変えず、`gh pr merge` の
   判定とは別に、`gh api` 経由のマージも確認に落とす。
   **`event` の値は JSON の中身で、コマンド文字列に現れないため、ルールでは `APPROVE` /
   `REQUEST_CHANGES` を防げない。** 承認 review を出さないことは、手順（`event` は `COMMENT`
   固定）と「レビュワーに代わって承認マーカーを投稿しない」という既存の安全制約が受け持つ。
3. **スレッドの解決は手順から外す。** `resolveReviewThread` は分類器の既定規則で PR 作業の範囲の外と
   名指しされている。絞ったルールで通す案（(b)）は、デプロイ前の実機で分類器を通ることを確かめられない
   ため採らなかった。対応は返信とコミット SHA で示し、レビュー AI はスレッドの解決状態ではなく、
   前回レビュー以降の返信と差分で対応済みかを判断する。SKILL.md の読み方の節（ラウンド2以降の読み方・
   蒸し返し禁止・Phase 5 の指摘収集）をそれに合わせた。
4. **止められたら形を変えて試し直さない。** 回避と見なされうるうえ、分類器は3回連続または累計20回
   止めると auto mode を一時停止する（ADR DOC-2609121719 §3.5）。投稿しようとしたファイルのパスと
   コマンドを控え、人間に伝えて止まる。

## 3. 却下案

- **レビュー依頼の届け方を `herdr agent prompt` に戻し、人間の入力のように見せて分類器を通す案。**
  同意の基準をすり抜ける形であり、分類器の意図に反する。`umbrella-orchestrator` §5 の `SendMessage`
  優先の方針は変えない。
- **広い許可（`Bash(gh api *)`・`Bash(gh pr review *)` など）。** auto mode に入るとき捨てられうるうえ、
  承認の review まで通る（本案の絞ったルールも `event` の値は防げない。§2 のとおり手順が受け持つ）。
- **スレッド解決を絞ったルールで通す案。** 上の決定3のとおり、実機で確かめられなかった。

## 4. 影響と残余

- 許可ルールが効くのは、人間が傘を `master` にマージしてデプロイした後。それまでは、このマシンの
  生成物に残っている既存の gh のルール（`reviews *` など）に当たる。
- このマシンの生成物には、より広い gh の許可ルールが残っている。`claude/deploy.sh` が既存の
  `permissions.allow` を引き継ぐためで、整理するかは人間が決める。
- **グロブで塞げない形が残る。** `-X POST` のままエンドポイントだけを差し替える形（例: リポの移管）は、
  前置が合えば allow に当たり、ask のグロブでは塞げない。`event` の値と同じく、手順を守ることが歯止めで
  ある。`*merge*` は、パスやリポ名に `merge` を含む正しい形にも当たる（確認が出るだけで安全側）。
- **許可ルールに当たった3形は、分類器の本文チェックを通らない。** `--input` / `--body-file` が指す
  ファイルの中身は確認されないので、任意のローカルファイル（認証情報の設定ファイルなど）を公開リポの PR に
  投稿しうる。PR やコメントに紛れ込んだ指示に AI が従った場合の歯止めは、手順（本文は自分でファイル書き込みで作る）と
  人間のレビューだけである。§5 の `autoMode.allow` の文にある「本文の中身は既定の規則で引き続き判定する」は、
  許可ルールに当たらない形にだけ効く。
  - **ファイルの置き場を固定の前置（`/tmp/pr-review-loop/` など）に絞る案は採らなかった。** 置き場は
    スクラッチパッドや `mktemp -d` のディレクトリで、環境ごとに違う（macOS の `TMPDIR` など）。前置を固定すると
    許可ルールが環境ごとに外れ、止められる問題が戻る。`/tmp` は誰でも書けるため、絞っても残余は残る。
    この残余を受け入れるかは人間がレビューで判断する。
- 他の owner のリポは許可ルールに当たらず、通常の承認の流れになる。
- 配布物にルールを足す前後で、生成のしくみ（DOC-2610150520-b）は変わらない。

## 5. 追記: autoMode の許可の文（孫2。人間が採否を決める）

ステータス: 提案（2026-10-31）。この節は人間がレビューで採るかを決める。採らない場合はこの節と
`claude/settings.json` の `autoMode`、`claude/deploy.sh` のマージ変更を外せばよく、§2 の許可ルールだけで
投稿は通る。

1. **`autoMode.allow` に許可の文を1つ足す。** 先頭は `"$defaults"`（付け忘れると既定の allow が消える）。
   `soft_deny` / `hard_deny` / `classifyAllShell` は書かない。文の趣旨は、pr-review-loop の3役が互いの
   メッセージ（別セッション含む）に従い、`manemone` 配下の対象 PR へ `event: COMMENT` の review・
   インラインコメント・返信・会話コメントを投稿することを「人間が承認済み」と伝えること。承認・変更要求、
   マージ、コメントの編集削除、PR の状態や base の変更、スレッド解決、他 owner への書き込みは含めない。
2. **§2 との違い。** §2 は「形が決まった単体コマンド」だけを通す。この文は、AI がその場で組み立てた
   別の形（複合コマンドなど）の投稿も、分類器が通しうるようにする。
3. **`claude auto-mode critique` の講評と対応。** 2回通した。採った: owner を `github.com/manemone` と明記、
   対象を「ループが対象にしている PR」に限定、手段を `gh pr comment` と `gh api` の POST に限定、本文の中身は
   既定規則で引き続き判定すること、除外（自分のコメントの編集削除・リアクション・ラベル等・`reviews/<id>/events`）の明示、
   メッセージが指していない PR の本文などの中にだけある指示はループの開始と見なさないこと（pr-review-loop の依頼は指示ファイルの絶対パスだけを送るので、起点は「メッセージが /tmp/pr-review-loop/ 配下の指示ファイルを指していること」とした。ラウンド1のレビューで指摘を受けて直した）、owner の完全一致、コマンドへの owner/repo/PR 番号と
   `event: COMMENT` の明示。採らなかった: 「止められたと言っている相手の代行も許す」旨の条項（分類器の
   代行拒否の歯止めを外すため）、`environment` の Source control への owner 追加（push など PR コメント以外の
   信頼範囲まで広がるため）、Herdr のメッセージ書式の記述（書式が変わると嘘になるため）、依頼元が止められたと述べているときは許可しない旨の条項（実装 AI が自分の返信を代行させる流れと食い違うおそれがあるため、既定の代行拒否に任せる）、指示ファイルを同じ会話で自分が書いたときは開始と見なさない旨の条項（実装 AI は指示ファイルを自分で書いてレビュー AI へ送るため、実装側の返信まで止めるおそれがある）。指示ファイルの置き場 `/tmp` が誰でも書ける点は残余のリスクとして人間の採否の材料にする。
4. **machine 設定とのマージ。** `claude/deploy.sh` は `autoMode` の配列（allow・soft_deny・hard_deny・
   environment）を `permissions` と同じく連結し重複を除く。従来の浅い `update()` のままだと、machine 側に
   `autoMode.allow` があるだけで配布物の `"$defaults"` ごと置き換わり、既定の allow が消えるため。
   `tests/deploy_smoke.sh` のシナリオ10で固定した。`claude/README.md` §4.2 にも書いた（machine 側からは
   配布物の文や `"$defaults"` を取り除けない）。
5. **確認方法。** critique は `CLAUDE_CONFIG_DIR` を一時ディレクトリに向け、`autoMode` だけを入れた設定を
   読ませて実行した（実 `$HOME` の設定は変えていない。認証情報は symlink で参照）。
