# ADR: 既定ブランチへのマージを、リポごとの宣言（opt-in）があるときだけ AI に任せる

## ステータス

決定（2026-11-26）。傘 `default-branch-automerge`（計画書 DOC-2611261524）の孫1 で決めた。

ADR [DOC-2609121719](DOC-2609121719_git-operation-permission-policy.md) の §1 の線引き
（「`main` / `master` へのマージは人間がやる」）と §3.1 の判定表の保護ブランチの行を、
**宣言のあるリポに限って**拡張する。宣言の無いリポでは何も変わらない。DOC-2609121719 の本文は書き換えない。
ADR [DOC-2610130212](DOC-2610130212_commander-merges-grandchildren.md) の「傘ブランチ向きの孫の PR は司令官がマージする」は
変えない。

## 1. 背景

いまの線引きは1本で、既定ブランチ（`main` / `master`）へのマージは人間、それ以外は AI に任せる。
この線を、リポごとに動かす仕組みがどこにも無い。フック `claude/hooks/git-guard.sh` は保護ブランチ
（`main` / `master` の固定集合）向きの `gh pr merge` を一律 `deny` し、スキル `pr-review-loop` と
`umbrella-orchestrator` は既定ブランチ向きの PR を「人間に依頼して止まる」と書いている。

非公開の業務リポジトリ（定型の書類作成を Claude Code で回すリポ）で、人間が「このリポでは、既定ブランチ向きの PR
すべてを、レビュー承認と CI green を条件に AI がマージしてよい」と判断した。人間が確定させた前提は次のとおり
で、本 ADR はこれを覆さない。

- 許可するのは、リポごとの明示的な宣言（opt-in）があるリポだけ。宣言の無いリポでは従来どおり人間がマージする
- 宣言のあるリポでは、既定ブランチ向きの PR すべてが対象（傘の最終 PR に限らない）
- 条件は少なくとも、レビュー承認と CI green。承認の対象 HEAD が PR の最新コミットと一致することも含める
- dotfiles 自身の `master` は対象外のまま。ルート `AGENTS.md`「最重要ルール」の `master` の規則は変えない

## 2. 決定

### 2.1 宣言のキー・値・置き場所・読む版

- 置き場所: そのリポの `.claude/pr-review.yml`（`pr-review-loop` が既に読んでいる設定ファイル）
- キー: `default_branch_merge`、値: `auto`
  - 宣言は、ファイルの**先頭の階層（インデント無し）**に `default_branch_merge: auto` と書く（値は引用符で囲んでもよい。
    行末のコメントも許す）
  - **キーが無い・値が `auto` 以外・ファイルが無い・形が違う、のどれも「宣言なし」**として扱う。`auto` 以外の値は
    将来のために予約し、今は意味を持たせない（`manual` と書いても宣言なしと同じ）
- **読む版: PR の base ブランチの、リモート上の版。** 作業ツリーでも PR の head でもない。base が既定ブランチの
  PR（この ADR の対象は常にこれ）では、リモートの既定ブランチに入っている版と同じになる
  - 理由: 作業ツリーや PR の head の版から読むと、AI が同じ PR の中で宣言を足して自分でマージできる。リモートの
    base の版から読めば、宣言を入れる PR は base に入る前の PR なので自分自身を許可できず、必ず人間がマージする
  - 読み方（スキルもフックも同じ）: `gh api -H 'Accept: application/vnd.github.raw' 'repos/<owner>/<name>/contents/.claude/pr-review.yml?ref=<base>'`
    （`<owner>/<name>` と base は PR のあるリポのもの。他リポの PR で cwd のリポを読まない）。ファイルが無いと
    HTTP 404 になり、これは「宣言なし」である
- **スキルがこのコマンドを打つとき、キー名（`default_branch_merge`）を同じコマンドの中に書かない**（`grep` の
  パターンなどにも）。`claude/settings.json` の `permissions.ask` に `Bash(gh api *merge*)` があり、コマンド文字列に
  `merge` を含むと承認ダイアログが出るため。出力は AI が目で読む。リポ名・ブランチ名に `merge` を含むリポでは
  ダイアログが出るが、安全側に倒れるだけで許容する

### 2.2 自動マージの条件（すべてを満たすときだけ）

宣言のあるリポで、既定ブランチ向きの PR をマージしてよいのは次をすべて満たすときだけ。1つでも欠けたら
マージせず、従来どおり人間に「承認済み。マージしてください」と伝えて止まる。

1. 宣言がある（§2.1。base の版から読む）
2. base がそのリポの既定ブランチである（`gh repo view <owner>/<name> --json defaultBranchRef -q .defaultBranchRef.name` と
   `gh pr view <PR番号> --json baseRefName` を突き合わせる。`main` / `master` に固定しない）。傘ブランチ向きなど
   既定ブランチ向きでない PR は、この ADR の対象外で従来どおり
3. 判定を含む**最後の**レビューが「承認」
4. その対象 HEAD が PR の最新コミットと前方一致する
5. 対象 HEAD の必須チェックが green（`umbrella-orchestrator` §2.4「CI の確認」の読み方をそのまま使う。必須チェックが
   無ければ全チェック、実行中なら待つ、CI の設定が無いリポは対象外）
6. 人間がその PR について「マージを待て」と言っていない
7. PR の変更ファイルに `.claude/pr-review.yml` が含まれない
8. マージするのが司令官のとき（§2.3 の表で司令官が行う場合）だけ、implementer が `working` でない

条件 3〜6 は DOC-2610130212 の §2.4 と同じ読み方で、AI が `gh` で自分で確認する（報告の本文や記憶を根拠にしない）。
条件 7 は本 ADR で足した。宣言の値や、レビューの設定（`ci_gate` など）を AI 自身が書き換えた PR を、その AI の
承認だけで既定ブランチへ入れないための歯止めで、変更を入れる PR は人間がマージする。

### 2.3 だれがどの PR をマージするか

| PR | マージする主体 | 変更 |
|---|---|---|
| 単独の PR（既定ブランチ向き。宣言あり） | その PR の実装側の `pr-review-loop`（承認を受け取った会話） | 新規。条件は §2.2 の 1〜7 |
| 傘の最終 PR（傘→既定ブランチ。宣言あり） | 司令官のワークスペースの implementer（`/finalize` が回す `pr-review-loop`） | 新規。条件は §2.2 の 1〜7 |
| 他リポの孫の PR（そのリポの既定ブランチ向き。そのリポに宣言あり） | その孫の実装側の `pr-review-loop` | 新規。条件は §2.2 の 1〜7 |
| 上のどれかで宣言なし | 人間 | 変更なし |
| 傘ブランチ向きの孫の PR | 傘の司令官 | 変更なし（DOC-2610130212） |

- 実装側がマージするのは、`pr-review-loop` が承認を受け取り、Phase 7 手順4（CI）まで済んだ直後。実装側が自分の PR の
  マージ条件を確認する点は、孫が人間のフィードバック前にマージしてしまう問題（DOC-2610130212 §1）と同じ形になるが、
  宣言したリポでは人間が「承認と CI green で自動マージ」を選んでいるので、止めどころは条件 6（人間の「待て」）に置く。
  人間が待てと言う相手は、実装側の会話か、司令官（司令官が孫へ伝える）
- 実装側は、CI が実行中なら待ってからマージする（待ち方は DOC-2611151330 の `ci_gate` の扱いに従う）。赤なら
  マージせず、承認したレビュワーに知らせて Phase 5 へ戻る
- 他リポの孫の PR を実装側がマージしても、司令官は従来どおり `gh pr list --state merged` でマージを検出するだけでよい。
  マージ後に司令官へ送る新しい報告は足さない（最終報告で人間に伝える）
- 傘向きの孫の PR のマージ条件（DOC-2610130212 の §2.3）は変えない

### 2.4 マージの方法と、マージが失敗したとき

- 方法: `gh pr merge <PR番号> --squash --delete-branch`（孫→傘のマージと同じ）。**リポ固有の別の方法を宣言するキーは
  足さない。** squash が許されないリポなどで `gh` が失敗したら、別の方法（`--merge` / `--rebase`）に切り替えず、
  人間に報告して止まる
- `--admin`・`--auto`・branch protection を回避する手段は使わない。必須レビューや保護の設定でマージが拒否されたら、
  回避せず人間に報告して止まる（GitHub のリポ設定は変えない）
- `--delete-branch` のローカル削除は、ワークツリーがブランチを掴んでいると失敗するが、マージは成功する。
  終了コードでなく `gh pr view <PR番号> --json state,mergedAt` で確認する（DOC-2610130212 §4 と同じ）

### 2.5 フックの新しい判定表

フックの担保範囲を「base 判定だけ」から「base 判定 + 保護ブランチ向きのときの宣言の確認」へ、保護ブランチ向きの
場合に限って広げる。承認の読み取りと CI の確認は**フックに持ち込まない**（§3.3）。

| 対象コマンド | 判定 |
|---|---|
| `gh pr merge` で base が `main`/`master` で、宣言あり（§2.1 のコマンドで読んで `default_branch_merge: auto`） | **allow**（本 ADR で追加） |
| `gh pr merge` で base が `main`/`master` で、宣言なし（404・キー無し・値が `auto` 以外） | **deny**（従来どおり） |
| `gh pr merge` で base が `main`/`master` で、宣言の確認に失敗（`gh` の失敗・タイムアウト・出力の形式の不一致・`-R` で指すリポの解決失敗） | **deny**（従来どおり。宣言なしと同じ扱い） |
| `gh pr merge` で base が上記以外と確定 | **allow**（変更なし） |
| `gh pr merge` だが base を解決できない | **何も言わない**（変更なし） |
| 上記以外のすべて | **何も言わない**（変更なし） |

- 置き換わるのは DOC-2609121719 §3.1 の1行目（base が `main`/`master` なら deny）だけ。2行目以降は変わらない。
  `ask` を返す経路を持たない点も変えない
- 宣言の確認は、保護ブランチ向きと確定した後にだけ行う。宣言なしのリポでは `gh` の呼び出しが1回（宣言の読み取り）
  増えて、結果は従来と同じ `deny` になる。**宣言なしのリポの `deny` の文言・判定は変えない**
- 宣言の読み取りは `-R` / `--repo` を引き継ぐ（DOC-2609121719 §3.1 と同じ穴を宣言の読み取りに作らない。他リポの PR の
  宣言を cwd のリポの版で読むと、別リポの宣言で allow しうる）
- `<owner>/<name>` は、base 解決と同じ `gh pr view` 呼び出しで `baseRefName,url` を引いて URL から取るか、
  `gh repo view [-R] --json nameWithOwner` を別に呼ぶかのどちらか。実装（孫2）で選んでよい
- 宣言の値の解釈は、`^default_branch_merge:[ \t]*["']?auto["']?[ \t]*(#.*)?$` に一致する行が先頭の階層にあるか、で行う
  （フックは POSIX sh + 標準の python3 で、YAML パーサを前提にしない）。判定を満たさない形（インデント付き・複数行の
  形・別の値）は宣言なしになる

### 2.6 `timeout` の配分

`claude/settings.json` のフック `timeout` は 15 秒、フック内の `gh` 呼び出しは `GH_TIMEOUT` 12 秒だった。
宣言の読み取りが加わるので、次のとおりにする。

- base の解決（既存）: 12 秒のまま。超えたら従来どおり**何も言わない**（宣言なしのリポの挙動を変えないため）
- 宣言の読み取り（新規）: 別に 8 秒（`GH_TIMEOUT_DECLARATION` のような別名の定数にする）。超えたら **deny**
- フック全体の `timeout`: 15 秒 → **25 秒**（12 + 8 = 20 秒に余裕を足す）。`timeout` に達してフックが打ち切られた
  ときにどう扱われるかは未検証なので、宣言の読み取りの方を先に 8 秒で打ち切って deny を確定させ、`timeout` に
  達しない配分にする
- 通常の `gh` は1秒未満で返るので、この配分が効くのは遅い環境（VPN・WSL2 の DNS 解決遅延）だけ

## 3. DOC-2609121719 の設計思想との関係

### 3.1 「判定できない入力は何も言わない」との関係

DOC-2609121719 §3 は、判定できない入力に対して `ask` に倒さず何も言わないと決めた。理由は、日常の無関係なコマンドを
巻き添えで止めるからである。本 ADR の「宣言の確認に失敗したら deny」は、これと向きが違って見える。

違いは判定の位置にある。**宣言の確認は、フックが担当する操作（保護ブランチ向きの `gh pr merge`）だと
確定した後に行う。** そこで確認できなかったのは、日常のコマンドが何か分からない場合ではなく、
既に `deny` になっている操作を**緩める根拠**が確認できない場合である。根拠が確認できなければ緩めず、
従来どおり `deny` のままにする。新しく止まる操作は増えない（宣言の無いリポの挙動は変わらない）。
一方、base を解決できないとき（担当かどうか分からないとき）は、これまでどおり何も言わない。

### 3.2 「フックは `gh pr merge` の base 判定だけ」との関係

担保範囲は、保護ブランチ向きの `gh pr merge` に限って、宣言の確認ぶん広がる。広げるのは、base が PR 側の属性で
グロブで書けないのと同じ理由で、宣言も PR の向き先のリポのリモートにあり、コマンド文字列に現れないためである。
ルート `AGENTS.md`「最重要ルール」の、フックが担保する範囲の説明は、孫2 がこの ADR に合わせて書き換える。

### 3.3 承認と CI をフックに持ち込まない

フックが確かめるのは宣言まで。承認の読み取り（レビュー本文の書式の揺れ・対象 HEAD の突き合わせ）と CI の
確認（必須チェックの有無・実行中の待ち・CI の無いリポ）は、スキル側の責務のままにする。

- 承認の判定はレビュー本文の書式（`markers`）に依存し、書式の揺れでフックが誤った deny/allow を返すと、
  無関係なマージを止める・通すの両方に倒れうる
- CI は実行中を待つ判断があり、15〜25 秒の同期フックの形に合わない
- 孫→傘のマージでも、フックは承認を見ていない（DOC-2610130212）。フックを「宣言のあるリポの外へ漏らさない歯止め」に
  留め、条件の全部はスキルが担う

### 3.4 分類器と `permissions`

`gh pr merge` は `permissions.ask` に無く、フックの `allow` で通る（DOC-2609121719 §3.5）。auto mode の分類器が、
既定ブランチ向きのマージを止める可能性がある（未確認。§5）。**止められたら回避せず、人間に知らせて止まる**
（DOC-2610130212 §5 と同じ。同じ PR で毎回通知しない）。**`claude/settings.json` の `permissions` は変えない**
（フックの `timeout` の数値だけ §2.6 のとおり変える）。

## 4. dotfiles 自身の扱い

- dotfiles は宣言しない。`.claude/pr-review.yml` に `default_branch_merge` を書かない。ルート `AGENTS.md`
  「最重要ルール」の `master` の規則は変えない
- **フックで dotfiles を特別扱いしない。** 宣言が無ければフックは従来どおり `deny` になり、特別扱いのコードは要らない
- 将来 dotfiles の `.claude/pr-review.yml` に宣言を書いた場合、フックは `allow` するが、ルート `AGENTS.md` の規則が
  禁じるので AI は実行してはならない。この食い違いはフックでなく規則（と、宣言を入れる PR を人間がレビューすること）が
  防ぐ。残余リスクとして §7 に書く

## 5. 未確認として残すこと

- auto mode の分類器が、既定ブランチ向きの `gh pr merge` を止めるか。止められたときの扱いは §3.4。結果は
  宣言を最初に使ったリポの運用で分かり、傘の計画書の「進行記録」に追記される
- `gh api ... ?ref=<base>` でのファイルの読み取りが、実際のリポ（権限が足りない・`contents` の読み取りが無い
  トークン）で失敗する場合の頻度。失敗すれば `deny`（宣言なしと同じ）に倒れるので、安全側には倒れるが、宣言のある
  リポで自動マージが効かなくなる

## 6. 却下案

### 6.1 宣言を PR の head や作業ツリーの版から読む

最も手軽だが、AI が同じ PR の中で宣言を足して自分でマージできる。却下。リモートの base の版から読む（§2.1）。

### 6.2 `.claude/settings.json` や環境変数で宣言する

`settings.json` は `claude/deploy.sh` が生成する実ファイルで、リポごとの宣言の置き場所に向かない。環境変数は
マシンごと（リポごとでなく）の設定で、「このリポで」という宣言にならない。リポの設定ファイル
`.claude/pr-review.yml` は `pr-review-loop` が既に読んでおり、リポのレビュー規約と同じ場所に宣言を置ける。

### 6.3 司令官が他リポの孫の PR もマージする

司令官の巡回で拾える利点はあるが、司令官は他リポの `main` へのマージを実行する主体になり、他リポの宣言を
司令官が読む必要が生まれる。実装側が自分の PR を、自分のリポの宣言で、承認直後にマージするほうが、経路が1本で
済む。却下。

### 6.4 フックで承認と CI の green まで確認する

§3.3 のとおり、書式の揺れと実行中の待ちがフックの形（同期・15〜25 秒）に合わない。却下。

### 6.5 リポごとのマージ方法を宣言できるようにする

`merge` / `rebase` の選択キーを足せるが、今必要なリポは squash で足りる。必要になった時点で足す（YAGNI）。
squash が拒否されたら人間に報告して止まる（§2.4）。

### 6.6 宣言を既存の ADR（DOC-2609121719）の改訂として書く

DOC-2609121719 は §6 に破棄の経緯を持つ長い文書で、さらに別の拡張を重ねると読み取りにくい。本 ADR に拡張の範囲を
書き、DOC-2609121719 のステータス節から指す形にした。

## 7. 受け入れる残余リスク

- **宣言の確認に成功しても、承認・CI・「待て」の確認はフックが担保しない。** 宣言のあるリポでは、スキルの手順を
  無視した AI が条件を満たさないままマージしうる。一次の担保はスキルの手順とルール、フックは「宣言のあるリポの
  外へ漏らさない」ための裏打ちにとどまる（DOC-2609121719 §7 と同じ構図）
- **宣言を入れる PR・外す PR・条件 7 に該当する PR は、人間がマージする**ことが前提で、宣言の追加を AI が
  承認だけで通す経路は条件 7 で塞いだが、それ以外のファイル（`AGENTS.md` や CI の設定）を AI が書き換えた
  PR は条件 7 の対象外である。宣言のあるリポは、これを承知で選ぶ
- dotfiles に誤って宣言が入ると、フックが `allow` する（§4）
- 宣言の値の解釈は行の正規表現で、YAML として正しいが形が違う書き方（フロー形式のマッピングなど）は宣言なしに
  倒れる。安全側に倒れるので許容する
- 既定ブランチが `main`/`master` でないリポ（例: `trunk`）では、フックは base を非保護と見て従来どおり `allow`
  する（宣言の有無を見ない）。既定ブランチ向きのマージを機械的に止める手段が元から無い点は、本 ADR で変わらない
  （DOC-2609121719 §7）。この ADR の自動マージの条件はスキルが実際の既定ブランチ名で判定する
