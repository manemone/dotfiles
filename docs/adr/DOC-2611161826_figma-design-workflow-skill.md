# ADR: Figma の画面の作り込み手順を、独立したスキル `figma-design-workflow` にする

## ステータス

決定（2026-11-16）。

## 1. 背景

傘ブランチ（司令官 1 人＋孫の会話）で Figma の画面の叩き台を作り込む手順を、再利用できる形にしたい。
手順と落とし穴は知見の文書にまとまっていた。既存のスキルは、リポの外にある**正本**（Figma のファイル）を担当が書き換える
作業を扱っていない。

- `umbrella-orchestrator` は孫を spawn してマージするまでで、外部の正本の控え・書き込みの範囲・数での突き合わせ・
  絵での確認・ユーザーに絵を見せて決めてもらう流れを持たない
- `pr-review-loop` のレビューはリポの差分だけを見る。Figma の変更は差分に出ず、記録（数・絵）でしかレビューできない
- `ui-review` は実装した画面の確認で、Figma の作り込みは対象外

この手順をスキルにして、次の傘で再利用できるようにする。

## 2. 決定

### 2.1 別のスキルにする

`skills/figma-design-workflow/` を新設する。外部の正本を書き換える作業の手順は、孫の spawn・マージ・巡回の手順と
**関心が違う**。また Figma を使わない傘には不要で、`umbrella-orchestrator`（すでに 1,800 行超）に足すと、
Figma と関係ない傘の司令官も毎回その節を読むことになる。

- 自動発動しない。`/figma-design-workflow` で明示的に起動する（`pr-review-loop`・`umbrella-handoff` と同じ）。
  孫用プロンプトからは「このスキルの〜を読め」と参照される
- AI 不問の自然言語（ADR DOC-2608272128）
- `skills/deploy.sh` が自動で拾うので、`shared/helpers.sh` は触らない

### 2.2 既存スキルとの分担（重複させず、参照でつなぐ）

| 関心 | 持ち主 |
|---|---|
| 孫の spawn・マージ・巡回・承認の報告の受け方 | `umbrella-orchestrator` |
| PR のレビューの往復 | `pr-review-loop` |
| 実装した画面の確認 | `ui-review` |
| 作業の振り分け | `task-intake` |
| Figma の API の使い方（`use_figma` の書き方など） | Figma 公式のスキル。このスキルには書かない |
| 体制・1 件の流れ・ユーザーとのやり取り・Figma の安全・パターン・点検スクリプト・実装への受け渡し・落とし穴 | このスキル |

既存スキルの手順そのものは変えない。既存スキル側に足すのは、このスキルへの短い参照だけにする。

### 2.3 構成

入口の `SKILL.md`（300 行以内）に、体制・1 件の流れ・ユーザーとのやり取り・Figma の安全を置き、細部は `references/` に逃がす。

- `record.md` 記録の書き方（1 件 1 記録。Figma の変更は記録でレビューする）
- `patterns-process.md` 進め方のパターン
- `patterns-visual.md` 見た目の決まりのパターン
- `audit.md` と `audit-template.js` 点検スクリプトの使い方と雛形
- `handoff-to-impl.md` 実装への受け渡し
- `pitfalls.md` よくある失敗と Figma の落とし穴（落とし穴の一覧はここ 1 か所に一本化する）

### 2.4 公開リポのため、固有名詞と固有の決めを入れない

この dotfiles は公開リポである。材料の傘の実績を**一般化した**ものを書き、会社名・製品名・画面名・人の名前・Figma の
ファイルの識別子・社内のリポ名などは入れない。例は一般的な業務画面（一覧画面・詳細画面・集計の画面など）に置き換える。
材料に固有の決め（色の段の具体値・アイコンの選び方・字や間隔の数値）も入れず、「決まりを作って点検する」という手順と
決めるときの観点だけを書く。数値の例が要るときは、明らかに例とわかる丸い値にする。人間の発言は逐語で書かず要約する。

### 2.5 点検スクリプトを雛形として配る

全画面を走査して決まりに外れた物を数える点検は、「決まり＋全画面の点検」の要で、毎回ゼロから書くと決まりごとに作り直しに
なる。そこで、材料のスクリプトの構造（読むだけ・全画面を走査して数える）を保ち、決まりの表をファイルの先頭にまとめ、
利用者がそこだけ差し替えれば使える形の雛形を `references/` に置く。特定のファイル名・ノードの識別子・材料の決まりの値は
抜き、表の中身は「例」と明記した丸い値にする。雛形は Figma の中でしか動かないので、リポの中で回すテストは作らず、
`node --check` で構文だけ確かめる。

## 3. 却下した案

- **`umbrella-orchestrator` に節を足す。** 関心が違い、Figma を使わない傘にも毎回読ませることになる。既に長いスキルがさらに
  肥大する
- **`ui-review` に足す。** `ui-review` は実装した画面を、別の目で 30 分以内に確かめるスキルで、Figma という外部の正本を
  書き換える作業の手順（控え・書き込みの範囲・上限）とは対象も時点も違う
- **材料の文書をそのまま写す。** 公開リポに固有名詞・固有の決めを持ち込むことになり、別の傘に使い回せない。また材料の文書に
  無かった後の知見（透明度の戻りなど）を足せない
- **記録の置き場をスキルが決める。** 記録は利用者のリポの決めに従うのがよく、スキルは「計画書から辿れる所に 1 件 1 ファイル」
  とだけ言う

## 4. 影響

- 新しいスキルが 1 つ増える（`skills/README.md`・ルート `README.md` の一覧に行を足す）
- 既存スキル 4 つ（`umbrella-orchestrator`・`pr-review-loop`・`ui-review`・`task-intake`）に、このスキルへの短い参照が入る
- 材料の傘の実績が一般化されて残る。固有の決めは残らない
