# ADR: 孫の PR は承認されてもマージせず、傘の司令官がマージする

## ステータス

確定（2026-10-13）。傘 `usage-diet`（計画書 DOC-2610122205）の孫1 で決めた。

## 1. 背景

傘ブランチ方式では、孫の実装 AI が `/pr-review-loop` で承認を得たあと、そのまま孫→傘の PR を
マージしていた（ADR DOC-2609121719 が、傘の内側のマージを承認ダイアログなしで通す線引きを置いた）。
このとき孫は、人間がレビュー結果を見てフィードバックを返す前にマージしてしまうことがある。
別の製品リポの傘で実際に起き、本来は不要だった追加の孫を起こす手間が出た。

## 2. 決定

1. **`pr-review-loop` はどの PR もマージしない。** 承認まで来たら止まる。base が既定ブランチなら
   人間に伝え、傘ブランチ向きの孫の PR で司令官の Herdr ペインが渡されていれば、最終報告のあとの
   最後の行動として承認を司令官へ1回だけ報告する。渡されていなければ人間に伝える。
2. **孫→傘のマージは司令官が行う。** 司令官は報告を合図に、承認を `gh` で自分で確かめてから
   `gh pr merge <PR番号> --squash --delete-branch` を実行する。報告の本文は根拠にしない。
   報告が届かなかった・孫が止まった場合の保険として、巡回 cron も承認済みの PR を見つけたら同じ手順で処理する。
3. **司令官のマージ条件**は `umbrella-orchestrator` §2.4 のまま（最後の判定が承認・対象HEAD が最新と
   前方一致・implementer が `working` でない・base が既定ブランチでない）に、2つを足す。
   - base が計画書の傘ブランチと一致すること。
   - 人間がその孫について「マージを待て」と言っていないこと（人間が先にフィードバックしたい場合の止めどころ）。
4. **巡回 cron は30分ごと**（`13,43 * * * *`）にする。巡回の目的は報告の取りこぼしや孫の停止の
   拾い上げで、検知が最大30分遅れるのは許容する。cron の本文には `gh pr merge` を書かず、
   スキルの節（§3.6 手順3）を参照させる。auto mode の分類器が、cron の本文を登録時に静的に判定して
   マージ系のコマンドを拒否した実績があるため。

## 3. ADR DOC-2609121719 との関係

引き継ぐもの: 既定ブランチへのマージは人間だけ、という唯一の線引き。`claude/hooks/git-guard.sh`
（base が保護ブランチなら deny、それ以外は allow）と `permissions` の構成。いずれも変えていない。
司令官のペインから叩く `gh pr merge` も、同じフックを同じ判定で通る。

変わるもの: 傘の内側のマージを**だれが**行うか。ADR DOC-2609121719 は「承認済みなら AI が行う」と
していたが、本 ADR はそれを「傘の司令官が行う」に絞る。孫の実装 AI は行わない。
ADR DOC-2609121719 自体は書き換えない。

## 4. 孫1 で洗い出して判断したこと

| 項目 | 判断 |
|---|---|
| `pr-review-loop` の「リポの `AGENTS.md` が傘ブランチ方式を明記しているか」の確認 | 司令官側には移さない。司令官が計画書の傘ブランチを進めていること自体で満たされ、代わりに「base が計画書の傘ブランチと一致」を条件にしたほうが厳しいため |
| `--delete-branch` | 付けたまま使う（`AGENTS.md`「最重要ルール」が許可の形として明記）。孫のワークツリーがブランチを掴んでいるためローカル削除とリモート削除は失敗するが、マージは成功する。終了コードでなく `gh pr list --state merged` で確かめ、リモートの消し残しは `ocw rm` の後に消す（`umbrella-orchestrator` §3.3） |
| `permissions` / `git-guard.sh` | 変更なし。`gh pr merge` は base が保護ブランチでない限り無音で通る。`tests/git_guard_test.sh` の契約も変わらない |
| 孫の完了通知（§3.2 手順5・§3.6） | 「マージしました」から「承認されました。マージをお願いします」へ、意味を変えて仕組み（宛先は spawn の送信文で渡すペインID、送り方は二段構え）はそのまま使う |
| `ocw rm` の前に孫の最終報告を待つ手順 | 報告は最終報告のあとに届くはずなので、`working` でないことの確認に軽くした |
| 他リポの孫 | 変わらない。もともと AI がマージしない（base が既定ブランチ） |
| `pr-group-request` | 他人にレビューを頼んだ PR では、手元の AI の承認で司令官へマージ依頼を報告させない注意に書き換えた |
| `AGENTS.md`「最重要ルール」と `templates/repo-baseline/template/AGENTS.md.jinja` | マージを行う主体を「AI」から「傘の司令官」に限定した |

## 5. 未確認として残すこと

司令官が `gh pr merge` を実行したとき、報告を受けた対話のターンと、巡回 cron のターンで、auto mode の
分類器に止められるかは未確認である。この傘の運用そのものが実地の検証になる。止められたときの扱い
（`PushNotification` で人間に知らせ、同じ PR で毎巡回は通知しない）はスキルに書いた。結果は計画書の
「進行記録」に追記される。
