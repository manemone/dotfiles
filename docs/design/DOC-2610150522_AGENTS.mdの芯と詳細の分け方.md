# AGENTS.md の芯と詳細の分け方

各リポジトリの `AGENTS.md`（Claude Code では `CLAUDE.md` の `@AGENTS.md` から読み込まれる）は、
**会話のたびに、compact の直後でも、丸ごと頭に載る固定分**である。大きいほど毎回のトークンと、
本題に向く注意の両方を食う。この文書は、`AGENTS.md` を「毎回要る芯」と「作業のときだけ読む詳細」に
分ける方針と、他リポジトリへの適用手順を定める。dotfiles 自身と `templates/repo-baseline` の雛形には
この方針を適用済みである。

## 1. 芯に残すものの基準

次のどれかに当たるものは芯に残す。

- **不可逆・破壊的な操作の禁止と許可の線引き**（`master` を書き換えない・deploy を勝手に実行しない・
  linter 抑制を足さない、など「最重要ルール」の類）。読み忘れた会話で事故になるものは必ず芯
- **全作業に共通する制約**（クロスプラットフォーム制約など数行で済むもの）
- **概要・ディレクトリ構成・3つの領域のような地図**（どこに何があるかが分からないと、詳細へ辿れない）
- **作業別の索引**（「この作業のときは先にこの文書を読め」の表）。これが芯と詳細をつなぐ

次は詳細へ出す。

- 特定の作業のときにしか要らない**手順・仕組みの説明**（dotfiles では「デプロイの仕組み」「テストを足す
  判断基準」「コミット前の必須ステップの内訳」「実装時の注意」）
- 数十行を超える**表・コマンド列・設計の経緯**

迷ったら「この節を読まずに作業した会話は、何かを壊すか」で決める。壊すなら芯、壊さず手戻りで済むなら詳細。
**ルールは消さずに移す。** 消したほうがよいルールを見つけたら、消さずに PR 本文で報告する。

## 2. 芯の大きさの目安

公式の目安（`CLAUDE.md` 1ファイル 200 行以内）を出発点にする。dotfiles は「最重要ルール」だけで約 90 行あり、
地図と索引を足すと 200 行に収まらないため、**240 行前後（241 行）を許容した**（分ける前は 505 行）。リポジトリごとに、
最重要ルールを削らずに収まる範囲で目安に近づける。無理に 200 行へ寄せるために芯のルールを詳細へ追い出さない。

## 3. 詳細の置き場と、芯からの参照の書き方

- **置き場は `docs/design/`（DOC-ID を採番）を第一候補にする。** 規範として「従うべきルール」を書く場所であり、
  Codex / OpenCode を含む全 AI が普通のファイルとして辿れる。ツール固有の説明は各ツールディレクトリの
  `README.md` でもよい。
- **芯からは `@` を付けない普通のパス（と DOC-ID）で書く。** `@` import は Claude Code が起動時に読み込むため、
  固定分が減らない。参照は「〜を触るときは、先に（パス）を読むこと」と、**いつ読むかを明記する**。
  索引表に載せ、各節の頭にも1行置く。
- 次は採らなかった。`.claude/rules/`（`paths:` で触ったファイルに応じて読み込まれるが Claude Code 専用で、
  Codex / OpenCode に効かない）。サブディレクトリの `AGENTS.md`（Claude Code の読み込み方と Codex・OpenCode の
  読み込み方が揃わず、効く範囲が AI で変わる）。必要になったら、効く範囲を確かめたうえで別の決定にする。
- 分けたあとの参照直し: `git grep` で「`AGENTS.md`「（節名）」」の形で移した節を指している箇所（スキル・文書・
  テストのコメント・README）を洗い、移した先の DOC-ID に直す。リポジトリ外の参照元（他リポの文書など）は
  PR 本文で報告する。

## 4. OpenCode の `instructions`

`opencode.json` の `instructions` に列挙した文書は OpenCode が毎回読むため、**分けた詳細を足さない**
（足すと OpenCode の固定分が減らない）。dotfiles では既存の3文書（PR 作法・シェル方針・デプロイ検証の
テスト方針）を残し、新しい詳細は列挙せず、芯の索引から辿らせる。列挙済みの既存文書を外すかは別の判断で、
この方針では触らない。

## 5. 他リポジトリへの適用手順

どのリポジトリでも、手順は「手で分ける」で揃える。雛形（`templates/repo-baseline`）の変更は
`AGENTS.md.jinja` の「実装時の注意」へ足した1項目だけで、本体の節構成は変えていないため、
`copier update` を待つ必要も、使う必要もない。

1. 分ける前に `wc -lm CLAUDE.md AGENTS.md` を記録する（測り方は §6）
2. §1 の基準で節を振り分ける。芯に「作業別の索引」を置き、移す節ごとに `docs/design/` へ文書を作る
   （`DOC-DOCID_PLACEHOLDER_<名前>.md` → `doc-id assign`。doc-id を使わないリポジトリは
   `docs/` 直下か各モジュールの `README.md`）。移した節の見出しは1段下げる
3. 芯の元の位置には、要約数行と「先に（パス）を読むこと」を残す
4. §3 の参照直し。移す前後で**ルールが1つも失われていない**ことを、前後の `AGENTS.md` の突き合わせで確かめる
5. リポジトリの「コミット前の手順」に従って検証する
6. PR 本文に前後の数値と、消したほうがよさそうなルールの報告（あれば）を書く

リポジトリ別の補足:

| リポジトリ | 状況 | 扱い |
|---|---|---|
| lora-dataset-forge | copier 無し | 上記の手順そのまま |
| pixidex・modeldex | copier 済み（`copier update` 可） | 上記の手順そのまま。`copier update` は雛形の変更が dotfiles の `master` に入るまで届かず、孫2〜6 の手の変更と同じ箇所を触るとコンフリクトしうるため、孫は update を実行しない。雛形側の追加項目（実装時の注意の1項目）は、傘がマージされた後の update で入る |
| sheaf・iosci | copier 済みだが `_commit` が無く `copier update` 不可 | 上記の手順そのまま。雛形側の追加項目は手で足したければ足してよい（`AGENTS.md.jinja` の「実装時の注意」の項目と同じ趣旨） |

## 6. 効果の測り方

分ける前後で、**毎回読み込まれるファイル**（`CLAUDE.md` と、そこから `@` で辿れるもの）の合計を比べる。

```
wc -lm CLAUDE.md AGENTS.md
```

トークンは `/context` の Memory files の行を人間が対話で見る（AI からは測れない）。

dotfiles での結果（`AGENTS.md` のみ。`CLAUDE.md` は 1 行・11 文字で変わらない）:

| | 行数 | 文字数 |
|---|---|---|
| 分ける前 | 505 | 22830 |
| 分けた後 | 241 | 12104 |
