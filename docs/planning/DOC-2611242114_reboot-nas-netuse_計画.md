# 計画書: 再起動の起動時タスク（S4U）で起きた WSL から NAS に届かない件を、起動時の net use で根本から直す

傘ブランチ: `reboot-nas-netuse`
ターゲット: `master`

## 概要

傘 `reboot-network-creds`（計画書 DOC-2611230305）で、起動時タスク（S4U）で起きた WSL から呼ぶ Windows のプログラムが
NAS に届かない件に、「Windows のプログラムには UNC でなく、WSL の中の cifs マウントを `wslpath -w` のパス
（`\\wsl.localhost\<ディストロ>\mnt\nas\...`）で渡す」案（ADR DOC-2611151248 §7 の案 1）を入れ、別リポ3つと PC 固有の設定を
その形に書き換えた。この回り道は 9P を経由するため NAS への転送が大きく遅くなり、WSL の起こし方の変更と合わせて人間の作業を
かえって妨げた。さらに、管制の会話を `$HOME` で起こしているため、Claude Code のフォルダの信頼の確認で毎回止まっていた。

この傘で次を行う。

1. **起動時タスクの最初に、そのログオンの中で NAS の資格情報を付けて `net use` する。** S4U の起動時タスクのまま、
   WSL の `/etc/nas-credentials`（root 600、既存）の資格情報で `net use \\<NAS>\<共有>` を張る。これで WSL から呼ぶ Windows の
   プログラムが UNC で NAS に直接届く。新しく保存する秘密は無い（孫1）
2. **NAS への経路を、再起動対策より前と同じ「Windows から UNC で直接」に戻す。** 前の傘で入れた `\\wsl.localhost` の回り道を、
   別リポ3つ（孫2〜4）と PC 固有の設定から外す
3. **管制の会話を、フォルダの信頼を保存できる専用のフォルダで起こす**（孫1）
4. **`rebootctl status` の NAS の確認の「想定どおりの形」と ADR を、直した後の形に合わせる**（孫1）

## 背景1: 問題意識（要約。PUBLIC リポのため逐語では書かない）

- 前の傘の再起動対策で WSL の起こし方と NAS への経路が変わり、NAS につながらなくなる・回り道を作らされる・転送の速度が
  ひどく落ちる、という実害が出た。人間はこれを強く問題視している
- 起動しても、管制の会話がフォルダの信頼の確認で止まっていて、再起動対策の効果が出ていなかった
- 相談の会話がパスワードを保存するタスクに登録し直す案を出したところ、人間はその安全性を問題にした
- 人間は、性能が落ちることを許さないとはっきり示した
- 人間の判断で、傘で進めることにした

## 背景2: 人間が確定させた決定事項（覆さないこと）

- **再起動後に自動で Claude の会話が復帰する仕組み（起動時タスク → `rebootctl boot` → Herdr の復帰・管制の会話・巡回）は残す。**
  やめる案は人間が退けた
- **Windows のパスワードを保存する方式（タスクの LogonType Password・自動ログオン）は採らない。** サインインは Microsoft
  アカウントと見られ、保存したパスワードは管理者権限で平文に戻せるため
- **採る案: S4U の起動時タスクのまま、起動の最初に、そのログオンの中で NAS の資格情報（WSL の `/etc/nas-credentials`、
  root 600、既存）を付けて `net use \\<NAS>\<共有>` する。** WSL から呼ぶ Windows のプログラム（`robocopy.exe` / `ruby.exe` /
  `powershell.exe`）が UNC で NAS に直接届く。新しく保存する秘密は無い
- **性能を落とさないことが必須条件。** NAS への経路は、再起動対策より前と同じ「Windows から UNC で直接」に戻す。
  `\\wsl.localhost\...`（9P 経由）の回り道は戻す対象
- **管制の会話を `$HOME` で起こさない。** Claude Code はホームディレクトリのフォルダの信頼を保存しないため、毎回の起動で信頼の
  確認で止まっていた。信頼を保存できる専用のフォルダで起こし、そのフォルダを信頼済みにする方法を用意する
- 傘で進める。マージ先は master（dotfiles の最終 PR のマージは人間）

## 背景3: 2026-11-24 に相談の会話が測った実測値（このマシン、WSL2）

- 今の WSL は人間のサインイン後に起き直したもので、ログオンの種類は 2（Interactive）。この状態で Windows から
  `\\<NAS>\homes\<ユーザー>` への `Test-Path` は True。資格情報マネージャーの NAS の資格情報は、**ホスト名の短い名前
  （`.local` 無し）**で登録されている。`.local` 付きの名前では Interactive でも `Test-Path` が False（名前が違うと資格情報が
  当たらない）
- 人間が管理者 PowerShell で一時的な S4U のタスク（`wsl.exe -d <ディストロ> -u root -e sh <試験スクリプト>`）を登録→実行→削除し、
  その中で:
  - `net use` の前: UNC への `Test-Path` が False（再起動後と同じ症状を再現）
  - `/etc/nas-credentials` の username / password で `net.exe use '\\<NAS>\homes' <password> /user:<username> /persistent:no`
    → 成功
  - `net use` の後: `Test-Path` が True
  - 256MB のファイルを `C:\Users\Public\...` から NAS へ `robocopy.exe`: 5.0 秒（1回）
- 基準: 同じ 256MB を Interactive のログオンから同じ UNC へ `robocopy.exe`: 4.7 秒（2回とも）。差は誤差の範囲と見ている
- S4U のタスクから `wsl.exe -u root` で走らせると、root として `/etc/nas-credentials` を読め、Windows の相互運用（`net.exe` 等）も
  動いた。試験スクリプトはパスワードを出力しないよう、出力からパスワードの文字列を取り除いていた（スクリプト自体は相談の
  会話の一時ファイルで、もう参照できない前提）
- **未確認:**
  - 起動時タスクの1つのログオンの中で、root の手順で張った `net use` が、同じタスクから起きた Herdr の会話（ユーザー権限）が
    呼ぶ Windows のプログラムにも効くか。ADR DOC-2611151248 §7 の実測では、起こした WSL から呼ぶ Windows のプログラムはすべて
    そのタスクのログオン ID で動くので、効く見込み（`net use` の接続はログオンセッションごと）
  - サインインしない本物の再起動での通し

## 背景4: 既存の穴

- ADR DOC-2611151248 §4 は「S4U ではネットワーク資格情報が使えない」と書きながら、確かめる対象に NAS を入れていなかった。
  §7（傘 `reboot-network-creds`）では案 1（`wslpath -w` のパスで渡す）を選び、別リポ3つと PC 固有の設定をその形に書き換えた。
  §7 の案の比較表には「S4U のログオンの中で資格情報を付けて `net use` する」案が無く、案 1 の性能（9P 経由の転送速度）も
  「確かめていない範囲」に置いたまま選んでいた
- `bin/rebootctl` の `start_control_tower`（395 行目付近の `herdr workspace create --cwd "$HOME"`）が管制の会話を `$HOME` で起こしている
- `rebootctl setup` の表示する登録コマンド（`cmd_setup`、288〜310 行目付近）は、`wsl.exe -d <ディストロ> -- bash -lc
  "$HOME/bin/rebootctl boot --hold"` を S4U で登録するだけで、NAS の資格情報を付ける手順が無い。表示のコメントも
  「UNC には届かない（WSL の中の cifs を wslpath -w で渡せば届く）」と案 1 を案内している
- `rebootctl status` の NAS の確認（`REBOOTCTL_NAS_MOUNT` / `REBOOTCTL_NAS_UNC`、`nas_windows_unc` / `nas_windows_via_wsl`）は、
  サインインしない再起動のあと「UNC は届かず、WSL 経由は届く」を想定どおりの形として表示・文書化している（`bin/README.md` の
  `rebootctl` の節も同じ）。直した後は UNC に届くのが正常になる

## 決定的な制約（孫は全部守ること）

- dotfiles `AGENTS.md` の最重要ルール（`master` への反映は人間だけ。deploy スクリプトを人間の明示指示なしに実オペレーションで
  回さない、など）
- **ADR DOC-2611151248 §2: `rebootctl setup` は管理者 PowerShell に貼るコマンドを表示するだけ。** AI も `rebootctl` も
  `powershell.exe` 経由で Windows の設定を書き込まない（テストで固定されている）。タスクの登録し直しは人間が貼る
- **NAS のパスワードを、ログ・`boot.log`・コマンドの出力・PR・タスクの登録内容に出さない。** `/etc/nas-credentials` 以外に

- **`net use` が失敗しても `boot` を止めない**（Herdr の復帰を優先し、失敗は `boot.log` に残す）。冪等であること（既に張って
  あってもエラーで止まらない）
- `rebootctl status` の NAS の確認は、直した後の「想定どおりの形」（UNC にも届くのが正常）に表示と ADR を合わせる
- **Windows のタスク・資格情報など管理者権限の変更は人間が叩く。** AI はコマンドと確かめ方を用意する。読み取りの確認
  （`powershell.exe` で読むだけ）は AI が叩いてよい
- **実機の再起動・`wsl --shutdown`・起動時タスクの手動実行で WSL を起こし直す試験は、このマシンの学習のキューや他の会話も止める。**
  孫は自分で叩かず、手順を用意して人間に頼む。いつ叩くかは人間が決める
- **性能:** NAS への転送経路が UNC 直接に戻ったことを、別リポ側の直しでも確かめる（`\\wsl.localhost` を経由する経路を残さない）
- `claude/CLAUDE.md`（配布物）は指示が無い限り編集しない
- **PUBLIC リポ: リポの文書・PR 本文・コミットに人間の発言の逐語を書かない。** NAS のホスト名・共有名のうち個人に結び付くもの・
  アカウント名・非公開リポの名前・マシン名も書かない（役割で書く）。別リポでも、NAS のホスト名を設定の例・テスト・文書に

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- NAS のパスワードが、`net use` の手順の出力・`boot.log`・`setup` の表示に出ない。
  **この regression は必ず自動テストで固定する**（漏れると取り消せない）
- `net use` の手順が失敗しても、`boot` は Herdr の復帰と管制の会話の起動まで進む
- `rebootctl setup` は表示だけで何も実行しない（既存の保護を壊さない）
- 管制の会話を `$HOME` で起こさない

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
ログオンの種類と `net use` の効き方は実機で確かめ（やること6）、確かめた範囲を ADR と PR 本文に書く。

人間の発言を逐語で書かない（PUBLIC リポ。要約する）。NAS のホスト名・アカウント名・マシン名・非公開リポの名前を書かない。

## 大きい出力を文脈へ流し込まない（実装中ずっと）
文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し修正して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）

## リポジトリに書かないもの
人間（持ち主）の発言そのものを、PR の本文・コミットメッセージ・文書・コードのコメントに書かない
（計画書や送信文にあっても写さない）。何への対応かを自分の言葉で書く。
非公開のリポジトリの名前・ホスト名も書かない。書き直すときは、人間が挙げた例を要件として言い切らない・
誰の判断や提案かを落とさない・意味に要らない固有名詞を残さない。

   実行しない（孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し修正して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）

## リポジトリに書かないもの
人間（持ち主）の発言そのものを、PR の本文・コミットメッセージ・文書・コードのコメントに書かない
（計画書や送信文にあっても写さない）。何への対応かを自分の言葉で書く。
NAS のホスト名を設定の例・テスト・文書に新しく書き込まない（このリポの既存の流儀で、設定から読む）。
書き直すときは、人間が挙げた例を要件として言い切らない・誰の判断や提案かを落とさない・意味に要らない固有名詞を残さない。

## 背景（要約）

このリポは、別リポの学習ツールから Windows の `ruby.exe` 経由で呼ばれ、NAS 上の保管庫・目録・作例の置き場を使う。前の傘で、
起動時タスクで起きた WSL から Windows のプログラムが NAS に届かない件の回避として、これらの置き場を `\\wsl.localhost\...\mnt\nas\...`
（9P 経由）の形で指す設定の書き方を文書にし、その形で別のマウントへの移動を取り違えない直しを入れた（#152）。この回り道で NAS
への読み書きが大きく遅くなる。dotfiles の傘で、起動時タスクの最初に NAS へ `net use` する形に直すので（Windows のプログラムが UNC
で NAS に直接届く）、このリポが案内する形を、前の傘より前と同じ「Windows から UNC で直接」に戻す。人間は、性能を落とさないことを
必須の条件にしている。

## やること

1. #152 で入れたものと、`\\wsl.localhost` の形を推している箇所（設定の文書・例・テスト）を洗い出す
2. 設定の文書と例を、置き場を UNC で直接指す形に戻す。`\\wsl.localhost` の形は推さない
3. #152 のコードの直し（別のマウントへの移動の判定）は、UNC で直接指す設定で害が無ければ残す（`\\wsl.localhost` の形のパスを
   渡されたときに取り違えない保護として意味がある）。害があるなら戻し、理由を PR 本文に書く
4. **性能を確かめる。** Windows の `ruby.exe` から UNC で直接と、`\\wsl.localhost` 経由とで、典型的な登録の読み書き
   （数十〜数百MB 程度のファイルの置き場への移動）の時間を比べ、PR 本文に数字で書く（今の WSL は人間のサインイン後に起きた
   もので UNC に届く。どのログオンから測ったかも書く）。NAS への書き込みはテスト用のフォルダだけで試し、試した後に消す
5. PC 固有の設定（リポの外の、Windows 側の設定。保管庫・目録・吸収元の置き場と、目録の clone の origin）は触らない（戻すか
   どうかは司令官が人間に聞いている）。PR 本文に、マージ後に PC 固有の設定で戻すべき項目を書き出す

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- 置き場を UNC で直接指す設定で、登録の読み書きと、別のマウントへの移動の判定が正しく動く
- #152 の保護を残すと決めたなら、`\\wsl.localhost` の形のパスで取り違えない保護を壊さない

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
NAS への実際の読み書きと速度は手で確かめ、確かめた範囲を PR 本文に書く。
このリポの AGENTS.md の「コミット前の必須ステップ」と検証コマンドを省略しない。
