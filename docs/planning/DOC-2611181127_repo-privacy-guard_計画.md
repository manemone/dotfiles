# 計画書: 人間の発言と非公開の名前を、リポジトリに入れない仕組み

傘ブランチ: `repo-privacy-guard`
ターゲット: `master`

## 概要

傘の進め方を定めたスキル（`umbrella-handoff`・`umbrella-orchestrator`・`task-intake` の雛形）は、
相談の会話から司令官へ引き継ぐときに「人間の発言を要約せず逐語で書く」ことを求めていた。逐語を
計画書や孫のプロンプトへ写すことを止める決まりが無かったため、司令官が持ち主の発言そのものを計画書・
孫のプロンプトに書き、孫がそれを文書・PR へ写してきた。持ち主は自分の発言がリポジトリに入ることを
望んでいない。dotfiles は公開のリポジトリで、発言の逐語の節や文中の引用と、非公開のリポジトリの名前が
すでに入っている（背景1）。

この傘の目的は**再発の防止**である。次の3つを行う。

1. **決まり（孫1）**: スキルの文を直し、人間の発言の逐語を書いてよいのはブリーフ（コミットされない
   一時ファイル）だけにする。計画書・孫のプロンプト・PR・コミット・文書には要点を自分の言葉で書く。
   非公開の名前も同じ扱いにする。レビュワーの観点にも足す
2. **コミット時の点検（孫2）**: 発言の逐語の節（見出し）と、非公開の名前を、コミットの時点で止める
   点検を作る。名前の一覧はリポジトリの外のマシンローカルな設定から読む（一覧そのものを公開しないため）。
   dotfiles 自身と、`templates/repo-baseline` が他リポジトリへ配る分の両方に入れる
3. **既存ファイルの修正（孫3。持ち主の判断待ち）**: dotfiles に今ある発言の節・引用・非公開の名前を
   直す。**どう反映するか（PR にするか等）は持ち主が決める**（設計3）。決まるまで孫3 は spawn しない

## 背景1: 問題意識（要点）

- 傘のスキルが逐語での引き継ぎを求めていたため、各リポジトリの司令官が持ち主の発言を計画書・孫の
  プロンプトに書き、孫が文書・PR へ写した。持ち主に確認したことは一度も無かった
- 2026-11-18 に持ち主が気づいた。持ち主は自分の発言がリポジトリに入ることを望んでいない
- 相談の会話が調べた時点で、公開の dotfiles には、発言の逐語の節が 13 ファイル・約 50 行、文中の引用が
  23 ファイル・約 60 行、非公開のリポジトリの名前が約 30 ファイル・数百行あった。履歴とマージ済みの PR の
  差分にも残っており、すでに外でクローンされている
- 持ち主が求めているのは、**二度と起きないようにすること**

## 背景2: 持ち主が確定させた決定事項（覆さないこと）

- dotfiles を非公開にはしない
- ホスティング側のサポートへ削除を頼まない
- リポジトリを消さない。PR のページ・履歴を失う方法は取らない
- 名前や発言を消した箇所が差分として並ぶ PR を作ることには否定的（PR にすると、その差分の記録が残るため）。
  既存ファイルの修正をどう反映するかは、**司令官が案を作って持ち主に確認する**（勝手に PR を出さない・
  push しない）
- 機械的な一括置き換えは不可（取りこぼしが出る・文書の意味が崩れる）。発言の節は1か所ずつ読んで要点に
  書き換える。非公開の名前を決まった仮の名前に替えるのは、対応が一定なので可。**ただし文脈によっては
  機械的に置き換えられない箇所がある**（名前が文の主語や説明の中心で、仮の名前にすると意味が通らない・
  パスや URL・識別子・テストデータの一部で、替えると動かなくなる・名前が一般の語と同じ綴りで、名前でない
  使い方もある、など）。置き換えの規則を当てる前に、ヒットを1か所ずつ前後と一緒に確かめる
- この件は相談元の会話（別リポジトリの傘の司令官）では進めず、dotfiles のこの傘で進める

## 決定的な制約（孫は全部守ること）

- dotfiles の `AGENTS.md` の最重要ルール（`master` への反映は人間だけ。孫→傘のマージは司令官がレビュー承認済み
  PR に限って行う。孫は承認されてもマージしない）
- **この傘自身が最初に守る**: 計画書・PR の本文・コミットメッセージ・文書・コードのコメント・テストデータに、
  持ち主の発言そのものと、非公開のリポジトリの名前・ホスト名を書かない。何への対応かは自分の言葉で書く。
  テストに使う名前は架空のもの（`example-private-repo` など）にする
- 非公開の名前を確かめる必要があるときは、手元の材料（背景5）の差分や実物のファイルを**読むだけ**にし、
  その名前を出力・PR・コミット・メモリに写さない
- `claude/CLAUDE.md`（配布物）は指示なしに編集しない
- linter の抑制や `.pre-commit-config.yaml` の `exclude` 追加を AI の判断で足さない（AGENTS.md）。新しく作る
  点検の許可の仕組み（設計0 の 4）は点検自身の設計であり、これには当たらないが、許可を足すのは最小限にし、
  足した箇所と理由を PR に書く
- deploy はしない（配るのは人間）。実 `$HOME` に名前の一覧ファイルを作らない（持ち主が作る）

## スコープ外

- 履歴の書き換え（外のクローンとずれる。持ち主は求めていない）
- 言葉づかいの癖（和語に開く・全面禁止に広げる等）。並走の傘 `wording-habits` の担当
- 非公開のリポジトリ側の既存ファイルの修正（それぞれのリポジトリで扱う）
- 文中の引用（見出しでない、地の文の中の「〜」）を機械で止めること。語や記号の並びでは、手順の例として
  書いた文（「人間が『〜しろ』と言ったら」など）と区別できない。文中の引用は決まり（孫1）とレビュー（孫1 の
  レビュワーの観点）で止める
- `master` 以外の全リポジトリへ一律に効かせる仕組み（グローバルな git フックなど）。必要なら持ち主が別に決める

## 必須の検証ステップ（dotfiles AGENTS.md「コミット前の必須ステップ」より。省略しない）

- `docs/` に新規ファイルを足すときは `DOC-DOCID_PLACEHOLDER_<名前>.md` で作り、`./tools/doc-id/doc-id assign <path>` で採番、
  `./tools/doc-id/doc-id verify` を通す
- 詳細は AGENTS.md「コミット前の必須ステップ」と DOC-2610150520

## テスト方針（dotfiles AGENTS.md「テスト方針」と DOC-2610150520-a に従う）

テストも保守対象。受け入れ条件の数に比例して増やさず、「このテストが無いとどんな現実的な regression を逃すか」に
答えられるものだけ足す。点検は、**止めるべきものを止めること**と、**止めてはいけないもの（誤検出）を止めないこと**の
両方が regression の対象になる。誤検出が多い点検は、人が許可を広げて骨抜きにする（背景4 の既存の点検の README も
同じ理由を挙げている）。

## 設計0: 全孫に共通の方針（司令官が決めた。縛り合う値はここで1つに固定する）

1. **点検のコマンド**: `tools/privacy-check/privacy-check`（dotfiles）と、同じ実体を
   `templates/repo-baseline/template/tools/privacy-check/privacy-check`（配る分）に置く。`[<file> ...]` を
   受け取って点検し、引数が無ければ git 管理下の全ファイルを点検する。`--stdin` を付けると標準入力の
   テキストを点検する（PR の本文など、ファイルにならないもの用）。ヒットありで終了コード 1、無しで 0。
   ヒットは `<path>:<行番号>: <どちらの点検か>` の形で出し、**名前の一覧に当たった語そのものは出力に含めない**
   （CI のログや PR のコメントへ写らないように。行番号で人が見に行く）
2. **非公開の名前の一覧**: `${XDG_CONFIG_HOME:-$HOME/.config}/privacy-check/private-names.txt`（1行1語、
   `#` から行末はコメント、空行は無視）。環境変数 `PRIVACY_CHECK_NAMES_FILE` があればそちらを読む。
   **リポジトリの中には置かない。** ファイルが無ければ名前の点検は黙って飛ばし、見出しの点検だけを行う
   （CI には一覧が無いので、名前の点検は手元のコミットでだけ効く。これは一覧を公開しないことの代償として受け入れる）
3. **発言の逐語の節の点検**: Markdown の見出し行（`#` で始まる行）に、発言をそのまま載せる節であることを示す語
   （「逐語」「持ち主の言葉」「人間の発言」「原文」など。一覧は孫2 が決め、点検の中に持つ。この一覧は公開して
   よい）があればヒットにする。**地の文は見ない**（スコープ外の理由）
4. **行の許可の印**: 行に `privacy-check:allow-line` があれば、その行は両方の点検で飛ばす。ファイル単位の許可は
   点検の中の許可リストに相対パスで書く（最小限。ディレクトリ丸ごとの除外はしない）
5. **pre-commit の段**: `pre-commit` の `repo: local` フックとして、ファイルの点検（`pre-commit` 段）と、
   コミットメッセージの点検（`commit-msg` 段。メッセージのファイルを引数で受ける）の両方に登録する。
   `commit-msg` 段を効かせるには `pre-commit install --hook-type commit-msg` が要るので、その案内を README と
   AGENTS.md（配る分）に書く
6. **孫のプロンプトの自動付与の節の見出し**: `umbrella-orchestrator` が孫のプロンプトに自動で付ける「発言と名前を
   写さない」節の見出しは `## リポジトリに書かないもの` にする（孫1 が書く）。叩き台 `7a377b4` の見出しは
   「人間の発言」を含み、見出しの点検（3）に当たるので使わない。点検は、こうした「書かない」ことを述べる見出しを
   止めてはいけない（孫2 がテストで確かめる）
7. **PR の本文**: PR を作る・本文を直す前に、リポジトリに `tools/privacy-check/privacy-check` があれば、本文を
   `--stdin` で通す（孫1 が `pr-review-loop` に書く）。無いリポジトリでは何もしない

## 設計3: 既存ファイルの修正と、その反映のしかた（孫3。持ち主の判断待ち）

### 前提として持ち主に伝える事実

- 履歴を書き換えない以上、古い文はコミットの履歴に残り続ける。どの方法で直しても、直したコミットの差分には
  古い行が見える（ただし、すでに履歴にあるものが見えるだけで、新しく公開される情報は無い）
- 一方、`master` の今のファイルから消すことには意味がある: リポジトリを開いた人が目にするのは今のファイルで、
  GitHub のコード検索も既定ブランチの今のファイルだけを対象にする
- 既存の差分を「一か所に並べて見つけやすくする」かどうかは、反映のしかたで変わる

### 案（司令官の推奨は案A）

- **案A: PR を作らず、持ち主が `master` へ直接 push する1コミットにする。** 孫3 が手元のブランチで修正を
  仕上げ、レビューは PR ではなくローカルの差分で行う（レビュワー AI に `git diff` を読ませる。GitHub に書き込まない）。
  コミットメッセージは中立にする（何を消したかを列挙しない）。PR のページは作られない。点検の登録（`.pre-commit-config.yaml`）
  は同じコミットに含めるか、この傘の最終 PR に含める
- **案B: 点検の導入と一緒に、この傘の最終 PR（傘→`master`）に含める。** 「点検を入れたら既存ファイルが当たったので
  直した」という形になり、修正だけを集めた PR は作らない。ただし最終 PR の差分に修正の行が並ぶ
- **案C: 既存ファイルは直さない。** 点検は新しく書くものだけを止める（既存のヒットはファイル単位の許可リストに載せる）。
  差分は一切増えないが、今のファイルとコード検索には残る
- いずれの案でも、非公開の名前の仮の名前への置き換え（`dec4c0b` の形）と、発言の節を1か所ずつ要点に書き直すことは
  同じ。違うのは反映の経路だけ

### 持ち主の決定（2026-11-18）

1. **案A**。持ち主は、どの案にも満足していない。案A は他の案よりましという位置づけである
2. 接続先の例として使われているホスト名と、スキルの文中の製品リポジトリの例の名前は、**どちらも実在の名前なので替える**
3. **名前の一覧のファイルは作らない。** 名前の一覧を作って照合する方法には意味が無い、というのが持ち主の判断。
   したがって設計0 の 2 の名前の点検（孫2 で入った）は、一覧が無いので何もしない。この点検の扱い（外すか等）と、
   dotfiles の `.pre-commit-config.yaml` への点検の登録は、司令官が別に提案して持ち主に確認する（孫3 には含めない）
4. 置き換えは名前も含めて機械的にはできない。全部のヒットを1か所ずつ読んで判断する（背景2）

### 案A の進め方（孫3）

- 孫3 のブランチは傘ではなく **`origin/master` から切る**（`master` へ直接入れる1コミットにするため。点検の道具は
  まだ `master` に無いので、孫3 は道具に依存しない）
- **孫3 は push しない**（ブランチの push も GitHub での公開になる）。PR も作らない

  何も書かない

## リポジトリに書かないもの

人間（持ち主）の発言そのものを、PR の本文・コミットメッセージ・文書・コードのコメントに書かない
（計画書や送信文にあっても写さない）。何への対応かを自分の言葉で書く。非公開のリポジトリの名前・ホスト名も書かない。

## 大きい出力を文脈へ流し込まない（実装中ずっと）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し直して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）

上の「実装開始前の必須手順」で確かめるだけでよい（`git pull` は使わない）。
