# 計画書: 人間の発言と非公開の名前を、リポジトリに入れない仕組み

傘ブランチ: `repo-privacy-guard`
ターゲット: `master`

## 概要

傘の進め方を定めたスキル（`umbrella-handoff`・`umbrella-orchestrator`・`task-intake` の雛形）は、
相談の会話から司令官へ引き継ぐときに「人間の発言を要約せず逐語で書く」ことを求めていた。逐語を
計画書や孫のプロンプトへ写すことを止める決まりが無かったため、司令官が持ち主の発言そのものを計画書・
孫のプロンプトに書き、孫がそれを文書・PR へ写してきた。持ち主は自分の発言がリポジトリに入ることを
望んでいない。dotfiles は公開のリポジトリで、発言の逐語の節や文中の引用と、非公開のリポジトリの名前が
すでに入っている（背景1）。

この傘の目的は**再発の防止**と、今ある分の修正である。次の2つを行う。

1. **決まり（孫1）**: スキルの文を直し、人間の発言の逐語を書いてよいのはブリーフ（コミットされない
   一時ファイル）だけにする。計画書・孫のプロンプト・PR・コミット・文書には要点を自分の言葉で書く。
   非公開の名前も同じ扱いにする。PR を出す側とレビュワーが、差分・PR の本文・コミットメッセージを**意味で読んで**
   判断する観点を足す
2. **既存ファイルの修正（孫2）**: dotfiles に今ある発言の節・引用・非公開の名前を、1か所ずつ読んで直す。
   反映は PR を作らず、持ち主が `master` へ push する（設計2）

## 背景1: 問題意識（要点）

- 傘のスキルが逐語での引き継ぎを求めていたため、各リポジトリの司令官が持ち主の発言を計画書・孫の
  プロンプトに書き、孫が文書・PR へ写した。持ち主に確認したことは一度も無かった
- 2026-11-18 に持ち主が気づいた。持ち主は自分の発言がリポジトリに入ることを望んでいない
- 相談の会話が調べた時点で、公開の dotfiles には、発言の逐語の節が 13 ファイル・約 50 行、文中の引用が
  23 ファイル・約 60 行、非公開のリポジトリの名前が約 30 ファイル・数百行あった。履歴とマージ済みの PR の
  差分にも残っており、すでに外でクローンされている
- 持ち主が求めているのは、**二度と起きないようにすること**

## 背景2: 持ち主が確定させた決定事項（覆さないこと）

- dotfiles を非公開にはしない
- ホスティング側のサポートへ削除を頼まない
- リポジトリを消さない。PR のページ・履歴を失う方法は取らない
- 名前や発言を消した箇所が差分として並ぶ PR を作ることには否定的（PR にすると、その差分の記録が残るため）
- 機械的な置き換えは不可。発言の節も非公開の名前も、文脈によって機械的には置き換えられない（名前が文の主語や
  説明の中心で、仮の名前にすると意味が通らない・パスや識別子の一部で、替えると動かなくなる・一般の語と同じ綴り
  など）。全部のヒットを1か所ずつ前後と一緒に読んで判断する
- この件は相談元の会話（別リポジトリの傘の司令官）では進めず、dotfiles のこの傘で進める

## 設計2: 既存ファイルの修正と、その反映のしかた（孫2）

### 持ち主に伝えた事実

- 履歴を書き換えない以上、古い文はコミットの履歴に残り続ける。どの方法で直しても、直したコミットの差分には
  古い行が見える（すでに履歴にあるものが見えるだけで、新しく公開される情報は無い）
- 一方、`master` の今のファイルから消すことには意味がある: リポジトリを開いた人が目にするのは今のファイルで、
  GitHub のコード検索も既定ブランチの今のファイルだけを対象にする

### 持ち主の決定（2026-11-18）

1. **PR を作らず、持ち主が `master` へ直接 push する1コミットにする**（他の案〈傘の最終 PR に混ぜる・直さない〉よりまし、
   という位置づけ。持ち主はどの案にも満足していない）
2. 接続先の例として使われているホスト名と、スキルの文中の製品リポジトリの例の名前は、**どちらも実在の名前なので替える**
3. 置き換えは名前も含めて機械的にはできない。全部のヒットを1か所ずつ読んで判断する（背景2）

### 進め方

- 孫2 のブランチは傘ではなく **`origin/master` から切る**（`master` へ直接入れる1コミットにするため）
- **孫2 は push しない**（ブランチの push も GitHub での公開になる）。PR も作らない
- レビューは GitHub を使わず、孫2 のワークスペースのレビュワー AI に手元の差分を読ませる。レビュワーは GitHub に
  何も書かない
- 仕上がったら1コミットにまとめ（メッセージは中立にし、何を消したかを書かない）、司令官へ SendMessage で知らせる。
  司令官が持ち主に知らせ、持ち主が中身を確かめて `master` へ push する
- 持ち主の push の後、司令官が傘を `origin/master` へ rebase する

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- スキルの文が、逐語を書いてよい場所をブリーフだけに限り、計画書・孫のプロンプト・PR・コミット・文書へ写さない
  ことを明記している（同じリポの孫用と他リポの孫用の自動付与指示の両方に入っている）
- 変更したスキルの既存の手順（spawn の送信文の推奨フォーマット・承認の報告など）が壊れていない
- 孫1 の差分・PR の本文・コミットメッセージに、人間の発言の逐語と非公開の名前が無い

文書の変更なので、新しい自動テストは原則として要らない。既存のテスト（`pre-commit`・`doc-id verify`）が通ることと、
差分の目視で確かめる。

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。

## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

1. PRを作成する。**PRの向き先は必ず `repo-privacy-guard` にすること。master には絶対に出さない。**
2. `/pr-review-loop` を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** `/pr-review-loop` の手順にマージへ進む記述があっても実行しない
   （孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）
5. （Herdr あり・司令官が宛先を埋め込んだときだけ）最終報告を書き終えたら、最後の行動として
   司令官へ承認を報告する。宛先は、司令官が spawn の送信文で渡した司令官の Herdr ペイン
   （渡されていなければ報告せず、人間に「承認済み。マージは司令官（または人間）が行う」と伝えて止まる）。
   送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」に従う。本文は
   「孫1 `rp-01-skill-rules` の PR #<番号> が HEAD <短縮SHA> で承認されました。マージをお願いします。」
   だけにする（「〜とだけ返事して」のような指示は付けない）。報告は1回だけ。送れなくても
   再送せず（司令官の巡回が拾う）、送れなかったことを人間に1行伝えて止まる

なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する（その手順は pr-review-loop 側。使えなければ何もしない）。compact の後は、
復帰メモに従ってレビュー待ちに戻り、この「実装完了後の流れ」を最後まで続けること。
実装の途中でも、検証が通ってコミットした直後の区切りで、文脈が

## やること

0. 探す名前は、叩き台 `dec4c0b` の差分の削除側・このマシンの `/home/manemone/projects/` 配下のリポジトリ名・
   司令官が送信文で伝える名前から、自分で拾う。**名前の一覧をファイルに保存しない**（リポジトリの中にも外にも）。
   検索の結果は件数とパス・行番号だけを見て、当たった行の中身を出力に流さない（読むときは1か所ずつ前後を読む）

1. 叩き台 `dec4c0b`（ブランチ `scrub-private-names`）を読み、使う・直す・捨てるを決める。名前の仮の名前への
   置き換えも、背景2 のとおり文脈によって機械的に置き換えられない箇所があるので、1か所ずつ前後を読んで確かめる
   （意味が通らない・動かなくなる箇所は、文を書き直すか、名前を出さない言い方にする）。発言の節の書き換えも、
   1か所ずつ前後を読んで要点になっているかを確かめる
2. 残りの発言の逐語の節と、文中の引用（計画書 背景5）を、**1か所ずつ読んで**要点に書き換える。機械的な一括置き換えは
   しない（背景2）。文書の意味（誰が何を決めたか・何が問題だったか）は保つ
3. 設計2 の決定 2 のホスト名と製品リポジトリの例の名前も替える（スキル・`bin/` の README・ADR・計画書の例）。
   架空の名前に替えるか、名前を出さない言い方にするかは、1か所ずつ文脈で決める
4. 0 で拾った名前で全ファイルを検索し、残りが 0 になるまで直す（意図して残す箇所は無い前提。残す必要があると
   判断したら直さずに司令官へ知らせる）
5. 終わったら全部を **1コミット**にまとめる（途中のコミットは squash する）。メッセージは中立にし（例:
   「docs: 文書の表記を整理する」）、何を消したか・名前・発言を書かない。末尾の Co-Authored-By 等の行は通常どおり
6. **ローカルのレビュー**: 自分のワークスペースのレビュワーのペインで `ocw agent reviewer` を起動し
   （`herdr pane run <reviewer-pane> "ocw agent reviewer"`。エージェントが既に動いていれば打たない）、
   SendMessage でレビューを頼む。頼む内容: `git diff origin/master...HEAD` を読み、(a) 名前・発言の消し残し、
   (b) 書き換えで文書の意味（誰が何を決めたか・何が問題だったか）が崩れていないか、(c) 参照・リンク・コードが
   壊れていないか、を見ること。**GitHub に何も投稿せず、結果は SendMessage で返すこと。指摘の中で名前や消した文を
   引用せず、パスと行番号で示すこと。** 指摘があれば直して（1コミットに保つ）再レビューを頼み、承認まで繰り返す
7. 承認されたら、司令官へ SendMessage で1回だけ知らせる。宛先は spawn の送信文で司令官が渡した名前。本文は
   「孫2 `rp-03-scrub-existing` をローカルレビューで承認まで仕上げました。コミット <短縮SHA>（origin/master <短縮SHA> の上）。
   push していません。」だけにする。送れなければ再送せず、人間に1行伝えて止まる。**push はしない**

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- 0 で拾った名前の検索が 0 件になる（コミットメッセージにも無い）
- 書き換えた文書が、元の文書の意味（決定・問題・経緯）を保っている（レビューで確かめる）
- `doc-id verify` が通る（文書の参照を壊していない）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
