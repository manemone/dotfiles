# 計画書: トークン削減の次の手（レビュワーの膨張・compact リマインドの素通り・学習の会話の閾値）

傘ブランチ: `token-levers`
ターゲット: `master`

## 概要

ここ1か月に入れたトークン節約の仕組み（実装の孫の区切りでの自己 compact と、それを思い出させるフック・
学習の会話の自己 compact・`AGENTS.md` の芯と詳細の分割）が意図どおり効いているかを、相談の会話が実測で
確かめた（背景4）。その結果から人間が決めた次の3件を、この傘で進める。

1. **レビュワー（`OCW_ROLE=reviewer`）の文脈の膨張を抑える（孫1）。** 再レビューのラウンドごとに、
   レビュワーの会話を新しくする。あわせて、レビュワーの読み方の作法（大きい出力の読み直しをしない等）を
   レビュー指示に足す。対象は dotfiles の `skills/pr-review-loop/SKILL.md`
2. **実装の孫への compact のリマインドが、作業の途中に届いて素通りされる問題を直す（孫2）。**
   区切りに当たるツール呼び出しで、閾値超えならリマインドを再掲する。対象は dotfiles の
   `claude/hooks/compact-reminder.sh`
3. **lora-dataset-forge（以下 LDF）の学習の会話の compact 閾値（300,000）を下げて試す（孫3・孫4）。**
   決め打ちで変えず、まず会話ごとに試せる口と測る道具を入れ（孫3）、人間が1〜2本で試したあと、
   実測で閾値を決める（孫4）

> **本計画書は、相談の会話から渡された引き継ぎブリーフ（一時ファイル。転記後に削除済みで
> 参照できない前提で書く）を material として司令官が起草したものである。** ブリーフに
> 書かれていた問題意識・決定事項・既存の穴・実測値・制約・スコープ外・必須の検証ステップ・
> 孫分割の叩き台は本計画書へ転記済みであり、以降はこの計画書が正典である。

## 背景1: 問題意識（要約）

人間は、最近入れたトークン節約の仕組みがどう効いているかを、ここ1か月ほどの範囲で確かめるよう相談の会話に頼んだ
（LDF にも同種の変更を入れているため、両方が対象）。さらに直近を含めて、何がトークンを食っているか、削減策が意図どおり
効いているかの確認を求めた。相談の会話は調査結果から次の手の候補を挙げ、人間はそのうち「レビュワーをラウンドごとに
新しくする」「compact のリマインドを区切りのツール呼び出しでも出す」の2件を調べさせ、「LDF の学習の会話の compact 閾値を
下げて試す」は検討だけさせた。調査結果を受けて、人間は前の2件を主案どおり進めることにし、3件目もやると決めた。

## 背景2: 人間が確定させた決定事項（覆さないこと）

- やるのは次の3件:
  1. **レビュワー（`OCW_ROLE=reviewer`）の文脈の膨張を抑える。** 主案は「レビューのラウンドごとにレビュワーの会話を
     新しくする」（dotfiles `skills/pr-review-loop/SKILL.md` 側）。読み方の作法（背景4.3 の C 案）も候補
  2. **`claude/hooks/compact-reminder.sh` のリマインドが、作業の途中に届いて素通りされる問題を直す。** 主案は
     「区切りに当たるツール呼び出し（`git commit` / `git push` / PR 作成 / `SendMessage` 等）で、閾値超えなら
     リマインドを再掲する（1区切り1回）」
  3. **LDF の学習の会話の compact 閾値（現在 300,000）を下げて試す。** 決め打ちせず、1〜2本で試して
     compact の書き直し費用の増加と cache read の減少を実測してから決める
- **Figma プラグインをユーザー全体で止める件はやらない**（浮くのが1回 約2.5k トークンで、PR 3本と順序管理に見合わないと人間が判断）
- **LDF の学習の会話の見回り（cron）の周期・別プロセス化には手を付けない**（見回りは呼び出しの 11%・費用の約6%しかなく、
  30分周期は1時間のキャッシュ TTL を温める役目も兼ねるため）

## 背景3: 既存の穴

- `claude/hooks/compact-reminder.sh` 冒頭の `[ "${OCW_ROLE:-}" = "implementer" ] || exit 0` により、レビュワー・司令官には効かない。
  **レビュワーには文脈の膨張対策が一切無い**（調査した64本で compact は全部ゼロ）
- 同フックは PostToolUse で文脈が 200k を超え、前回差し込みから 50k 増えるたびに「区切りなら self-compact を判断すること」を
  差し込む。**差し込みのタイミングが区切りと無関係**なので、作業途中に届くと判断自体が起きない（背景4.4）
- LDF の `context_check.py` の `THRESHOLD = 300_000`（`waiting.md` §3）。根拠の LDF 調査文書 §6 は「150,000 では compact の
  元を取るのに再開後 90 回の呼び出しが要り低すぎる。300,000 なら約 26 回」という、**見回りを前提にした試算**で、
  呼び出しの大半が対話・通知のターンだという今回の実測（背景4.5）を織り込んでいない

## 設計1: レビュワーをラウンドごとに新しくする（孫1）

### 1.1 決めること

- **作り直す時点**: Phase 6 の再レビュー依頼を送る前（ラウンド2以降の頭）。既定は「再レビューのたびに必ず新しくする」。
  条件付き（例: レビュワーの文脈が一定以上のときだけ）にするなら、その根拠を ADR に書く。費用の見込みは、作り直しで払う
  固定分（開始時 約58k ＋読み直し）と、続けた場合の毎呼び出しの cache read（ラウンド2の時点で中央値 約147k、以後増える）の比較で
  示す（背景4.3）
- **作り直す方法**: レビュワーのペインのエージェントを終了させて Phase 2 Step 2 の手順（`ocw agent reviewer`）で起動し直すか、
  Claude Code なら `/clear` を送るか、など。**`pr-review-loop` は AI 不問（Claude Code / Codex / OpenCode）**なので、どのレビュワーでも
  動く方法を既定にする。実機で1回は確かめ（このリポで自分の PR のレビューを回すときに確かめてよい）、確かめた結果を ADR に書く。
  Herdr なしの経路でどうなるか（作り直さない、でよいか）も決める
- **新しいレビュワーに渡すもの**: 既にレビュー指示ファイルのパスと前回レビュー対象 SHA を渡している（Phase 6 手順4。作り直された
  レビュワーを想定済み）。足りないものを足す: 何ラウンド目か（「後続ラウンド（ラウンド2以降）の新規 finding 閾値」を新しい
  レビュワーにも効かせるため）、前ラウンドの指摘と返信の読み方（`gh pr view --json reviews` の全件を読み直すと最初の1周の
  約19k をまた払うので、最新のレビューと未解決のスレッドだけを読む、など）
- **計測**: レビュワーのセッション ID がラウンドごとに変わる。ocw-meter の `quota.sample`（session_id → role）と、
  `review-tiering` の `by_unit.py`（PR・傘単位の役割別費用）が、1 PR に複数のレビュワーのセッションがあっても正しく集計できるかを
  確かめる。壊れるなら直し方を PR 本文と司令官への報告に書く（`bin/ocw-meter` の改修はスコープ外。必要なら別件として人間に提案）

### 1.2 読み方の作法（C 案）

レビュー指示テンプレート（毎ラウンド読まれる）に、短い作法を足す。背景4.3 の内訳から次の3つが候補:

- 保存ファイルに逃がされた大きい出力（persisted-output）を Read で全文読み直さない（`grep` / `tail` / 行範囲で読む）
- 旧版の状態を `git show <sha>:<path> | cat -n` で全文取り直さない（`git diff <前回SHA>..HEAD -- <path>` で差分だけ読む）
- 規約文書を全文 cat しない（見出しを `grep -n '^#'` で引いて要る節だけ読む）

テンプレートは毎ラウンド読まれる固定分でもあるので、足すのは数行にとどめる。グローバルの `claude/CLAUDE.md` にある
「大きい出力を文脈へ流し込まない」は配布物で、レビュワーにも既に載っているが効いていない（背景4.3）。レビューの手順の中に
置く理由はここにある。`claude/CLAUDE.md` は触らない。

### 1.3 記録

ADR を1本書く（`docs/adr/`、`DOC-DOCID_PLACEHOLDER_*.md` で作って採番）。決定・却下案（B 案〈レビュワーにも区切りの compact〉を
採らない理由を含む）・見込みの効果・効果の測り方（デプロイ後に、再レビュー回数別のレビュワーのピークを背景4.3 と同じ方法で比べる）を書く。
`pr-review-loop` の文言の変更は、`umbrella-orchestrator` の §5 等の参照と食い違わないか `git grep` で確かめる。

## 設計2: リマインドを区切りのツール呼び出しで再掲する（孫2）

### 2.1 区切りの判定

PostToolUse の入力（`tool_name` / `tool_input`）から、区切りに当たるツール呼び出しを見分ける。叩き台:
Bash の `git commit` / `git push` / `gh pr create`、`SendMessage`、Bash の `herdr agent prompt`（再レビュー依頼・司令官への承認の報告）。
区切りの定義は ADR DOC-2610142337 と `pr-review-loop`「区切りでの自己 compact（実装側のみ）」に合わせる（WIP のコミットや指摘対応の
途中はフックでは見分けられないので、従来どおり文面で除外を伝える）。`SendMessage` などで PostToolUse の入力に何が入るかは実機で確かめる。

### 2.2 1区切り1回

閾値（200,000）超えで区切りのツール呼び出しが来たら、50k の間引きとは別枠でリマインドを出す。ただし同じ区切り
（例: `git commit` の直後の `git push`、続く `gh pr create`）で何度も出さない。重複の抑え方（直前の区切りのリマインドからの文脈の増分・
ツール呼び出しの回数・時刻など）は孫2 が決める。区切りでない呼び出しの 50k ごとの再掲は残すか消すかも孫2 が判断する
（残すなら区切りのリマインドと合わせた頻度が過剰にならないこと）。

### 2.3 文面

「次のターンの冒頭で、compact するか見送るかを1行書くこと（見送るなら理由も）」の形にする（背景4.4 の (1)）。判断を言葉に
させることで、素通りを減らす。区切りで出す文面と、区切りでない時の文面を分けてよい。

### 2.4 守ること

- フックは全ツール呼び出しで走る。**対象外の役割は python3 を起動せずに抜ける作りを維持する。** 区切りの判定のために
  対象外の役割でも python3 を起動する形にしない
- エージェントを止めない（`git-guard.sh` と同じ方針。何があっても exit 0）
- サブエージェント（`agent_id` あり）では黙る、を維持する
- 既存のテスト `tests/compact_reminder_test.sh` を足場にする

### 2.5 記録・触らないもの

ADR DOC-2610142359 に追記する（区切りでの再掲・文面の変更と、背景4.4 の根拠）。閾値・回数上限を変えるなら DOC-2610142337 も直す
（この傘では変えない想定）。`skills/pr-review-loop/SKILL.md` は孫1 が触るので、孫2 は**原則触らない**。リマインドの記述が
`pr-review-loop` や `umbrella-orchestrator` にあって食い違うなら、直さずに PR 本文と司令官への報告に書く（司令官が孫1 と調整する）。

## 設計3: 学習の会話の閾値を試す口と測る道具（孫3、LDF）

### 3.1 試す口

`context_check.py` の閾値を、**既定（300,000）を変えずに**会話ごとに下げて試せるようにする。仕組み（例: 環境変数。学習の会話の

試したあと何を司令官に伝えるか〈会話のセッション ID〉）を書く。

### 3.2 測る道具

会話（トランスクリプト）ごとに、compact の損益を出すスクリプトを入れる。少なくとも:

- 各 compact の前後の文脈の大きさ、compact そのものの費用（要約の呼び出し）、compact 直後の再構築（cache creation）の量
- compact から次の compact（または会話の終わり）までの呼び出し回数と、その間に浮いた cache read（compact しなかった場合との差）
- 損益分岐に要る呼び出し回数と、実際の呼び出し回数

金額にするなら単価の当て方を ocw-meter と揃えるか、トークン数で出す（背景4.5 の桁の食い違いを持ち込まない）。比較の基準として、
#498 後（10/17〜19）の 300k の会話にも同じスクリプトを当てて結果を PR 本文に書く。置き場所とテストは LDF の規約に従う
（既存の `dev/token-survey/cron_fires.py` は `training-sessions` ワークツリー側にある。流用してよい）。

## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

1. PRを作成する。**PRの向き先は `main`（このリポの既定ブランチ）。**
   PR 本文に、傘の計画書（dotfiles の `docs/planning/` にある計画書。DOC-ID で書く）と、孫3 の PR への参照を書く
2. /pr-review-loop を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** base が既定ブランチなので、マージは人間の仕事である。
   人間に「承認済みです。マージしてください」と依頼して止まる
なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する。compact の後は、復帰メモに従ってレビュー待ちに戻り、この流れを最後まで続けること
実装が終わったタイミングで止まらず、必ずここまでやりきってください。
reviewerはdone状態で完了し完了通知は来ないので、待機して停止せず gh pr view をポーリングして
レビューの有無を確認してください。

## 大きい出力を文脈へ流し込まない（実装中ずっと）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し直して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）
- トランスクリプトは数百 MB になりうる。全文を出力しない
