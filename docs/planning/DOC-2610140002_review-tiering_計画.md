# 計画書: 孫ごとのレビューの費用対効果を検証し、レビュー運用を見直す

傘ブランチ: `review-tiering`
ターゲット: `master`

## 概要

傘ブランチ方式では、孫の PR 1本ごとに `pr-review-loop` でレビューをかけ、承認まで回している。
相談の会話で過去の PR を集計したところ、孫ごとのレビューは実害のあるバグを確かに止めている一方、
PR の種類（文書だけ・小さい・土台・実装コード）にかかわらず同じ厚さでかけており、文書・文言の
指摘でもラウンドが回っていることが分かった（背景4）。人間は「孫ごとのレビューは過剰か、最後に
1回でよいか」を、**過去データと実験で確かめてから**運用を変えたい。結果は実装役のモデルで
変わるはずだと見ている（背景2）。

この傘では次の4つを行う。

1. **過去データの分析**（孫1）: 指摘を決まった基準で分類し直し、PR の種類・実装役のモデル別に
   孫ごとのレビューが何を止めてきたかを記録する
2. **効果測定の土台**（孫2）: 役割別（実装・レビュー・司令官）の費用を PR・傘の単位で測れるようにする。
   運用を変えたあとに効果を確かめる前提
3. **再現実験**（孫3）: 過去の傘で「孫レビューを省いて最後に1回だけレビューした」場合に何を
   取りこぼすかを、レビュアーのモデルを条件に入れて測る。**費用の承認を人間から得てから走らせる**
4. **段階的レビューの反映**（孫4）: 1〜3 の結果を受けて人間と決めた形を、スキルに反映する。
   結果が否定的なら反映しない

> **本計画書は、相談の会話から渡された引き継ぎブリーフ（一時ファイル。転記後に削除済みで
> 参照できない前提で書く）を material として司令官が起草したものである。** ブリーフに
> 書かれていた問題意識・経緯・決定事項・既存の穴・実測値・制約・スコープ外・必須の検証ステップ・
> 孫分割の叩き台は本計画書へ転記済みであり、以降はこの計画書が正典である。人間の発言は要約で
> 転記した（このリポは PUBLIC。逐語では残さない）。

## 背景1: 問題意識と相談の経緯（要約）

人間の問題意識:

- 傘ブランチ方式と `ocw` で独自の開発の流れを作って、うまく動いてはいる。ただ Claude Code や Codex にも
  レビューやワークツリーを自動で切る公式の仕組みがあるらしい。独自方式と公式のものを、効率・手間・
  トークン消費・追跡性などの観点で比べてほしい。わざわざ作っている意味があるのか心配になった
- 傘の孫ごとにレビューを入れるやり方は過剰か。最後に1回でよいのか。過去の実例を見たり、実験したりが
  要ると思う
- 進めたい。モデルによっても差が出るはず。実装役が DeepSeek v4 pro のような弱いモデルだと
  （最後に1回だけ、は）成立しないだろうと思う

相談の経緯:

1. 公式機能（Claude Code: `--worktree`・`/code-review`・ultrareview・Agent Teams・Workflow・
   バックグラウンドエージェント／Codex: app のワークツリー・`/review`・`@codex review`・subagents）と
   自作の仕組みを比べた。相談AIの結論は「自作は追跡性・人間ゲート・複数日の進行・AI 横断で公式に無い
   価値がある。一方、孫ごとのレビューを一律にかけている点と、nit でラウンドが回る点は削れる余地がある」
2. 過去データ（背景4）を集め、「孫ごとのレビューは過剰ではないが、一律に同じ厚さでかけているのは過剰。
   最後に1回だけ、は推奨しない」と見立てた
3. 人間は検証と見直しを進めたいと言い、モデル（特に実装役のモデル）で結果が変わるはずだと指摘した

## 背景3: 既存の穴

- `skills/pr-review-loop/SKILL.md` は、PR の種類（文書だけ・小さい・土台を作る・実装コード）に
  かかわらず同じ厚さでレビューをかける。文書・文言の指摘だけでもラウンドが回る
  - **司令官の補足（起草時に確認）**: 同スキルには既に「finding の判定基準（general finding
    qualification gate）」があり、pure nit（折り返し・好みの命名など）は finding にしない、後続
    ラウンドで nit を新規 blocking にしない、と書いてある。一方で「実際に誤操作を誘発するドキュメント
    不整合」は blocking にしてよいとしている。背景4 の分類 D（文書・文言・nit 54%）は、この gate を
    **通るもの（誤操作を誘発する文書の不整合）と通らないもの（本来出すべきでない nit）の両方を含んでいる**
    可能性が高い。どちらが多いかで打ち手が変わる（gate の運用が守られていないのか、gate は守られて
    いるが文書の不整合そのものが多いのか）ので、孫1 で D を分けて数える（設計1）
- `skills/umbrella-orchestrator/SKILL.md` は、孫ごとにレビューを必須にする前提で書かれている
- `bin/ocw-meter report --role` は役割の割り当てが約36〜40%解決できず、reviewer の
  `cost_estimate_usd` は null（Claude Opus の単価表が無い。`bin/prices/` には DeepSeek の表しかない）。
  このままでは運用を変えても費用の効果を測れない
- 孫ごとのレビューが何を止めてきたかを記録した文書は無い（相談での集計が初）

## 設計1: 過去データの分析（孫1）

### 1.1 分類の基準を文書にして分け直す

背景4 の A〜D を、次のように**判定手順つきで**定義し直して文書にする（孫1 が細部を詰めてよいが、
A〜D の大枠と D の2分割は変えない）。

| 分類 | 定義 |
|---|---|
| A 実害のあるバグ | 直さずにマージすると、利用者・後続の孫・運用が誤動作するもの |
| B 計画逸脱・孫どうしのズレ | 計画書・他の孫・既存の契約と食い違っているもの（今は動いても後続で壊れる） |
| C テスト・検証の穴 | risk-based testing の入口判定を通るテスト不足、検証手順の欠落 |
| D1 誤操作を誘発する文書の不整合 | `pr-review-loop` の gate を通る文書・文言の指摘（読んだ人が誤った操作をしうる） |
| D2 nit | gate を通らないもの（表現の好み・折り返し・統一感など） |

あわせて各指摘に「**後続の孫に波及するか**（後から直すと後続の孫も直す必要が出るか）」を付ける。

### 1.2 PR の属性

各孫 PR に次を付ける。

- **PR の種類**: 文書だけ／小さい（目安: 変更100行以下で実装コードを含む）／土台（後続の孫が上に
  書く API・スキーマ・ディレクトリ構成を作る）／実装コード。判定方法は文書にする
- **実装役のモデル**: 背景5 の方法で逆引きする。引けなければ「不明」とし、不明の割合を書く
- リポ・ラウンド数・変更行数（`rows.json` にあるもの）

### 1.3 範囲と費用の上限

- 全932本を分類し直す必要はない。**PR の種類 × 実装役のモデルで層を作り、各層から抜き取る**
  （合計150本程度を目安。少ない層は全数）。抜き取りの方法と本数を結果に書く
- 孫3 の正解データとして、**再現実験の対象にする傘（設計3.2）を5本程度選び、その傘の孫 PR は
  全数・全ラウンドを分類する**（抜き取りと重なってよい）
- 分類はサブエージェント（`model: sonnet` を明示）に分担させてよい。**サブエージェントの費用は
  合計 $30 を上限**とし、超えそうなら止めて司令官へ報告する（人間が費用を気にしている）
- 目視の基準ぶれを測るため、同じ指摘20件程度を2回（別のサブエージェント）分類し、一致率を書く

### 1.4 出すもの

- `docs/reference/` に結果の文書（新規。DOC-ID を採番する）: 分類の基準・抜き取りの方法・
  PR の種類別 / 実装役のモデル別の指摘の内訳（A/B/C/D1/D2・波及）・ラウンド数・「1回目で承認」の割合・
  再現実験の対象の傘の一覧と選んだ理由・限界（引けなかった割合・基準ぶれ）
- `docs/adr/probes/review-tiering/` に集計スクリプト（リポ名・パスをハードコードしない。
  usage-diet の付録A と同じ作法）
- `derived/`（リポの外。背景4.1）に指摘ごとのラベル（孫3 が正解データとして読む）。形式は文書に書く
- 結論は「どの種類・どのモデルの PR で、孫ごとのレビューが A/B を止めているか」に絞る。運用を
  どう変えるかの提案は書いてよいが、決めるのは孫3 の後に人間（設計4）

## 設計2: 役割別の費用の測定（孫2）

運用を変えたあと（孫4 の後）に、「孫レビューを省いた PR でレビュー役の費用がどれだけ減ったか、
最終レビューの費用がどれだけ増えたか」を測れるようにする。必要なのは次の数字:

- PR ごと・傘ごとの、役割別（実装・レビュー・司令官）のトークンと API 単価換算の費用
- Claude（Opus / Sonnet）と DeepSeek の両方

やること:

1. `ocw-meter report --role` で役割の割り当てが約36〜40% 解決できない原因を突き止める
2. 次のどちらかを選び、理由を ADR か結果の文書に残す
   - (a) `ocw-meter` を直す（役割の割り当て・Claude の単価表 `bin/prices/`）
   - (b) DOC-2610130216 の集計スクリプト（`docs/adr/probes/usage-diet/`）を PR・傘の単位で
     測れるように広げ、`ocw-meter` は直さない（その場合、`ocw-meter --role` が当てにならないことを
     `bin/README.md` 等に書く）
   - 選ぶ基準: 孫4 の後に人間か司令官が**1コマンドで**before/after を出せること、維持の手間が小さいこと
3. 直近の傘（例: usage-diet の5本）で役割別の費用を出し、DOC-2610130216 の数字と大きく食い違わない
   ことを確かめる

単価は DOC-2610130216 が使ったもの（Opus 5.5・Sonnet 5.5 の API 単価）に揃える。

## 設計3: 再現実験（孫3）

### 3.1 問い

「孫ごとのレビューを省き、傘の最後に1回だけレビューした」とき、孫ごとのレビューが実際に止めた
A/B（と C）を何割拾えるか。レビュアーのモデル（Opus / Sonnet）と、元の実装役のモデルで差があるか。

### 3.2 対象

孫1 が選んだ過去の傘5本程度（設計1.3）。選ぶ基準: 実装役のモデルが混ざる（DeepSeek が実装した傘が
あれば必ず1本入れる）、リポが偏らない、孫が3本以上、A/B の指摘がある孫を含む。

### 3.3 手順の大枠（孫3 が詰める）

1. 対象の傘ごとに、scratch の clone か `git worktree` を**一時ディレクトリ**に作る（他リポの人間の
   ワークツリーは触らない。**リモートへは一切 push しない**）
2. 各孫 PR の「最初のレビュー前の head」を特定する（`gh pr view <番号> -R <owner/name> --json commits,reviews`
   のコミット時刻と最初のレビューの投稿時刻。`refs/pull/<番号>/head` を fetch して祖先として取る）
3. 傘の分岐点から、各孫の「レビュー前の head」の差分を順に当てたブランチを作る。衝突したら、
   その孫は当てられた範囲と衝突した範囲を記録し、衝突の箇所はレビュー後の版で埋める（埋めた分は
   取りこぼしの判定から外す）
4. そのブランチの差分全体（傘の分岐点から）を、`pr-review-loop` のレビュー指示（Phase 2 Step 1 の
   本文。マーカーを埋めたもの）と同じ指示でレビューさせる。レビュアーはサブエージェントで、条件は
   `model: opus` と `model: sonnet`。**GitHub へは投稿しない**（結果はローカルのファイル）
5. 孫1 の正解データ（その傘の孫レビューが止めた A/B/C）と突き合わせ、拾えた割合・拾えなかった
   指摘・最終レビューだけが見つけた新しい指摘を数える。突き合わせもサブエージェント（`model: sonnet`）
   でよいが、判定の基準を文書にし、20件程度を人の目（孫3 自身）で確かめる
6. ばらつきを見るため、各条件を2回走らせる

既知の弱点（結果に必ず書く）: 実際の後続の孫は**レビュー済みの土台の上**に書かれているので、
「レビュー前の head」をつなぐと波及の効果（レビューが無かったら後続の孫がどう書かれたか）は
再現できず、取りこぼしの害は小さめに出る。

````markdown
## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

1. PRを作成する。**PRの向き先は必ず `review-tiering` にすること。master には絶対に出さない。**
2. `/pr-review-loop` を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** `/pr-review-loop` の手順にマージへ進む記述があっても実行しない
   （孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）
5. 最終報告を書き終えたら、最後の行動として、司令官が spawn の送信文で渡した司令官の Herdr ペインへ
   承認を報告する（渡されていなければ人間に「承認済み。マージは司令官が行う」と伝えて止まる）。
   送り方は `skills/umbrella-orchestrator/SKILL.md` §5「AI間送信手順（二段構え）」に従う。
   本文は「孫2 `rt-02-meter-roles` の PR #<番号> が HEAD <短縮SHA> で承認されました。マージをお願いします。」
   だけにする。報告は1回だけ。送れなくても再送せず、送れなかったことを人間に1行伝えて止まる

なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する（その手順は pr-review-loop 側。使えなければ何もしない）。compact の後は、
復帰メモに従ってレビュー待ちに戻り、この「実装完了後の流れ」を最後まで続けること。
実装が終わったタイミングで止まらず、必ずここまでやりきってください。
reviewerはdone状態で完了し完了通知は来ないので、待機して停止せず gh pr view をポーリングして
レビューの有無を確認してください。
傘ブランチが先へ進んでコンフリクトしたら `git rebase origin/review-tiering` と
`git push --force-with-lease` で追随する（AGENTS.md「最重要ルール」）。
````

## 孫3用プロンプト:

````markdown
# 傘ブランチ: review-tiering
# 孫ブランチ: rt-03-replay-experiment
# ターゲット: master（傘経由）

計画書: `/home/manemone/projects/dotfiles/review-tiering/docs/planning/DOC-2610140002_review-tiering_計画.md`

**まず計画書の「概要」「背景2〜5」「設計3」「決定的な制約」「スコープ外」「必須の検証ステップ」
「テスト方針」「進行記録」（設計3.5 の費用の人間の承認が書かれていること）と、孫1 の結果の文書
（`docs/reference/` にある。分類の基準・対象の傘・正解データの形式）、`skills/pr-review-loop/SKILL.md`
の Phase 2 Step 1（レビュー指示の本文）を読むこと。**

## 実装開始前の必須手順

`ocw` がすでに `rt-03-replay-experiment` ブランチのワークツリーを用意しているので、
`git fetch origin` と `git log --oneline -3` で、そのブランチが `origin/review-tiering` の
先端から切られていることを確かめる（`git pull` は使わない）。

## やること

計画書 設計3 に従い、孫1 が選んだ過去の傘で「孫レビューなし・最後に1回だけ」の再現実験をし、
取りこぼしを測って結果を文書にする。

1. 対象の傘ごとに、一時ディレクトリ（`mktemp -d`）に scratch の clone を作り、各孫 PR の
   「最初のレビュー前の head」をつないだブランチを作る（設計3.3 の1〜3）。**リモートへは一切 push しない。
   他リポの人間のワークツリーは触らない**
2. 最終レビューをサブエージェントで走らせる（設計3.3 の4・6。`model: opus` と `model: sonnet` を各2回）。
   **GitHub へは投稿しない**
3. 孫1 の正解データと突き合わせる（設計3.3 の5）
4. 結果を孫1 の結果の文書に節として足す（または新しい文書。新規なら `DOC-DOCID_PLACEHOLDER_*.md` で作り
   採番し、`docs/README.md` の索引に行を足す）。既知の弱点（設計3.3 末尾）を必ず書く
5. スクリプトは `docs/adr/probes/review-tiering/` に、レビュー結果の本文は
   `/home/manemone/projects/dotfiles/_handoff_review-value-data/derived/` に置く（リポに入れない）

**費用の上限は $150（計画書 設計3.5）。超えそうなら止めて司令官へ報告する。ultrareview は使わない**
（人間が別に承認した場合だけ。進行記録に書かれる）。

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- 実験の手順を文書どおりに再実行できる（手順を文書に書く。全部の再実行はしなくてよい）
- 突き合わせの判定を20件程度、自分の目で確かめ、一致しなかった数を書く
- リポに入る差分に、PRIVATE なリポの PR 本文・指摘の中身・コードが含まれていない（`git diff` を自分で読んで確かめる）
- 他リポのリモートに何も push していない（scratch の clone に push 先を残さない、など手順で防ぐ）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
````
