# 計画書: 傘運用の使用量を減らし、孫のマージを司令官に集める

傘ブランチ: `usage-diet`
ターゲット: `master`

## 概要

傘ブランチ方式で並列に開発すると、Claude の週の使用量が急速に減る（2026-10-11 16:00 以降の
約1日で、週の使用量の25%を使った）。相談の会話で実ログを集計したところ、費用の主因は
**大きな文脈のキャッシュ読み**で、役割別では実装30%・司令官29%・レビュー20%・会話（学習系）18%
だった（背景4）。

この傘では次の4つを行う。

1. **孫は承認後もマージせず、司令官がマージする。** 目的は節約ではなく、孫が勝手にマージするのを
   防ぐこと（人間の実ログに不満がある。背景3）。あわせて司令官の巡回 cron を約10分ごとから
   30分ごとにする
2. **司令官はマージしたら自動で compact する。** まず司令官が自分自身に compact をかける手段が
   あるかを確かめ（プローブ）、それから組み込む
3. **他の削りどころを調査する。** 調査結果から追加の孫を起こすかは、司令官が人間と決める
4. 上記をスキル（`umbrella-orchestrator` / `pr-review-loop` ほか）と README に反映する

> **本計画書は、相談の会話から渡された引き継ぎブリーフ（一時ファイル。転記後に削除済みで
> 参照できない前提で書く）を material として司令官が起草したものである。** ブリーフに
> 書かれていた問題意識・決定事項・既存の穴・未確認の前提・実測値・制約・スコープ外・必須の
> 検証ステップ・孫分割の叩き台は本計画書へ転記済みであり、以降はこの計画書が正典である。
> ブリーフと一緒に渡された集計スクリプトは `docs/adr/probes/usage-diet/` へ移設した（付録A）。

## 背景1: 問題意識（要約）

- 2026-10-11 16:00 以降の約1日で、Claude の週の使用量の25%を使った。何かおかしいのではないか
- レビュー・実装・司令官・会話の割合を、最新の単価で知りたい。週の使用量が何で数えられているかも知りたい
- 特別たくさん開発しているつもりはない。どうすれば減らせるか
- 司令官を Sonnet にすると性能が落ちるのではないかと懸念している
- 提案: 司令官の巡回を30分ごとにし、孫の完了報告はセッション間会話で受ける。孫はマージせず
  司令官がマージする。マージしたら自動で compact する
- 司令官がマージするのは、孫が勝手にマージするのを防ぐためで、節約目的ではない
- 他にも削りどころが無いか探してほしい

## 背景2: 人間が確定させた決定事項（覆さないこと）

- **司令官の autopilot 巡回 cron を約10分ごとから30分ごとにする。** 巡回の目的はハングの
  拾い上げで、検知が最大30分遅れるのは許容する
- **孫は承認後もマージしない。** 承認まで来たら止まり、司令官へセッション間メッセージで
  報告する。**マージは司令官が行う。** 目的は「孫が勝手にマージするのを防止する」ことで、
  節約目的ではない
- **司令官はマージしたら自動で compact する。**（実現手段は未確認。背景5）
- **他にも削りどころが無いか探す**（調査も傘のスコープに含む）
- 司令官のモデルを Sonnet に落とすことは、人間は性能低下を懸念している。安易に
  モデル切り替えを結論にしない（判断力が要る工程は Opus のまま、が相談時の結論）

## 背景5: 先に潰すべき前提（未確認）

ブリーフ時点で未確認だった点と、司令官が割り当てた確かめ方。

1. **司令官が自分自身に `/compact` を実行させる手段があるか**（例: `herdr agent prompt <自分のペイン>
   "/compact ..."` で自ペインへ送る、ターン終了後に入力として処理されるか、cron／SendMessage
   との競合は無いか）。無ければ代替（人間への提案のまま／セッションを新しい司令官へ引き継ぐ等）
   → **孫2 が使い捨ての環境で確かめる**（設計2）
2. **司令官が `gh pr merge` を実行するとき auto mode の分類器に止められないか。**
   既知の事実: **autopilot の巡回 cron の本文に `gh pr merge` を書くと、登録時に auto mode の
   分類器が `[Merge Without Review]` で拒否する**（2026-09-12、傘 `autopilot-permissions` で発生。
   レビュー承認を条件に書いてあっても拒否された。cron の本文は登録時に静的に判定され、条件文が
   伝わらないため）。そのため「cron の中ではなく、孫からの報告を受けたときにマージする」形を
   想定している。cron 巡回で承認済みを拾ったときの扱いも要検討
   → **この傘の孫は全員、すでに新しい決定のとおり「承認で止まって司令官へ報告」させ、司令官
   （本計画書の起草者）が実際にマージする。** 報告を受けた対話のターンで分類器に止められるか、
   巡回 cron のターンではどうかは、この傘の運用そのものが実地の検証になる。結果は司令官が
   「進行記録」節に書き、孫1（間に合わなければ孫4）がスキルに反映する
3. **孫がマージしなくなることで、マージ前提で書かれた箇所への波及**: `ocw rm`・ワークツリー後片付け・
   孫の傘への追随（§3.3）・`pr-review-loop` の終了条件など
   → **孫1 が洗い出して直す**（設計1）

## 設計1: 孫のマージを司令官に集める（孫1）

### 1.1 新しい流れ

```
孫（実装AI）: 実装 → PR（base=傘） → /pr-review-loop → 承認
  → マージしない。司令官へ「孫N <ブランチ> の PR #X が HEAD <sha> で承認された」と報告して止まる
司令官: 報告を合図に gh で承認を確かめる（§2.4 の読み方。報告の本文を根拠にしない）
  → gh pr merge → 傘で検証 → 計画書を ✅ に → 孫のワークスペースを片付け → 次の孫を spawn
巡回 cron（30分ごと）: 報告を取りこぼした・孫が報告せず止まった場合の保険。承認済みの PR を
  見つけたら、報告を受けたときと同じ手順で処理する
```

### 1.2 決めてあること（孫1 はこれに従う）

- **`pr-review-loop` は、base が傘ブランチの PR でもマージしない。** 承認まで来たら、司令官の
  ペインが渡されていれば承認を報告し、渡されていなければ人間に「承認済み。司令官（または人間）が
  マージする」と伝えて止まる。傘を使わない PR（base が既定ブランチ）は今までどおりマージしない。
  結果として `pr-review-loop` 自身は**どの PR もマージしなくなる**。Phase 7 手順5・6 と「安全制約」の
  傘ブランチ判定（AGENTS.md の「傘ブランチ方式」明記の確認）は、マージの判断材料としては不要に
  なる。司令官側のマージ条件（§2.4）に同等の安全確認が要るかを孫1 が判断して移す
- **報告の宛先と送り方は、今の完了通知（§3.2 手順5・§3.6）の仕組みをそのまま使う。**
  宛先は spawn の送信文で渡す司令官のペインID。送り方は §5「AI間送信手順（二段構え）」
- **司令官のマージ条件は §2.4 のまま**（最後の判定が承認・対象HEAD が最新と前方一致・
  implementer が `working` でない・base が既定ブランチでない）。加えて、人間がその孫について
  「マージを待て」と言っていればマージしない（人間が先にフィードバックしたい場合の止めどころ。
  これが背景3 の不満への答えでもある）
- **巡回 cron は30分ごと**（`:00` `:30` を避ける。例 `13,43 * * * *`）。cron の本文には
  `gh pr merge` を書かない（背景5-2）。「承認済みの孫を見つけたら §X の手順で処理する」と
  節を参照する形にする
- 巡回のターンでマージが分類器に止められたら、`PushNotification` で人間に知らせて次へ進む
  （同じ PR で毎巡回通知しないこと）。報告を受けた対話のターンで止められた場合も、人間に知らせる

### 1.3 孫1 が洗い出して判断すること

- `gh pr merge --delete-branch` を司令官のワークツリーから叩くと、孫のワークツリーがブランチを
  掴んでいるためローカル削除が失敗し、リモートブランチも消えない（§3.3 の実測: 4本中4本）。
  司令官がマージするなら、`--delete-branch` を付けるか、マージ→`ocw rm`→リモート削除の順にするか。
  AGENTS.md「最重要ルール」が許可の形として `gh pr merge <PR番号> --squash --delete-branch` を
  明記していること・`.claude/settings.json` / `claude/settings.json` の permissions・
  `claude/hooks/git-guard.sh` との整合も確かめる
- マージ前提で書かれた箇所: `umbrella-orchestrator` §1 の役割表・§3.2（自動付与指示・推奨
  フォーマットの通知の1文）・§3.3・§3.5（cron 本文の手順3〜5・注意）・§3.6（完了通知→承認報告）・
  §6 分業、`pr-review-loop` Phase 7・安全制約・完了報告、`task-intake` / `umbrella-handoff` /
  `ocw` スキル・`bin/README.md`・ルート `README.md`・AGENTS.md「最重要ルール」の言い回し・
  `templates/repo-baseline/template/AGENTS.md.jinja`（同じ「最重要ルール」の写しがある）。
  `git grep -n -e 'マージまで' -e '承認されたら' -e 'gh pr merge' -e '10分' -- skills templates AGENTS.md README.md bin/README.md`
  で探す
- 承認の報告を受けた司令官が、孫の実装AIの最終報告を待ってから `ocw rm` する手順（§3.6 手順4）は
  そのまま要るか
- 他リポの孫（§2.1）の扱いは変わらない（もともと AI はマージしない）ことを確かめる

## 設計2: 司令官の自己 compact（孫2 → 孫4）

### 2.1 孫2（プローブ）が確かめること

候補（孫2 は他の手段を見つけたら足してよい）:

- (a) 司令官がターンの最後に、自分のペインへ `herdr agent prompt "$HERDR_PANE_ID" "/compact <残す内容>"`
  を `--wait` なしで送る。ターン終了後に `/compact` がスラッシュコマンドとして実行されるか、
  ただの文として届くか
- (b) Claude Code の自動 compact の閾値を司令官だけ下げる手段（環境変数や設定。あるかどうかから
  確かめる。あれば `OCW_COMMANDER_COMMAND` で司令官にだけ効かせられる）。ただし発動の
  タイミングは選べない
- (c) compact ではなく、区切りで司令官の会話を新しい会話に置き換える（`/clear` や新しいセッションへの
  引き継ぎ）。計画書が正典なので、要約を作らずに読み直すほうが安い可能性がある
- いずれも、**compact／置き換えの後に CronCreate の巡回 cron が残るか**（`CronList`）、
  compact 中に cron の発火・セッション間メッセージが来たらどうなるか、を確かめる
- compact 1回の費用（要約を作る呼び出しの入力・出力トークン）と、その後の1ターンの文脈の大きさを
  測る。孫4 で「毎回 compact するか、閾値を残すか」を決める材料にする

作法:

- **使い捨ての Claude Code セッションを、使い捨ての Herdr ワークスペース（名前付きの別セッションが
  望ましい）で起動して試す。** 人間のワークスペース・司令官・他の孫には一切触れない。
  試したセッションとワークスペースは片付ける
- 使い捨てのセッションは小さな文脈で試す（使用量の削減の傘で、プローブ自体が大きく食わないように）
- **追記（2026-10-13、進行記録を参照）: 使い捨ての Claude Code の起動は auto mode の分類器に
  拒否されたため、孫2 は自分自身のセッションを被験体にする。** 新しいエージェントは起動しない。
  - (a) は孫2 が自分のペイン（`$HERDR_PANE_ID`）へ `/compact` を `--wait` なしで送り、ターンを
    終えて確かめる。**送る前に、それまでの実測値と次にやることをワークツリー外の一時ファイル
    （ADR の下書き）に書き出しておく**（compact で細部が落ちても続きができるように）

  人間の返答待ちは除く）は §3.7 のまま

## 付録A: 集計スクリプト（ブリーフから移設）

背景4 の数字を出したスクリプト。相談AIが書いた使い捨てのもので、期間（`since`）・リポ名の一覧
（`REPOS`）・単価（`P`）はハードコードされている。孫3 が出発点にし、直したら同じ場所を更新する。
置き場所: `docs/adr/probes/usage-diet/`

公開リポに置くため、ブリーフ時点のスクリプトから次だけ変えた（集計の中身は同じ）: 役割の分類に使う
リポ名の一覧（`REPOS`）を製品リポの名前のベタ書きから環境変数 `USAGE_REPOS`（カンマ区切り。
既定 `dotfiles`）に、プロジェクトディレクトリ名からホームのパスを外す処理を特定のユーザー名に
依存しない形にした。背景4 と同じ分類で再集計するには、そのとき集計したリポ名を全部 `USAGE_REPOS` に渡す。

| ファイル | 出すもの |
|---|---|
| `agg.py` | 全体の集計: モデル別・プロジェクト（ワークツリー）別・セッション別・時間帯別のトークン数、モデル別の1コールあたり文脈（中央値・p90・30万超の数）、サイドチェーンの量、深夜帯の呼び出し |
| `role.py` | 役割（実装・司令官・レビュー・会話・会話(学習)）の分類と、役割別のトークン・相対費用（旧版。`trig.py` が分類関数 `classify` をここから読み込む） |
| `role2.py` | 役割別の API 単価換算（背景4 の表。読み・書き込み・出力の内訳つき） |
| `trig.py` | 司令官の費用を、起こされたきっかけ（cron 巡回・セッション間メッセージ・孫の完了通知・バックグラウンド/Monitor 通知・人間など）別に分ける |
| `bcast.py` | セッション間メッセージで起こされたターンの費用を、ハブの周知・他の傘からのお知らせ・その他に分ける |

実行は `USAGE_REPOS=dotfiles,<他のリポ名> python3 -I docs/adr/probes/usage-diet/role2.py` のように行う（`trig.py` は同じディレクトリの
`role.py` を読むので、パスを変えずに実行する）。
