# 計画書: 再起動の自動起動タスク（S4U）で起きた WSL から、Windows 経由の NAS アクセスが全部失敗する

傘ブランチ: `reboot-network-creds`
ターゲット: `master`

## 概要

傘 `reboot-recovery`（計画書 DOC-2611151244）で、Windows の再起動のあとサインイン無しで WSL を起こす起動時タスク
（方式 A・S4U。ADR DOC-2611151248）を入れた。2026-11-21 の再起動ではこのタスクが WSL を起こしたが、その WSL の中からは
**Windows を経由した NAS へのアクセスが全部失敗した**（drvfs のマウント、WSL から呼んだ Windows のプログラム）。
人間がサインインしたエクスプローラーからは NAS に入れていた。S4U のログオンにはネットワーク資格情報が無く、その
セッションで起動した WSL から呼ぶ Windows 側の処理も、同じ資格情報の無いログオンで動くためと見られる（未検証。孫1 が確かめる）。

再起動はまた起きるので、この傘で次を行う。

1. **原因を確かめる。** WSL がどのログオンで起動したかで、Windows 経由の NAS アクセスが失敗するのかを、実機で確かめられる範囲で確かめる
2. **影響を受ける処理を洗い出す。** WSL から Windows のプログラムを呼んで NAS を使う処理（下の背景3）がほかに何があるか
3. **直し方の案を比べて人間に選んでもらい、選ばれた案を入れる。** 案の比較では ADR DOC-2611151248 が S4U を選んだ理由
   （秘密をマシンの外にも中にも置かない）との折り合いを示す
4. **起動後の確認に NAS を足す。** `rebootctl` の起動後の確認と ADR の「実験で確かめる対象」から、NAS が漏れていた（背景4）

## 背景1: 問題意識（要約。PUBLIC リポのため逐語では書かない）

- 再起動は今後も起きるので、場当たりの回避でなく、原因まで調べてほしいというのが人間の求め
- 人間は、以前の傘で入れた「再起動のとき自動で WSL を起こす設定」が原因ではないかと見立てている
- 人間の判断で、再起動のタスクの側も直すことにし、直し方の調査を含むので傘にした

## 背景2: 人間が確定させた決定事項（覆さないこと）

- この件は dotfiles の傘で進める（直し方の調査を含むため）
- NAS のマウント `/mnt/nas` は、人間が WSL の中の cifs でマウントする形に変えた（背景5）。drvfs に戻さない
- 直し方（タスクの方式を変える／WSL 側で回避する／ほか）はまだ決まっていない。案を人間に見せて選んでもらう

## 背景3: 2026-11-23 に引き継ぎ元が確かめた実測値

- 起動時タスク `\dotfiles-reboot-recovery`: 起動時トリガー（30秒遅延）・LogonType S4U・RunLevel Limited・
  `wsl.exe -d <ディストリ> -- bash -lc "$HOME/bin/rebootctl boot --hold"`。登録コマンドは `bin/rebootctl` の `setup` が表示する
  PowerShell（175 行目付近）
- 2026-11-21 の再起動: 23:08:09 Windows 起動 → 23:08:40 タスク実行 → 23:08:45 WSL の fstab の drvfs マウント（NAS の共有フォルダ）が
  失敗。以後この WSL の中からは、Windows 経由の NAS アクセスが全部失敗した:
  - drvfs のマウント（手で `mount -t drvfs` を打っても「間違ったオプション設定」）
  - WSL から呼んだ `cmd.exe` は「A specified logon session does not exist」、`powershell.exe` の `Test-Path <NAS の共有フォルダ>` は False
  - 別リポ（非公開）の学習ツールが、モデルを公開する手順の中で WSL から Windows の `ruby.exe` 経由で呼ぶ登録ツールが、
    NAS 上の保存先フォルダを「フォルダがありません」で見つけられず失敗した
- 同じとき、人間のサインインしたエクスプローラーからは NAS に入れた。資格情報マネージャーにも NAS の資格情報がある。
  NAS の 445 番ポートには届く
- 2026-11-15 の起動（タスク登録の前）では、人間が手で WSL を開いたので drvfs のマウントは成功していた
- 2026-11-23 に引き継ぎ元が追加で確かめた: S4U で起きた同じ WSL からでも、LogonType Interactive の一時タスクを登録して
  走らせ（`Register-ScheduledTask` → `Start-ScheduledTask`）、その中で Windows の `ruby.exe` から上の登録ツールを動かすと、
  NAS 上の保存先に届いて登録が通った（終了コード 0。タスクは実行後に消した）。人間がサインインしている間なら、
  Interactive のログオンを経由すれば資格情報が使えることを示す

## 背景4: 既存の穴

- ADR DOC-2611151248 §4 は「S4U ではネットワーク資格情報が使えないため、Claude の認証や Remote Control が動くかは実験で確かめる」と
  書いたうえで方式 A を選んだ。確かめる対象に、WSL から Windows 経由で NAS を使う処理（drvfs のマウント、WSL から呼ぶ Windows の
  プログラム）が入っていなかった
- `bin/rebootctl` の 175〜177 行目のコメント（`setup` が表示する PowerShell の中）は「ネットワーク資格情報が要る処理は S4U では
  動かないので、起動後の確認を必ず行うこと」と書いているが、起動後の確認に NAS が入っていない

## 背景5: 済んでいる回避（触らない・前提として知っておく）

- 2026-11-23 に人間が、`/mnt/nas` を WSL の中の cifs でマウントするよう変えた（fstab は NAS の `.local` 名、資格情報は
  `/etc/nas-credentials`〔root 600〕、`.local` 名は avahi-daemon と libnss-mdns で引く。元の fstab は `/etc/fstab.bak-drvfs`）。
  これで WSL の中だけで完結する NAS の読み書き（別リポの学習ツールの知見の同期など）は通っている
- 残っているのは、WSL から Windows のプログラムを呼んで NAS を使う処理（背景3 の登録ツールなど）。ほかにどれがあるかは未調査

## やること

1. **原因を確かめる（読み取りだけ）。** いま動いている WSL がどのログオンのセッションで起動したか、そのセッションに NAS の
   ネットワーク資格情報があるかを、`powershell.exe -NoProfile -Command` の読み取り（`klist`・`Get-CimInstance Win32_LogonSession`・
   `cmdkey /list`・`Test-Path` など）と公式の文書で確かめる。S4U のログオンで起動した `wsl.exe` の子として WSL から呼ぶ Windows の
   プログラムが、同じログオンで動くのかを確かめる。いまの WSL が人間のサインイン後に起きたものなら、それも記録する。
   WSL を起こし直す試験が要るなら、手順を用意して人間に頼む（自分では叩かない）
2. **影響を受ける処理を洗い出す。** WSL から Windows のプログラム（`*.exe`）を呼び、NAS（UNC パス・drvfs）を使う処理を、
   このマシンの `$HOME` 配下のリポとスクリプトから探す（読み取りだけ。司令官が送信文で渡した名前を手がかりにする）。
   結果は ADR に役割で書く（非公開の名前は書かない）
3. **直し方の案を比べ、人間に選んでもらう（AskUserQuestion）。** 少なくとも次を比べる。ほかの案を足してよい:
   - タスクの方式を変える（ADR DOC-2611151248 §4 の B・C、または資格情報を持つログオンの種類で登録する）。何をどこに保存するかと、
     S4U を選んだ理由との折り合いを示す
   - S4U のまま、WSL の中だけで NAS を使う形へ寄せる（背景5 の cifs マウントを、Windows のプログラムが使えるパスで渡せるか等）
   - S4U のまま、人間のサインイン後に WSL 側から Windows 経由の処理を使えるように切り替える（いつ切り替わるか・何が止まるか）
   - S4U のまま、NAS を使う Windows のプログラムだけを LogonType Interactive の一時タスク経由で走らせる（計画書 背景3 の
     最後の実測で登録が通った経路。サインインしていないときの振る舞い・一時タスクの登録に管理者が要るか・出力と終了コードの受け渡しを確かめる）
   各案に、実機で確かめた範囲・確かめていない範囲と、案ごとに要る人間の作業（管理者コマンド・再起動）を添える。
   別リポの学習ツール側を直す案になるときは、その作業はこの孫ではせず、PR 本文と司令官への報告に書く

   表示だけ。AI は実行しない）。あわせて、**起動後の確認に NAS を足す**: `rebootctl status`（`--json` も）で、Windows 経由で NAS に

   設定（環境変数か設定ファイル。既存の流儀に合わせる）から読み、未設定なら確認を飛ばしたと出す
5. **ADR を更新する。** ADR DOC-2611151248 に、2026-11-21 の経過の要約（計画書 背景3）、§4 の「実験で確かめる対象」に NAS が漏れていたこと、

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- `rebootctl setup` は管理者コマンドを表示するだけで、`powershell.exe` 経由で何も書き換えない（既存の保護を壊さない）
- `rebootctl status` は NAS に届かない・NAS の設定が無い・Windows 側を呼べないときにも落ちず、それぞれを区別して出す
- `rebootctl boot` は冪等のまま（何度呼んでも害が無い）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
Windows の実機の確認は手で行い、確かめた範囲を PR 本文に書く。

## 背景（要約）

Windows の再起動のあとサインイン無しで起きた WSL（起動時タスクの S4U のログオン）から呼ぶ Windows のプログラムは、NAS の
資格情報を持たず、UNC パスで NAS に届かない。人間は、S4U のままにし、Windows のプログラムには UNC でなく、WSL の中の cifs
マウント（`/mnt/nas`）を `wslpath -w` で変換したパス（`\\wsl.localhost\<ディストロ>\mnt\nas\...`）を渡す案を選んだ。
このリポは NAS を UNC 前提で使っているので、その案に合わせて直す。

## やること

1. NAS を UNC で使っている箇所を洗い出す。少なくとも、NAS 転送（`robocopy.exe` で送り `powershell.exe` で読み戻す。
   `lib/` の NAS 転送の実装）と、モデルを公開する手順で Windows の `ruby.exe` 経由で呼ぶ登録ツール（登録ツールに渡す保存先と、
   `ruby.exe` の作業フォルダ）。ほかに UNC を前提にした箇所（設定の例・文書・テスト）も拾う
2. Windows のプログラムに渡す NAS のパスを、WSL の中のマウント先から `wslpath -w` で作る形に直す。マウント先は設定から読み、
   ホスト名などをコードに書かない。マウントされていないときは、黙って UNC に戻らず、分かるメッセージで失敗させる
   （どちらに倒すかで迷ったら、既存の流儀と人間への確認を優先する）
3. WSL の中から直接読み書きできるところは、Windows のプログラムを経由せず WSL の中で済ませる形にしてよい（既存のコメントに
   「WSL から NAS の名前を引けないので robocopy を使う」とある前提は、cifs マウントで崩れている）。どこまで変えるかは、
   差分の大きさと安全（転送の検証・失敗時に原本を消さない）を比べて決め、PR 本文に理由を書く
4. 登録ツールの側（別リポ）に直しが要ると分かったら、このリポでは直さず、司令官のペインへ1回だけ報告する
5. 人間が `/mnt/nas` に作った cifs マウントの設定は触らない。学習の作業（キュー・学習中のジョブ）には触れない。
   実際の NAS への書き込みを試すときは、テスト用の小さなフォルダだけを使い、試した後に消す

学習ツールが Windows の `ruby.exe` で呼んだときで、登録ツールの設定の保管庫・目録・作例の置き場が UNC で書かれているためである。
人間は、Windows のプログラムには UNC でなく WSL の中の cifs マウント（`/mnt/nas`）を `wslpath -w` で変換したパス
（`\\wsl.localhost\<ディストロ>\mnt\nas\...`）を渡す案を選んだ。孫3 では、その形のパスで Windows の Ruby の読み書き・
robocopy・名前の付け替えが通る一方、Windows の Ruby からは同じボリュームかの点検が効かない（ボリューム番号が常に 0）と分かっている。

## やること

1. 登録ツールが設定から受ける NAS のパス（保管庫・目録の bare リポジトリ・作例の置き場・モデルの置き場など）と、そのパスの形に
   依存する処理（同じボリュームかの点検・名前の付け替え・ハードリンク・git の操作・パスの正規化や比較）を洗い出す
2. `\\wsl.localhost\...` の形のパスで設定したとき、登録（学習ツールから呼ばれる経路）と、ほかの NAS を使う操作が通るかを、
   テスト用の小さな置き場で確かめる（サインイン済みのログオンの WSL からでよい。S4U からは未確認と書く）。目録の bare リポジトリを
   その形のパスで git が扱えるかも確かめる
3. 通らない箇所を直す。UNC と `\\wsl.localhost` の両方を受けられる形にし、ホスト名などをコードに書かない
4. 設定の書き方（`\\wsl.localhost` の形・置き場は同じマウント先の下に置くこと・外れているときの振る舞い）を文書にする。
   **人間の PC 固有の設定ファイル（Windows 側の設定と `~/.config/` 配下）は書き換えない。** 書き換えの手順を PR 本文の
   「マージ後に人間がやること」に書く
5. このリポには別の作業のワークツリー（`three-machine-sync`）がある。そのブランチと作業には触れない。触るファイルが重なりそうなら、
   先に司令官のペインへ報告する
6. 人間が `/mnt/nas` に作った cifs マウントの設定は触らない。NAS 上の既存の保管庫・目録・作例を動かしたり消したりする操作は、
   試しでも実行しない（試しはテスト用の小さなフォルダだけで行い、終わったら消す）

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- 保管庫・目録・作例の置き場を `\\wsl.localhost\<ディストロ>\mnt\nas\...` の形で設定しても、登録（学習ツールが呼ぶ経路）が通る
- 同じボリュームかの点検・名前の付け替え・目録（git の bare リポジトリ）の操作など、パスの形に依存する箇所が、その形で誤判定しない（直した場合）
- 置き場が見つからないとき、作らず分かるメッセージで止まる（既存の保護を壊さない）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
NAS への実際の読み書きは手で確かめ、確かめた範囲（どのログオンの WSL から確かめたか）を PR 本文に書く。
このリポの AGENTS.md の「コミット前の必須ステップ」と検証コマンドを省略しない。

## 大きい出力を文脈へ流し込まない（実装中ずっと）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し修正して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）

## リポジトリに書かないもの

人間（持ち主）の発言そのものを、PR の本文・コミットメッセージ・文書・コードのコメントに書かない
（計画書や送信文にあっても写さない）。何への対応かを自分の言葉で書く。
NAS のホスト名を設定の例・テスト・文書に新しく書き込まない（このリポの既存の流儀で、設定から読む）。
書き直すときは、人間が挙げた例を要件として言い切らない・誰の判断や提案かを落とさない・意味に要らない固有名詞を残さない。

## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

1. PRを作成する。**PRの向き先は `main`（このリポの既定ブランチ）。**
   PR 本文に、傘の計画書（dotfiles の `docs/planning/DOC-2611230305_reboot-network-creds_計画.md`）と、関係する傘側の PR
   （dotfiles の PR #243）へのリンクを書く（複数リポにまたがる作業の継ぎ目）
2. `/pr-review-loop` を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** base が既定ブランチなので、マージは人間の仕事である。
   人間に「承認済みです。マージしてください」と依頼して止まる。あわせて、司令官のペイン（spawn の送信文で渡す）へ
   「孫N `<孫ブランチ名>` の PR <owner/name>#<番号> が HEAD <短縮SHA> で承認されました。人間のマージ待ちです。」を1回だけ送る
   （送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」。送れなくても再送しない）

なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する。compact の後は、復帰メモに従ってレビュー待ちに戻り、この流れを最後まで続けること。
実装の途中でも、検証が通ってコミットした直後の区切りで、文脈が
150,000 トークン（claude-ds 以外の Claude は 200,000。`ANTHROPIC_BASE_URL` に `deepseek` を含むかで見分ける）を超えていれば
`ocw self-compact` で自分を compact してよい（WIP のコミットは区切りでない。指摘対応の修正の途中は対象外。回数の上限は無いが、
前回の compact から文脈が 100,000 以上増えていなければ見送る。ADR DOC-2610142337・DOC-2611032102）。
測り方は `/pr-review-loop` の「区切りでの自己 compact（実装側のみ）」の手順1のコマンドと同じ（その節の (3) の項だけを読めばよい。
手順の「Phase 3 へ進む」は実装途中には当てはまらない）。復帰メモ（リポの外の一時ファイル）には、計画書のパスと孫の節・
済んだこと・作業中に下した判断とその理由・残り・次の一手・検証コマンドを書き（増分の起点は復帰後に測るのでメモには書かない）、
先頭に「計画書の続きから実装を再開する。レビュー待ちではない」と書く。コマンドを実行したらそのターンを終える。
使えない・拒否・失敗なら何もせず実装を続ける。
実装が終わったタイミングで止まらず、必ずここまでやりきってください。
このリポ自身の AGENTS.md 等の規約（ブランチ名・PR の作法・検証コマンド）に従うこと。
reviewerはdone状態で完了し完了通知は来ないので、待機して停止せず gh pr view をポーリングして
