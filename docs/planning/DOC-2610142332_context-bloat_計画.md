# 計画書: 実装の孫の文脈の膨張を抑える

傘ブランチ: `context-bloat`
ターゲット: `master`

## 概要

傘 `usage-diet`（計画書 DOC-2610122205）で入れた自己 compact（`ocw self-compact`）は効いている
（約33時間で差し引き約 $72 の節約。背景4）。一方で、実装の孫は最初の PR を出す前に文脈が
300〜430k まで膨らみ、200k 超のまま数十〜百回以上の呼び出しを走っている（背景3・背景4）。
この傘では、実装の孫の文脈の膨張を次の3つで抑える。

1. **膨らむ元を減らす作法（孫1）。** 大きいツール出力を文脈へ流し込まない（ファイルへ書き出し、
   `head`・件数・要約だけを見る）作法を、実装の孫が実装中に読む場所へ入れる。まず膨らむ孫の
   ツール出力の内訳を実ログで調べ、作法の中身と置き場をそこから決める
2. **実装途中の区切りを1つ足す（孫2）。** 実装の孫は今、レビューを依頼した直後にしか compact しない
   （ADR DOC-2610131214 §2.1）。実装の途中にも区切りを1つ足し、閾値を超えていれば
   `ocw self-compact` する。同 ADR の「実装・修正の途中では行わない」を覆すので、新しい ADR で記録する。
   あわせて、途中の compact が品質を落としていないかを測る方法を決める
3. **思い出させる仕組み（孫3）。** compact の判断はスキル本文の特定の区切りでしか起きず、作業に
   没頭すると判断自体が起きない。Claude Code のフックで文脈の大きさを見て、閾値を超えていれば
   「区切りなら self-compact を判断すること」と差し込む。フックは compact を打たず、判断を促すだけ

## 背景1: 問題意識（要約）

人間の発言は逐語で書かない（このリポは公開。過去に逐語引用で push を止められている）。

- 最近入れた自動 compact などのトークン節約の仕組みが、本当に効いているのかを知りたい
- 相談AIが実ログで測り、「効いているが、実装の孫は compact に入る時点で 300〜430k まで膨らんでいる」と
  報告した。人間は、まずどれだけ節約できたかを知り、そのうえでレビュー前に膨らむ問題を詰めたいとした
- 相談AIは方向を3つ示した: (1) 膨らむ元を減らす作法、(2) 実装途中に区切りを1つ足す、(3) 両方。
  推奨は「(1) から入り、足りなければ (2)」だった。人間は**両方やる**と決めた。どうせレビューするので、
  それでレビューの指摘が増えたらまた考える、両方のほうが節約できそうだ、という判断
- 引き継ぎの準備中に、人間は「compact してくれないのはなぜか、定期的に思い出させられないか」と追加で
  問うた。相談AIの見立ては次のとおり（司令官が計画に入れるか判断する。人間は望んでいる → 孫3 として入れた）:
  - compact するかの判断はスキル本文に書いた特定の区切りでしか起きず、その本文は文脈のずっと前に
    読んだもので、作業に没頭すると判断自体が起きない。司令官側でも ADR DOC-2610140044 §1 で
    「判断の機会が1回しか無く、外れたら次が無い」と同じ形の取りこぼしが観測済み
  - 定期的に思い出させる手段として、Claude Code のフック（例: PostToolUse や Stop で transcript の
    直近の使用量を読み、閾値を超えていれば「文脈が N k。区切りなら self-compact を判断」と
    additionalContext で差し込む）が考えられる。フックは compact そのものを打たず、判断を促すだけにする

## 背景2: 人間が確定させた決定事項（覆さないこと）

- **(1) と (2) の両方をやる。**
  - (1) 大きいツール出力を文脈に流し込まない作法を入れる（例: 大きい出力はファイルへ書き出し、
    `head`・件数・要約だけ見る）
  - (2) 実装の孫に、**実装の途中**の区切りを1つ足し、そこで閾値を超えていれば `ocw self-compact` する
    （例: テストが通ってコミットした直後かつ 200k 超。区切りの具体は司令官が決めてよい → 設計2 で孫2 に委ねる）。
    これは ADR DOC-2610131214 §2.1 の「実装・修正の途中では行わない」を覆す判断であり、**新しい ADR で記録する**
- **様子見の約束**: (2) で compact が増えた結果、レビューでの指摘が増える（作業中の判断が要約で落ちて
  品質が下がる）ようなら、(2) の区切りを再考する。人間はそれを承知で両方を選んだ
- 振り分け（task-intake）で人間確認済み: dotfiles 1リポ・PR 複数（(1) と (2) は関心事が別で、
  (2) は ADR を覆すため混ぜない）・司令官は dotfiles

## 背景3: 既存の穴

- 実装の孫の compact の区切りは、`skills/pr-review-loop/SKILL.md`「区切りでの自己 compact
  （実装側のみ）」の2か所だけ: PR を出してレビューを依頼した直後（Phase 2 Step 4 のあと）と、
  指摘対応を push して再レビューを依頼した直後（Phase 6 手順7）。同節は「実装・修正の途中…では
  行わない。途中で compact すると作業中の判断が落ちる」と明記している（ADR DOC-2610131214 §2.1）
- そのため、実装の途中で 200k を超えた孫は、最初の PR 作成まで数十〜百回以上の呼び出しを 200k 超のまま走る
- 大きいツール出力についての作法は、`skills/umbrella-orchestrator/SKILL.md`・`skills/pr-review-loop/SKILL.md`・
  `claude/CLAUDE.md`・`templates/repo-baseline/template/AGENTS.md.jinja` のどこにも無い（相談AIが grep で確認）
- **（司令官が追記）`pr-review-loop` は実装が終わってから起動される。** 実装の孫が実装の最中に
  読んでいるのは、計画書の孫用プロンプト（`umbrella-orchestrator` §3.2 の自動付与指示を含む）・
  `claude/CLAUDE.md`・リポの `AGENTS.md` だけで、`pr-review-loop` の本文はまだ読んでいない。
  したがって (1) の作法も (2) の区切りも、`pr-review-loop` に書くだけでは実装中の孫に届かない。
  実装中に届く置き場（少なくとも §3.2 の自動付与指示）へ入れる必要がある（設計1・設計2）

### 4.1 既存の仕組みは効いている（`cmp.py` / `resume.py`）

- `ocw self-compact` は 14 回呼ばれ、全部 `queued` で通った（分類器の拒否 0）。全回で 1〜2分以内に
  compact が実行され、続きを促す1通が届き、セッションは作業を再開した。ADR DOC-2610130913 §6 の未検証点は
  本番で通ったと言える
- 文脈は compact 前 163k〜428k → 直後 62k〜90k

### 4.2 節約額（`save.py`）

- 自己 compact 14 回の差し引き節約 **約 $72**（減った読み・書き込み 約 $79 − compact のコスト 約 $7）。
  同期間の全セッションの総額 約 $627 に対し1割強
- 反実仮想: compact しなければ次の compact までの各呼び出しで (pre − post) を余計に読んでいた、とした。
  キャッシュ書き込みの比率が高い呼び出しは書き込み単価で数えた。要約の出力は 1 回 1万トークンと仮置き（測れない）
- 1回あたりの得は compact 後に長く続いたセッションほど大きい（例: 司令官 analysis-methods の4回で約 $39、
  browse-polish 1回で約 $12.5）。直後に終わったセッション（usage-diet）は得 0 でコストだけ

### 4.3 実装の孫の取りこぼし（`miss.py` / `when.py`）

- 実装の孫（ワークツリー名 `xxx-NN-`、26 セッション）: 呼び出しの **52%** が文脈 200k 超。その呼び出しで
  80k を超えていた分の費用は **約 $118**（取れる上限の目安）。今の区切りで回収できたのは約 $30
- 200k を超えるのは 40〜90 回目の呼び出し付近、`gh pr create` は 100〜220 回目（pixidex の分析系の孫）
- 膨らむ孫はツール結果の合計が **100万〜750万文字**（例: analysis-08-report 757万、03-grouping 350万、
  polish-02-preview-shots 313万）。dotfiles の孫（rt-01〜03）は 10万〜17万文字。膨張の主因は大きい
  ツール出力と見ている（どのツール・どのコマンドの出力が大きいかの内訳はまだ見ていない → 孫1）
- レビュワーは 200k 超が 1,178 呼び出し中 86 回で、ほぼ問題無し

## 設計1: 大きいツール出力の作法（孫1）

### 1.1 内訳の調査

`docs/adr/probes/context-bloat/when.py` はツール結果の合計文字数しか出さない。これを出発点に、
膨らむ孫（ツール結果の合計が多い順に上位のセッション）について、ツール結果を次の軸で分ける:

- ツールの種類（Bash・Read・Grep・Glob・画像〔Read の画像やスクリーンショット〕・Agent〔サブエージェント〕・MCP など）
- Bash ならコマンドの先頭語（`python`・`pytest`・`cat`・`git diff`・`gh`・`jq` など）
- 1回あたりの大きさの分布（大きい1回が効いているのか、中くらいが積もっているのか）
- 同じファイル・同じコマンドの出力を何度も読み直しているか

文字数だけでなく、**トークン換算でどれだけ文脈を押し上げたか**も見る（画像は文字数では測れない。
次の呼び出しの文脈の増分で見るなど、測り方は孫1 が決める）。スクリプトは
`docs/adr/probes/context-bloat/` に足し、付録A の表に行を足す。結果は文書にする（置き場は孫1 が
`docs/README.md` の分類に従って決める。参考: 前例の調査結果は `docs/reference/` にある DOC-2610130216）。
孫の実装ログを文書に貼るときは、他のリポの中身（コード・データ・パス）を書き写さず、ツール名・
コマンドの種類・量にとどめる（このリポは公開）。

### 1.2 作法の中身と置き場

- 中身は調査で決める。叩き台: 大きくなりうる出力（テスト・分析スクリプト・ログ・`git diff`・
  JSON など）は最初からファイルへ書き出し（`> out.txt 2>&1`。置き場はリポ外の一時ディレクトリ）、
  `head` / `tail` / `wc -l` / `grep` / 要約だけを見る。大きいファイルは範囲を絞って読む。
  画像は要るときだけ見る。同じ出力を繰り返し読まない
- **置き場は「実装中の孫に届く場所」を必ず含める**（背景3 の司令官の追記）:
  - `skills/umbrella-orchestrator/SKILL.md` §3.2 の自動付与指示（同じリポの孫用・他リポの孫用の両方）。
    これは傘の司令官が計画書の孫用プロンプトへ入れるもので、pixidex の傘にも届く
  - `skills/pr-review-loop/SKILL.md`（指摘対応の修正中にも同じことが起きる）
  - 他に実装の孫・単発の実装（`task-intake` の軽いハンドオフ）が実装中に読む場所があれば洗い出す
  - `templates/repo-baseline/template/AGENTS.md.jinja`: 撒いた先の全エージェントに効く。入れるかは孫1 が
    判断する（入れたら `tests/template_smoke.sh`）
  - `claude/CLAUDE.md`: 背景5-2 の人間の確認が済むまで編集しない。進行記録に人間の許可が書かれていれば編集してよい
  - pixidex の `AGENTS.md`: この傘では変えない（傘は dotfiles 1リポ）。要りそうなら PR 本文と最終報告に書く
    （司令官が人間に上げる）
- 作法は短く書く（毎回読まれる場所に長文を置くと、それ自体が文脈を太らせる）

## 設計2: 実装途中の自己 compact（孫2）

### 2.1 区切り

- 叩き台は「テストが通ってコミットした直後、かつ文脈が閾値（200,000）超」。孫2 が実ログ（背景4.3、
  付録A のスクリプト）と照らして具体を決める: どのコミットを区切りとみなすか（WIP コミットを除くか）、
  1本の PR の中で何回まで行うか、閾値を 200k のままにするか
- 区切りの判断のあとの手順は既存の自己 compact と同じ（文脈の測り方・`ocw self-compact` の呼び方・
  コマンドを実行したらターンを終える・使えなければ何もしない〔ADR DOC-2610131214 §2.4〕）
- **置き場は実装中の孫に届く場所**（背景3 の司令官の追記）: 少なくとも `umbrella-orchestrator` §3.2 の
  自動付与指示（同じリポ・他リポの両方）。`pr-review-loop` の「区切りでの自己 compact（実装側のみ）」も、
  区切りの一覧・「途中では行わない」の記述を新しい決定に合わせて直す（指摘対応の修正の途中を対象に
  含めるかも孫2 が決める）

### 2.2 復帰メモ

既存の復帰メモ（レビュー待ちに戻る用）とは中身が違う。実装途中の判断が落ちにくいよう、少なくとも次を
書く形にする: 計画書のパスと孫N の節、ここまでに済んだこと（コミットの一覧）、**作業中に下した判断と
その理由**（要約で一番落ちやすい）、まだ残っていること、次に打つ一手、検証に使うコマンド。
`ocw self-compact` の続きを促す固定文（「復帰メモがあれば読み、計画書の続きから再開してください。」）は
変えない（決定的な制約）。

### 2.3 品質低下の検知（様子見の約束）

「レビューで指摘が増えたら区切りを再考する」を何で測るかを決め、ADR に書く。叩き台: 実装途中の
compact があった PR と無かった PR で、レビューのラウンド数・変更要求の指摘数を比べる（実装ログの
`compact_boundary` と `pr-review-loop` の投稿から）。測るスクリプトは `docs/adr/probes/context-bloat/` に置く。
いつ・誰が測るか（例: 実装途中の compact が N 回たまったら、次の傘の司令官が測る）も決める。

### 2.4 ADR

新しい ADR を書き、ADR DOC-2610131214 との関係（§2.1 の「途中では行わない」を覆す。何を引き継ぎ、

## 設計3: 思い出させるフック（孫3）

### 3.1 決めてあること（孫3 はこれに従う）

- **フックは compact を打たない。** 文脈が閾値を超えていれば、判断を促す一文を差し込むだけ
  （例: 「文脈が約 N k。今が区切りなら self-compact を判断すること。区切りでなければ続けてよい」）
- **効かせるのは実装の孫だけ。** `ocw -H` は各ペインのシェルに `OCW_ROLE`（commander / implementer /
  reviewer）を渡している（`bin/ocw`）ので、`OCW_ROLE=implementer` のときだけ働く。司令官の compact
  （ADR DOC-2610130913 / DOC-2610140044）とレビュワーはスコープ外。傘の運用外のセッションにも効かせない
- 閾値と「区切り」の言い方は孫2 の決定に合わせる（孫3 は孫2 のマージ後に始める）
- 判定できない・失敗した・transcript が読めないときは何も言わない（エージェントを止めない。
  `claude/hooks/git-guard.sh` と同じ方針）
- 置き場は `claude/hooks/`（前例: `git-guard.sh`）と `claude/settings.json` の `hooks`。配布の一覧
  （`shared/helpers.sh`）にも足す

### 3.2 孫3 が決めること

- フックの種類（PostToolUse が第一候補。実装の孫は長い1ターンで走り続けるので、ターンの終わりにしか来ない
  Stop では届きにくい）と、`additionalContext` の返し方
- 文脈の測り方: フックの入力の `transcript_path` の**末尾だけ**を読んで直近の assistant の使用量を取る
  （transcript は数十 MB になりうるので、毎回全部を読まない）
- 間引き: 毎呼び出しで差し込むと、それ自体が文脈を太らせ、無視されるようにもなる。閾値を越えた最初の1回と、
  その後は一定の増分（例: 50k ごと）か一定の呼び出し回数ごとにする等。状態はセッション ID ごとにリポ外へ置く
- 実装言語（AGENTS.md「クロスプラットフォーム制約」とシェルスクリプトの方針 DOC-2608020715-a に従う）
- 呼び出しごとのオーバーヘッド（全ツール呼び出しで走るので軽くする）

### 3.3 検証の限界

フックを実 `$HOME` で効かせるにはデプロイが要るが、デプロイは人間の指示が要る（AGENTS.md「最重要ルール」）。
孫3 はテスト（入力 JSON を与えて出力を確かめる。前例 `tests/git_guard_test.sh`）と
`tests/deploy_smoke.sh`（サンドボックス）で確かめ、**実機で `additionalContext` がエージェントに届くかは
未検証として ADR か PR に残す**。新しいエージェントを起動して試すことは、auto mode の分類器に
`[Create Unsafe Agents]` で拒否される（計画書 DOC-2610122205 進行記録）ので行わない。

## 決定的な制約（孫は全部守ること）

- AGENTS.md「最重要ルール」（master を書き換えるのは人間だけ、孫→傘のマージは司令官がレビュー承認済み PR に限る、
  linter 抑制を AI 判断で足さない、deploy スクリプトを AI 判断で実 `$HOME` に実行しない）
- 配布物 `claude/CLAUDE.md` は指示が無い限り編集しない。編集すると Claude Code / Codex / OpenCode の3エージェントへ
  及ぶ（背景5-2 の人間の確認が済むまで触らない）
- `ocw self-compact` の仕様（宛先は `$HERDR_PANE_ID` 固定、続きを促す1通は固定文）と allow ルール
  `Bash(ocw self-compact *)` は変えない（ADR DOC-2610130913・DOC-2610131214 §2.5）。変える必要が出たら
  司令官経由で人間に確認する
- 実装の孫で compact が使えない（コマンドが無い・拒否・失敗・Claude Code 以外）ときは何もしない、の落とし方は
  維持する（ADR DOC-2610131214 §2.4）
- risk-based なテスト方針は3箇所（`skills/pr-review-loop/SKILL.md`・`templates/repo-baseline/template/AGENTS.md.jinja`・
  ルート `AGENTS.md`）に意図的に重複している。どれかを触るなら残り2つも確認する
- リポの文書に人間の発言を逐語で書かない（要約する）。他のリポ（pixidex 等）の中身を書き写さない

## スコープ外

- 傘の運用外のセッション（lora-dataset-forge・modeldex・iosci などの会話。600〜900k まで膨らんで人間が
  手で compact している）
- 司令官の compact（ADR DOC-2610130913 / DOC-2610140044）は変えない
- レビュワーの compact（200k に届かず損になる。ADR DOC-2610131214 §2.1）

## 必須の検証ステップ（AGENTS.md「コミット前の必須ステップ」より。省略しない）

## テスト方針（AGENTS.md「テスト方針」に従う）

スキル・文書の変更はテスト対象外（レビューで矛盾を見る）。孫3 のフックは public な契約（入力 JSON →
差し込む／黙る）を持つので、閾値の境界・`OCW_ROLE` による絞り込み・判定できない入力で黙ることを
テストで固定する。配布の一覧に足したら `tests/deploy_smoke.sh` で配置を確かめる。

## 孫ブランチ分割の叩き台（ブリーフより転記。採った分割は上の進捗テーブル）

叩き台であり、司令官が再設計してよいとされていた。

- 孫A: 膨らむ孫の大きいツール出力の内訳調査（既存のスクリプトを流用）→ (1) の作法を書き、置き場に入れる

司令官の判断: A→孫1、B→孫2、C→孫3 とした。孫1・孫2 は並列（孫2 は既定の 200k で始め、孫1 の調査で直したく

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- `OCW_ROLE=implementer` 以外（司令官・レビュワー・未設定）では何も差し込まない
- 閾値以下では何も差し込まず、超えたら差し込む。間引きが効いて毎呼び出しは差し込まない
- transcript が読めない・入力が壊れているときは黙って抜け、エージェントを止めない
- フックは compact を打たない（コマンドを実行しない）
- deploy / uninstall で配置・撤去される（`tests/deploy_smoke.sh`）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。

## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

1. PRを作成する。**PRの向き先は必ず `context-bloat` にすること。master には絶対に出さない。**
2. `/pr-review-loop` を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** `/pr-review-loop` の手順にマージへ進む記述があっても実行しない
   （孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）
5. 最終報告を書き終えたら、最後の行動として、司令官が spawn の送信文で渡した司令官の Herdr ペインへ
   承認を報告する（渡されていなければ報告せず、人間に「承認済み。マージは司令官（または人間）が行う」と伝えて止まる）。
   送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」に従う。本文は
   「孫3 `cb-03-compact-reminder-hook` の PR #<番号> が HEAD <短縮SHA> で承認されました。マージをお願いします。」
   だけにする。報告は1回だけ。送れなくても再送せず、送れなかったことを人間に1行伝えて止まる

なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する（その手順は pr-review-loop 側。使えなければ何もしない）。compact の後は、
復帰メモに従ってレビュー待ちに戻り、この「実装完了後の流れ」を最後まで続けること。
実装が終わったタイミングで止まらず、必ずここまでやりきってください。
reviewerはdone状態で完了し完了通知は来ないので、待機して停止せず gh pr view をポーリングして
レビューの有無を確認してください。
傘ブランチが先へ進んでコンフリクトしたら `git rebase origin/context-bloat` と
`git push --force-with-lease` で追随する（AGENTS.md「最重要ルール」）。

## ブランチ作成時の注意（最重要）

作業ブランチは**必ず `context-bloat` から切ること**。master から切ると PR の diff に傘ブランチ全体が
混入してレビュー不能になる。`ocw` が `origin/context-bloat` から切ったワークツリーを用意済みなので、
上の「実装開始前の必須手順」で確かめるだけでよい（`git pull` は使わない）。
