# 計画書: リポごとの許可（opt-in）で、既定ブランチへのマージも AI に任せられるようにする

傘ブランチ: `default-branch-automerge`
ターゲット: `master`

## 概要

いまの線引きは「既定ブランチ（`main` / `master`）へのマージは人間がやる。それ以外は AI に任せる」の1本で、
ADR DOC-2609121719・フック `claude/hooks/git-guard.sh`・スキル `pr-review-loop` / `umbrella-orchestrator` の
どれにも、リポごとにこの線を動かす仕組みが無い。非公開の業務リポジトリ（定型の書類作成を Claude Code で回すリポ）で、
人間が「このリポでは、既定ブランチ向きの PR もレビュー承認と CI green を条件に AI がマージしてよい」と判断した。
これを受けて、この傘で次を行う。

1. **線引きを改訂する ADR を書く**（孫1）。リポごとの許可をどこにどう書くか、自動マージの条件、だれがマージするか、
   フックがどこまで担保するかを決める
2. **フックを、許可のあるリポでだけ既定ブランチ向きの `gh pr merge` を通すようにする**（孫2）。許可の無いリポの挙動は変えない
3. **スキルの手順を書き換える**（孫3）。許可のあるリポでは、承認＋CI green を確かめて既定ブランチへマージする手順を
   `pr-review-loop` と `umbrella-orchestrator` に足す

> material として司令官が起草したものである。** ブリーフの問題意識（要約）・決定事項・既存の穴・実測値・関係するリポ・
> 制約・スコープ外・必須の検証ステップ・孫分割の叩き台は本計画書へ転記済みであり、以降はこの計画書が正典である。

## 背景1: 問題意識（要約。公開リポのため逐語では書かない）

きっかけは、非公開の業務リポジトリ（既定ブランチは `main`）で傘を回していた司令官と人間の会話。人間は、このリポでは
既定ブランチまでのマージも自動で行えるようにしたいと伝えた。司令官が「この傘の最終 PR だけ／このリポの全 PR／両方」の
どれかを尋ねたところ、人間は**このリポの全 PR**（今後のスクリプト改修の PR も含め、レビュー承認＋CI green で既定ブランチへ
自動マージ）を選んだ。続いて司令官が「dotfiles に傘を立てる・2〜3本・司令官は dotfiles」という振り分けを示し、人間が了承した。

## 背景2: 人間が確定させた決定事項（覆さないこと）

- 自動マージを許すのは、**リポごとの明示的な許可（opt-in）があるリポだけ**。許可の無いリポでは、既定ブランチへのマージは
  従来どおり人間が行う
- 許可のあるリポでは、**既定ブランチ向きの PR すべて**が対象（傘の最終 PR に限らない）
- 条件は少なくとも**レビュー承認＋CI green**（司令官が提示し人間が了承した）。承認の対象 HEAD が PR の最新コミットと
  一致することも、既存の孫→傘マージの条件（`umbrella-orchestrator` §2.4）に合わせて含める（相談の会話の提案）
- **dotfiles 自身の `master` は対象外のまま。** dotfiles の `AGENTS.md`「最重要ルール」の「`master` を書き換える操作は
  人間だけが行う。例外はない」は dotfiles 自身についての規則で、今回は変えない（相談の会話の理解。迷ったら人間に確認する）

## 背景5: 孫1（ADR）で決める論点と、司令官の推奨

ADR の孫が最終的に決める。司令官の推奨は叩き台であり、根拠があれば覆してよい（ただし背景2 の決定は覆さない）。

1. **許可の書き場所**: 推奨は、そのリポの `.claude/pr-review.yml` に1キー（名前は ADR で決める。例: `default_branch_merge: auto`）。
   **許可は、PR の head や作業ツリーではなく、リモートの既定ブランチに入っている版から読む**（例:
   `gh api repos/<owner>/<name>/contents/.claude/pr-review.yml?ref=<既定ブランチ>`）。作業ツリーや PR の版から読むと、AI が
   同じ PR の中で許可を足して自分でマージできてしまう。既定ブランチの版から読めば、許可を入れる PR は必ず人間がマージする
2. **条件**: 背景2 の3つ（最後の判定が承認・対象 HEAD が最新と前方一致・CI green）に加え、既存の §2.4 と同じく「implementer が
   `working` でない」「人間がその PR について待てと言っていない」。CI の読み方は §2.4「CI の確認」をそのまま使う
3. **マージする主体**: 推奨は、承認を受け取る `pr-review-loop`（実装側）が、許可のあるリポで既定ブランチ向きの PR のときに
   マージする。傘の最終 PR（`/finalize` で司令官のワークスペースの implementer が回す）も、他リポの孫の PR（そのリポの既定
   ブランチ向き）も同じ経路になる。傘ブランチ向きの孫 PR は従来どおり司令官がマージする（変えない）。司令官は他リポの孫の
   マージを従来どおり検出するだけでよい
4. **フックの担保範囲**: 推奨は、base が既定ブランチ（保護ブランチ）のときだけ、追加で「リモートの既定ブランチ上の許可」
   （と、余裕があれば CI の green）を確かめて、満たせば `allow`、満たさなければ従来どおり `deny`。**許可の確認に失敗した
   ら（`gh` の失敗・タイムアウト・形式の不一致）`deny` のまま**（＝許可の無いリポと同じ扱い）。これは「判定できない入力は
   何も言わない」の原則と向きが違うので、ADR にその関係を書く（base が保護ブランチと確定した後の分岐であり、既存の
   `deny` を緩める条件が確かめられなければ緩めない、という整理になる見込み）。承認の読み取り（レビュー本文の書式の揺れ）を
   フックに持ち込むかは ADR で判断する（推奨は持ち込まず、スキル側の責務にする）。`gh` 呼び出しが増えるので、フックの
   `timeout: 15` に収まる時間の配分も書く
5. **dotfiles 自身の扱い**: dotfiles は許可を宣言しない。`AGENTS.md`「最重要ルール」は変えない。フックで dotfiles を特別扱い
   するかは ADR で判断する（推奨は特別扱いしない。宣言が無ければ従来どおり `deny` になるため）
6. **改訂の形**: ADR DOC-2609121719 を改訂するか、新しい ADR を立てて上書き範囲を明記するか。推奨は新しい ADR を立て、
   DOC-2609121719 のステータスに「§1 の線引きと §3.1 の判定表の保護ブランチの行は ADR <新ID> で拡張」と1行追記する
7. **分類器・settings との関係**: `gh pr merge` は `permissions.ask` に無い。auto mode の分類器に止められた場合は、回避せず
   人間に知らせる（既存の §3.6 と同じ扱い）。settings を変える要否を書く
8. **マージの方法**: 推奨は `gh pr merge <PR番号> --squash --delete-branch`（既存の孫→傘と同じ）。リポに別の作法があれば
   そちらを優先できるかを書く

## 決定的な制約（孫は全部守ること）

- ADR DOC-2609121719 を改訂する（または新しい ADR で上書き範囲を明記する）。フックの担保範囲を広げるなら、その ADR の
  設計思想（判定できない入力は止めずに何も言わない、フックは `gh pr merge` の base 判定だけ）との関係を書く
- **許可の無いリポの挙動は一切変えない**（既存の全リポで、既定ブランチへのマージは人間のまま。フックも `deny` のまま）

- dotfiles の `AGENTS.md`「最重要ルール」と「コミット前の必須ステップ」に従う
- 公開リポジトリなので、人間の発言の逐語・業務リポジトリの名前・業務の中身・ホスト名を、PR・コミット・文書に書かない
- linter の抑制ディレクティブや設定の緩和を足さない

## 大きい出力を文脈へ流し込まない（実装中ずっと）

- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し修正して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）

## リポジトリに書かないもの
人間（持ち主）の発言そのものを、PR の本文・コミットメッセージ・文書・コードのコメントに書かない
（計画書や送信文にあっても写さない）。何への対応かを自分の言葉で書く。
非公開のリポジトリの名前・ホスト名も書かない。書き直すときは、人間が挙げた例を要件として言い切らない・
誰の判断や提案かを落とさない・意味に要らない固有名詞を残さない。

## 実装完了後の流れ（必須）
実装が完了したら、以下を**自律的に**実行してください:
1. PRを作成する。**PRの向き先は必ず default-branch-automerge にすること。master には絶対に出さない。**
2. /pr-review-loop を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** `/pr-review-loop` の手順にマージへ進む記述があっても
   実行しない（孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）
5. （Herdr あり・司令官が宛先を埋め込んだときだけ）最終報告を書き終えたら、最後の行動として
   司令官へ承認を報告する。宛先は、司令官が spawn の送信文で渡した司令官の Herdr ペイン
   （渡されていなければ報告せず、人間に「承認済み。マージは司令官（または人間）が行う」と伝えて止まる）。
   送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」に従う。本文は
   「孫3 `dam-03-skills` の PR #<番号> が HEAD <短縮SHA> で承認されました。マージをお願いします。」
   だけにする（「〜とだけ返事して」のような指示は付けない）。報告は1回だけ。送れなくても
   再送せず（司令官の巡回が拾う）、送れなかったことを人間に1行伝えて止まる
なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する（その手順は pr-review-loop 側。使えなければ何もしない）。compact の後は、
復帰メモに従ってレビュー待ちに戻り、この「実装完了後の流れ」を最後まで続けること
実装の途中でも、検証が通ってコミットした直後の区切りで、文脈が
150,000 トークン（claude-ds 以外の Claude は 200,000。`ANTHROPIC_BASE_URL` に `deepseek` を含むかで見分ける）を超えていれば `ocw self-compact` で自分を compact してよい（WIP のコミットは
区切りでない。指摘対応の修正の途中は対象外。回数の上限は無いが、前回の compact から文脈が
100,000 以上増えていなければ見送る。ADR DOC-2610142337・DOC-2611032102）。
測り方は `/pr-review-loop` の「区切りでの自己 compact（実装側のみ）」の手順1のコマンドと同じ（その節の (3) の項だけを読めばよい。手順の「Phase 3 へ進む」は実装途中には当てはまらない）。復帰メモ
（リポの外の一時ファイル）には、計画書のパスと孫の節・済んだこと（コミットの一覧）・作業中に下した
判断とその理由・残り・次の一手・検証コマンドを書き（増分の起点は復帰後に測るのでメモには書かない）、先頭に「計画書の
続きから実装を再開する。レビュー待ちではない」と書く。コマンドを実行したらそのターンを終える。
使えない・拒否・失敗なら何もせず実装を続ける（人間に提案もしない）
実装が終わったタイミングで止まらず、必ずここまでやりきってください。

## ブランチ作成時の注意（最重要）
作業ブランチは**必ず default-branch-automerge から切ること**。
master から切ると PR の diff に傘ブランチ全体が混入してレビュー不能になる。
ocw が既に dam-03-skills を作って checkout 済みなら、`git fetch origin` のあと
`git log --oneline -1 origin/default-branch-automerge` が作業ブランチに含まれていること（孫1 の ADR が入っていること）だけ確認すればよい。
自分で切る場合は次を別々のコマンドとして実行する（`git pull` は使わない）:
git checkout default-branch-automerge
git fetch origin
git merge --ff-only origin/default-branch-automerge
git checkout -b dam-03-skills
