# 計画書: ocw-meter の report を人間向けに読みやすくし、端末にグラフを出す

傘ブランチ: `ocw-meter-pretty-charts`
ターゲット: `master`

## 概要

`bin/ocw-meter report` について、次の4件をこの傘で進める。どれも出力先は端末（CLI）である。

1. **人間向けの pretty 表示を作り、`report` の既定にする（孫1）。** 表・桁区切り・単位の丸め（K / M / B）・色。今の
   key: value の羅列は `--plain` で残す。描画の部品（表・棒・色の判定・数値の整形）はこの孫が作り、孫2〜4 が使う
2. **日ごとのモデル別使用量のグラフ（孫2）。** 日ごとの集計を作り、日×モデルの積み上げ棒を端末に描く
3. **週の上限が 100% に届くまでの推移グラフ（孫3）。** 今の週の `seven_day_used_pct` の推移を描き、今の消費の速さで
   いつ 100% に届くかの見込みと、残りの % が系統ごとに何トークンに当たるか（`--quota-per-pct` の見積もり）を添える
4. **日ごとの消費量のヒートマップ（孫4）。** GitHub の草のように、週を列・曜日を行にして、消費の多い日ほど濃く塗る。
   日ごとの集計は孫2 のものを使う

## 背景1: 問題意識（要約）

- 持ち主は、`ocw-meter` の出力が全体に人間には読みにくい形だと感じている。ふだんは AI に読ませるので困らないが、人間向けの
  pretty 表示を作り、それを既定にしたいと述べた
- あわせて、日ごとのモデル別使用量のグラフと、週の上限が 100% に届くまでの推移のグラフを、端末で出せるようにしたいと述べた
- さらに、GitHub の草のような週ごとのヒートマップ（消費の激しい日ほど色が濃い）も欲しいと述べた。傘になる規模だと見て、
  task-intake での振り分けを頼んだ

## 背景2: 人間が確定させた決定事項（覆さないこと）

- 出力先は CLI（端末上に描く）。HTML やブラウザで見るものではない
- 人間向けの pretty 表示を作り、それを `report` の既定にする
- 欲しいものは次の4つ:
  1. pretty 表示（既定にする）
  2. 日ごとのモデル別使用量グラフ
  3. 週の上限が 100% に届くまでの推移グラフ
  4. GitHub の草のような日ごとの消費量ヒートマップ（消費が激しい日ほど色が濃い）
- task-intake で振り分け済み: リポは dotfiles のみ、規模は複数 PR、司令官は dotfiles（2026-10-31）

## 背景3: 既存の穴

- `ocw-meter report` の今のテキスト出力は YAML 風の key: value の羅列である。例: `report --model` はモデルごとに messages /
  input_tokens / cache_read_input_tokens … を縦に並べ、末尾に completeness / attribution / price_table などの診断行が続く。
  数字に桁区切りが無く、億単位のトークンが読みにくい
- 日ごとの集計・グラフ・ヒートマップを出す手段は無い
- `report --quota-per-pct`（#183）は週の上限の 1% あたりのトークン見積もりを出すが、推移の可視化は無い

## 背景4: 実測値

### 4.1 ブリーフに書かれていた実測（2026-10-31）

- 本物の保存先（`~/.local/state/ocw-meter`）で `report --model`: `usage.message` は約28万件、モデルは Anthropic 9種 + DeepSeek 2種 +
  `unknown/<synthetic>`。cache_read は最大で 251億トークン級（Opus 5.5）。桁が大きいので単位の丸め（M / B など）が効く
- 同日 `report --quota-per-pct --no-ingest`: periods 2、opus と sonnet は推定値あり、haiku は「測れない（使用のあった区切りが少ない）」、
  fable は「測れない（使用がない）」。→ 見積もれない系統の表示を決める必要がある（設計1 で決めた）
- `ingest` は全量で約1分半かかる（1999 個の transcript ファイル）。`report` は既定で ingest を走らせる

### 4.2 司令官が確かめたこと（2026-10-31 時点の `bin/ocw-meter`。master 2267ba8）

- `bin/ocw-meter`（約 6,400 行）は bash のラッパーで、Python の本体をヒアドキュメントで一時ファイルへ書き出して `python3` で実行する
  1ファイル構成である。**import は全部標準ライブラリ**（`bisect` `contextlib` `datetime` `errno` `fcntl` `json` `math` `os` `pathlib`
  `re` `select` `shutil` `subprocess` `sys` `tempfile` `time` `uuid`）。外部の pip パッケージには依存していない
- テキスト出力の組み立ては、ビューごとの `print()` の連続である。主な所:
  - `cmd_report()`（引数の解析・ビューの振り分け。`--quota-per-pct` `--periods` `--since` `--until` `--pr` `--repo` `--json`
    `--reconcile` `--no-ingest` `--phase` `--model` `--role` `--window` `--month` `--provider-total`）
  - `_print_grouped_report()`（`--model` / `--role` / `--phase` / `--window` / `--since` の共通の印字）
  - `print_footer_text()`（completeness / attribution / price_table / ingest の鮮度などの診断行）
  - `print_quota_per_pct()`、`_report_month_standalone()`、`_report_reconcile()`、`cmd_report()` 末尾の既定ビュー（`--pr` の詳細を含む）
- 色の出力・`isatty` の判定・`NO_COLOR` の扱いは、`report` にはまだ無い
- `bin/tests/test_ocw_meter.py`（約 5,200 行）は実行ファイルを subprocess で叩く black-box テストで、**`--json` を付けずに `report` を
  叩いてテキストの文字列を `assertIn` で確かめているテストが約 37 か所ある**（例: `"total events:  0"`、
  `"ingest (this run): skipped (--no-ingest)"`、`"ingest_freshness_warning: (none)"`）。既定を pretty に変えるとこれらが落ちる
  （設計1 の 6 で扱う）
- リポ内で `report` のテキスト出力をパースしているコード（`bin/` `skills/` `claude/` `zsh/` `tmux/`）は見当たらない（相談の会話と司令官の
  grep で確認）。出力例を載せている文書は `docs/reference/DOC-2608021229-b_LLM費用観測ベースライン計測手順.md`（`report --pr` と
  `report --month` の出力例、`report --pr <N> > /tmp/pr-<N>-report.txt` のようにテキストをファイルへ残す手順）と `bin/README.md` の
  `report` の節
- イベントは保存先の `events/` に日ごとの JSONL（`YYYY-MM-DD.jsonl`）で置かれている（2026-10-31 時点で 123 ファイル）
- `quota.sample` は `seven_day_used_pct` / `seven_day_resets_at` / `five_hour_used_pct` などを持つ。週の区切りは
  `seven_day_resets_at` で分かれる（`--quota-per-pct` の実装がこれで区切りを数えている）
- mise の Python は 3.12 だが、`bin/ocw-meter` は各マシンの `python3`（macOS 標準のものを含む）で動く前提である

## 決定的な制約（孫は全部守ること）

- dotfiles の `AGENTS.md` の最重要ルール（`master` を書き換える操作は人間だけ。deploy スクリプトを人間の指示なしに実 `$HOME` で
  実行しない。linter の抑制を AI の判断で足さない）
- `bin/ocw-meter` は bash ラッパー + Python 実装。**macOS（BSD / bash 3.2）互換を壊さない**（#49 で対応済みの領域。bash 側を触るなら
  bashism の新規追加に注意する）
- **新しい外部依存を足さない**（設計0 で決めた。`rich` などの pip パッケージは使わず、標準ライブラリだけで描く）
- **`--json` の出力形式を変えない**（AI と文書が依存している）。キーを足すのは可。新しいビューの `--json` は新しく決めてよい
- **`--plain` は今のテキスト出力を変えずに出す**（設計0）。既存のビューの `--plain` の出力は、この傘の前の既定の出力と同じであること
- 色付き出力は、標準出力が端末で、かつ環境変数 `NO_COLOR` が空でない値で立っていないときだけ出す（設計0）
- **fail-open の方針を崩さない。** `report` の自動 ingest の失敗が `report` を止めない今の振る舞いを保つ。statusLine から呼ばれる経路
  （`quota.sample` の記録）は触らない
- 見積もり（`--quota-per-pct` と、孫3 の 100% に届く見込み）は**見積もりとして**出す。止める・モデルを替えるなどの自動の制御には使わない
  （ADR DOC-2610310237）

## テスト方針（dotfiles AGENTS.md「テスト方針」と DOC-2610150520-a に従う）

- 描画の結果を丸ごと文字列で固定するテスト（スナップショット）は作らない。端末幅や記号の細かい調整のたびに壊れ、守る価値が薄い。
  守るのは振る舞い（色コードが混ざらない・`--plain` が変わらない・集計が正しい・数値の丸めが正しい）である
- 孫1: **端末でない出力（パイプ・ファイル）と `NO_COLOR` で色コード（`\x1b[`）が混ざらないことは必ず自動テストで固定する**（`report > file`
  で残す手順が文書にあり、ここが壊れるとファイルが汚れる）。既存のテキストを確かめるテストは `--plain` を付けて守る
- 孫2・孫4: 日ごとの集計（ローカル時刻の日の境目・モデルのまとめ方）と、ヒートマップの濃さの段階分けを、合成のイベントで1つずつの
  scenario で確かめる程度
- 孫3: 合成の `quota.sample` から、100% に届く見込みの時刻（または「届かない」）が出ることを1つの scenario で確かめる程度

## 設計0: 全孫に共通の方針（司令官が決めた）

1. **標準ライブラリだけで描く。** `bin/ocw-meter` は1ファイルを symlink で各マシン（macOS / Linux / WSL2）へ配るもので、今は外部依存が
   無い。`rich` などを足すとマシンごとにインストールが要り、入っていないマシンで `report` が動かなくなる（fail-open に反する）。
   描画の部品（表・棒・色・数値の整形・東アジアの文字幅）は `bin/ocw-meter` の Python 本体の中に、まとまった1区画として置く
2. **出力のモードは3つ。** 既定は pretty（人間向け）、`--plain` は今のテキスト出力（AI 向け・旧形式）、`--json` は今の JSON。
   `--plain` と `--json` を両方付けたらエラーにする（今の `report` が組み合わせられないフラグをエラーにしているのと同じ扱い）。
   pretty は端末でないとき（パイプ・ファイル）も pretty のまま出し、色だけを落とす（「既定は pretty」という人間の決定を、端末かどうかで
   変えない。AI やスクリプトが読むなら `--plain` か `--json` を付ける）
3. **色の判定。** 色を出すのは、標準出力が端末（`sys.stdout.isatty()`）で、かつ `NO_COLOR` が空でない値で立っていないときだけ
   （no-color.org の約束に従う）。色を強制する `--color` のようなフラグは足さない（要るとなったら別件）。色が無くても読めるように作る
   （濃淡は記号で、系列は記号か凡例の順で区別する）
4. **幅。** 端末幅は `shutil.get_terminal_size()`（`COLUMNS` を尊重する。取れなければ 80）。日本語のラベルは表示幅（全角は2）で揃える
   （`unicodedata.east_asian_width`）。幅が足りなければ、列や期間を減らして描き、崩さない
5. **数値。** 件数は桁区切り（`281,234`）。トークンは表では単位を丸める（`25.1B` `340.2M` `12.3K`。1,000 未満はそのまま）。正確な値は
   `--plain` と `--json` で取れる。費用は `$` と小数2桁
6. **診断行。** completeness / attribution / price_table / ingest の鮮度などは、pretty では末尾の短い「注記」欄にまとめてよいが、
   **警告（ingest の鮮度の警告・ingest の失敗・数え漏れの疑いなど）は落とさず目立たせる**。詳細は `--plain` で見られる
7. **新しいビューの口。** 孫2〜4 のビューは `report` のフラグとして足す（`--daily` / `--quota-progress` / `--heatmap`）。既存の
   `--model` / `--role` / `--phase` / `--window` / `--month` / `--reconcile` / `--quota-per-pct` / `--pr` / `--since` / `--until` とは
   組み合わせられない（エラーにする）。`--no-ingest` / `--json` / `--plain` はどれにも付けられる。新しいビューの `--plain` は、グラフの
   元になった数値を今のテキスト出力と同じ key: value の形で出す

## 設計1: pretty 表示の土台と既定化（孫1）

1. 描画の部品を作る: 表（列の左右寄せ・東アジアの文字幅・見出し）、数値の整形（桁区切り・単位の丸め・費用）、色（判定と、色を付ける
   小さな関数。色が無いときは素の文字列を返す）、横棒（`█` と 1/8 刻みの `▏▎▍▌▋▊▉`）。孫2〜4 が使うので、関数名と引数を分かりやすくし、
   区画の頭に使い方を短く書く
2. 全ビューのテキスト出力を pretty にする: 既定のビュー（`--pr` の詳細を含む）、`--model` / `--role` / `--phase` / `--window` /
   `--since`（`_print_grouped_report()`）、`--quota-per-pct`、`--month`、`--reconcile`。行が同じ形のビューは表に、1件の詳細のような
   ビューは揃えた key: value（数値は整形）にしてよい。`--quota-per-pct` で見積もれない系統は、数値の欄を `—` にして理由を添える
3. `--plain` を足す。今のテキスト出力の関数は、そのまま `--plain` の経路として残す（書き直さない。変わっていないことが一目で分かる）
4. 色: モデル系統や警告など、意味のある所にだけ使う（何でも塗らない）
5. ヘルプ文（`bin/ocw-meter` の `report` の節）と `bin/README.md` の `report` の節に、pretty が既定であること・`--plain`・色の条件を書く
6. 既存のテキストを確かめるテスト（約 37 か所）は、テキストの中身を守るためのものなので `--plain` を付けて守る（期待値は変えない）。
   pretty の新しいテストは「テスト方針」の範囲にとどめる
7. 文書: `docs/reference/DOC-2608021229-b` の出力例を pretty に合わせて直す。テキストをファイルへ残す手順（`report --pr <N> > ...txt`）は、
   後から機械で読み比べる用途なら `--plain` を付ける形に直す（判断して PR 本文に理由を書く）
8. ADR を1本足す: 表示の方針（標準ライブラリだけ・pretty を既定に・`--plain` を残す・端末でなくても pretty で色だけ落とす・色の条件・
   単位の丸め・診断行の扱い）と、却下した案（`rich` などを足す・端末でないときは旧形式に戻す・旧形式を消す）。設計0 をそのまま
   根拠にしてよい

## 設計2: 日ごとのモデル別使用量（孫2）

1. **日ごとの集計を作る**（孫4 も使う）。`usage.message` を日ごと × provider+model で集める。日の境目は**ローカル時刻**（人間が端末で
   読むため。`ts` は UTC なのでローカルへ直して日付を取る）。集計の値は今の `--model` と同じ内訳（input / output / cache_creation /
   cache_read / messages / 費用）を持たせる
2. **グラフに使う量は「重み付きトークン」**（`input + 1.25*cache_creation + 0.1*cache_read + 5*output`。`--quota-per-pct` と同じ式。
   ADR DOC-2610310237）。素のトークンは cache_read が桁違いに大きく（背景4.1）、消費の実感とずれるため。式は1か所にまとめ、
   `--quota-per-pct` の実装と共有する（同じ式を2か所に書かない）。グラフの見出しか凡例に、重み付きであることを書く
3. `report --daily [--days N]`: 直近 N 日（既定 14。今日を含む）を、1日1行の横向きの積み上げ棒で描く。棒はモデルごとに色（色が無いときは
   記号）で塗り分け、行末に合計を丸めた数値を出す。モデルは期間内の量の多い順に上位いくつか（端末幅と色の数で決める。5 程度）を
   個別に、残りを「その他」にまとめ、凡例を付ける。使用の無い日も行を出す（空の棒）
4. `--json` は日ごと × モデルの数値（重み付きと内訳の両方）を出す。`--plain` は同じ数値を key: value で出す
5. ヘルプ文と `bin/README.md` に足す

## 設計3: 週の上限が 100% に届くまでの推移（孫3）

1. `report --quota-progress`: 今の週（最新の `seven_day_resets_at` の区切り。リセットの7日前から リセットまで）の
   `quota.sample` の `seven_day_used_pct` を、横軸を時刻・縦軸を 0〜100% にした折れ線（文字のグリッド。高さは 10 行程度）で描く。
   横軸には日付の目盛り、縦軸には 0 / 50 / 100% の目盛りを付ける。今の時刻の位置が分かるようにする
2. **100% に届く見込み**: 直近の消費の速さ（例: 直近 24 時間の `seven_day_used_pct` の増え。区間の取り方は孫が決めて ADR か
   ヘルプに書く）で延ばし、いつ 100% に届くかを出す。リセットまでに届かないなら「この週のうちには届かない見込み」と出す。グラフにも
   見込みの線を別の記号で描く。**見積もりであることを必ず書く**
3. **残りのトークン換算**: 残りの %（100 − 今の %）に、`--quota-per-pct` の系統ごとの「1% あたりの重み付きトークン」を掛けて、
   「残り N% ≈ opus なら X、sonnet なら Y（重み付きトークン）」を出す。見積もれない系統は `—` と理由（設計1 の 2 と同じ扱い）。
   `--quota-per-pct` の計算を呼び出して使い、同じ計算を書き直さない
4. 今の週に `quota.sample` が無い・1件しか無いときは、グラフを描かずにその旨を出す（エラーにしない）
5. `--json` は今の週の点列・見込み・換算を出す。`--plain` は同じ数値を key: value で出す
6. ヘルプ文と `bin/README.md` に足す

## 設計4: 日ごとの消費量のヒートマップ（孫4）

1. `report --heatmap [--weeks N]`: 週を列、曜日を行（月〜日の 7 行）にしたマス目。量は孫2 の日ごとの集計の**重み付きトークンの合計**
   （全モデル）。既定の週数は、端末幅に入るだけ（最大 52 週）。`--weeks` で減らせる。今日より先のマスは描かない
2. 濃さは 0（使用なし）と、使用のあった日の量の分位で分けた 4 段階の計 5 段階（GitHub と同じ考え方。外れ値の1日に引っ張られない）。
   色があるときは緑系の 256 色、無いときは ` ` `░` `▒` `▓` `█` で描く
3. 列の上に月のラベル、行の左に曜日のラベル（月・水・金 など間引いてよい）、下に凡例（少 ░▒▓█ 多）と、期間の合計・いちばん多かった日を出す
4. `--json` は日ごとの値と段階、段階の境目を出す。`--plain` は同じ数値を key: value で出す
5. ヘルプ文と `bin/README.md` に足す

## 設計5: 週の上限のグラフに直近の週の平均を重ねる（孫5）

全孫のマージ後に人間がプレビューを見て足した要望。今の週の推移を、過去の週と比べて速いか遅いかを1枚で見たい。人間は、過去の週を
1本ずつ線にするのではなく、**直近 4 週の平均を1本の線にする**ことを選んだ。

1. `report --quota-progress` のグラフに、**直近 4 週（今の週より前で、区切りが終わった週）の `seven_day_used_pct` の平均**を、
   実績・見込みとは別の記号（と色）の線で重ねる。凡例にも足す
2. **週の揃え方。** 各週を「その週の始まり（リセットの7日前）からの経過時間」で揃え、今の週のグラフの横軸の同じ位置に描く。週の区切りは
   `--quota-per-pct` / 孫3 と同じく `seven_day_resets_at` で分ける。各列での週ごとの値は、その経過時間までの最後の記録の値
   （記録の無い時間帯を補間で作らない）。平均はその列で値のある週だけで取る
3. **週の数。** 既定は 4。`--compare-weeks N` で変えられる。`0` なら重ねない（孫3 のままの表示）。区切りの終わった週が N に
   足りなければ、ある分だけで平均を取り、何週分の平均かを凡例に書く。1週も無ければ線を描かず、その旨を1行出す（エラーにしない）
4. **数字でも比べる。** 今の時点の行に「直近 N 週の平均の同じ時点: X%」と、平均の週末（リセット時点）の値を足す
5. `--json` / `--plain` に、平均の点列・使った週（区切り）の一覧・週の数を足す。`--compare-weeks` を `--quota-progress` 以外と
   組み合わせたらエラーにする（設計0 の 7 と同じ扱い）
6. ヘルプ文と `bin/README.md` に足す

## 設計6: 日ごとのモデル別使用量を縦棒にする（孫6）

孫5 の追加と同じく、人間がプレビューを見たあとで足した要望。日付を横軸にして、時間の流れを左から右へ読みたい。

1. `report --daily` の既定を、**横軸が日付・縦軸が重み付きトークンの縦向きの積み上げ棒**にする。1日1本（幅は端末幅と日数で決める）。
   モデルの塗り分け・上位いくつか＋「その他」・凡例は設計2 のまま。縦軸に目盛り（丸めた単位）、横軸に日付（間引いてよい）と曜日の目印
   （例: 週の頭）を付ける。高さは 10〜12 行程度
2. 今の横向きの棒は **`--rows`** で残す（人間の選択。1日ごとの合計が数字で並ぶ利点があるため）。`--rows` を `--daily` 以外と
   組み合わせたらエラーにする（設計0 の 7 と同じ扱い）
3. 日数が多くて端末幅に入らないときは、棒の幅を詰め、それでも入らなければ古い日から削って描く（崩さない。削ったことを1行出す）
4. 描画の部品（縦の積み上げ棒・縦軸の目盛り）は、孫7 のダッシュボードが**高さと幅を渡して呼べる関数**として作る
5. `--json` / `--plain` は変えない（同じ数値。描き方だけの変更）
6. ヘルプ文と `bin/README.md` を直す

## 設計7: 一画面のダッシュボード `ocw-meter dash`（孫7）

人間の要望で、ここまでのグラフを一画面で見るコマンドを足す。**個別のビュー（`report --daily` など）はそのまま残す**（人間の確認済み）。

1. 新しいサブコマンド **`ocw-meter dash`**（人間が名前を選んだ。設計0 の 7「新しいビューは `report` のフラグ」の例外で、
   打ちやすさを優先した）。`report` と同じく、先頭で ingest してから描く（`--no-ingest` で飛ばせる。ingest の失敗は fail-open で注記に出す）
2. 一画面に次を縦に並べる: 見出し（今の週の使用率・リセットまでの時間・ingest の鮮度）、週の上限の推移（孫3＋孫5 の直近 N 週の平均の線）、
   日ごとのモデル別の縦棒（孫6）、消費のヒートマップ（孫4。端末幅に入る週数）。各部品は**高さと幅を受け取って描く**ように呼び、
   端末の高さ（`shutil.get_terminal_size()`）に収まるよう高さを配分する。収まらないときは、グラフの高さを詰め、それでも足りなければ
   ヒートマップ → 日ごとの縦棒の順に省き、省いたことを1行出す（崩さない）
3. **`--watch [秒]`**（人間が選んだ）: 既定 300 秒ごとに ingest して描き直す。端末のときだけ画面を消してから描く（ANSI のエスケープで。
   `curses` は使わない）。Ctrl-C で終了コード 0 で抜ける。ingest が間隔より長くかかっても重ねて走らせない（終わってから次を数える）。
   ingest が失敗しても前の集計で描き、注記に出す。端末でないときの `--watch` はエラーにする（ファイルへ延々と書き続けないため）
4. `dash` は人間向けの表示だけを持つ。`--json` / `--plain` は付けない（エラーにする）。機械が読むなら個別の `report` のビューを使う
5. ヘルプ文と `bin/README.md` に足す。`dash` を足した理由（設計0 の 7 の例外）と `--watch` の約束を、表示の方針の ADR
   DOC-2610312031 に追記する

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- 端末でない出力（パイプ・ファイル）と `NO_COLOR` で、出力に色コード（`\x1b[`）が混ざらない
  > **この regression は必ず自動テストで固定する**
- `--plain` の出力が、この傘の前の既定のテキスト出力と変わらない（既存のテキストを確かめるテストに `--plain` を付けて守ればよい）
- `--json` の出力が変わらない（既存テストで守られていればよい）
- 単位の丸め（K / M / B の境目）と桁区切りが正しい
- `--plain` と `--json` の同時指定がエラーになる

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
描画の結果を丸ごと文字列で固定するテストは作らない（計画書「テスト方針」）。

## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

1. PRを作成する。**PRの向き先は必ず `ocw-meter-pretty-charts` にすること。master には絶対に出さない。**
2. `/pr-review-loop` を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** `/pr-review-loop` の手順にマージへ進む記述があっても実行しない
   （孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）
5. 最終報告を書き終えたら、最後の行動として、司令官が spawn の送信文で渡した司令官の Herdr ペインへ
   承認を報告する（渡されていなければ報告せず、人間に「承認済み。マージは司令官（または人間）が行う」と伝えて止まる）。
   送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」に従う。本文は
   「孫1 `omp-01-pretty-default` の PR #<番号> が HEAD <短縮SHA> で承認されました。マージをお願いします。」
   だけにする。報告は1回だけ。送れなくても再送せず、送れなかったことを人間に1行伝えて止まる

なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する（その手順は pr-review-loop 側。使えなければ何もしない）。compact の後は、
復帰メモに従ってレビュー待ちに戻り、この「実装完了後の流れ」を最後まで続けること。
実装の途中でも、検証が通ってコミットした直後の区切りで、文脈が
200,000 トークンを超えていれば `ocw self-compact` で自分を compact してよい（WIP のコミットは
