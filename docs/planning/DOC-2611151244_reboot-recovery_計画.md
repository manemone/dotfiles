# 計画書: Windows の勝手な再起動から作業を自力で復帰させ、外出先から制御する

傘ブランチ: `reboot-recovery`
ターゲット: `master`

## 概要

2026-11-15 の早朝、Windows Update が Windows を勝手に再起動し、WSL は人間がターミナルを開くまで約5時間半
起動しなかった。その間、動いていた Claude の会話（傘の司令官と孫）はすべて止まっていた。人間は時間を区切って
トークンを使い切る運用をしており、止まっている時間はそのまま損失である（背景1・2）。この傘で次の3つを作る。

1. **勝手な再起動を減らす（孫1）。** Windows Update のポリシーが効いているかを確かめるコマンドと、効かせるための
   管理者コマンド（人間が叩く）を用意する
2. **再起動のあと、人間がサインインしなくても WSL と Herdr が立ち上がる（孫1）。** Windows 側の起動の入口を作る
3. **立ち上がったら、中断された会話のうち再開してよいものだけを再開させ（孫2）、外出先のスマホへ知らせ、外から
   状況を見る・再開させる・止める入口を用意する（孫3）**

> **本計画書は、相談の会話から渡された引き継ぎブリーフ（一時ファイル。転記後に削除済みで参照できない前提で書く）を
> material として司令官が起草したものである。** ブリーフに書かれていた問題意識（要約）・決定事項・2026-11-15 の
> 経過・確認済みの現状・関係するリポ・制約・スコープ外・必須の検証ステップ・孫分割の叩き台は本計画書へ転記済みであり、
> 以降はこの計画書が正典である。

## 背景1: 問題意識（要約。PUBLIC リポのため逐語では書かない）

- 人間は、Windows が勝手に再起動して処理が全部止まっていたことに強く怒っている。決めていた時刻までにトークンを
  使い切るつもりだったのに、その前に止まった
- 相談の AI は最初「Windows は再起動していない（WSL だけ）」と誤って報告し、調べ方が足りないと指摘された
- 相談の AI が出した3案（勝手な再起動を止める／ログオン時に WSL と Herdr を起こす／再起動から自分で立ち直って
  作業途中の司令官に続きを送る）を、人間は全部やれと言い、さらに外から制御できるようにもしたいと言った。外出中に
  起きるのが最悪だから、という理由である

## 背景2: 人間が確定させた決定事項（覆さないこと）

- 再起動からの自動復帰と、**外出先から状況を知り・制御できること**の両方をこの傘で扱う
- 人間は「〜時まで」のように時間を区切ってトークンを使い切る運用をしている。止まっている時間はそのまま損失である

## 背景3: 2026-11-15 に起きたこと（Windows のイベントログで確認済み）

ブリーフに書かれていた事実:

- 06:29:25 `User32 1074`: `C:\WINDOWS\uus\AMD64\MoUsoCoreWorker.exe` が SYSTEM として再起動を開始（理由 Service pack、0x80020010）
- 06:32:44 `User32 1074`: `TrustedInstaller.exe` がもう1回再起動（0x80020003）
- 06:33:20 Windows 起動完了。06:35:58 `WindowsUpdateClient 19`: 2026-11 の累積更新 KB5132061（26200.9974）のインストール成功
- **WSL は 11:59:24 まで起動しなかった**（人間がターミナルを開くまで）。約5時間半、すべて止まっていた
- 止まる直前（04:55〜06:15）に動いていた Claude の会話は pixidex の傘 `story-grouping` の司令官と孫3本。作業そのものは
  失われていない（Herdr はワークスペースと会話を戻した。ただし会話は再開の指示が来るまで待つだけ）
- Windows Update のアクティブ時間は `ActiveHoursStart=11`・`ActiveHoursEnd=5`（`HKLM:\SOFTWARE\Microsoft\WindowsUpdate\UX\Settings`）。
  05〜11 時は再起動してよい時間になっていた
- 相談の AI は人間に、管理者 PowerShell で `NoAutoRebootWithLoggedOnUsers=1` を入れる1行を渡した
- **調べるときは時間の幅を広く取ること**（相談の AI が狭い幅で調べて「Windows は再起動していない」と誤った）

## 背景4: 司令官が確かめたこと（2026-11-15、master 415751d、このマシン。読み取りだけ）

`powershell.exe -NoProfile -Command ...` を WSL から叩いて読んだ（書き換えはしていない）。

1. **`NoAutoRebootWithLoggedOnUsers` はまだ入っていない。** `HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU`
   キー自体が無い（人間は相談の AI が渡した1行をまだ叩いていない）。`AUOptions` も無い
2. **再起動の後、11:58:36 まで誰もサインインしていない。** System ログの `Winlogon 7002`（ログオフ通知）が 06:29:32、
   次の `Winlogon 7001`（ログオン通知）が 11:58:36。つまり **「ログオン時に WSL と Herdr を起こす」だけでは今朝の
   ケースは救えない**（サインインが起きないので発火しない）。サインイン無しで起こすか、更新後の自動サインインを
   効かせる必要がある（設計1 の判断ゲート）
3. 更新後の自動サインイン（ARSO。設定の「更新後に自分のサインイン情報を使ってセットアップを自動的に完了する」）の
   ユーザーごとのキー `HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\UserARSO\<SID>` は無く、
   ポリシー `DisableAutomaticRestartSignOn` も無い。既定で効くはずかどうかは未確認（上の2のとおり、今朝は自動サインインが
   起きなかった）
4. エディションは Windows 11 Pro（グループポリシー相当のレジストリが効く）。最終起動は 2026-11-15 06:33:20。
   いま再起動待ち（`HKLM:\SOFTWARE\Microsoft\WindowsUpdate\Auto Update\RebootRequired`）は無い
5. スタートアップフォルダには WSL・Herdr と無関係のショートカットが1つだけ（WSL・Herdr を起こすものは無い）
6. WSL は `systemd=true`（`/etc/wsl.conf`）。WSL の起動ごとに `/proc/sys/kernel/random/boot_id` が変わる。
   WSL は Windows を再起動しなくても `wsl --shutdown` やアイドル停止で落ちうるので、「WSL が落ちた」ことの判定は
   Windows の起動時刻ではなく `boot_id` の変化で取るのが素直（Windows の起動時刻は通知の文面に添える）
7. Herdr 0.9.0 は `herdr server`（ヘッドレスのサーバとして動かす）を持つ。既定設定の `[session] resume_agents_on_restore = true`
   により、サーバの再起動で Claude のペインは元の会話へ戻る（背景3 の「会話は戻ったが待つだけ」と一致）
8. `CronCreate` の巡回は**会話の中にしか無い**（ツールの説明: ディスクに書かれず、Claude が終われば消える。7日で期限切れ）。
   つまり再起動で戻った司令官は、巡回 cron を失ったまま `idle` で止まる。再開の指示には巡回の再登録を含める必要がある
9. `claude/settings.json` には既に `PreToolUse` のフック（`git-guard.sh` など）があり、フックを足す配布の経路はある

## 決定的な制約（孫は全部守ること）

- dotfiles `AGENTS.md` の最重要ルール（`master` を書き換える操作は人間だけ、など）
- **Windows のレジストリ・タスク スケジューラなど管理者権限の変更は人間が叩く。** AI はコマンドと確かめ方を用意し、
  読み取りの確認（`powershell.exe` で読むだけ）は AI が叩いてよい。管理者コマンドを AI が `powershell.exe` 経由で
  実行しない（UAC で止まる・止まらなくても人間の承認を飛ばす）
- **外から制御する経路は、人間のアカウントの外へ秘密を出さない。** 外部サービス（ntfy・Slack・Tailscale 等）を新たに
  足すなら、足す前に人間に確認する。既定の経路は Claude アプリ（Remote Control と `PushNotification`）だけで作る
- **自動で「続けろ」と送る仕組みは、人間の承認待ちで止まっていた会話を勝手に進めない（承認を飛ばさない）。** 何を
  再開してよいかの判定を設計に含める（設計2）
- **WSL や Herdr を落とす試験（`wsl --shutdown`・`herdr server stop`・Windows の再起動）は、このマシンで動いている
  会話を全部止める**（司令官・他の孫・他リポの作業を含む）。孫は自分で叩かず、手順を用意して人間に頼む。いつ叩くかは
  人間が決める
- deploy スクリプトを人間の指示なしに実行しない。配るのは人間（マージ後に `deploy-all.sh`）
- `claude/CLAUDE.md`（配布物）は指示が無い限り編集しない
- **PUBLIC リポ: リポの文書・PR 本文に人間の発言を逐語で書かない（要約する）。** マシン名・アカウント名など個人を
  特定する値も文書に書かない（イベントログを引用するときは伏せる）
- `docs/` 新規は `DOC-DOCID_PLACEHOLDER_<名前>.md` で作り `./tools/doc-id/doc-id assign` で採番。地の文で文書に触れるときは
  DOC-ID を明示
- 新しい `bin/` のツールは `shared/helpers.sh` の `links_for_tool()` の `bin` の arm に足す（足し忘れると `uninstall.sh` /
  `--status` から静かに漏れる。DOC-2610150520-c）

## テスト方針（dotfiles AGENTS.md「テスト方針」と DOC-2610150520-a に従う）

- 孫1 の `bin/rebootctl` は `powershell.exe` と Windows の状態に依存し、自動テストに向かない。pre-commit（shellcheck / shfmt）と
  手での確認でよい。ただし「`setup` は管理者コマンドを表示するだけで実行しない」ことは壊れると危ないので、`powershell.exe` を
  偽物に差し替えて呼ばれないことを確かめる小さなテストを1つ置く価値があるか、孫1 が判断して PR に書く
- 孫2 の判定（どの会話に再開を送るか）は、この傘でいちばん壊れると危ない部分である。**「承認待ち（`blocked`）だった会話に
  再開を送らない」は必ず自動テストで固定する。** 判定は入力（状態の記録・会話ログ）から出力（送る／送らない／人間に回す）を
  返す純粋な関数として切り出し、`bin/tests` の既存の流儀で守る。同じ起動で2回送らないこと（冪等）も同じ scenario で守ってよい
- 孫3 はスキルの本文と `rebootctl boot` への1手順の追加が主で、新しい自動テストは原則要らない

## 設計0: 全孫に共通の方針（司令官が決めた。縛り合う値はここで1つに固定する）

1. **置き場所。** Windows 側の確認・管理者コマンドの提示・起動の入口は `bin/rebootctl`（bash、`#!/usr/bin/env bash`。孫1）。
   再開の判定と送信は `bin/herdr-resume`（Python 3、標準ライブラリだけ。孫2）。管制の会話の振る舞いはスキル
   `skills/control-tower/`（孫3。名前を変えるなら計画書の進行記録に書く）。新しいトップレベルのツールディレクトリ
   （`windows/` など）は作らない。Windows 側に置くもの（タスクの定義など）は `rebootctl setup` が表示するコマンドの中に
   収め、Windows のファイルシステムへ dotfiles から配らない（配る経路が無く、管理者操作は人間が叩くため）
2. **状態の置き場所は1か所。** `${XDG_STATE_HOME:-$HOME/.local/state}/reboot-recovery/`。中身の名前は次で固定する:
   - `sessions/`: 孫2 が会話ごとの状態を記録する場所（形式は孫2 が決める）
   - `last-recovery.json`: 孫2 の `herdr-resume recover` が書き、孫3 の管制の会話が読む報告（形式は孫2 が決め、ADR に書く。
     少なくとも、起動の識別子〈`boot_id`〉・Windows の最終起動時刻・再開を送った会話・送らなかった会話と理由を含む）
   - `boot.log`: 孫1 の `rebootctl boot` の記録
3. **継ぎ目（呼び出しの順番）。**
   - Windows のタスク → `wsl.exe -d <ディストリビューション名> -- ~/bin/rebootctl boot`（細部は孫1 が決める）
   - `rebootctl boot`: (1) Herdr のサーバが動いていなければ起動する (2) Herdr が会話を戻し終えるのを待つ
     (3) `herdr-resume` があれば `herdr-resume recover` を呼ぶ（無ければ飛ばす。孫2 が未マージでも孫1 が動くように）
     (4) 管制の会話を起こす（孫3 が足す）。**何度呼ばれても害が無いこと**（冪等。人間が手で WSL を起こしたあとにも
     安全に叩ける）
   - `herdr-resume recover` は**同じ `boot_id` では1回だけ送る**（2回目以降は報告を返すだけ）
4. **WSL を落とさない。** タスクから起こした WSL は、`wsl.exe` のプロセスが終わるとアイドル停止で落ちうる（未確認。孫1 が
   確かめる）。起こしたあと少なくとも10分経っても WSL と Herdr のサーバが生きていることを、孫1 の受け入れの確認に入れる
5. **費用。** 管制の会話は常駐するので、モデルは Sonnet にする（`claude --model sonnet`）。巡回は1時間おき程度にする

## 設計1: Windows 側の起動と再起動止め（孫1）

### 1.1 勝手な再起動を減らす

- `rebootctl status`（読み取りだけ。AI が叩いてよい）: Windows Update のポリシー（`NoAutoRebootWithLoggedOnUsers`・`AUOptions`
  など）、アクティブ時間、再起動待ちの有無と予定時刻（取れれば）、Windows の最終起動時刻、起動の入口（タスク）の登録の有無、
  WSL 側の Herdr サーバの生死を、人が読める形と `--json` で出す。孫3 の巡回がこの `--json` を読む
- `rebootctl setup`: 人間が管理者 PowerShell に貼る管理者コマンドを**表示するだけ**（実行しない）。各コマンドの後に、
  効いたかを確かめる読み取りのコマンド（または `rebootctl status`）を添える
- **どの設定が今の Windows 11（26200 系、Update Orchestrator）で本当に効くかを、公式の文書で調べてから選ぶ。**
  `NoAutoRebootWithLoggedOnUsers` は「ログオン中は自動で再起動しない」ポリシーだが、自動更新の構成（`AUOptions` など）と
  組で効くとされる情報があり、単独で効くかは未確認。アクティブ時間は最大18時間で、今は 11〜5 時の18時間いっぱいなので、
  アクティブ時間だけでは6時間の穴が必ず残る。調べた結果（効く設定・効かない設定・出典）を ADR に書く
- サインインしたまま放置していれば再起動しない、を最初の防壁にし、それでも再起動したとき（セキュリティ更新の期限切れ等）に
  備えて 1.2・設計2・設計3 がある、という二段構えにする

### 1.2 サインイン無しで WSL と Herdr を起こす（判断ゲート: 人間が方式を選ぶ）

背景4 の2のとおり、今朝はサインインが起きなかったので、ログオン時のタスクだけでは救えない。候補:

- **A. 起動時のタスク（サインイン不要）。** タスク スケジューラで「ユーザーがログオンしているかどうかにかかわらず実行」。
  パスワードを保存するか S4U で登録する（管理者操作）。**WSL がサインイン無しのセッションで起動できるか、Herdr と Claude が
  そこで普通に動くか（認証・ネットワーク・Remote Control）は未確認**で、実験が要る
- **B. ログオン時のタスク＋更新後の自動サインイン（ARSO）。** タスクは管理者無しで登録できる可能性がある。ARSO が更新の
  再起動で確実に効くかは未確認（今朝は効かなかった）。ARSO は BitLocker 等の条件に左右されるとされる
- **C. 自動ログオン（Sysinternals Autologon 等）＋ログオン時のタスク。** 確実に近いが、パスワードがマシンに保存され、
  物理的に触れる人がサインインできる。安全とのトレードオフを人間が決める

**司令官の推奨は A（動くなら最も素直で、秘密をマシンの外へ出さない）、駄目なら B。** 孫1 は各方式の条件を調べ、A の実験の
手順（管理者操作・WSL を落とす操作は人間が叩く。決定的な制約）を用意し、結果を添えて人間に方式を選んでもらう。人間の
選択と理由は ADR と計画書の進行記録に書く。選んだ方式のタスクの登録コマンドは `rebootctl setup` に入れる。

- 試験の作法: 本物の再起動の前に「タスクを手で走らせる（`schtasks /run` 相当）」「`wsl --shutdown` してからタスクを走らせる」で
  確かめられる範囲を確かめる。どちらも動いている会話を全部止めるので、人間が叩く時刻を決める。本物の再起動の試験は
  全孫のマージと配布の後の宿題（必須の検証ステップ）でよい
- 起動の入口から呼ぶのは `~/bin/rebootctl`（配布されたもの）。マージ前の実験で孫のワークツリーのスクリプトを指すときは、
  実験の後にタスクを消す手順も添える

## 設計2: 再開の判定と送信（孫2）

### 2.1 会話ごとの状態を、落ちる直前まで記録する

Herdr の `agent_status`（`idle` / `working` / `blocked` / `done`）は再起動で失われる。再開の判定には「落ちる直前に何をしていたか」が
要るので、会話ごとの状態を設計0 の 2 の `sessions/` に書き続ける。方式の候補（孫2 が調べて選び、ADR に書く）:

- **a. Claude Code のフック（司令官の推奨）。** プロンプトを受けた（`UserPromptSubmit`）→作業中、ターンを終えた（`Stop`）→待機、
  承認や質問の画面を出した（`Notification` の承認待ち・`AskUserQuestion`）→承認待ち、`CronCreate` / `CronDelete` を呼んだ→巡回の
  有無、を会話の ID ごとに書く。落ちた瞬間の状態が正確に残る。**フックは速く、失敗しても会話を止めないこと**（例外を握りつぶして
  0 で終わる）。`claude/settings.json` と `claude/hooks/` に足す
- **b. 定期的な Herdr のスナップショット。** `herdr pane list` を数分おきに記録する。記録の間隔ぶん古くなり、定期実行の仕組み
  （systemd の user timer など）の配布が新たに要る

### 2.2 何を再開してよいか（司令官が決めた判定。変えるなら人間に確かめる）

再起動で戻った Claude の会話（Herdr のペインの `agent_session` から引く）ごとに、落ちる直前の状態で判定する:

| 落ちる直前の状態 | 判定 | 送る内容 |
|---|---|---|
| 作業中（ターンの途中で落ちた） | **再開を送る** | 再開の文（下） |
| 待機中で、有効な巡回 cron があった（作って消しておらず、7日以内） | **再開を送る** | 巡回の再登録を促す文（下） |
| 承認待ち・質問待ち（`blocked` 相当） | **送らない** | —（報告に「人間の承認待ちだった」と載せる） |
| 待機中で巡回 cron も無い（人間の返答待ち・完了） | **送らない** | — |
| 状態の記録が無い・古すぎて当てにならない・Claude 以外のエージェント | **送らない** | —（報告に「判定できない。人間が見る」と載せる） |

- 迷ったら送らない側に倒す。送らなかった会話は報告に理由つきで載り、管制の会話（孫3）経由で人間が外から再開できる
- 再開の文は固定文にする。最低限含めること: Windows（または WSL）の再起動で中断されたこと、**落ちる直前の操作（push・
  PR 作成・マージなど）が完了したかを確かめてから続けること**、`CronCreate` の巡回は再起動で消えているので、登録していたなら
  計画書・復帰メモの手順で再登録すること、人間の承認が要る操作は承認を待つこと。「〜とだけ返事して」のようなメタ指示は付けない
- 送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」のフォールバック（`herdr agent prompt`）の作法に従う
  （`timeout` / `stalled` で再送しない。`agent_blocked` なら送らず報告に載せる）
- **同じ `boot_id` では1回だけ送る**（設計0 の 3）。報告ファイル `last-recovery.json` を書く
- `herdr-resume plan`（送らずに判定だけ出す）を用意し、人間と管制の会話が中身を確かめられるようにする

## 設計3: 管制の会話と外からの制御（孫3）

- **管制の会話**: Herdr に常駐する Claude の会話を1つ立てる（`rebootctl boot` の手順4。既に立っていれば何もしない）。会話名は
  Claude アプリの一覧で一目で分かる日本語の名前にする（ADR DOC-2610111939 の `--name` の流儀）。モデルは Sonnet
- **起動時**: `last-recovery.json` を読み、`PushNotification` でスマホへ「再起動から戻った。再開N件・要確認M件（承認待ちだった
  会話の名前）」を1回知らせる。`agentPushNotifEnabled` が有効なので Remote Control 経由でスマホへ届く（届くことを実機で確かめる）
- **再起動の予告**: 1時間おき程度の巡回（`CronCreate`）で `rebootctl status --json` を読み、再起動待ちが新たに現れたら予定時刻つきで
  知らせる（同じ予告を毎回は知らせない）。巡回はこの会話の中にしか無いので、会話が立ち上がるたびに登録する（スキルの手順に書く）
- **外からの制御**: 人間はスマホの Claude アプリでこの会話を開き、「状況は」「〜を再開して」「〜を止めて」と頼む。管制の会話は
  `herdr` と `herdr-resume plan` で状況を答え、再開は設計2 の送り方で、止めるのは対象の会話の今のターンを中断する形
  （Herdr のキー送信など。プロセスを殺す・ワークツリーを消すような破壊的な操作はしない）で行う。どの操作も Claude Code の
  権限の確認を飛ばさない（承認はスマホから Remote Control で返せる）
- **一覧に出ること**: 再起動で戻った会話が Claude アプリの Remote Control の一覧に出るか（`remoteControlAtStartup`）を実機で確かめ、
  出なければ原因と対処を ADR に書く
- **スキルの中身**: `skills/control-tower/SKILL.md` に、起動時の手順・巡回の登録・外からの依頼の受け方・やらないこと（破壊的操作・
  承認の代行・外部サービスへの送信）を書く。スキルの配布は `skills/deploy.sh`（`skill_links()`）の既存の経路に乗る

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- `rebootctl setup` は管理者コマンドを表示するだけで、`powershell.exe` 経由で何も書き換えない
- `rebootctl boot` は何度呼んでも害が無い（Herdr のサーバを二重に起動しない）。`herdr-resume` が無くても止まらない
- `rebootctl status` は Windows 側を読めないとき（`powershell.exe` が無い・失敗する）にも落ちず、読めなかったことを出す
- 新しい `bin/` のツールが `uninstall.sh` / `--status` から漏れない（`links_for_tool()`）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
Windows の実機の確認は手で行い、確かめた範囲を PR 本文に書く。

3. レビュー指摘があれば修正し、承認されるまで繰り返す

   （渡されていなければ報告せず、人間に「承認済み。マージは司令官（または人間）が行う」と伝えて止まる）。
   送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」に従う。本文は

   だけにする（「〜とだけ返事して」のような指示は付けない）。報告は1回だけ。送れなくても

メモには書かない）、先頭に「計画書の続きから実装を再開する。レビュー待ちではない」と書く。コマンドを実行したらそのターンを終える。

## 大きい出力を文脈へ流し込まない（実装中ずっと）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し直して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）

## やること

1. 会話ごとの状態を落ちる直前まで記録する方式を選ぶ（計画書 設計2 の 2.1。司令官の推奨は Claude Code のフック）。

2. `bin/herdr-resume`（Python 3、標準ライブラリだけ）を作る: `plan`（判定だけ出す）・`recover`（判定して送り、
   `last-recovery.json` を書く。同じ `boot_id` では1回だけ送る）。状態の置き場所は設計0 の 2 に従う。判定は計画書 設計2 の 2.2 の
   表のとおりにし、入力から出力を返す純粋な関数として切り出す。`shared/helpers.sh` の `links_for_tool()` の `bin` の arm に足す
3. 再開の文を固定文で書く（設計2 の 2.2 の「最低限含めること」）
4. 手で確かめる: Herdr の上で使い捨ての Claude の会話を作り、作業中・承認待ち・待機中の状態を作って `plan` の判定を見る。
   **`wsl --shutdown` や `herdr server stop` は自分で叩かない**（このマシンの会話が全部止まる）。落ちた後の状況は、記録の
   ファイルと `boot_id` を偽物に差し替えて模す。本物の再起動での確認は傘の宿題でよい
5. `bin/README.md` に `herdr-resume` の節を足す
6. ADR を `docs/adr/` に足す（`DOC-DOCID_PLACEHOLDER_<名前>.md` で作って `./tools/doc-id/doc-id assign <path>`）。書くこと: 記録の
   方式の比較と選んだ理由、判定の表と「迷ったら送らない」の理由、`last-recovery.json` の形式（孫3 が読む）、確かめた範囲と未確認の範囲
7. deploy はしない（配るのは人間）。PR 本文に「マージ後に人間が `deploy-all.sh` で配ると効く」と書く。フックを足した場合は
   すべての Claude の会話に効くことを PR 本文に明記する

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- 承認待ち・質問待ちだった会話には再開を送らない
  > **この regression は必ず自動テストで固定する**
- 作業中だった会話と、巡回 cron が有効だった待機中の会話には送り、巡回の無い待機中の会話・記録の無い会話には送らない
- 同じ `boot_id` で `recover` を2回呼んでも、2回目は送らない
- フックが失敗しても（書き込めない・入力が壊れている）会話を止めない
- 新しい `bin/` のツールが `uninstall.sh` / `--status` から漏れない（`links_for_tool()`）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
テストは `bin/tests` の既存の流儀（unittest）に合わせる。

済んだこと（コミットの一覧）・作業中に下した判断とその理由・残り・次の一手・検証コマンドを書き（増分の起点は復帰後に測るので

## 大きい出力を文脈へ流し込まない（実装中ずっと）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し直して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）
