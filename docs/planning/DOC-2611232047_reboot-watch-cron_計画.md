# 計画書: 再起動の予告の巡回を、管制の会話の CronCreate から OS の cron へ移す

傘ブランチ: `reboot-watch-cron`
ターゲット: `master`

## 概要

管制の会話（`control-tower` スキル。ADR DOC-2611151326）は、Windows が再起動待ちかどうかを、会話の中の `CronCreate` で
1時間おきに確かめている。再起動待ちはごく稀なのに、巡回のたびにモデルが1往復し、「変化なし」と答えるだけの往復が会話に溜まって
トークンを使い、人間には読む価値の無い記録になる。巡回は会話の中にしか無く、会話の再起動・終了で消え、期限切れもある。

この傘では、巡回を OS の cron（WSL の `crontab`）へ移す。普段は `rebootctl status --json` を読むだけでモデルを呼ばず、
再起動待ちを見つけたときだけ `claude -p` を呼んで、Claude の通知（`PushNotification`）でスマホへ知らせる。
管制の会話に残る役割は、起動時の1回の通知と、外（スマホの Claude アプリ）からの依頼の受け付けになる。

**方針全体の前提が1つ未確認である:** 非対話の `claude -p`（cron の下・端末なし）から `PushNotification` が実際にスマホへ
届くか。`PushNotification` のツールの説明には「Remote Control がつながっていればスマホへも送る」とあり、`claude -p` では
つながっていない可能性がある。孫1 は最初にこれを実機で確かめ、成り立たなければ実装に進まず、人間に代案を選んでもらう。

## 背景1: 問題意識（要約。PUBLIC リポのため逐語では書かない）

- 巡回のたびにモデルを1往復させるのは、通知が要る場面の稀さに対して費用が見合わない（2026-11-23 時点まで、巡回は一度も通知を
  出していない）
- 巡回の返事が常駐の会話に溜まり、人間がその会話を開いたときのノイズになる
- 巡回は会話の中にしか無いので、会話の再起動・終了で消え、期限が来ると切れる

## 背景2: 人間が確定させた決定事項（覆さないこと）

- 巡回は会話の `CronCreate` から外し、OS の cron（`crontab`）に移す
- 再起動待ちでないときは、モデルを一切呼ばない（トークンを使わない）
- 再起動待ちのときだけ `claude -p` を使って通知する。別の経路を足さず、`claude -p` の方向で進める
  - **2026-11-23 に置き換わった（進行記録）:** `claude -p` からはスマホへ届かないと孫1 が実機で確かめ、人間の判断で「cron が管制の会話へ
    1文を送り、Remote Control がつながった管制の会話が通知する」案になった。平常時にモデルを呼ばない点は変わらない
- 通知は Claude の通知機構だけを使う（`control-tower` スキル §4 のとおり、ntfy・Slack・メールなどの外部サービスへ送らない）
- 同じ予告は繰り返さない（`control-tower.json` の `announced_reboot_for` の考え方を引き継ぐ）

## 背景3: 2026-11-23 時点の実測値

- `rebootctl status --json` は `reboot_required: false`、`windows_last_boot` は 2026-11-21T23:07:45+09:00
- WSL の中で cron が動いている（`cron -f` が起動済み）。人間の crontab には既存の毎分の項目が1つある（孫は消さない・書き換えない）
- `claude`・`jq`・`rebootctl` はシェルの PATH 上にある（cron の PATH は別。孫が確かめる）
- **期限の食い違い（司令官が確かめた）:** `control-tower` スキル §2 と `bin/herdr-resume` の `CRON_MAX_AGE`（と、それを流用した
  `IDLE_MAX_AGE`）は、`CronCreate` の巡回が「7日で期限切れ」という前提で書かれている。2026-11-23 時点の `CronCreate` のツールの説明は
  「繰り返しの巡回は30日で期限切れ（最後に1回発火して消える）」。
- **`CRON_TEXT` の行き先（司令官が確かめた）:** `bin/herdr-resume` は管制のワークスペース（ラベル `管制`）を `control_tower` として
  送信の対象から外している。`CRON_TEXT`（巡回の再登録を促す文）は、管制ではなく、`CronCreate` の巡回を持っていたほかの会話
  （傘の司令官など）へ送られる。管制の巡回を cron へ移しても、`CRON_TEXT` の宛先と役目は変わらない見込み（孫1 が確かめる）

## 背景4: 既存の穴

- `skills/control-tower/SKILL.md` の frontmatter の description、§1 手順5（巡回の登録）、§2（巡回の手順）が、会話内の `CronCreate` を
  前提にしている。cron へ移すと書き換えが要る。§3 の「再開して」が `CRON_TEXT` に触れている箇所は、上のとおり宛先が別の会話なので
  文意は変わらない見込み
- ADR DOC-2611151326 §3 は「巡回の間隔: 1時間おき（`CronCreate`）」と決めている。決定が変わるので記録が要る
- cron は WSL が動いているときしか動かない。WSL の停止中・Windows の再起動中は回らない。「再起動の前に人間へ知らせる」という目的に
  対して、cron の起動条件と間隔で足りるかを判断して記録する（WSL が止まっているあいだは止まる会話も無いので、予告の意味も薄い、
  という見立てを含めて確かめる）
- 管制の会話から巡回が無くなると、管制は起動時の1回の通知と外からの依頼だけになる。会話のモデルや常駐のさせ方まで変えるかは、
  この傘では扱わない（スコープ外）

## 背景5: 叩き台の資産（リポの外・未コミット・未検証）

引き継ぎ元の会話が、相談中に `~/.local/bin/reboot-watch`（bash）を作ってしまっている。中身は次の流れ:

1. `$HOME/bin/rebootctl status --json` を読む。失敗・`windows_readable` が真でなければ何もしない
2. `reboot_required` が真でなければ、`control-tower.json` から `announced_reboot_for` を消して終わる
3. `announced_reboot_for` が今の `windows_last_boot` と同じなら終わる（同じ予告を繰り返さない）
4. `claude -p --model haiku --allowedTools PushNotification "<固定の1文を PushNotification で送って終わる>"` を呼び、
   成功したら `announced_reboot_for` に今の `windows_last_boot` を書く（`jq` で一時ファイルに書いて `mv`）

**実行も crontab への登録もしていない。** 孫1 は流れの参考にしてよいが、これを実行・登録・削除しない。リポの中へ作り直したあと、
このファイルを消すかは司令官が人間に確かめる（傘の最終 PR の前）。引き継ぎ元が会話内に登録していた巡回（`CronCreate`）は削除済み。

## 決定的な制約（孫は全部守ること）

- dotfiles `AGENTS.md` の最重要ルール（`master` を書き換える操作は人間だけ、deploy スクリプトを人間の指示なしに実行しない、など）
- `control-tower` スキル §4（破壊的操作・承認の代行・外部サービスへの送信をしない）。通知は `PushNotification`（Claude アプリ）だけ。
  cron からは直接呼べないので `claude -p` を経由する
- **人間の crontab は、既存の項目を消さない・書き換えない。** 実機確認のために一時的な項目を足すなら、足す前に `crontab -l` の控えを
  リポの外の一時ファイルに取り、確認が済んだら一時的な項目だけを外し、控えと同じ中身に戻ったことを確かめる
- **恒久の crontab への登録はこの孫ではしない。** `$HOME/bin/rebootctl` などは配布実体（`current`）を指しており、マージと人間の
  `deploy-all.sh` のあとでしか新しい版にならない。恒久の登録は、人間がマージと配布のあとで行う（登録の1行と確かめ方を README と
  PR 本文に書く）。deploy スクリプトに crontab を書き換えさせる形は、`links_for_tool()` / `uninstall.sh` で追えない状態を
  `$HOME` の外に作るので、採るなら実装する前に司令官経由で人間の判断を仰ぐ
- **実機確認でスマホへ届く通知は、試験だと分かる文面にして、回数を最小にする。** 届いたかは人間にしか分からないので、送ったら
  人間に確かめる（AskUserQuestion）
- 実機確認で本物の `$ST/control-tower.json`（`${XDG_STATE_HOME:-$HOME/.local/state}/reboot-recovery/`）を書き換えない。
  `XDG_STATE_HOME` の差し替えや偽の `rebootctl status` を使う
- `claude/CLAUDE.md`（配布物）は指示が無い限り編集しない
- **PUBLIC リポ: リポの文書・PR 本文・コミットに人間の発言の逐語を書かない。** マシン名・アカウント名も書かない
- `docs/` 新規は `DOC-DOCID_PLACEHOLDER_<名前>.md` で作り `./tools/doc-id/doc-id assign` で採番。地の文で文書に触れるときは DOC-ID を明示

## テスト方針（dotfiles AGENTS.md「テスト方針」と DOC-2610150520-a に従う）

- 守る挙動: 再起動待ちでないときはモデル（`claude`）を呼ばない。同じ `windows_last_boot` への予告は1回だけ。再起動待ちが解けたら
  印を消す。`rebootctl status` が失敗・読めないときは何もしない（印も触らない）
- `bin/tests/test_rebootctl.py` の既存の偽物の差し替え（偽の `powershell.exe` など）の流儀に合わせ、偽の `claude` を PATH に置いて
  呼ばれた回数を数える形で守れるなら守る。新しいテストの数は DOC-2610150520-a の基準で孫が判断する
- `PushNotification` がスマホへ届くかは自動テストに向かない。実機で確かめる

## やること

1. **前提の実機確認（ここが成り立たなければ実装に進まない）。** 次を順に確かめる。どれも通知の文面は試験だと分かるものにし、
   スマホに届いたかは送るたびに人間に確かめる（AskUserQuestion）:
   - (a) 対話のシェルから `claude -p --allowedTools PushNotification "<試験の1文を PushNotification で送って終わる>"` を叩き、
     `PushNotification` が `claude -p` で使えるか（ツールが無い・「送らなかった」と返る、を含めて出力を見る）と、スマホに届くか
   - (b) cron の下から同じことをする。`crontab -l` の控えを取ってから、数分後に1回だけ走る一時的な項目を足し、出力を
     リポの外の一時ファイルへ書き出させる。cron の最小の PATH で `claude` を見つけられるか（絶対パスが要るか）、認証が通るか、
     スマホに届くかを見る。済んだら一時的な項目を外し、`crontab -l` が控えと同じに戻ったことを確かめる
   - **届かなかったら、ここで止まる。** 実装もコミットもせず、何を試して何が起きたかをまとめ、人間に代案を見せて選んでもらう
     （AskUserQuestion）。代案の例: Windows のトースト通知、状態ファイルに書いて管制の会話が次に開かれたときに読む、`claude -p`
     から管制の会話へ伝えて管制が通知する。例は例であって、ほかの案を足してよい。各案に、モデルを呼ぶ回数（費用）・
     外部サービスへ送らない制約との関係・確かめた範囲を添える。人間の選択を司令官のペインへ1回報告し、選ばれた案で続ける
     （計画の前提が変わる案なら、司令官の返事を待つ）
2. **予告の巡回を cron で回す仕組みを作る。** 置き場所は、`bin/rebootctl` のサブコマンド（例: `rebootctl watch`）にするのを推す
   （配布のリンク・`links_for_tool()` を足さずに済み、`status --json` の読み取りと `test_rebootctl.py` の偽物をそのまま使える）。
   別のスクリプトにするほうがよい理由があれば、そちらでもよい（その場合は `bin/deploy.sh` と `shared/helpers.sh` の
   `links_for_tool()` にも足す）。流れは計画書の背景5 の叩き台と同じ。次を満たす:
   - 再起動待ちでないとき・`status` が失敗したとき・Windows が読めないときは `claude` を呼ばない
   - 同じ `windows_last_boot` への予告は1回だけ（`announced_reboot_for`）。再起動待ちが解けたら印を消す。`control-tower.json` の
     ほかの鍵（`notified_boot_id` など）は残す
   - cron の下で動く: `claude` を見つける方法（絶対パスか PATH の設定）、`claude -p` が固まったときの打ち切り（`timeout` など）、
     失敗の記録の残し方（既存の `$ST/boot.log` の流儀に合わせるか、別のログか）を決める
   - 通知の文面は今の §2 の手順3 と同じ趣旨（再起動待ちであること・予定時刻は `status` から分からないこと）
   - `claude -p` に使わせるツールは `PushNotification` だけに絞る。モデルは軽いものでよい（今の管制は Sonnet。理由を ADR に書く）
3. **crontab への登録の手順を用意する。** 恒久の登録はこの孫ではしない（計画書「決定的な制約」）。登録の1行（間隔は1時間おき、
   分は 0 を避ける。`$HOME/bin/rebootctl` など配布されたパスを使う）と、登録されたことの確かめ方を `bin/README.md` に書く。
   `rebootctl setup` の表示に足すほうが自然ならそちらでもよい（`setup` は表示だけで何も実行しない、という既存の約束を守る）
4. **`control-tower` スキルを書き換える。** frontmatter の description、§1 手順5、§2 を、巡回が会話の外（cron）にある形に直す。
   管制の会話は巡回を登録しない。§2 には、巡回が cron で回ること・何を読むか・いつ通知するか・印の扱いを、管制の会話が知って
   おくべき範囲で書く（管制が「状況は」と聞かれたときに巡回の有無を確かめる方法があれば添える）。§1 手順1〜4 と §3 は変えない
5. **`bin/herdr-resume` を確かめる。** `CRON_TEXT` の宛先が管制でないこと（計画書 背景3）を確かめ、文意が変わらなければ触らない。
   `CRON_MAX_AGE` の「7日」は `CronCreate` の今の期限（30日）と食い違っている。同じ値を `IDLE_MAX_AGE` が流用しているので、
   直すなら両方の意味を確かめたうえで直し、既存のテストを合わせる（直さないと判断したら、理由を PR 本文に書く）
6. **ADR を書く。** 巡回を会話の `CronCreate` から OS の cron へ移した決定（理由: 背景1）、手順1 の実機確認の結果、cron は WSL が
   動いているときしか回らないことの扱い（予告の目的に足りるかの判断）、`rebootctl status` を1時間おきに呼ぶ重さ（実測した所要時間）、
   7日と30日の食い違いを記録する。新しい ADR を立て、ADR DOC-2611151326 §3 の「巡回の間隔」から辿れるようにする
   （どちらが読みやすいかは `docs/README.md` の流儀に合わせて判断してよい）
7. deploy はしない（配るのは人間）。PR 本文に、マージ後に人間がやること（`deploy-all.sh` で配る → crontab に1行を登録する →
   次に再起動待ちになったときスマホに1回届くのを確かめる）を書く。`~/.local/bin/reboot-watch`（叩き台）は消さない（司令官が人間に聞く）

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって
保護されていること。

- 再起動待ちでないとき（`status` が失敗・Windows が読めないときを含む）は `claude` を呼ばない。
  **この regression は必ず自動テストで固定する**（モデルを呼ばないことがこの傘の目的そのもの）
- 同じ `windows_last_boot` への予告は1回だけで、再起動待ちが解けたら印が消え、次の再起動待ちでまた1回知らせる
- `claude -p` が失敗したときは印を書かない（次の巡回でまた試す）。`control-tower.json` のほかの鍵を壊さない
- `rebootctl setup` は表示だけで何も実行しない（既存の保護を壊さない）

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
スマホへ届くかと cron の下で動くかは実機で確かめ、確かめた範囲を ADR と PR 本文に書く。

## PR作成時の注意

PR を作る前に `docs/design/DOC-2608020715_プルリクエストの作法.md` を読むこと。
人間の発言を逐語で書かない（PUBLIC リポ。要約する）。マシン名・アカウント名を書かない。

## 大きい出力を文脈へ流し込まない（実装中ずっと）
文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し修正して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）

## リポジトリに書かないもの
人間（持ち主）の発言そのものを、PR の本文・コミットメッセージ・文書・コードのコメントに書かない
（計画書や送信文にあっても写さない）。何への対応かを自分の言葉で書く。
非公開のリポジトリの名前・ホスト名も書かない。書き直すときは、人間が挙げた例を要件として言い切らない・
誰の判断や提案かを落とさない・意味に要らない固有名詞を残さない。

## 実装完了後の流れ（必須）
実装が完了したら、以下を**自律的に**実行してください:
1. PRを作成する。**PRの向き先は必ず `reboot-watch-cron` にすること。master には絶対に出さない。**
2. /pr-review-loop を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** `/pr-review-loop` の手順にマージへ進む記述があっても
   実行しない（孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）
5. （Herdr あり・司令官が宛先を埋め込んだときだけ）最終報告を書き終えたら、最後の行動として
   司令官へ承認を報告する。宛先は、司令官が spawn の送信文で渡した司令官の Herdr ペイン
   （渡されていなければ報告せず、人間に「承認済み。マージは司令官（または人間）が行う」と伝えて止まる）。
   送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」に従う。本文は
   「孫1 `rw-01-cron-watch` の PR #<番号> が HEAD <短縮SHA> で承認されました。マージをお願いします。」
   だけにする（「〜とだけ返事して」のような指示は付けない）。報告は1回だけ。送れなくても
   再送せず（司令官の巡回が拾う）、送れなかったことを人間に1行伝えて止まる
なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する（その手順は pr-review-loop 側。使えなければ何もしない）。compact の後は、
復帰メモに従ってレビュー待ちに戻り、この「実装完了後の流れ」を最後まで続けること
実装の途中でも、検証が通ってコミットした直後の区切りで、文脈が
150,000 トークン（claude-ds 以外の Claude は 200,000。`ANTHROPIC_BASE_URL` に `deepseek` を含むかで見分ける）を超えていれば `ocw self-compact` で自分を compact してよい（WIP のコミットは
区切りでない。指摘対応の修正の途中は対象外。回数の上限は無いが、前回の compact から文脈が
100,000 以上増えていなければ見送る。ADR DOC-2610142337・DOC-2611032102）。
測り方は `/pr-review-loop` の「区切りでの自己 compact（実装側のみ）」の手順1のコマンドと同じ（その節の (3) の項だけを読めばよい。手順の「Phase 3 へ進む」は実装途中には当てはまらない）。復帰メモ
（リポの外の一時ファイル）には、計画書のパスと孫の節・済んだこと（コミットの一覧）・作業中に下した
判断とその理由・残り・次の一手・検証コマンドを書き（増分の起点は復帰後に測るのでメモには書かない）、先頭に「計画書の
続きから実装を再開する。レビュー待ちではない」と書く。コマンドを実行したらそのターンを終える。
使えない・拒否・失敗なら何もせず実装を続ける（人間に提案もしない）
実装が終わったタイミングで止まらず、必ずここまでやりきってください。
reviewerはdone状態で完了し完了通知は来ないので、待機して停止せず gh pr view をポーリングして
レビューの有無を確認してください。
