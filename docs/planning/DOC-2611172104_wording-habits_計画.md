# 計画書: AI の言葉の悪癖を、仕組みで抑える方法を調査して導入する

傘ブランチ: `wording-habits`
ターゲット: `master`

## 概要

AI（主に Claude Code）の会話の言葉に、持ち主が何十回も指摘しても直らない悪癖が2つある（背景2）。
1つは「ふだん漢語・カタカナ語で言う物事を、わざわざ和語に開いて言い換える」こと、もう1つは
「その場面での判断が悪いと言われたのを、全面禁止に広げて宣言する」ことである。
メモリへの記録・指示文の追記では直らなかった（背景4）。

この傘では、まず悪癖を**計測する方法**と、**仕組みで抑える方法**（hooks・指示の置き場・出力スタイルなど）を調査し、
その結果を持ち主が判断したうえで、選ばれた仕組みを dotfiles の配布物として導入する。

## 背景1: 問題意識（要約。PUBLIC リポのため逐語では書かない）

2026-11-17、別リポの傘の司令官（Claude Code）との会話で、持ち主が強い不快感とともに次を指摘した。

- 「確認」で済むところを「確かめ」、「修正」を「直し」と言うような、無理に和語に開いた言い換えをやめろ。
  何十回も言っているのに直らない。言い換えのせいで AI の言うことの理解が遠回りになり、認知負荷が高い。
  結果として持ち主側の指示まで曖昧になることがある
- ただし「引く」「探す」「立てる・止める」「回す」のような和語は普通に通じる。司令官がそれらまで避ける語に
  入れたことに対し、この境界の感覚が無いと指摘した
- 「この状況ではそのやり方が不適切」と言っただけなのに、AI は「今後一切しません」と全面禁止に広げて宣言する。
  ある判断が拙いという指摘は、以後それをやるなという意味ではない。全面禁止として言質を取るのは
  責任回避の逃げに見え、信用をなくす。これも何十回も指摘している
  - 例え話: 豆腐を賽の目に切る作業で、ハサミを使って時間がかかり角も崩れたのを叱ったら、AI が
    「今後ハサミは二度と使いません。袋を開けているほかの担当にも伝えます」と返した。これがどれだけ
    おかしいかが、持ち主の言う悪癖2 である
- 中の部品の名前（「焼いた指示書」のような、プロンプトを指す造語）を説明なしに持ち主向けの説明に使うな
- 司令官が `~/.claude/CLAUDE.md` を直接編集したことに対し、dotfiles の手順を読めと叱った
- こうした悪癖を抑える仕組みが無いかの調査も含めて、作業の入口（task-intake）に回せと指示した

## 背景2: 悪癖の中身（ブリーフより転記。背景1 と合わせて読むこと）

1. **漢語を無理に和語に開く**: ふだん漢語・カタカナ語で言う物事を、わざわざ和語に開いた言い換えにする。
   会話で実際に出た例: 確認→「確かめ」、修正→「直し」、計測→「測り」、原因の切り分け・内訳→「割る」「割り出し」、
   キャッシュ→「控え」、コピー→「写し」。中の部品の名前（「焼いた指示書」など）を説明なしに持ち主向けの説明に
   使うのも同じ系統（持ち主には造語に見える）。
   - **境界**: 「引く」「探す」「立てる・止める」「回す」のように普通に通じる和語は問題ない。
     つまり「和語を全部避ける」は外れで、「ふだん漢語で言うものをわざわざ開く」だけが悪い。
     **機械的な禁止語リストは、この境界を誤ると逆効果になる**
2. **状況への指摘を全面禁止に広げる**: 「この場面でのその判断が悪い」と言われると、「もう一切しません」
   「入れません」と言い換え、メモ・ほかの会話への指示にまで書いて広げる。持ち主はこれを、言質を取って判断を
   押し付ける逃げ・責任回避と見ている
   - これは言葉の点検だけでは抑えにくい（言葉ではなく判断の癖）。どう扱うかも調査する

- 「引く・探す・立てる・止める・回す」は使ってよい言葉

## 決定的な制約（孫は全部守ること）

- dotfiles の `AGENTS.md` の最重要ルール: `claude/CLAUDE.md` は配布物で、指示が無い限り編集しない
  （この傘では、孫2 で持ち主が選んだ案がそれを求める場合に限り、その範囲で編集してよい）。
  `CLAUDE.machine.md` は機械ごとの人格の置き場で、リポの外の固定パスにある。どちらも**配布先の実ファイル
  （`~/.claude/` 配下）を直接触らない**
- **deploy しない**（`deploy-all.sh` も個別の `deploy.sh` も実 `$HOME` に対して実行しない。配るのは人間）。
  `~/.claude/settings.json` などの実 `$HOME` の設定ファイルも書き換えない。hooks の試験は、合成した入力の JSON を
  hook のスクリプトへ直接渡すか、一時ディレクトリの設定ファイル（`claude --settings <一時ファイル>`）で行う
- 持ち主は、**規則を作って判断を丸投げすること**を責任逃れとして嫌う。仕組みも「禁止語で機械的に止める」
  だけにすると、背景2 の境界を誤って逆に不快にさせうる。調査・導入とも、この点を正面から扱う
- 背景3 の「使ってよい言葉」を禁止・警告の対象に入れない
- **この傘の文書・コード・PR 本文自体が、悪癖の見本にならないこと**: 「確認」「修正」「計測」など普通の漢語で書き、
  和語に開いた言い換えや説明の無い造語を使わない。「今後一切〜しない」のような全面禁止の言い回しで規則を書かない
  （規則を書くときは、どの状況で何が悪いかを書く）
- **公開リポ**: 人間の発言を逐語で書かない（要約する）。会話ログ（transcript）の本文を文書・コミット・PR に貼らない。
  計測結果は件数・割合などの集計値と、背景2 に既に出ている語だけで書く。他リポの名前・中身も持ち込まない
  （「製品リポ」「別リポの傘」と呼ぶ）
- スキル・指示文は AI 不問の自然言語（YAML frontmatter を除く。ADR DOC-2608272128）。Claude Code 固有の仕組み
  （hooks・出力スタイル）を入れる場合は、Codex・OpenCode に何が届き何が届かないかを明記する
- 確定した技術決定は ADR（`docs/adr/`）、運用中に繰り返し引く事実（計測方法・調査結果）は `docs/reference/`。
  `docs/` の文書への言及には DOC-ID を明示する

## テスト方針（dotfiles AGENTS.md「テスト方針」と DOC-2610150520-a に従う）

孫1 は調査で、計測スクリプトは `docs/adr/probes/wording-habits/` に置く調査用の道具なので、自動テストは足さない。
孫2 で hook のスクリプトなど配布するコードを足す場合は、「背景3 の使ってよい言葉を誤って止めない」ことと
「悪癖の典型例を検出する」ことを、合成した入力で守るテストを最小限置く（境界を誤ると持ち主を逆に不快にさせるので、
誤検出の側は**必ず自動テストで固定する**）。

## 設計0: 全孫に共通の方針（司令官が決めた）

### 1. 調査結果と計測の置き場（孫1 が作り、孫2 が使う）

- 調査結果: `docs/reference/DOC-<採番>_言葉の悪癖を抑える仕組みの調査結果.md`（`docs/README.md` の索引表にも行を足す）
- 計測スクリプト: `docs/adr/probes/wording-habits/`（前例は `docs/adr/probes/usage-diet/`）。
  入力はこのマシンの `~/.claude/projects/*/*.jsonl` の assistant の本文、出力は集計値だけ。
  **孫2 の導入の前後比較に同じスクリプトを使えるようにする**（期間・対象を引数で指定できる形）
- 計測の指標（孫1 が決めて調査結果に書く）は、少なくとも次の2つを分けて出す:
  - 悪癖1: 背景2 の例の語（開いた言い換え）の出現数と、同じ意味の漢語（確認・修正・計測など）の出現数の比
  - 悪癖2: 全面禁止の宣言の言い回し（「一切〜しない」「二度と〜しない」「今後は〜しません」など）の出現数
  - どちらも、背景3 の使ってよい言葉は数えない

### 2. 判断の流れ

孫1 の調査結果は、候補ごとの効果・副作用・費用を並べ、**推奨案を1つ**示す（複数案の羅列で判断を持ち主に
丸投げしない）。司令官はそれを持ち主に提示し、持ち主が選んだ案を「進行記録」に書いてから孫2 を spawn する。

## 検証方針

## 検証方針

以下の重要な behavior / regression risk が、自動テストまたは既存テストによって保護されていること。

- 背景3 の使ってよい言葉（引く・探す・立てる・止める・回す）や、引用・コード・ファイル名の中の語で、仕組みが反応しない
  **この regression は必ず自動テストで固定する**（境界を誤ると持ち主を逆に不快にさせるため）
- 背景2 の悪癖の典型例に、仕組みが反応する（hook などコードを足した場合）
- 既存の hooks・設定・デプロイ（`tests/deploy_smoke.sh` の範囲）が壊れていない

各項目と test example を1対1対応させる必要はない。
複数の条件を1つの scenario で検証してよい。
既存テストで同じ regression を検出できる場合、新規テストは追加しない。
選ばれた案が指示文の変更だけでコードを足さない場合、自動テストは足さず、上の1つ目を文書の読み直しで確認する。

文書・指示文・PR 本文自体が悪癖の見本になっていないこと（和語に開いた言い換え・説明の無い造語・全面禁止の言い回しが無い）も
自分で読み直して確認する。
