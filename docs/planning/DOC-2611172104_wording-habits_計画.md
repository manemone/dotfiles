# 計画書: AI が書く日本語の癖を、基準の文書と読まれる文書の書き直しで抑える

傘ブランチ: `wording-habits`
ターゲット: `master`

## 概要

AI（主に Claude Code）が書く日本語に、持ち主が何十回も指摘しても改善しない癖がある（背景2）。
メモリへの記録・指示文の追記では改善しなかった（背景4）。

孫1 の調査（DOC-2611172119）は、例として挙がった語を正規表現で数え、正規表現の hook を推奨したが、
**語の適否は文脈で決まるので、意味を扱えない方法では判定できない**（背景5）。持ち主の指摘を受けて方針を変え、
指示文で抑える方法を外部の事例から調査した（背景6）。その結果、この傘では次を行う。

1. 癖の本質を、向きを持たない基準として文章にする（読み手がその文脈で実際に使う名前で書く、など。設計0 の 1）
2. その基準を `claude/CLAUDE.md` の指示文にし、向きを持った既存の規則（「横文字を避ける」など）を修正する
3. **AI が毎回・頻繁に読む文書そのものを、基準に沿った文体へ書き直す**。指示文の文体が出力の文体に影響する
   （Anthropic の公式ガイド）ので、今の文体で書かれたスキル・指示文がお手本になっている可能性が高い。
   対象は dotfiles と、このマシンのほかの5リポ（lorahaus・sheaf・modeldex・iosci・pixidex）、各リポのメモリ
4. 効果は、過去の返事のサンプルをモデルに文脈で判定させて計測する（正規表現は使わない）

毎ターンの再注入（UserPromptSubmit の hook）は、書き直しの後に、長い会話で癖が残るかを見てから判断する（背景7）。

## 背景1: 問題意識（要約。PUBLIC リポのため逐語では書かない）

2026-11-17、別リポの傘の司令官（Claude Code）との会話で、持ち主が強い不快感とともに次を指摘した。

- 「確認」で済むところを「確かめ」、「修正」を「直し」と言うような、無理に和語に開いた言い換えをやめてほしい。
  何十回も言っているのに改善しない。言い換えのせいで AI の言うことの理解が遠回りになり、認知負荷が高い。
  結果として持ち主側の指示まで曖昧になることがある
- ただし「引く」「探す」「立てる・止める」「回す」のような和語は普通に通じる。司令官がそれらまで避ける語に
  入れたことに対し、この境界の感覚が無いと指摘した
- 「この状況ではそのやり方が不適切」と言っただけなのに、AI は「今後一切しません」と全面禁止に広げて宣言する。
  ある判断が拙いという指摘は、以後それをやるなという意味ではない。全面禁止として言質を取るのは
  責任回避の逃げに見え、信用をなくす。これも何十回も指摘している
  - 例え話: 豆腐を賽の目に切る作業で、ハサミを使って時間がかかり角も崩れたのを叱ったら、AI が
    「今後ハサミは二度と使いません。袋を開けているほかの担当にも伝えます」と返した。これがどれだけ
    おかしいかが、持ち主の言う癖である
- 中の部品の名前（「焼いた指示書」のような、プロンプトを指す造語）を説明なしに持ち主向けの説明に使うのも同じ問題
- 司令官が `~/.claude/CLAUDE.md` を直接編集したことに対し、dotfiles の手順に従うよう指摘した
- こうした癖を抑える仕組みの調査も含めて、作業の入口（task-intake）に回すよう指示した

## 背景2: 癖の中身（ブリーフと、2026-11-17 の持ち主とのやり取りから）

計画書の中では次の番号で呼ぶが、**持ち主への報告では番号でなく中身で書く**（番号は計画書の中だけの名前で、
持ち主には説明の無い造語に見える。背景2 の 1 の問題そのもの）。

1. **読み手がふだん使う名前を使わず、別の言い方に置き換える**
   - 持ち主がその物事を呼ぶ決まった名前（その分野・その文脈で実際に使われる用語）があるのに、別の言い方にする。
     読み手は毎回それを決まった名前へ翻訳し直す必要があり、遠回りで認知負荷が高い。開いた和語は意味の幅も広く
     （「直す」は修正・修理・変換・復元のどれか決まらない）、指示が曖昧になる
   - 型はいろいろある。和語に開く（確認→確かめ、修正→直し、計測→測り、内訳→割り出し、キャッシュ→控え、
     コピー→写し）、定着したカタカナの IT 用語を日本語にする（シード→種）、定着していないカタカナ語を押し通す
     （スパイク・ドリフト）、英語の直訳の造語（「壊れ方が静か」= fails silently）、中の部品に付けた造語のラベル
     （「焼いた指示書」）、定着した用語を比喩の造語で呼ぶ（API トークン→「ダウンロードの合言葉」。別の会話で
     持ち主が遭遇した）、同じ物事を毎回違う名前で呼ぶ（英語の文章論の elegant variation）。
     **これらは例にすぎず、対象の全部ではない**
   - 判定の基準は「和語か漢語かカタカナか」という向きではなく、「**読み手がその文脈で実際に使う名前か**」。
     「引く」「探す」「回す」は持ち主自身がそう呼ぶので問題ない。同じ語でも文脈によって適切にも意味不明にもなる
2. **AI 特有の決まり文句・文体**: 「それが本質です」「結論から言うと」のような、AI が多用する言い回し。
   持ち主によれば、今の口調の指定（`CLAUDE.machine.md`）でかなり減ったが残っている
3. **状況への指摘を全面禁止に広げる**: 「この場面でのその判断が悪い」という指摘を、「今後一切しません」という
   規則に置き換え、メモ・ほかの会話への指示にまで書いて広げる。本質は、判断の誤りという指摘を、自分の判断を
   省ける規則に置き換えること（規則に従っていれば考えずに済み、外れても「言われたとおりにした」と言える）。
   言葉ではなく判断の癖である
   - 3 が 1 を生んでいる可能性がある（背景6）: 「定着していないカタカナ語を使わない」という指摘を
     「カタカナ語を避ける」という向きの規則に広げると、定着した「シード」まで「種」にする

## 背景3: 人間が確定させた決定事項（覆さないこと）

- `~/.claude/CLAUDE.md` などの配布先を直接編集しない。配布物は dotfiles の手順（このリポの PR とデプロイ）で変える
- 「引く・探す・立てる・止める・回す」は使ってよい言葉
- 2026-11-17（孫1 のマージ後）の持ち主の決定:
  - 正規表現で判定・計測する方法は採らない（背景5）
  - スキル本文の書き直しを行う
  - 書き直しは dotfiles だけでなく、ほかのリポ（pixidex を含む全部）でも行う
  - 毎ターンの再注入は、書き直しの後に回す（背景7）
  - 書き直す範囲は、AI が実際に読む頻度の高い文書から優先する。ADR と終わった傘の計画書は対象外
  - メモリは、目次と、向きを持った規則・全面禁止に広げた記録を先に修正する

## 背景5: 孫1 の方法の誤り（2026-11-17）

孫1 は、この計画書の旧版の設計0 が「背景2 の例の語の出現数」を指標に指定したとおり、例の語を正規表現で数え、
正規表現の `Stop` hook を推奨した。持ち主の指摘で次が分かった。

- 挙がった語は例にすぎず、癖は一般的な傾向として出る。例の語だけを数えても、例以外の分は見えない
- 同じ語でも文脈によって適切にも意味不明にもなる。それを見分けるには意味の理解が要り、正規表現では判定できない

出発点の誤りは計画書の指標の指定（司令官）にある。孫1 の計測スクリプト（`docs/adr/probes/wording-habits/wh.py`）の値は、
例の語の出現の目安としてだけ扱う。調査結果 DOC-2611172119 の推奨案は孫2 が修正する。

## 背景6: 指示文で抑える方法の外部の事例（司令官がサブエージェントで調査。2026-11-17）

- **Anthropic の公式ガイド**（https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices）:
  するなより何をするかを書く。理由を添えると、モデルが表に無い場合にも一般化する。良い例と悪い例を3〜5組示すのが
  最も確実な方法の1つ。**指示文自体の文体が出力の文体に影響する**
- **見本を渡すのが最も効いた**という報告（個人の感想）: 「AI 臭を避けて」の指示はそこそこ、自分の文書を2〜3本渡して
  「この文体を真似して」と指示すると定型句がほぼ消えた（https://zenn.dev/tabayashi/articles/how-to-deodorize-ai-writing）
- 「指示は個々の語には効くが、癖を生む機構には効かない」「比喩をやめて、実物や実際の動作を名指す」（自社の実測1件、
  約25万字。https://fyve.co.jp/ai-advisor/articles/ai-text-style-english-calque）
- 禁止語を名指しすると、かえって出やすくなる研究（小型モデルでの実測。https://www.arxiv.org/abs/2601.08070）
- Wikipedia の Signs of AI writing（https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing）: 決まり文句は症状で、
  原因は中身（具体的な主張・数字）の欠如。表面だけ消すと検出しにくくなるだけ
- Claude の公式システムプロンプトも、特定の語を理由付きで避けさせている（「不誠実に聞こえるから」）
- 長い会話では CLAUDE.md の効きが落ちるという報告が複数ある（GitHub の issue）。毎ターンの再注入で多少は保てるが、ずれる
- 背景2 の 1（読み手の用語）と 3（全面禁止への拡大）を指示文で扱って効果を計測した事例は見つからなかった
- 実際に読み込まれる文書の調査: dotfiles のスキル本文は開いた和語の文体で書かれている（例: umbrella-orchestrator の
  「セッション ID を控える」「承認と対象HEAD を確かめ直してから」）。プルリクエストの作法（DOC-2608020715）には
  「平易な言葉を使う」「必要がない場合は横文字（英語の専門用語）を避ける」という向きの規則がある。
  別リポのメモリには「一般に定着していないカタカナ語を使わない」がある（指摘の中身は正しいが、向きの規則として
  広がりうる）

## 背景7: 毎ターンの再注入の試算（2026-11-17、直近7日の会話 344本）

- 人間（または他の AI）からの入力の回数は、中央値1・上位10% で5・上位1% で29・最大911（司令官の長い会話）。
  会話の最後の文脈は中央値約12万・上位10% で約20万トークン
- 注入する文を1回約250トークンとすると、5回で約1,250（文脈の0.6%）、29回で約7,000（約3%）、911回で約22万で、
  長い会話ほど文脈を圧迫する。効いてほしいのはその長い会話（CLAUDE.md が遠くなる）
- 効果は計算できない。計測するなら、過去の長い会話を途中から分岐させ（`claude --resume --fork-session`）、注入の
  有無で返事を作らせてモデルに判定させる実験になる
- 判断: 書き直しの後に、長い会話で癖が残るかを見てから実施を判断する。実施する場合も、前回の注入から文脈が一定量
  増えたときだけ注入する（`claude/hooks/compact-reminder.sh` と同じ間引き方）

## 決定的な制約（孫は全部守ること）

- dotfiles の `AGENTS.md` の最重要ルール: `claude/CLAUDE.md` は配布物で、指示が無い限り編集しない
  （この傘では、孫2 が設計0 の 2 の範囲で編集する）。`CLAUDE.machine.md`（人格）はリポの外にあり、スコープ外。
  **配布先の実ファイル（`~/.claude/` 配下）を直接編集しない**
- **deploy しない**（`deploy-all.sh` も個別の `deploy.sh` も実 `$HOME` に対して実行しない。配るのは人間）
- **書き直しは、文脈を読んで行う。** 語の置換スクリプトや sed で一括に変換しない（背景5 と同じ誤りになる）
- **書き直しで意味を変えない。** 規則・手順・条件・数値・例外・参照先は元のとおりに保つ。言葉と文の組み立てだけを変える
- コード・コマンド・パス・識別子・設定のキー・引用（`>` やコードブロック）・他の文書やプログラムが文字列として
  参照する見出し・書式（例: 計画書の `## 孫N用プロンプト:`、状況の絵文字と値、`pr-review-loop` の判定の書式）は変えない。
  見出しを変えるときは、その見出しを参照している箇所をリポ全体で検索して合わせる
- 持ち主は、**規則を作って判断を丸投げすること**を責任逃れとして嫌う。基準の文書も書き直しも、「〜を避ける」の
  列挙ではなく、何をどう書くかと理由で書く
- 「引く・探す・立てる・止める・回す」など、読み手がふだん使う和語を別の言い方にしない（背景2 の 1 の逆向きの誤り）
- **この傘の文書・コード・PR 本文自体が、基準に沿っていること**（背景2 の 1〜3 の見本にならない）
- **公開リポ（dotfiles）**: 人間の発言を逐語で書かない（要約する）。会話ログの本文を文書・コミット・PR に貼らない。
  ほかのリポの中身を書かない。非公開の値は、リポの外の `~/.local/state/umbrella/wording-habits/` に置く
- 確定した技術決定は ADR（`docs/adr/`）、規範は `docs/design/`、事実の記録は `docs/reference/`。
  `docs/` の文書への言及には DOC-ID を明示する

## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

2. `/pr-review-loop` を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す

5. （Herdr あり・司令官が宛先を埋め込んだときだけ）最終報告を書き終えたら、最後の行動として
   司令官へ承認を報告する。宛先は、司令官が spawn の送信文で渡した司令官の Herdr ペイン

   だけにする（「〜とだけ返事して」のような指示は付けない）。報告は1回だけ。送れなくても
   再送せず（司令官の巡回が拾う）、送れなかったことを人間に1行伝えて止まる

## 大きい出力を文脈へ流し込まない（実装中ずっと）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:

## 実装完了後の流れ（必須）

実装が完了したら、以下を**自律的に**実行してください:

1. PRを作成する。**PRの向き先は必ず `wording-habits` にすること。master には絶対に出さない。**
2. `/pr-review-loop` を起動する（PRがない場合は自動で作成し、そのままレビューを開始する）
3. レビュー指摘があれば修正し、承認されるまで繰り返す
4. **承認されてもマージしない。** `/pr-review-loop` の手順にマージへ進む記述があっても実行しない
   （孫が人間のフィードバック前に勝手にマージするのを防ぐため。マージは傘の司令官が行う）
5. （Herdr あり・司令官が宛先を埋め込んだときだけ）最終報告を書き終えたら、最後の行動として
   司令官へ承認を報告する。宛先は、司令官が spawn の送信文で渡した司令官の Herdr ペイン
   （渡されていなければ報告せず、人間に「承認済み。マージは司令官（または人間）が行う」と伝えて止まる）。
   送り方は umbrella-orchestrator スキル §5「AI間送信手順（二段構え）」に従う。本文は
   「孫4 `wh-04-skills-rest` の PR #<番号> が HEAD <短縮SHA> で承認されました。マージをお願いします。」
   だけにする（「〜とだけ返事して」のような指示は付けない）。報告は1回だけ。送れなくても
   再送せず（司令官の巡回が拾う）、送れなかったことを人間に1行伝えて止まる

なお `/pr-review-loop` は、レビューを依頼した直後の区切りで文脈が大きければ `ocw self-compact` で
自分を compact する（その手順は pr-review-loop 側。使えなければ何もしない）。compact の後は、
復帰メモに従ってレビュー待ちに戻り、この「実装完了後の流れ」を最後まで続けること。

150,000 トークン（claude-ds 以外の Claude は 200,000。`ANTHROPIC_BASE_URL` に `deepseek` を含むかで見分ける）を超えていれば
`ocw self-compact` で自分を compact してよい（WIP のコミットは区切りでない。指摘対応の修正の途中は対象外。回数の上限は無いが、
前回の compact から文脈が 100,000 以上増えていなければ見送る。ADR DOC-2610142337・DOC-2611032102）。
測り方は `/pr-review-loop` の「区切りでの自己 compact（実装側のみ）」の手順1のコマンドと同じ（その節の (3) の項だけを読めばよい。
手順の「Phase 3 へ進む」は実装途中には当てはまらない）。復帰メモ（リポの外の一時ファイル）には、計画書のパスと孫の節・
済んだこと（コミットの一覧）・作業中に下した判断とその理由・残り・次の一手・検証コマンドを書き（増分の起点は復帰後に測るので
メモには書かない）、先頭に「計画書の続きから実装を再開する。レビュー待ちではない」と書く。コマンドを実行したらそのターンを終える。
使えない・拒否・失敗なら何もせず実装を続ける（人間に提案もしない）。
実装が終わったタイミングで止まらず、必ずここまでやりきってください。
reviewerはdone状態で完了し完了通知は来ないので、待機して停止せず gh pr view をポーリングして
レビューの有無を確認してください。

## 大きい出力を文脈へ流し込まない（実装中ずっと）

文脈の膨張は、1k〜20k字級の出力の積み重ねと、自分で書く長い出力で起きる。次を守ること:
- ファイルを `cat` / `sed -n` で丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・分析・ログ・`git diff`・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルや、繰り返し直して実行するスクリプトを Write / heredoc で丸ごと書き直さない。一度ファイルに置き、変更は Edit の差分で行う（新規ファイルを最初に1回書くのは構わない）
