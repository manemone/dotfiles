# 実装の孫の文脈の内訳調査と大きい出力の作法

傘 `context-bloat` 孫1 の調査結果。実装の孫の文脈が 300〜430k まで膨らむ理由を実ログで分け、
「大きいツール出力を文脈へ流し込まない作法」の中身と置き場を決めた根拠を残す。
測定の手法と前例は DOC-2610130216（使用量の測り方と削りどころの調査結果）。

## 測定

- 期間: 2026-10-13 13:53 JST（`ocw self-compact` 入りの配布）以降。対象は実装の孫（ワークツリー名に `-NN-` を含む）の
  セッション 55 本、ツール結果 5,170 件、画像 91 枚
- スクリプト（`docs/adr/probes/context-bloat/`）: `tools.py`（ツールの種類・Bash の先頭語・1回の大きさ・読み直し）、
  `share.py`（文脈の最大値の内訳と、スキル呼び出し直後の増分）。出力が大きいのでファイルへ書き出して要約を見ること
- 注意: ツール結果の文字数→トークンは 3.5 文字/トークンで換算した。日本語の多い出力ではトークンが多くなるため
  ツール結果の寄与は過小に出る。`tools.py` のトークン推定は「次の呼び出しの文脈の増分を直前のツール結果へ
  文字数比で配った」粗い按分で、ツール結果以外の増分も混ざる。**順位づけの目安にとどめ、絶対値は信用しない**

## 結果

### ツール結果の内訳

| 軸 | 結果 |
|---|---|
| ツールの種類 | Bash が文字数の約 89%（4,598 件・約 831 万文字）。次が Read（約 10%、162 件）。Agent・SendMessage・Monitor などは合わせて 2% 未満 |
| Bash の先頭語 | `cat` 約 23%・`sed` 約 19%・`grep` 約 9%・`python3` 約 6%・`git diff` 約 5%（全ツール結果に対する割合）。**ファイルを読むための `cat` / `sed -n` で Bash 結果の約 5 割**を占める |
| 1回の大きさ | 1,000 字未満が 10%、1,000〜5,000 字が 37%、5,000〜20,000 字が 43%、20,000 字以上は 10%（33 件）。上位 10 件で 4%。**巨大な 1 回ではなく、1k〜20k 字級が 4,000 件近く積もっている** |
| 読み直し | 5,000 字超の結果で、同じコマンド・同じファイルを繰り返したものは 476 種のうち 3 種だけ。読み直しは主因ではない |
| 画像 | 91 枚（55 本の孫で 1 本あたり 2 枚弱）。主因ではない |

### 文脈の最大値の内訳（上位の孫）

最大文脈 250〜740k の孫で、最初の呼び出し時点で約 44k（システム・CLAUDE.md・スキル一覧）。最大値のうち:

- ツール結果は（過小見積りで）約 15〜30%
- **出力トークンの累計（思考・本文・ツール入力）は約 25〜40%**。例: 最大 737k の孫は出力 280k、494k の孫は 164k
- 残りは `pr-review-loop` の本文注入（1 回あたり約 33k。26 回で中央値 33k・最大 36k）やユーザー側メッセージなど

つまり、ツール出力の絞り込みだけでは**膨張の一部（見積りで 2〜4 割）にしか効かない**。残りは孫自身の出力と
スキル本文で、これは作法ではなく区切りでの compact（孫2・孫3）で抑える領域である。

## 決めたこと

### 作法の中身

巨大な出力を警戒するだけでは足りない（20,000 字以上は文字数の 10%）。効くのは、**中くらいの出力を積もらせない**こと。

1. ファイルを `cat` / `sed -n` で丸ごと読まない。まず `grep -n` / `wc -l` / `head` で当たりをつけ、必要な行範囲だけ読む
2. 出力が約 100 行・5,000 字を超えそうなコマンド（テスト・分析スクリプト・ログ・`git diff`・JSON など）は、
   最初から一時ファイルへ書き出し（`> "$TMP/out.txt" 2>&1`。`$TMP` は `mktemp -d`）、`tail` / `grep` / 件数だけ見る
3. 長いファイルを `Write` や heredoc で丸ごと書くと、その全文が出力トークンとして文脈へ積まれる。
   生成できるものはスクリプトで生成し、変更は `Edit` の差分で行う

「同じ出力を読み直さない」「画像は要るときだけ」は実測で主因でなかったため、作法には入れない（短く保つため）。

### 置き場

- 入れる: `skills/umbrella-orchestrator/SKILL.md` §3.2 の自動付与指示（同じリポの孫用・他リポの孫用）。
  実装中の孫が読むのは計画書の孫用プロンプトだけで、ここが唯一確実に届く。`skills/pr-review-loop/SKILL.md`
  （指摘対応の修正中にも同じことが起きる）
- 入れない: `templates/repo-baseline/template/AGENTS.md.jinja`（撒く先の全エージェントに常時読まれる文書を、
  実測で見積り 3〜4 割にしか効かない作法のために太らせない。入れるなら孫2・孫3 の効果を見てから判断する）、
  `claude/CLAUDE.md`（人間の許可が進行記録に無いため触っていない）
- `task-intake` の軽いハンドオフ（実装の孫がブリーフから起動する経路）は、ブリーフに実装中の作法の欄が無く、
  人間の指示と AGENTS.md が正典のため変更なし
