# 孫 PR ごとのレビューが何を止めてきたか（過去データの分析）

傘ブランチ方式の孫 PR ごとのレビューが、PR の種類・実装役のモデル別に何を止めてきたかを、
決まった基準で数え直した記録である。**§2 の基準と §3 の手順は再利用する。§4 以降は日付つきの結果。**

運用をどう変えるかは決めない。結論は「どの種類・どのモデルの PR で、孫ごとのレビューが
実害のあるバグ・計画逸脱を止めているか」に絞り、運用の提案は §7 に分けて書く。決めるのは人間である
（計画書 DOC-2610140002 の設計4）。

このリポジトリは公開リポジトリで、対象の5リポのうち dotfiles 以外は非公開である。
**ここには件数・割合・分類ラベル・PR 番号と、製品の中身に触れない一般化した説明だけを書く。**
PR 本文・指摘の中身・コード・パスは書かない。

## 1. 前提と限界

限界は §8 に集約した。**数字を使う前に §8 を読むこと**（特に、指摘のインラインコメント本体が
生データに無いこと、分類担当が AI 1種類であること、抜き取りが層化で母集団の縮図ではないこと）。

## 2. 分類の基準

### 2.1 指摘（finding）の数え方

- 数えるのは、🤖🔍 レビュー指摘のコメントのうち、「指摘」の節にある番号つきの項目（`### 1.` など）
  1つ。「確認して問題なしとしたもの」「検証」の節は指摘ではない
- 見出しに「（インラインコメント参照）」とある項目は数える。インラインコメント本体は
  生データに含まれない（本文が空のレビューとして入っている）ので、見出しと要約だけで判定する
- 同じ内容が次のラウンドで再掲された場合は、新しい指摘として数えず「再掲」とする
- 指摘に番号が無く散文だけのレビューは、指摘と読める単位に分けて数える

### 2.2 カテゴリ（判定は上から順に当てはめ、最初に当てはまったもの）

| 分類 | 定義 | 当てはめの問い |
|---|---|---|
| A 実害のあるバグ | 直さずにマージすると、利用者・後続の孫・運用が誤動作するもの | 実行されるコード・設定・スクリプトの誤りで、具体的な誤動作の筋書きが書けるか |
| B 計画逸脱・孫どうしのズレ | 計画書・他の孫・既存の契約と食い違っているもの（今は動いても後続で壊れる） | 食い違う先（計画書の記述・他の孫の成果・既存の API やスキーマ）を指せるか |
| C テスト・検証の穴 | テスト不足（risk-based testing の入口判定を通るもの）、検証手順の欠落 | 逃す regression を書けるか |
| D1 誤操作を誘発する文書の不整合 | `pr-review-loop` の gate（`skills/pr-review-loop/SKILL.md`「blocking finding にしてよいもの」）を通る文書・文言の指摘 | 文書を信じて動いた人が誤った操作をしうるか |
| D2 nit | gate を通らないもの（表現の好み・折り返し・統一感・軽微な命名） | A〜D1 のどれでもない |

境界の約束:

- 文書の誤りは D1 までとする。実行される設定・スクリプト・コード内の文字列の誤りで誤動作するなら A
- 「テストを足すべき」でも、逃す regression が書けないものは C にしない（D2）
- A と B の両方に当てはまるときは A
- gate は 2026-10 に整った（導入の経緯は同スキルの履歴）。**古い PR にも同じ基準を遡って当てる**
  ので、当時は出してよかった nit も D2 に数える

### 2.3 付ける属性

| 属性 | 値 | 意味 |
|---|---|---|
| `spill` | true / false | 後から直すと後続の孫も直す必要が出るか（後続の孫が、その箇所の上に書く・参照する場合に true） |
| `resolution` | fixed / declined / unknown | 対応報告で、指摘に沿って直したか、実装者が反論・見送りしたか |
| `repeat` | true / false | 前のラウンドの再掲か（true なら集計から除く） |

## 3. PR の属性

- **PR の種類**（上から順に当てはめる）:
  文書だけ（変更が文書・コメントだけで、実行されるコードや設定を含まない）→
  土台（後続の孫が上に書く API・スキーマ・ディレクトリ構成・共通基盤を作る）→
  小さい（変更100行以下で実装コードを含む）→ 実装コード（上のどれでもない）
- **実装役のモデル**: 対応報告コメントの見出し `[モデル | 努力量]` > コミットの `Co-Authored-By`
  trailer > 不明。系統（Opus / Sonnet / DeepSeek / Qwen など）に寄せる。複数系統は「混在」

## 4. 手順（再実行できる）

スクリプトは [`docs/adr/probes/review-tiering/`](../adr/probes/review-tiering/) にある。**使い捨ての調査用**で、
リポジトリのルートから実行する。生データ（各リポの PR 一覧と本文）は非公開リポの内容を含むので
リポジトリに入れず、`REVIEW_DATA` で場所を渡す。リポ名・パスはスクリプトに書かない。

```sh
export REVIEW_DATA=<生データのディレクトリ>   # rows.json（孫 PR 一覧）と pr/<リポ>-<番号>.json を置く
export REVIEW_OWNER=<GitHub の所有者名>        # gh の読み取り専用で使う（fetch_trailers.py のみ）
# 再現実験の対象の傘（全数を分類する）。<リポ>/<ベース>,... の並び順が傘の通し番号（§5.4）。
# 値は derived/umbrellas.txt に保存してあり、環境変数 REVIEW_UMBRELLAS を省くとそこから読む。並び順を変えない

cd docs/adr/probes/review-tiering
python3 build_prs.py         # PR ごとの属性（ラウンド数・見出しのモデル）→ derived/prs.json
python3 fetch_trailers.py    # 対応報告の無い PR だけ、コミットの Co-Authored-By を gh で読む（書き込みなし）
python3 attribute.py         # 実装役のモデル系統と、層化用の仮の PR 種類 → derived/prs_attr.json
python3 sample.py            # 層化抜き取り（固定シード）→ derived/sample_ids.json
python3 make_inputs.py       # 分類担当への入力（実装役のモデルは伏せる）→ derived/inputs/
# ここで分類担当（§2 の基準を読ませたサブエージェント）が derived/labels/<リポ>-<番号>.json を書く
# 基準ぶれの確認（§5.3）: derived/kappa_ids.json の PR（指摘が2〜5件のものを乱数で8本、指摘計26件）を、別のサブエージェントに
#   同じ入力・同じ手順で分類させ、結果を derived/labels2/ に書かせる（出力先だけ labels/ から変える）
python3 aggregate.py all     # 表を標準出力へ（population / sample / kappa / umbrella の個別実行も可）
```

`python3 -I` は付けない（同じディレクトリの `common.py` を読むため）。

### 4.0 生データの形と、作り方が記録されていないこと

集計スクリプトが読む生データ（`REVIEW_DATA` 配下）は、この傘の外の会話で `gh` の読み取りだけで
集めたもので、**集めるスクリプトはリポジトリに無い**。形は次のとおり。

- `rows.json`: 孫 PR 1本が1要素の配列。キーは `repo` `n`（PR 番号）`base` `head` `title` `url`
  `size`（追加行 + 削除行）`find`（変更要求のレビューの回数）`appr`（承認のレビューの回数）
  `rep`（対応報告コメントの回数）
- `pr/<リポ>-<番号>.json`: `gh pr view --json` 相当。キーは `additions` `baseRefName` `comments`
  `deletions` `headRefName` `number` `reviews` `title` `url`（コミットの一覧と時刻は含まない）
- `um.json`: 傘 → 既定ブランチの PR の配列。キーは `rows.json` と同じ

`find` の数え方（何を1ラウンドとするか）と、孫 PR の抽出条件（base が既定ブランチ以外の merged PR、
という意図）は、収集スクリプトとして残っていないため**正確には再現できない**。ただし近い数え方は
ある。変更要求のマーカー（🤖🔍）で始まる本文を、PR の `reviews` と `comments` の**両方**から数える方法
（`build_prs.py` の `rounds_with_findings`。変更要求が会話コメントとして投稿されている PR があるため
両方を見る）で、全1208本のうち 13 本（約1%）だけが `find` と食い違う。`reviews` だけを数えると
89 本（約7%）が食い違うので、`reviews` だけにしないこと。

運用を変えた後の傘のラウンド数を比べるときは、上の形に合わせて新しい傘の PR を集め、この
`rounds_with_findings` の数え方でラウンド数を出す。DOC-2610140007 の数字とは約1%ずれうるので、
大きな変化だけを読むこと。

### 4.1 指摘ラベルの形式（`derived/labels/<リポ>-<番号>.json`、リポの外）

```json
{"id": "<リポ>-<番号>", "kind": "docs|foundation|small|code", "kind_reason": "…",
  "first_round_approved": false,
  "findings": [{"round": 1, "idx": 1, "cat": "A|B|C|D1|D2", "spill": false,
                "resolution": "fixed|declined|unknown", "repeat": false, "note": "…"}]}
```

指摘の本文を含むため、このファイルはリポジトリに入れない。再現実験（孫3）はこれを正解データとして読む。

### 4.2 抜き取りの方法

- 母集団は、指摘のあったラウンドが1回以上ある孫 PR。層は **仮の PR 種類 × 実装役のモデル群**
  （題名と行数だけで付ける仮判定。`attribute.py`）。各層から人数比例で取り、最低3本（層が3本未満なら全数）
- 目標は150本程度。再現実験の対象の傘（§6）は指摘のある孫 PR を全数入れ、残りを層から取る。結果は
  **165本**（傘から46本＋層から119本）。分類は PR 単位で 22 バッチに分け、`model: sonnet` のサブエージェントに分担させた
- 分類担当には **実装役のモデルを見せない**（入力から見出しのモデル名を除く）。PR の最終的な種類は
  分類担当が差分の概要（題名・行数・指摘の内容）から付けた
- 乱数のシードは固定（`sample.py`）。層ごとの母数と抜き取り数は `sample.py` の標準出力に出る

### 5.4 再現実験の対象の傘

リポ名・ベースブランチ名は非公開リポの情報なので通し番号で書く（実体は `derived/umbrellas.txt`（リポの外）の並び順。§4）。

### 5.5 読み取り（結論は「止めている」まで）

下の数字は §5.2 の抜き取りを分類し直したもの（再掲を除く 976件）で、母集団の縮図ではない（§8）。

- **孫ごとのレビューは A（実害のあるバグ）を止めている。** 実装コードの孫 PR の 75%、土台の 89% が A を1件以上含み、
  A/B/C のどれも含まない PR は抜き取り全体の 19% だった。背景4 の「A を含む孫 PR は 42%」より高いのは、
  抜き取りが指摘のある PR に限られること（指摘ゼロの PR を母集団から除いた）と、実装コード・土台に厚く取ったことによる
- **文書だけの PR では A はほぼ出ず（1%）、止めているのは B（計画逸脱）と D1（誤操作を誘発する文書の不整合）。**
  A/B を含む文書だけの PR は 41%。背景3 の問い（D の中身）への答え: D は **gate を通る D1 が 25%、通らない D2 が 17%**
  で、文書の指摘の過半は gate を通る側（D1 は文書だけの PR の指摘の 60%）。「gate が守られず nit でラウンドが回る」より、
  「gate を通る文書の不整合そのものが多い」が主である。ただし D2 も §5.6 のとおり直されており、
  nit を直すラウンドは一定数ある
- **実装役のモデル別**: Sonnet・Opus の実装は A を含む PR が 51% / 70%、弱いモデル（DeepSeek・Qwen・Kimi）は 91%（11本）。
  弱いモデルは A の割合が高く D2 が多い（指摘の 33%）。本数が少ない（11本）ので傾向としてだけ読む。Fable・GPT（2本）は
  弱いモデルではなく、別の区分に分けて表に出した。実装役の違いより、PR の種類（土台・実装コードか）の違いのほうが
  A の出方を強く分ける
- **後続の孫に波及する指摘は全体の 10%**（A 8%、B 24%、D1 16%、C 2%、D2 0%）。B は計画逸脱なので波及しやすい。
  「最後に1回でよい」案の取りこぼしコストは、この B と D1 の波及分に集中する
- **「小さい」PR は指摘なしで承認される割合が高い**（母集団・仮判定で 42%、指摘ラウンドの平均 0.79）。ただし抜き取りは
  11本なので、小さい PR の A/B の出方は判断できない

### 5.6 対応の結末

上の表「指摘への対応の結末」のとおり、再掲を除く 976 件のうち、対応報告で「指摘に沿って直した」は 968 件（99%）、
「実装者が反論・見送り」は 6 件（A 3・B 1・C 1・D1 1）、判定不能 2 件。**孫ごとの指摘はほぼそのまま修正されている**

## 7. 運用への提案（決めるのは人間）

- **文書だけの PR**: 孫ごとのレビューで止めている主な指摘は B（計画逸脱）と D1。レビューを省くなら
  B と D1 の波及（§5.5）を最後の1回で拾えるかが論点で、これは孫3 の実験の対象
- **土台・実装コードの PR**: A を含む割合が高く（89% / 75%）、孫ごとのレビューを省く根拠は過去データからは出ない
- **「最後に1回だけ」は、このデータだけでは支持も否定もできない。** 過去データが示せるのは「孫ごとに何を止めたか」
  までで、「最後にまとめて見れば拾えたか」は孫3 の実験でしか分からない

## 8. 限界

- **インラインコメント本体は生データに無い。** レビューは本文が空の「インラインコメント」と、指摘の見出しと要約を持つ
  本文からなり、前者の中身は取れていない。見出しに「（インラインコメント参照）」とある指摘は数えたが、
  見出しだけで分類したため、A と D の境界はぶれうる
- **分類担当は AI（Sonnet）1種類で、人間の目視ではない。** 同じ8本（指摘26件）を別のサブエージェントで分け直した一致率は
  81%（§5.3）。目視との一致は測っていない。**A/B の割合は ±10pt 程度と見る**
- **抜き取りは層化であり母集団の縮図ではない。** 指摘のあった孫 PR だけから取り、再現実験の傘は全数入れ、層ごとに
  最低3本取っている。種類別・モデル別の表は層の中の割合として読み、全体の割合に引き直していない。
  仮判定の種類ごとの母数と抜き取り本数は、文書だけ 192 本に対し 23 本、土台 39 本に対し 10 本、小さい 121 本に対し 16 本、
  実装コード 856 本に対し 116 本（いずれも仮判定で数えた本数。§5.2 の突き合わせ表の行の合計）。表の「PR の種類別」は
  最終判定で数えるので、文書だけ 34・土台 19・小さい 11・実装コード 101 本になる
- **層の作り方では、弱いモデルに Fable・GPT が混ざっている。** `sample.py` の層は Sonnet・Opus・不明（混在を含む）・
  その他の4つで、その他には DeepSeek・Qwen・Kimi に加えて Fable・GPT が入る（抜き取りの 13 本のうち Fable が 2 本）。
  層の作り方は抜き取りの再現のため変えず、集計（`aggregate.py`）の表だけ「弱いモデル（DeepSeek・Qwen・Kimi）」と
  「その他（Fable・GPT）」に分けた
- **PR の種類は分類担当の判断で、題名と行数の仮判定とは一致しない**（仮判定の「実装コード」116本のうち、最終判定も
  実装コードのものは 92本）。母集団の種類別（§5.1）は仮判定の数字である
- **実装役のモデルが引けなかった PR は 75 本（6%）。** 対応報告の見出し（886本）か、コミットの `Co-Authored-By`
  （247本）から引いた。トランスクリプトやエージェントのログは使っていない（見出しと trailer で足りたため）。
  trailer が `Claude` だけでモデル名が無いものは不明に入れた。複数系統が混ざる PR は「混在」（18本）として不明の側に数えた
- **DeepSeek が実装したと確実に言える孫 PR は 7本、Qwen は 11本、Kimi は 2本で、弱いモデルは合計 20本**と少ない。弱いモデルの結論は
  傾向以上には言えない
- **gate は 2026-10 に整った** ので、古い PR の D1/D2 は当時の運用より厳しい基準で数え直している
- 分類担当の費用は、サブエージェント 24 本の合計トークンが約 250万（入力中心）で、Sonnet の入力単価でも約 $5 に収まる計算であり、
  上限の $30 を大きく下回る。請求額そのものは測っていない
- 対応報告は先頭 1,800 文字、レビュー本文は 7,000 文字で切って渡している。長い指摘の後半は読めていない

## 9. 再現実験（孫3。2026-10-14）

「孫ごとのレビューを省き、傘の最後に1回だけレビューした」とき、孫ごとのレビューが実際に止めた A/B/C を
何割拾えるかを測った（計画書 DOC-2610140002 の設計3）。**結論は §9.5 の「読み取り」まで。運用をどうするかは決めない。**
§9 でも非公開リポの内容（指摘の中身・コード・パス）は書かず、件数・割合・PR 番号・一般化した説明に限る。

### 9.1 条件

- 対象: §5.4 の5つの傘（傘1〜5。孫 PR は計53本）
- 最終レビュー: 傘ごとに、孫 PR の「最初のレビュー前の head」の差分を merge 順に当てた `replay` ブランチ
  （起点は最初の孫のマージ点の親）の差分全体を、`pr-review-loop` の Phase 2 Step 1 のレビュー指示
  （マーカーを埋め、finding の判定基準・譲れないレビュー基準・テスト不足の判定基準の本文を貼ったもの。GitHub への
  投稿だけをローカルのファイルへの書き出しに差し替え）で、サブエージェントに**1回だけ**レビューさせた
- 条件は `model: opus` と `model: sonnet` を傘ごとに各2回（5傘×2モデル×2回=20本）。lint / test の実行コマンドは渡していない
- 正解: §4.1 の `derived/labels/` から、傘に属する孫 PR の A/B/C の指摘（再掲を除く）。除外前 204 件。
  ただし、replay ブランチに**欠陥が存在しない**孫の指摘は判定から外した（分母に入れない。直った後のコードをレビューさせても拾えないため）。
  外したのは次の孫 PR: (a) レビュー前の head が取れず最終版で埋めた孫（傘3 の2本・傘4 の3本・傘5 の2本）、
  (b) 傘の履歴に無くブランチに当たらなかった孫（傘2 の2本。指摘なし）、
  (c) 衝突で**全ファイル**をマージ後の版（レビュー対応済み）で埋めた孫（傘1 の2本・傘3 の1本・傘4 の3本・傘5 の1本。傘2 の1本は指摘なし）。
  外した後は計 131 件（のべ判定数は 4 回分）で、傘1: 27件、傘2: 15件、傘3: 59件、傘4: 12件、傘5: 18件
  （A/B/C の内訳は `replay_truth.py` が出す）。**一部のファイルだけ**マージ後の版で埋めた孫は、ラベルにファイルの情報が無く
  ファイル単位では外せないので残した。その影響は §9.4 の感度分析で示す
- 突き合わせ: `model: sonnet` のサブエージェント（傘ごとに同じ担当が4〜3本を同じ基準で判定）。基準は次のとおり
  - hit: 最終レビューの finding が、正解と**同じ欠陥・同じ箇所の問題**を指している（表現は違ってよい）
  - partial: 同じ領域・ファイルは指すが、欠陥の核心を言い当てていない、または一部しか覆っていない
  - miss: 該当する指摘が無い
  - さらに、正解に対応しない最終レビューの finding（新規）を A/B/C/D に分け、レビュー前の head をつないだことによる**土台の不整合**
    （存在しないファイルを require する、未定義の定数を参照する等）と読めるものに `artifact` を付けた

### 9.2 手順（再実行できる）

スクリプトは [`docs/adr/probes/review-tiering/`](../adr/probes/review-tiering/) の `replay_*`。**使い捨て**で、§4 と同じく
リポジトリのルートから実行する。環境変数は `REVIEW_DATA`（生データ）・`REVIEW_OWNER`（所有者名。gh の読み取り専用）。

```sh
cd docs/adr/probes/review-tiering
python3 replay_prepare.py                       # 傘ごとの孫 PR・最初のレビュー前の head・マージ点 → derived/replay/umbrella<N>.json
S=$(mktemp -d)                                  # scratch の置き場（リポの外）
for n in 1 2 3 4 5; do bash replay_build.sh $n "$S"; done   # scratch に clone し、replay ブランチを作る。作り終えたら origin を外す
REPLAY_SCRATCH="$S" python3 replay_truth.py     # 正解データ（傘ごと）→ derived/replay/truth/u<N>.json
cd ../../../.. && for n in 1 2 3 4 5; do python3 docs/adr/probes/review-tiering/replay_prompt.py skills/pr-review-loop/SKILL.md $n "$S/u$n" '<OUT>' > <プロンプトの置き場>/u$n.md; done
# ここでレビュー担当（サブエージェント。モデルを指定）に <OUT> をレビュー結果の出力先に読み替えさせ、各傘を2回ずつレビューさせる
# 続けて突き合わせ担当（model: sonnet）が match/<傘>-<モデル>-<回>.json を書く（形式は replay_aggregate.py が読む）
python3 docs/adr/probes/review-tiering/replay_aggregate.py   # 表を標準出力へ
```

- `replay_build.sh` は clone を **fetch にだけ使い**、終わると `git remote remove origin` で push 先を残さない。
  gh の認証は環境変数（`GIT_CONFIG_*`）で一時的に渡し、git の設定ファイルは書き換えない。他リポの人間のワークツリーは触らない
- ブランチの作り方: 傘の first-parent の履歴を古い順にたどり、孫 PR のマージ点は「最初のレビュー前の head」の差分
  （`git apply --3way`）に差し替え、それ以外の直コミット（司令官の計画書更新など）はそのまま当てる。孫 PR のレビュー指摘への対応を
  傘へ直接入れた直コミット（題名に「レビュー」を含むもの）は当てない。当たらなかった差分は、その孫のマージ後の版でファイルごと埋める
- 傘5 は傘の履歴に孫のマージ点が見つからなかったため、孫 PR のマージ順に当てる方式（直コミットは扱わない）に落とした

### 9.5 読み取り（運用の提案ではない）

- **「最後に1回だけ」は、孫ごとのレビューが止めた A/B/C の大部分を拾えなかった。** 全体の hit は Sonnet 8%・Opus 14%（partial を足して 12%・18%）。
  傘別では 4〜31%（最低は傘3、最高は傘2）、傘×モデルでも傘2 の Opus（46%、partial を足して 53%）以外は 20% 以下。A は B・C より高めだが、いずれも低い。2回走らせて結果がほぼ一致したので、ぶれではない
- **レビュアーのモデルは Opus のほうが高い**（hit 14% 対 8%）が、どちらも低く、モデルを上げても「最後に1回」を孫ごとのレビューの代わりにできる水準には届いていない
- **主因は、最終レビューが見る finding の数にある。** 3000行を超える差分に1回のレビューでは finding が平均 6 件前後に収まり、
  孫ごとのレビューが 1 PR あたりで積み上げた指摘の件数（複数ラウンドの合計）に遠く及ばない。最終レビューは、最も目立つ欠陥（動かない、
  落ちる）を先に拾い、細かい実害や計画逸脱へ進む前に収まる傾向が見える
- **実装役が弱いモデル（Qwen。傘2）の傘は拾えた割合が高い**（31%。DeepSeek を含む混在の傘1 は 16%、Sonnet の傘3〜5 は 5%）。これは「最後に1回でも足りる」ではなく、
  A の欠陥が目立つ（最終レビューでも見つけやすい）形で出ていた、と読める。傘と実装役が1対1なので、実装役の効果とは断定できない。
  人間の見立て（弱い実装役では最後に1回は成立しない）を、このデータが支持も否定もしない
- 「2回目以降の指摘」は hit が 3% と低い（修正の差分への指摘は、レビュー前のコードに存在しない欠陥が多い）。
  最終レビューが拾えないのは当然の部分を含む。この区分だけを見た「1回目のレビューで出た指摘」でも hit は 13% である
- 最終レビューは、正解に無い**実在する新規の A を見つける**（独立の指摘がある）。「孫ごとのレビューの代わり」にはならないが、
  「傘の最後に足す」価値はある。これは傘→master PR で 82% に指摘が付く事実（計画書 背景4）とも整合する

### 9.6 既知の弱点・限界（必ず割り引くこと）

- **波及の効果は再現できていない（計画書の既知の弱点）。** 実際の後続の孫は**レビュー済みの土台の上**に書かれているが、
  「レビュー前の head」をつなぐと、後続の孫がレビュー前の土台に合わせて書き直されたはずの部分が再現されない。
  逆に、後続の孫が前提にしたレビュー後の土台と食い違い、**存在しないファイル・未定義の定数を参照する人工的な不整合**が出る（傘3 に顕著）。
  このため、最終レビューが人工物に気を取られ、本来拾えたはずの欠陥への注意が薄くなった可能性がある。拾えた割合は**下振れ**しているかもしれない（大きさは測っていない）。
  衝突を「マージ後の版」で埋めたファイルは、レビュー対応済みで欠陥が残っておらず、これも拾えた割合を**下振れ**させる。全ファイルを埋めた孫は判定から外し、
  一部だけ埋めた孫は外した場合の割合を §9.4 の感度分析に示した（動かなかった）
- **正解データの限界は §8 のとおり**（分類担当が AI 1種類・A/B の境界が ±10pt・インラインコメント本体が無い）。
  正解の件数は、孫ごとのレビューが複数ラウンドで積み上げた数であり、1回のレビューが全部を出す想定では多すぎる
- **最終レビュー担当は lint / test を回せていない**（gem が入らない・ネットワーク禁止）。実環境で `bundle exec` 等を回せば、
  落ちるテストや lint の指摘から拾える件数が増える可能性がある。サブエージェントが素の言語処理系で一部再現した例はある
- 傘ごとの孫 PR の規模が違う（傘3 は約15,000行追加）。拾えた割合は差分が大きいほど低く出る傾向があり、傘の性質と規模は分けられていない
- 実装役の効果は、傘と1対1なので分離できない（上述）。DeepSeek の孫は傘1 で1本だけで、弱いモデルの傘は実質 Qwen の傘2 だけ
- 突き合わせ担当は Sonnet 1系統。目視確認は 20 件（のべ判定の約 3〜4%）で、判定のぶれは ±5pt 程度と見る
