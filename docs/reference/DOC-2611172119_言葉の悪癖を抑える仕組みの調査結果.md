# 言葉の悪癖を抑える仕組みの調査結果

AI の会話の言葉に出る2つの悪癖（和語に開いた言い換え、全面禁止の宣言）について、
**計測する方法と現状の値**、**抑える仕組みの候補ごとの効果・副作用**、**推奨案**を残す文書である。
傘ブランチ `wording-habits` の孫1 の成果で、計画書は DOC-2611172104（傘が閉じたあとは歴史的記録）。
この文書の本体（§1〜§5）は孫1 が正規表現で数えた結果で、**§6 の推奨案（正規表現の `Stop` hook）は取り下げた**（理由は §6）。
取り下げのあと、指示文で抑える方法の外部の事例（§7）と、毎ターンの再注入の試算（§8）、モデルが文脈で判定する計測の基準値と
読まれる頻度（§9）を足した。採用した方法は ADR DOC-2611172307-a にある。

このリポジトリは公開リポジトリなので、会話の本文・人間の発言・他のリポジトリの名前は書かない。
集計値と、計画書に既に出ている語だけを書く。

## 1. 2つの悪癖の定義（計画書 背景2 の要約）

- **悪癖1**: ふだん漢語・カタカナ語で言う物事を、わざわざ和語に開いて言い換える
  （確認→確かめ、修正→直し、計測→測り、切り分け→割り出し、キャッシュ→控え、コピー→写し、
  説明の無い造語）。普通に通じる和語（引く・探す・立てる・止める・回す）は問題ない
- **悪癖2**: 「この場面でその判断が悪い」という指摘を、以後の全面禁止の宣言に広げる

## 2. 計測方法

集計スクリプトは `docs/adr/probes/wording-habits/wh.py`。**この数え方は、例として挙がった語の出現の目安にすぎない。**
癖は一般的な傾向として出るので、例の語だけを数えても例以外の分は見えず、同じ語でも文脈によって適切にも意味不明にもなる
（これは正規表現では判定できない）。効果の判断には、§9 のモデルが文脈で判定する方法を使う。`wh.py` の値は、その参考として読む。

```bash
# 週別（悪癖1・2 の件数）。期間は ISO 8601 で渡す
python3 docs/adr/probes/wording-habits/wh.py --since 2026-10-20 --by week --exclude-project 'wording|wh-[0-9]+'
# 語別の件数と、開いた語の直前・直後1文字の分布（正規表現の誤検出の点検用）
python3 docs/adr/probes/wording-habits/wh.py --since 2026-10-20 --by word --ctx --exclude-project 'wording|wh-[0-9]+'
# 系統別（text・final・send・memory・herdr・gh）。final は各ターンの最後の本文
python3 docs/adr/probes/wording-habits/wh.py --since 2026-10-20 --by channel --channel text,final,send,memory,herdr,gh
```

- 入力は `~/.claude/projects/*/*.jsonl` の assistant の発言。次の6系統を分けて数える。全体で約20GBあり、全期間の走査は10分前後かかる
  - `text`: 返事の本文のブロックすべて（ツール呼び出しの合間の本文も含む。持ち主には表示される）
  - `final`: **各ターン（人間の入力から次の入力まで）の最後の本文**。Stop hook が点検できる範囲に当たる
  - `send`: `SendMessage` の本文。`memory`: `/memory/` 配下への Write・Edit の本文
  - `herdr`: `herdr agent prompt`・`herdr pane run`・`herdr pane send-text` を打つ Bash のコマンド全体
  - `gh`: PR の作成・コメント・編集（`gh pr create/comment/edit`）と、レビュー・コメント・返信への `gh api` の**書き込み**
    （パスに `reviews|comments|replies` を含み、`-X`/`--method` の POST・PATCH・PUT、`-f`/`-F`/`--field`/`--raw-field`、`--input`
    のどれかがあるもの。オプションの順序に依らない）を打つ Bash のコマンド全体。読み取りの `gh api` は数えない。
    **`--body-file`・`--input` に渡すファイルの中身（Write で作る本文）は含まない**ので、PR 本文・レビュー本文の数字は過小になる
- 出力は件数・割合だけで、本文は出さない。`--ctx` が出すのも前後1文字の分布だけ
- 指標: 開いた語の出現数（OPEN）、同じ意味の漢語・カタカナ語の出現数（PLAIN）、
  両者の比（開いた語 ÷ 合計）、万字あたりの出現数、全面禁止の言い回し数（BAN）、
  開いた語を1つ以上含む発言の数。使ってよい和語は、どの正規表現にも入れていない
- 誤検出を除く方法:
  - コードブロック・インラインコード・`>` の引用行・パスと URL・「」『』の中を数えない（語そのものへの言及を外すため）
  - 普通の用法を前後の文字で外す。直し: やり直し・見直し・書き直し・立て直しのような「〜し直す」型
    （前の文字で外す。後ろの文字では外さないので、直した・直したい・直しました・直して はすべて数える）。
    写し: 書き写し・映し・写し出す。控え: 控えめ・控える・控えて。測り: 計測り・推測り。
    全面禁止: 「一切」単独は数えず、禁止の述語と組になったときだけ数える
  - 語を話題にした会話（この傘の作業のセッション）は `--exclude-project` で外す
- 限界: **開いた語の比は上限の見積もり**。「確かめる」「直す」は、文脈によっては普通の言葉であり、
  計測では悪癖の用法と区別しきれない。絶対値より、同じ式での前後の差を見る道具として使う。
  悪癖2 は件数が少なく、週ごとの揺れが大きい

### 4.1 試験（実際の Claude Code と合成入力）

試作は `docs/adr/probes/wording-habits/stop_hook_prototype.py`。判定の語・正規表現は `wh.py` と同じものを使う。

- **合成した入力の JSON を直接渡す試験**（8ケース）: 開いた語（確かめ・直し）→ block。全面禁止（二度と〜しない）→ block。
  漢語だけ、使ってよい和語（引く・探す・止める・立てる・回す）、やり直し・見直し・書き写し・控えめ、
  事実としての「一切変更は無い」、コード・「」の中、`stop_hook_active` が真の再入 → いずれも何も出さない
- **実機の試験**（一時ディレクトリで `claude -p --settings <一時ファイル> --model haiku`、1回）:
  hook が起動して結果を返し、返事が2ターンになった（書き直しが起きた）。追加の費用は約0.004ドル。
  ただし試験の指示が「そのまま書き写して」だったので、書き直し後の返事にも元の語が残った。
  **仕組みが動くことは確認できたが、自然な返事で悪癖が減るかは未確認**。実 `$HOME` の設定は触っていない
- 公式文書で確認できた仕様: Stop の入力に `last_assistant_message` と `stop_hook_active` がある。
  `decision: block` か exit 2 で続行させる。連続8回続くと次の block は無視される（`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` で変更可）。
  `prompt` 型は `Stop` と `PreToolUse` で使え、`SessionStart` では使えない

## 5. 悪癖2 の扱い

- 悪癖2 は言葉ではなく判断の癖で、**点検で抑えられるのは、言い回しとして表に出た部分だけ**である。
  「一切〜しない」「二度と〜しない」「今後は〜しない」のような宣言の形は C・E の正規表現で検出できる
  （上の試験で確認）。ただし判断そのもの（指摘を禁止に広げる）は検出できない
- メモリ・ほかの会話への指示に広げる行為は、E（メモリへの書き込み・`SendMessage`・`herdr` と `gh` の送信の点検）で止められる見込みがある。
  この調査での件数はメモリ 0件・送る文 2件で、計測上はほぼ出ていないが、件数が少なくても影響の大きい癖である
- 指示文の書き方としては、「指摘は、その場面で何が悪かったかの話である」と**状況を述べる形**で書き、
  「〜してはいけない」の列挙にしない。規則を作って判断を丸投げする形を避ける（計画書 決定的な制約）
- 抑えられない範囲: 宣言の形をとらずに、静かに振る舞いを変える・メモに残す、といった形の広げ方は、言葉の点検では見つからない

## 6. 推奨案（取り下げた）

孫1 は、`Stop` hook（command 型、正規表現）を1本入れ、開いた語と全面禁止の言い回しを点検して書き直しを促す案を推奨した。
**この推奨は取り下げた。** 理由は次の2点。

- 挙がった語は例にすぎず、癖は一般的な傾向として出る。語のリストを増やしても例以外の分は見えず、リストが長くなるほど
  普通の用法を止める誤りが増える
- 語の適否は文脈で決まる。同じ語が、ある文脈では読み手の使う名前で、別の文脈では意味不明になる。それを見分けるには
  意味の理解が要り、正規表現では判定できない。「確かめる」「直す」を誤検出なしに分ける正規表現は書けない
  （§2 の限界の節が既に認めていた点を、推奨の根拠にしてしまった）

出発点の誤りは、計画書の指標の指定（例の語の出現数）にある。採用した方法は、読み手の名前という向きを持たない基準を
文章にして指示文にし、AI が毎回読む文書そのものを基準に沿った文体へ書き直し、効果をモデルの文脈での判定で測る方法である。
理由と採らなかった案は ADR DOC-2611172307-a にある。

候補 C・E（hook で点検する案）の表の記述（§4）は、孫1 が調べた仕様と費用の記録として残す。D（モデル判定の `Stop` hook）は、
毎ターンの費用と遅延が全返事に乗るので、計測の道具としてだけ使う（§9）。

## 7. 指示文で抑える方法の外部の事例（2026-11-17、サブエージェントで調査）

要点だけを残す（出典は各リンク）。

- Anthropic の公式ガイド（https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices）:
  「するな」より何をするかを書く。理由を添えると、モデルが表に無い場合にも一般化する。良い例と悪い例を3〜5組示すのが
  最も確実な方法の1つ。**指示文自体の文体が出力の文体に影響する**
- 見本を渡すのが最も効いたという個人の報告（https://zenn.dev/tabayashi/articles/how-to-deodorize-ai-writing）: 「AI 臭を避けて」の指示は
  そこそこで、自分の文書を2〜3本渡して「この文体を真似して」と指示すると定型句がほぼ消えた
- 「指示は個々の語には効くが、癖を生む機構には効かない」「比喩をやめて、実物や実際の動作を名指す」
  （自社の実測1件、約25万字。https://fyve.co.jp/ai-advisor/articles/ai-text-style-english-calque）
- 禁止語を名指しすると、かえって出やすくなる研究（小型モデルでの実測。https://www.arxiv.org/abs/2601.08070）
- 決まり文句は症状で、原因は中身（具体的な主張・数字）の欠如。表面だけ消すと検出しにくくなるだけ
  （https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing）
- 長い会話では CLAUDE.md の効きが落ちるという報告が複数ある（GitHub の issue）。毎ターンの再注入で多少は保てるが、ずれる
- 「読み手の名前」と「指摘の全面禁止への拡大」を指示文で扱って効果を計測した事例は見つからなかった
- 実際に読み込まれる文書の文体: dotfiles のスキル本文は開いた和語の文体で書かれている。向きを持った規則
  （「横文字を避ける」）が、定着した語まで日本語にする原因になりうる

これらから、基準の文書は禁止の列挙ではなく、目標・理由・境界・良い例と悪い例で書くことにした（ADR DOC-2611172307-a）。

## 8. 毎ターンの再注入の試算（直近7日の会話 344本）

- 人間（または他の AI）からの入力の回数は、中央値1・上位10% で5・上位1% で29・最大911。会話の最後の文脈は、中央値約12万・
  上位10% で約20万トークン
- 注入する文を1回約250トークンとすると、5回で約1,250（文脈の0.6%）、29回で約7,000（約3%）、911回で約22万で、
  長い会話ほど文脈を圧迫する。効いてほしいのはその長い会話（CLAUDE.md が遠くなる）
- 効果は計算できない。計測するなら、過去の長い会話を途中から分岐させて（`claude --resume --fork-session`）、注入の有無で
  返事を作らせてモデルに判定させる実験になる
- 判断: 書き直しの後に、長い会話で癖が残るかを見てから採否を決める。実施するなら、前回の注入から文脈が一定量増えたときだけ

## 9. モデルが文脈で判定する計測の基準値と、読まれる頻度（導入前、2026-11-17）

正規表現でなく、基準の文書（DOC-2611172307）をそのまま判定の基準に渡して、モデルが文脈で判定する。判定の対象は、
持ち主に表示される各ターンの最後の本文（final）と、他の AI への送る文（send）。会話の本文は書かず、集計値だけを残す。

### 9.1 モデル判定の基準値

```bash
# 基準値（Haiku）。同じ引数で期間だけ変えて、導入後に比べる
python3 docs/adr/probes/wording-habits/wh_judge.py --since 2026-11-10 --until 2026-11-17 --n 300 --batch 10 \
  --exclude-project 'wording|wh-[0-9]+' --out-dir "$(mktemp -d)" --samples <リポの外のファイル>
```

- 期間 2026-11-10〜2026-11-17（`--exclude-project 'wording|wh-[0-9]+'`）、候補の発言 3,892 件（80字以上6,000字以下）から無作為に300件（乱数の種 1）。10件ずつまとめて判定
- 結果（Haiku）:

  | 対象 | 件数 | 読み手の名前から外れる（1） | 決まり文句（2） | 全面禁止への拡大（3） |
  |---|---|---|---|---|
  | 全体 | 300 | 17.7%（53件） | 0.0%（0件） | 1.3%（4件） |
  | final | 225 | 15.6% | 0.0% | 1.8% |
  | send | 75 | 24.0% | 0.0% | 0.0% |

- **判定役の条件**: 判定役は一時の作業ディレクトリと一時の設定ディレクトリ（`CLAUDE_CONFIG_DIR`。認証は、実設定のアクセストークンを環境変数
  `CLAUDE_CODE_OAUTH_TOKEN` で渡し、資格情報のファイルは置かない。symlink で渡すと、判定役がトークンを更新したときに
  更新後の資格情報が一時ディレクトリにだけ書かれて消え、実ファイルが古いまま残るため）で動かし、プロジェクトの `CLAUDE.md` も `~/.claude/CLAUDE.md`（人格の import を含む）も読ませない。
  読ませると、この PR の配布後に `~/.claude/CLAUDE.md` が変わって判定の条件が変わり、導入前後を比べられなくなる。
  最初に取った値（21.3%）は `~/.claude/CLAUDE.md` を読んだ判定役のものだったので、この条件で取り直した
- **費用**: 300件で約0.09ドル（1件約0.0003ドル）。Sonnet は同じ式で60件が約0.18ドル（1件約0.0029ドル）で、約10倍。
  Sonnet の同じ期間60件（乱数の種 1 で別の件が選ばれる）は、1 が53.3%、2 が0%、3 が0%
- **Haiku と Sonnet で1の割合が3倍ほど違う**。判定の厳しさがモデルで違い、絶対値は判定のモデルに依る。**同じモデル・同じ式で
  前後を比べる**こと。2 が両モデルで0%なのは、基準の「中身の無い決まり文句か」を、判定が厳しく取りすぎているか、
  この期間の返事に実際に出ていないかのどちらか。口調の指定（`CLAUDE.machine.md`）で減ったという報告と合うが、
  判定が人の読み方と合っているかは、次の抜粋で確認する
- **判定の妥当性は未確認**。約20件（該当と非該当を混ぜる。本文と判定の理由つき）をリポの外の
  `~/.local/state/umbrella/wording-habits/judge-samples.md` に置いた。判定の割合が人の読み方と合っているかを
  確認する。合わなければ判定の基準（基準の文書）か判定のモデルを直して基準値を取り直す
- 限界: 判定は1回の呼び出しで10件をまとめて見る。1件ずつ見る場合と結果が変わる可能性がある（未確認）。送る文の件数は少ない
