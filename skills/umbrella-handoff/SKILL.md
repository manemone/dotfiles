# umbrella-handoff — 相談から傘司令官への引き継ぎ自動化

**AI 不問。** 相談を受けていた側（以下「相談AI」）がこのスキルを読んで振る舞う。
YAML frontmatter を除き自然言語のみで完結する。

## 1. 埋める空白地帯

`skills/umbrella-orchestrator/SKILL.md` は**計画書が既にある地点からしか始まらない**
（同スキル §3.5 の前提「計画書が作成済みで、全孫のプロンプトが記述済みであること」、
補足「計画書の作成・レビューは人間が行う前提」）。その手前の工程は誰の担当でもなく、
これまで人間が毎回口頭で指示していた。このスキルはその工程を埋める。

```
相談で問題意識が固まる
  → ブリーフを起草する（相談AIの仕事。§3 のテンプレートを使う）
  → 傘ブランチ名を決める
  → 傘ブランチをターゲットブランチから切る
  → ocw -H（--no-commander を付けない = 3ペイン）で司令官ワークスペースを作る
  → herdr workspace rename で日本語ラベル化（既定形のときだけ上書き）
  → ブリーフを傘ワークツリー内に置く（§4。scratchpad には置かない）
  → commander へ「ブリーフを読んで計画書を書き、umbrella-orchestrator で進めろ」を渡す
  → 到達を確認する
  ↑↑↑ ここまでがこのスキルの担当範囲 ↑↑↑
  → （ここから umbrella-orchestrator の担当範囲。相談AIは手を引く）
```

## 2. 線引き（最重要・明示的に禁止する）

人間の不満の核心は「**相談AIが、その場で実装を始めたり計画書を書き始めたりする**」
ことである。このスキルを実行している間、相談AIは次を**行わない**。

- 相談していた会話で実装を始めない
- 相談していた会話で計画書（`docs/planning/DOC-*_計画.md`）を書かない
- 孫の分割・順序・孫用プロンプトの起草をしない（すべて司令官＝commander の仕事）

**ブリーフはあくまで material であり、計画書ではない。** §3 のテンプレートの冒頭に
必ず「これは計画書ではない。計画書は司令官が本ブリーフを material として書くこと」を
書かせる。これを欠くと、commander がブリーフをそのまま計画書として扱ってしまう
（またはブリーフを薄い要約と誤解して詳細を落とす）事故につながる。

## 3. ブリーフのテンプレート

相談AIが対話から起こす。**逐語引用を要約に置き換えないこと。** commander は人間と
直接話していないので、要約すると人間が本当に困っている点が失われる。

```markdown
# ブリーフ: <傘の一言テーマ>

**これは計画書ではない。** 計画書は司令官が本ブリーフを material として
`docs/planning/DOC-*_計画.md` に書くこと。本ブリーフは一時ファイルであり、
以降のどこかの時点で消える・参照できなくなる前提で扱われる。**必要な内容は
計画書へ全部転記すること。**

## 問題意識（逐語）

> （人間の発言をそのまま引用する。要約しない。複数回に分かれていれば全部引用する）

## 人間が確定させた決定事項（覆さないこと）

- （相談中に人間が明言した「これはこうする」「これは変えない」を列挙）

## 既存の穴

- （どのスキル／どの工程がこの問題意識をカバーしていないか。根拠となる該当箇所を引用する）

## 実測値

- （測った日・対象・条件を添える。測っていなければこの節ごと省略してよい）

## 決定的な制約

- （既存 ADR・AGENTS.md の最重要ルールなど、司令官の判断を縛る制約）

## スコープ外

- （この傘で扱わないと決まっているもの。並走する別の傘との切り分けも含む）

## 必須の検証ステップ

- （AGENTS.md「コミット前の必須ステップ」からこの傘に関係するものを転記）

## 孫分割の叩き台

**これは叩き台であり、司令官が再設計してよい。** 相談AIが孫分割・順序・
孫用プロンプトを確定させる権限は持たない。

- （思いつく分割案があれば書く。無ければ「未検討」と明記する）
```

## 4. ブリーフの置き場所

**scratchpad には置かない。** scratchpad は相談AI自身のセッション固有の一時
ディレクトリであり、commander は別のワークツリー・別のセッションで動くため、
パスが読めない／読めても消えている可能性がある（過去にこれで人間が「一時ファイル
なので計画書に全部落とし込め」と口頭で補う事故が起きている）。

代わりに、**§5 で作った傘ワークツリーの直下**に置く。

```bash
git worktree list | grep "\[<傘ブランチ名>\]"
```

の1列目（絶対パス）を取り、そのディレクトリ直下に `.umbrella-handoff-brief.md` として
書き込む。ドット始まりのファイル名で「一時ファイルである」ことを示す。`docs/planning/`
配下には置かない（DOC-ID 採番の対象と誤認されるのを避けるため。§3 のテンプレート冒頭で
「一時ファイルである」ことは既に明示している）。

commander には**絶対パス**で渡す（§6）。commander が計画書への転記を終えたら、
このファイルは削除してよい（コミット対象ではないため必須ではない）。

## 5. 傘ブランチとワークスペースの作成

1. **傘ブランチ名を決める。** 相談の内容から短い英語スラグを起こす
   （例: `agent-handoff`）。人間に確認してよい
2. **ターゲットブランチを決める。** 通常は `master`。人間から別の指示があれば従う
3. **ワークスペースを作る**（3ペイン。`--no-commander` を付けない — 傘の司令官
   ワークスペースは常に3ペインであることは `umbrella-orchestrator/SKILL.md` §5
   「ワークスペース階層」参照）:

   ```bash
   ocw -H <傘ブランチ名> <ターゲットブランチ>
   ```

   出力例:
   ```
   workspace:   w0
   commander:   w0:p1
   implementer: w0:p2
   reviewer:    w0:p3
   ```

4. **日本語ラベルへ改名する**（`umbrella-orchestrator/SKILL.md` §5「ワークスペース
   ラベル」の書式に従う）:

   ```bash
   herdr workspace rename <workspace_id> "<repo_name> :: <傘の日本語要約>"
   ```

   傘の日本語要約は全角12文字以内の目安（サイドバー幅で末尾が切れないように）。
   ブリーフの問題意識から相談AI自身が起こしてよい（commander が計画書の H1 から
   機械導出する既定ロジックを待つ必要はない。この時点で計画書はまだ無い）。
   **rename が失敗しても警告のみで続行する**（表示上の都合であり引き継ぎを止める
   理由にならない）。

   **Herdr が使えない環境**（`HERDR_ENV` が立っていない、`ocw -H` が使えない）では、
   ワークスペース作成・改名の代わりに次を行う:

   ```bash
   git worktree add -b <傘ブランチ名> ../<傘ブランチ名> <ターゲットブランチ>
   ```

   を実行し、人間に「新しい会話でこのワークツリーを開き、ブリーフ
   `<ブリーフの絶対パス>` を material として計画書を書き `umbrella-orchestrator`
   で進めるよう指示してください」と案内する。§6・§7 は Herdr がある場合のみの手順。

## 6. commander への引き継ぎ送信

**送信は `skills/umbrella-orchestrator/SKILL.md` §5「AI間送信手順（二段構え）」に
従う。正典はそちらにあり、本スキルは参照するだけで全文をコピーしない。**
背景・実測・却下案は ADR
[DOC-2609072215](../../docs/adr/DOC-2609072215_ai-to-ai-messaging-channel.md) 参照。

要点（詳細は参照先）:

- 相談AI自身が `SendMessage` を呼べる Claude Code セッションで、かつ commander
  ペインの `agent`（`herdr pane get w0:p1`）が `"claude"` であれば `SendMessage`
- どちらかが満たされなければ、従来どおり `herdr pane run` + `send-keys Enter`
  （§5「herdr pane run の最重要注意点」の4項目 — 全文を打ち込まない、メタ指示を
  付けない、Enter を確認する、同じ本文を再送しない — をそのまま踏む）

**送信内容に必ず含める要素**（`SendMessage` 経路でもこれは変えない。長さの制約が
消えても、正典を1箇所に保つという理由は消えないため）:

- ブリーフの**絶対パス**
- 「このブリーフを material として `docs/planning/` に計画書を作成し、
  `umbrella-orchestrator` の作法に従って孫の spawn まで自律的に進めてください」
- 「ブリーフは一時ファイルなので、必要な内容は計画書に全部落とし込んでください」

**付けてはいけないもの**:

- プロンプト全文の詳細な指示（計画書の書き方は `umbrella-orchestrator/SKILL.md` が
  持っている。二重に書かない）
- 「〜とだけ返事してください」のようなメタ指示（受け手がそれを実行して返事だけして
  停止する）

**推奨フォーマット（これだけ送ればよい）**:

```
ブリーフ <ブリーフの絶対パス> を material として docs/planning/ に計画書を作成し、umbrella-orchestrator の作法に従って孫の spawn まで自律的に進めてください。ブリーフは一時ファイルなので、必要な内容は計画書に全部落とし込んでください。
```

## 7. 到達確認

`umbrella-orchestrator/SKILL.md` §5「AI間送信手順（二段構え）」#4「到達確認」に従う。
送信直前の commander ペインの `agent_status` を控え、送信後に変化していることを
確認する。変化していなければ `herdr pane read` で画面を目視するか、フォールバック
経路へ切り替える。

到達を確認できたら、**相談AIはここで手を引く。** 計画書の内容にも孫分割にも
以降口を出さない（§2 の線引き）。人間には「傘 `<傘ブランチ名>` の commander へ
引き継ぎました」とだけ報告する。
