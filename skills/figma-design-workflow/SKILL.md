# figma-design-workflow — Figma の画面の作り込みを、傘ブランチで進める

リポの外にある**正本**（Figma のファイル）を、複数の会話で書き換えながら画面を作り込む手順。
芯は次の 3 つ。

- **戻せる形で書く。** 書く前に控えを取り、書いた後に控えと数で突き合わせる。危ない作業は「読むだけ」と「書く」に分け、間で止まる
- **決まりにして、全画面で点検する。** 指摘された 1 か所だけ直さない。決まりを書き、スクリプトで全画面を数え、0 を確かめる
- **変更は記録でレビューする。** リポの差分には Figma の変更が出ない。数と絵を 1 件 1 記録にして、そこをレビューの対象にする

主な読み手は、作り込みを進める傘の**司令官**と、その傘の**担当**（孫の会話。孫用プロンプトから
「このスキルの〜を読め」と参照される）。

## いつ使うか・使わないか

使う: 傘ブランチで、Figma の画面（叩き台・デザイン案）を複数の会話で作り込むとき。

使わない:

| 場面 | 向かう先 |
|---|---|
| 実装した画面（ブラウザの画面）の確認 | `ui-review` |
| Figma の API の使い方そのもの（`use_figma` の書き方など） | Figma 公式のスキル（`figma-use` など）。このスキルには書かない |
| 孫の spawn・マージ・巡回 | `umbrella-orchestrator` |
| PR のレビューの往復 | `pr-review-loop` |
| 作業の振り分け（傘にするか・どこへ引き継ぐか） | `task-intake` |

Figma を使わない傘には要らない。既存スキルが扱わない部分（外部の正本の書き換え・数と絵での確認・ユーザーに絵を見せて
決めてもらう流れ）だけをこのスキルが持つ。理由と却下案は ADR DOC-2611161826（本文は
`docs/adr/` の `figma-design-workflow-skill`）にある。

## 用語

| 用語 | 意味 |
|---|---|
| 司令官 | 傘を進める会話。Figma の決まり（色・字・すき間などの決め）の持ち主でもある |
| 担当 | 孫の会話。Figma を書く作業を 1 件ずつ受け持つ（`umbrella-orchestrator` の「実装AI」にあたる） |
| レビュワー | 担当の PR（記録）をレビューする会話（`pr-review-loop` のレビュー役） |
| 画像生成役 | 案の絵・比較の絵を作る会話 |
| 下請け | 担当が細かい調べ物に使うサブエージェント |
| ユーザー | 決めをする人間。絵を見せて選んでもらう相手 |
| 正本 | Figma のファイル（リポの外にある、書き換える対象） |
| 控え | 書く前に正本から取る写し（戻せるようにするため） |
| 記録 | 1 件ごとにリポへ残す文書（控え・前後の数・絵・決め）。Figma の変更のレビューはこれで行う |
| 決まり | 色・字・すき間などの、画面をまたいで揃える決め。点検スクリプトの表になる |

## 体制

| 役 | 中身 | 連絡 |
|---|---|---|
| 司令官 | ユーザーと話し、担当へ仕事を出し、絵と数で受け入れを決め、承認された孫の PR を傘へマージする。自分では Figma の大きな作業をしない（読むだけの下調べと 1 か所の直しは自分でしてよい） | ユーザーとは本文。担当とは AI間送信（`umbrella-orchestrator` §5） |
| 担当 | 画面のまとまり・共通の部品など、範囲で分けた会話。Figma を書き、記録を書き、PR を出し、`pr-review-loop` で承認まで回す。**マージはしない** | 司令官へ送信。担当どうしも送信で合わせる |
| レビュワー | 担当ごとのペイン。`pr-review-loop` が頼む。上限に当たりにくい AI で起動する手もある（後述「上限と自動再開」） | `pr-review-loop` |
| 画像生成役 | 案の絵・比較の絵を作る。依頼は依頼書ファイルに書き、パスだけ送る | 相手の AI に合わせた送り方 |
| 下請け | 読むだけの調べ（コードの現状・Figma 全体の分析など）。軽いモデルでよい | 結果は呼んだ会話へ返る |
| ユーザー | 見た目の決めをする | 司令官の会話だけを見ている |

- 担当の範囲は「画面のまとまり」と「部品」で切る。共通の部品の担当が、部品の本体・字のスタイル・変数の大きな作業を持つ
- 担当がいない範囲は、手の空いた担当へ回す。宛先は `ListAgents` などで確かめる
- 実装の傘が別にあるときは、その司令官とも連絡する約束をする（記録が傘に入ったら知らせる）。実装への受け渡しは
  [references/handoff-to-impl.md](references/handoff-to-impl.md)

### 誰が何を決めるか

- **決まり（色・字・すき間などの決め）** は司令官が持つ。実装の側から決めを聞かれたら司令官が決める。Figma の方が誤りなら、
  Figma を実装に合わせて直す
- **微差**（数 px・字の 1 段・影・色のわずかな差）は司令官が決め、結果だけまとめて知らせる
- **見た目が目に見えて変わる物・意味が変わる物・決まりを覆す物・外への書き込み**は、ユーザーが決める
- 他の会話から回ってきた仕事は、自分の範囲かをまず確かめる（[patterns-process.md](references/patterns-process.md)）

### 担当が人間の承認で止まったとき

担当が、人間の承認が要る操作（権限の確認・Figma の書き込みの許可など）で止まったら、**司令官が自分の会話のダイアログで
ユーザーに聞く。** 「担当のペインで答えて」と言わない（ユーザーは司令官の会話だけを見ていて、どのペインのことか分からない）。

- 何を・なぜ・消える物・おすすめを、それだけで分かる文で書く。同じ種類の承認が複数の担当に要りそうなら、まとめて 1 回で聞く
- 答えは担当へ送る。「司令官のダイアログで承認された」と出所を書き、確かめの条件（残る変更が想定の物だけか、など）を付ける
- **ただし、破壊的な操作は伝言の承認では担当が動けない**（会話をまたいで許可を渡せない。担当が断るのが正しい）。その種の
  操作は、「担当のペインで直接答えてもらう」か「担当に頼まず司令官の会話から人間に実行してもらう」かをダイアログで選んでもらう
- Figma の書き込みが担当側の自動判定に止められたら、回避せず**1 回だけ**聞く。作業全体の書き換え（範囲を書く）をまとめて
  1 つの問いにする。1 画面ずつ聞かない。聞く役（司令官か担当）を決め、二重に聞かない

## 1 件の流れ

1. **依頼を受ける。** ユーザーの指摘・依頼を受け、今の Figma を自分で読んで、指摘の場所と原因を確かめる
   （画像 1 枚と、読むだけの 1 回まで）
2. **決まりにする。** 決まりにできる物は決まりの形にする（例: 「この画面の灰色が浮く」→「カードの中に灰色の地を付けない」）。
   1 か所だけ直して終わりにしない（[patterns-process.md](references/patterns-process.md)「決まり＋全画面の点検」）
3. **担当へ依頼を出す。** 依頼には、ユーザーの指摘（要点）と決まり・直す所と触らない所・確かめ方（数の突き合わせ・絵の枚数）・
   書く記録のファイル名・PR の出し方・誰の判断か（ユーザー／司令官）を入れる
4. **危ない作業は 2 段に分ける。** 部品の本体の作り替え・入れ替え・消す・結び直しは、担当が先に**読むだけ**で調べて報告し、
   司令官が了承してから書く。消す前には、控えが全部のインスタンス・全部の段を拾えているかを、司令官が自分の読み方で
   抜き取って確かめる（「控えを取れ」と指示しただけで中身を確かめない、をしない）。いきなり全部に書かせず、1 画面で試して広げる
5. **控えを取って書き、数で突き合わせる。** 書く前に控えを取る（後述「Figma の安全」）。書いた後に、控えと前後の数を突き合わせる。
   比べる元の数は、書いた後どうしでなく**必ず書く前に取る**
6. **絵を見る。** 見た目がはっきり変わる物は、担当が絵を司令官へ送り、司令官が見てからユーザーに見せる。微差は司令官が
   決め、直した後に画面を 1 枚見るだけにする（切り出し・拡大図・比べの枠を何枚も作らない）
7. **記録を書き、PR を出す。** 1 件 1 記録。書き方は [references/record.md](references/record.md)。PR は傘ブランチ向きで、
   `pr-review-loop` で承認まで回す。Figma の変更はリポの差分に出ないので、レビュワーは記録（数・絵）を見る
8. **傘へマージする。** 承認の確認・マージは司令官が `umbrella-orchestrator` の手順（§3.6）で行う。担当はマージしない。
   マージしたら担当へ傘の先頭を知らせ、実装の傘に関係する物はそちらの司令官へ知らせる

spawn・マージ・巡回の手順は `umbrella-orchestrator`、PR の往復は `pr-review-loop` にあり、ここには写さない。

## ユーザーとのやり取り

- **問いは、それだけで分かる文にする。** 場所（画面 → パネル → 物の順に、画面に出ている言葉で）・今の見え方・案の見え方・
  おすすめと理由・迷っている理由を書く。「案A/B」や記号だけの表、こちらの作業の中でしか通じない呼び名に縮めない。
  状況のまとめを頼まれたときも、問いの部分は縮めない。多いときは縮めず分けて出す。複数あれば 1 回にまとめて聞く
- **担当の報告の言葉をそのまま流さない。** 司令官が実物を見て、ユーザーに通じる言葉に言い直す
- **聞く前に、今の Figma で確かめる。** 決定の表に残った古い未決を、今の画面を見ずに投げない（もう決まっている項目・画面に
  無い項目を聞く失敗が実際にあった）
- **足りない物は、聞かずに作って見せる。** 文書にも Figma にも無い物（吹き出しの文・押した先の決まり・ふつうの作りで決まる
  仕様）は、「作ってよいか」と聞かず、作ってできた物を見せて直しを受ける。確認事項の一覧に「作ってよいか」を混ぜない。
  聞くのは、見た目を作り替える物（案を並べて聞く）と、ユーザーしか知らない事実だけ
- **絵を見せて選んでもらう。** 言葉で説明せず、今の形と案を並べた絵を見せる。案は、まず同じ画面の既存の型の当てはめから作る
  （新しい作りは、既存の型で収まらない理由を言えるときだけ出す。[patterns-process.md](references/patterns-process.md)）
- **両極端にしない。** 全部聞くのも、全部黙って進めるのもよくない。値をそろえるだけの物は司令官が決めて進める
- **返事を待つときは、何を待っているかを最後に必ず書く。**
- **誤りは言い訳せずに先に謝り、** 原因と直し方を短く書く
- **画面の言葉づかい**（くだけすぎていないか）は、指摘される前に司令官が気づいて直す案を出す
- **報告には、ユーザーが見に行ける場所**（画面名・ノードの識別子）を書く。ブラウザのリンクは本文に貼らない
- **司令官は、担当の返事待ちで手を止めない。** 待つなら見張り（定期の巡回）を仕掛け、ペインの状態と PR を見て、止まっていたら
  原因を調べて動かす。返事の要らない仕事（レビュー依頼・読むだけの調べ・手の空いた担当への振り分け・文書）は、待つ前に
  全部出す。ターンを終える前に、(1) 返事に頼らない仕事を全部出したか (2) 見張りを仕掛けたか、を確かめる

## Figma の安全

### 書いてよい範囲

- 書いてよいのは**作業のページだけ**。試作置き場はその中に置く
- 答えの出た試作と、見てもらった札の置き場（保管のページ）に書くのは、**ユーザーの許しがあるときだけ**。許しの範囲
  （字の中身だけ・大きさだけ、など）を記録に書く
- ほかのページは読むだけ
- **部品の本体を直すと、保管や他のページのインスタンスにも伝わる。** 直接書いていなくても伝わるので、伝わる数を先に数えて
  記録に書く

### 控えの取り方

- インスタンスの上書き（字・大きさ・表示/非表示・入れ子やスロットの中）を、**層の順で**控える。層の名前で探さない
  （同じ名前が多く、名前を上書きした物を拾えない）
- 字は中身だけでなく**値も**控える（識別子と欄の名前だけの控えでは戻せなかった）
- 塗りの**不透明度も**控える
- Figma の MCP は版の履歴を読めない。**消した物は AI だけでは戻せない**と考える
- 戻し元が要るときは、作業の前の時点のファイルの複製を、ユーザーに作ってもらう（版の履歴から）。複製はノードの識別子を
  引き継ぐので、識別子で突き合わせられる。複製の時刻（どの作業より前か）を記録に書く。古い複製を使うときは、その後に
  足された物が無いかを確かめる
- 部品の本体を消す・作り替える前に、司令官が控えを抜き取って確かめる（上の「1 件の流れ」4）

落とし穴（結ぶと不透明度が戻る・入れ替えると上書きが落ちる、など）は [references/pitfalls.md](references/pitfalls.md) を引く。
ここには写さない。

### 上限と自動再開

- **Figma の MCP の呼び出しには上限がある**（1 日あたり・1 分あたり。傘のすべての会話で分け合う。数値は公式の文書で確かめる）。
  読む呼び出しを減らし、1 回に読み書きをまとめる。上限のエラーが出たら 2〜3 分待ってやり直す（3 回まで）。戻らなければ
  止めて、記録に書いて司令官へ知らせる。直しは「戻せる形で 1 回に」入れる。担当は、その日の回数を報告に書く
- **AI の利用の上限で会話が止まる**ことがある。レビュワーは、上限に当たりにくい別の AI で起動する手がある。今動いている
  レビュワーは、途中で止めると無駄になるので止めない
- **司令官は、定期の巡回（例: 20 分おき）でペインを見回り、** 利用の上限で止まったペインにだけ「続けてください」と送る。
  巡回は会話の中だけで動き、期限がある（切れたら入れ直す）。`umbrella-orchestrator` の巡回の手順に従う
- **担当は、文脈が大きくなったら、区切りで `ocw self-compact` で自分を compact する。** 復帰メモに続きの手順を書いてから行う
  （手順は `pr-review-loop` と `umbrella-orchestrator` §3.7）

## 作業量の目安

丸めた目安。計画と巡回の間隔を決めるのに使う。

- 担当 1 人の Figma の大きな作業（部品の入れ替え・結び直し）は、1 件で数時間かかる。控え・突き合わせで、読み書きの呼び出しを
  1 日に数十回使う（上限の節の呼び出し回数を超えないよう、担当の数と並行度を決める）
- 1 件の孫の PR は、レビューで 2〜5 回まわる
