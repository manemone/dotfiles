# よく指摘されることと、Figma の落とし穴

Figma の作業に入る前、または記録・PR を出す前に、同じ失敗を踏まないかを確かめるときに読む。
1 項目 1〜3 行で「何が起きる → どうする → 詳しくは」の形にしてある。手順の本文はここに写さず、引く先に任せる。

引く先の略称: [SKILL] = [SKILL.md](../SKILL.md)、[進め方] = [patterns-process.md](patterns-process.md)、
[見た目] = [patterns-visual.md](patterns-visual.md)、[記録] = [record.md](record.md)、
[点検] = [audit.md](audit.md)、[受け渡し] = [handoff-to-impl.md](handoff-to-impl.md)。

## Figma の落とし穴（実際に踏んだ物）

### 塗り・色

- **塗りを変数に結ぶと、塗りの不透明度が 1 に戻る。** → 結んだ後に元の値を書き戻す。点検に「半透明の数が結ぶ前後で
  同じか」を入れる。詳しくは [見た目]「色の 2 段」・[点検]「書く前の数と比べる」
- **変数の値を別名に書き換えても、結んだ塗りの不透明度が 1 に戻る**（結び直しに気をつけていても起きる）。
  → 比べる元の数は、書いた後どうしでなく**必ず書く前に取る**。半透明の役割は、色に透明度を持たせた直の値にする。
  同じ変数に結んだ他の層も半透明になるので、結ばれている層を先に全部見る。詳しくは [見た目]「色の 2 段」・
  [点検]「書く前の数と比べる」

### 字

- **字をスタイルに結ぶと、元のスタイルにあった括弧の半角詰め（OpenType の HALT）が消えて字の幅が変わる。**
  プラグインの API では HALT を書けず、消えたら戻せない。→ HALT の要る字は元のスタイルのまま残す。
  まとめて結ぶ前に、HALT の有無で対象を分ける。詳しくは [見た目]「字のスタイル」
- **部品の本体の字をスタイルに結ぶと、インスタンス側の字の大きさの上書きが外れることがある。**
  → 結ぶ前後で、インスタンスの字の大きさを数で突き合わせる。詳しくは [進め方]「部品化と差し口」

### 部品・インスタンス

- **インスタンスを入れ替える（swap）と、外からの上書き（字・幅・高さ）が落ちる。** → 入れ替えの前に上書きを
  層の順で控え、入れ替えた後に戻して数で突き合わせる。保管のページで落ちる物は書けないので、ユーザーの許しを取るか
  受け入れる。詳しくは [進め方]「部品化と差し口」・[SKILL]「控えの取り方」
- **部品の本体を直すと、保管や他のページのインスタンスにも伝わる。** → 直す前に、伝わる数を数えて記録に書く。
  詳しくは [SKILL]「書いてよい範囲」
- **変数・変数のまとまりの名前を変えても、結びは切れない。** → 名前の変更は安全。結びを切る・結び直すのは
  別の作業として控えを取る。詳しくは [進め方]「名前と世代」
- **消した物は、AI だけでは戻せない**（Figma の MCP は版の履歴を読めない）。→ 消す前に、控えが全部のインスタンス・
  全部の段を拾えているかを、司令官が抜き取りで確かめる。戻し元はユーザーに複製を作ってもらう。
  詳しくは [SKILL]「1 件の流れ」4・「控えの取り方」

### 読み書き・上限

- **MCP の呼び出しには上限があり、傘の全会話で分け合う。** → 読み書きを 1 回にまとめる。上限のエラーは
  2〜3 分待ってやり直す（3 回まで）。担当は、その日の回数を報告に書く。詳しくは [SKILL]「上限と自動再開」
- **自動の判定で、画面の書き換えが止められることがある。** → 回避せず、ユーザーに 1 回だけ聞く。
  聞く役を決め、司令官と担当で二重に聞かない。詳しくは [SKILL]「担当が人間の承認で止まったとき」
- **長く動く書き込みは、背景の作業に回されることがある。** → 結果は通知で来る。待たずに、返事の要らない仕事を先に進める。
  詳しくは [SKILL]「ユーザーとのやり取り」の「司令官は、担当の返事待ちで手を止めない」
- **絵を撮ると全面が同じ色しか写らないときは、ノードが図形 1 枚（幕など）のことがある。** → 親を読んで、
  絵に撮る範囲を選び直す。詳しくは [SKILL]「1 件の流れ」6
- **部品の中の字を探す `findAll` は、子を持たない型（図形など）には使えない。** → 子を持つ型（枠・インスタンスなど）に
  だけ呼ぶ。点検スクリプトを書き足すときも同じ。詳しくは [点検]

## よく指摘されること（ユーザーから）

### 進め方・確かめ方

- **1 か所ずつ直して、漏れが次々見つかる。** → 指摘を決まりにして、全画面を点検で数え、0 を確かめる。
  詳しくは [進め方]「決まり＋全画面の点検」
- **直して副作用が出て、また直すの繰り返しで時間がかかる。** → 書く前の数を取り、1 画面で試してから広げる。
  詳しくは [SKILL]「1 件の流れ」4・5
- **整理が見た目だけで終わる。** → スタイル・変数・見本・共通の部品・点検にして、次から自動でそろう形にする。
  詳しくは [進め方]「部品化と差し口」
- **部品は、新しく作る前に既存の部品へ寄せる。** → 同じ働きの部品を探す。まとめるためのバリアントやプロパティを足すのはよい。
  詳しくは [進め方]「部品化と差し口」
- **レビューで通った見た目や、見てもらっている途中の試作を、まとめの作業で変えてしまう。** → 通った見た目は変えない。
  変える前に、通った物かどうかを確かめる。詳しくは [進め方]「試作と札」
- **些末な確かめにトークンを使いすぎる。逆に、極端に確かめないこともある。** → 数 px の余白・影・字色などの微差は、
  切り出しや拡大図を作らず、そろえる方向で司令官が決めて進める。目に見える変更だけ絵で見る。
  詳しくは [SKILL]「1 件の流れ」6
- **見本の一覧が無い**（アイコン・色・字）。→ 見本の枠を作る。基本の色ごとにまとめて並べる
  （役割の名前を 1 枚ずつ並べると、色が増えたように見える）。詳しくは [進め方]「見本の枠」

### 見た目

- **灰色の地の有無や、数字の大きさ・色が場当たり的。** → 決まりにして点検する。詳しくは [見た目]「色の 2 段」・
  「字のスタイル」
- **飾りが字と重なる。置き場が型と違う。** 「薄いから読める」で通すと、後で差し戻される。→ 字と重なる飾りは、
  薄くても通らない。「背景の飾り」は広い領域の右上に 1 つのときだけ。列の中では、名前か主役の数字の横に置く。
  詳しくは [見た目]「アイコンと飾り」の「字と重なる飾りは通らない」
- **区切りの線が、まとまりを割る。** 列ごとのまとまりを横に通る線で上下に割ると、まとまりに見えない。
  → 上下の分かれ目は、線ではなくすき間の段で示す。詳しくは [見た目]「レイアウトの直し」
- **アイコンが、正方形に近い形だけ大きく見える。** → 枠いっぱいでなく、形ごとに見た目の面積を揃える。
  段ごとの見比べ表を作って選んでもらう。字との縦の位置は、測ってから決める。
  詳しくは [見た目]「アイコンと飾り」の「見た目の大きさは形ごとに揃える」
- **部品の中のアイコンの置き方で、実装が大変になる作り**（例: まとまりの幅を縮めて入れる）になっている。
  → 実装の側の組みやすさを、実装の傘の司令官に先に聞く。
  詳しくは [受け渡し]「実装の側から Figma の決めを聞かれたとき」

### ユーザーとのやり取り

- **質問が短すぎて意味が分からない。「返事待ち」かどうかが分からない。** → 場所・今の見え方・案の見え方・おすすめ・
  迷う理由を、それだけで分かる文で書く。待つときは、何を待っているかを最後に書く。
  詳しくは [SKILL]「ユーザーとのやり取り」
- **古い未決を、今の画面を見ずに聞く。** → 聞く前に、今の Figma で確かめる。詳しくは [SKILL]「ユーザーとのやり取り」
- **直しの案に、その画面に無い作り**（表の形・札付きの箱など）**を出して、「どちらもほかと違って一貫していない」と両方断られた。**
  → 案は、まず同じ画面の既存の型（数字の列など）の当てはめから作る。新しい作りは、既存の型で収まらない理由を
  言えるときだけ出す。詳しくは [進め方]「試作と札」の「決めるときの観点（案の作り方）」
- **足りない物を、「作ってよいか」と聞いてしまう。** → 作って見せて、直しを受ける。聞くのは、見た目を作り替える物と、
  ユーザーしか知らない事実だけ。詳しくは [SKILL]「ユーザーとのやり取り」

### 作業場所・マシン

- **一時のワークツリーで docker を動かすと、root が作ったファイルが残り、片付けに sudo が要ることがある。**
  → 消す前に、何が残っているかを見る。消す物は人間が決める。
- **マシンの `/home` が満杯になると、司令官が commit もワークツリー作りもできずに止まる。** → 容量を見張り、
  大きな一時物（画像・ワークツリー）は早めに知らせる。何を消すかは人間が決める。

### 会話どうしの受け渡し

- **他の会話に依頼したきりで、様子を見ていない。** → 返事の要らない仕事は先に出し、見張りを仕掛けて、
  止まっていたら原因を調べて動かす。詳しくは [SKILL]「ユーザーとのやり取り」・[進め方]「他の会話から回ってきた仕事」
- **人の発言をそのまま担当へ流して、事実を確かめなかった**（「マージした」が、別のブランチへの取り込みのことだった）。
  → 状態は GitHub などで確かめてから伝える。詳しくは [進め方]「他の会話から回ってきた仕事」
- **上流の変更を取り込むとき、rebase でなく merge を使う。** → 特別な理由が無ければ rebase。
  詳しくは [受け渡し]「issue のコメントで動きを合わせる」と、リポの `AGENTS.md`
- **ユーザーの承認が要る操作で、担当のペインで答えてと言う。** → 司令官が自分のダイアログで聞く。
  破壊的な操作は伝言の承認では動けないので、担当のペインで直接答えてもらうか、司令官の会話から人間に実行してもらう。
  詳しくは [SKILL]「担当が人間の承認で止まったとき」
- **実装の側から Figma の決めを聞かれて、実装に合わせるか迷う。** → 決まりの持ち主（司令官）が決める。
  Figma の方が誤りなら、Figma を実装に合わせて直す。詳しくは [受け渡し]「実装の側から Figma の決めを聞かれたとき」
