# 記録の書き方と、記録での見方

記録を書くとき（担当）と、記録で Figma の変更をレビューするとき（レビュワー・司令官）に読む。
Figma の変更はリポの差分に出ないので、**レビューの対象は記録そのもの**になる。「数が合っているか・絵で確かめたか・控えから
戻せるか」が記録から読み取れなければ、レビューは通せない。

記録は、作り込みを進める傘のリポに、1 件 1 ファイルで置く。置くディレクトリはリポの決めに任せる（計画書から辿れる所に置く）。
番号は司令官が配る（2 人の担当が同じ番号を使う事故が起きうる）。決まりの文書には記録の番号を付けない
（[patterns-process.md](patterns-process.md)「文書」）。

## 雛形

次の順に書く。見出しの名前は合わせなくてよいが、中身は全部入れる。長い記録でも、**先頭の「いまの状態」だけで続きが
引き継げる**ようにする。

```markdown
# 記録 NN: <この件で何をしたか（一文）>（ブランチ `<ブランチ名>`）

担当: <担当の範囲>（<日付>。司令官より）

## いまの状態（続きをする人へ）
- Figma は済み／途中。触ったページと範囲（例: 作業のページだけ）
- 確かめたこと（数の突き合わせ・見た絵の枚数）と、了承した人（ユーザー／司令官）
- 直した文書の一覧

## 0. なぜ直したか
- きっかけ（ユーザーの指摘の要点。逐語で写さない）と、何を決まりにしたか

## 1. 決まり
- 今回の決まりを表か箇条書きで。前の決まりを改めるなら、どの記録のどこを改めたかを書く

## 2. 触った所と、触らなかった所
- ノードの識別子・名前・前後の値（表にする）
- 触らなかった所（特に、レビューで通った見た目・見てもらっている途中の試作）

## 3. 控え
- 何を取ったか・どこに置いたか・取った時刻（どの作業より前か）
- 控えが拾えている範囲（インスタンスの数・段の数）

## 4. 前後の数
- 書く前の数・書いた後の数・差（表にする）

## 5. 絵
- 見た絵（画面名・ノードの識別子）と、見た人。見に行ける場所を書く

## 6. 決め
- 決めた内容と、誰の判断か（ユーザーの答え／司令官の判断）。未決があれば何を待っているか

## 7. 書かなかったこと
- 今回やらなかったこと・次の件へ回したこと
```

## 各節で書くこと

### 控え（戻せる根拠）

- **何を・どの層まで**取ったか。インスタンスの上書き（字・大きさ・表示/非表示・入れ子やスロットの中）を層の順で、字は
  中身と値、塗りは不透明度まで（取り方は SKILL.md「控えの取り方」）
- **どこに置いたか。** 控えの本体（長いデータ）は記録に貼らず、置き場と件数・取った時刻だけを書く。置き場は、リポの中の
  読める所（作業用の一時ファイルは記録から辿れない）。戻し元が正本の複製なら、複製の時刻と、その後に足された物の有無を書く
- **控えが拾えている範囲。** 「全部のインスタンス・全部の段を拾えた」と言い切れる根拠（数）を書く。消す・作り替える件では、
  司令官が抜き取って確かめた結果（何件見て何件一致したか）も書く

### 前後の数

- 比べる元は**書く前に取った数**。書いた後どうしで比べない（どちらも同じ向きに狂うと見逃す）
- 数える物は件に合わせて選ぶ: 部品の本体の数・インスタンスの数・結ばれた変数の数・半透明の塗りの数・層の数・
  決まりに外れた物の数（点検スクリプトの出力。[audit.md](audit.md)）。**決まりの件は、点検の違反が 0 になった数**を載せる
- 差は表に出し、**差が出るはずの物と、出ないはずの物を分けて**書く。予定外の差が出たら、理由を書く（書けなければ、
  突き合わせは済んでいない）
- 部品の本体を変えた件は、**伝わる先の数**（作業のページ・保管のページのインスタンスと、上書きの数）を書く

### 絵

- 見た目がはっきり変わる件は、前と後の絵を同じ範囲で見比べ、画面名・ノードの識別子と一緒に書く。ブラウザのリンクは
  貼らない（見に行けるのは識別子で足りる）
- 絵の置き場がリポの外のとき（画像を貼れないとき）は、見た場所と見た枚数を書く
- 微差の件は、画面を 1 枚見たと書くだけでよい。切り出し・拡大図・比べの枠を何枚も作らない（確かめの重さを微差に
  合わせる）

### 決め

- 誰の判断かを必ず書く（ユーザーの答え／司令官の判断）。ユーザーの発言は逐語で書かず、要点と決めだけにする
- 決まりを改めた件は、前の決まり（何番の記録か）と、改めた点だけを書く。前の記録は書き換えない
- 実装に渡る決めは、実装の傘が引ける形にする（[handoff-to-impl.md](handoff-to-impl.md)）

## レビュワーが記録で見ること

Figma の変更はリポの差分に出ない。レビュワーは、記録を読んで次を確かめる。確かめられない項目は、指摘として返す。

| 見ること | 確かめ方 | 通らない例 |
|---|---|---|
| **数が合っているか** | 前の数が「書く前に取った数」か。差が出るはずの物にだけ出ているか。予定外の差に理由があるか | 後どうしの比較だけ・差の理由が無い・数が文章に埋もれて表が無い |
| **絵で確かめたか** | 見た目が変わる件に、前後の絵と見に行ける識別子があるか。見た人（ユーザー／司令官）が書いてあるか | 絵の記述が無い・「問題なし」だけで場所が分からない |
| **控えから戻せるか** | 控えの層（上書き・字の値・不透明度）が足りているか。置き場が辿れるか。拾えた範囲が数で言えるか | 識別子と欄の名前だけの控え・置き場が一時ファイル |
| **範囲を守っているか** | 触った所が書いてよい範囲の中か。許しが要る所（保管のページなど）に許しの記録があるか。触らない所を触っていないか | 範囲外のページの変更・許しの範囲を超えた書き込み |
| **決まりにしたか** | 1 か所の直しで終わらず、決まりと全画面の点検（違反 0）があるか | 指摘された画面だけ直して、点検を回していない |
| **決めの出所があるか** | 誰の判断かが書いてあるか。ユーザーが決める物を担当が決めていないか | 見た目が変わるのに出所が無い |
| **レビューで通った見た目を変えていないか** | 「触らなかった所」に、通った見た目・試作の途中の物が書いてあるか | まとめの作業で通った見た目が変わっている |

- レビュワーは Figma の実物を直接開かなくてよい。記録の数・絵・控えが読み取れなければ、そのこと自体を指摘する
  （実物の確認が要るときは、司令官に頼む）
- 絵と数が食い違っていたら、数を正とせず、どちらが誤りかを担当に確かめさせる
- PR の往復（指摘・修正・再レビュー）の手順は `pr-review-loop`。ここには写さない

## よくある失敗

- 記録を最後にまとめて書く。控えの置き場・取った時刻・前の数は、作業の途中で書き留めないと後で出せない
- 控えを取ったと書くだけで、拾えた範囲（数）が無い
- 絵の識別子が無く、レビュワーも司令官もどこを見ればよいか分からない
- 決まりを改めたのに、前の記録の何を改めたかが無い
- 記録の中に、ユーザーの発言を逐語で貼る（要点と決めだけにする）
