# 実装への受け渡し

Figma の仕上げ（または途中まで）を、製品のリポの実装へ渡すときと、実装の側から Figma の決めを聞かれたときに読む。
読み手は、Figma の傘の司令官と担当、実装の傘の司令官。

実装の傘をどう立てるか・孫の spawn・マージ・巡回は、このファイルに写さない。傘の立て方は `task-intake`
（振り分け）→ `umbrella-handoff`、複数リポの傘の扱いは `umbrella-orchestrator` の「2.1 孫ブランチ進捗テーブル」の
複数リポの傘の節と、spawn の節（§3.2。他リポの孫は同節の「他リポの孫の spawn」）、マージの節（§3.6）を引く。ここが持つのは、**Figma と実装の差分を、人と AI に渡せる形にする
手順**と、実装の側から決めを聞かれたときの答え方。

## 全体の流れ

1. Figma と実装の差分を、担当で手分けして洗い出す
2. 差分を束にする（人ごと・ファイルの持ち主ごと）
3. 製品のリポに分担ボードの issue を立てる
4. チャットで、各人の AI へのプロンプトを渡す
5. 各人の AI が、issue のコメントで動きを合わせる
6. 実装の側から Figma の決めを聞かれたら、決まりの持ち主（司令官）が決める

実装の傘は、Figma の仕上げを待たずに立ててよい。仕組みの孫（直書きの検査・変数・置き換えの道具・共通の部品）から始め、
Figma の該当の記録が入ってから、見た目の孫を始める。

## 1. 差分を洗い出す

**いつ使う:** Figma の叩き台が、実装へ渡せる程度に固まったとき。

**やること:**

- Figma の画面と実装の画面を、担当で**画面のまとまりごとに手分け**して見比べる。担当の範囲は、Figma を書いたときの
  範囲（[SKILL.md](../SKILL.md)「体制」）に合わせると、見る人が画面を知っている
- 見つけた差分は、**人に渡せば直せる粒**で 1 件ずつ書く。1 件に入れるのは、
  - どの画面の・どの物か（画面に出ている言葉で）と、Figma の見え方・実装の見え方
  - 違いの数（Figma の値・実装の値）と、Figma 側の場所（ノードの識別子）
  - 実装のどのファイルが当たりそうか
  - 原因の種類（下の分類）と、決めが要るかどうか
- 件には、画面のまとまりごとの頭文字と連番の識別子を付ける（例: 一覧の画面なら `L-01`、共通の部品なら `C-01`）。
  issue や PR の題から引けるようにするため
- 実装の側は、実際にブラウザで画面を開いて撮って比べる。コードを読んだだけで「合っているはず」としない。実装は
  **一時のワークツリーで動かして**撮り、Figma の絵と並べる
- 一覧は **1 件 1 行の表**にする。列は、番号・場所・違い・種類（下の分類）・元の記録・当たる仕組み・順番と重なり
- 計画を立てた**後に Figma で決めた物**が、一覧に入っているかを必ず見る（古い計画のまま洗うと、決め直した物を落とす）

**分類（集計して束を切るのに使う）:**

| 種類 | 中身 | 直し方の傾向 |
|---|---|---|
| A | 変数・段の当て漏れ（直書きの色・すき間が残っている） | 変数を当てるだけ。道具で機械的に置き換えられることが多い |
| B | 共通の部品の違い（枠・見出し・ボタンなど） | 部品を直す・足す。呼ぶ側の置き換えが後から続く |
| C | 画面ごとの並べ方の違い | その画面のファイルだけで直せる |
| D | データ・機能が足りない | 表示の置き換えでは直らない。別の件として扱う |

**決めるときの観点:**

- 同じ物が 2 つの画面の件に出ることがある。**乗る先の件を決めて、片方は「〜に乗る」と書く**（二重に直さない）。
  同じ原因の件は 1 件にまとめ、共通の部品の担当へ回す
- 大きさ（S・M・L）は付けてもよいが、実装を AI で進めるなら、時間より「ファイルがかぶらないか」「どこが先か」が効く。
  **時間の見積もりは分担に使わず**、触るファイル・依存・決めが要るか・開いている他人の PR との重なりで割る

**よくある失敗:**

- 差分の一覧を Figma の側の記憶だけで書き、実装を撮らない（見えていない違いを落とす）
- 件が粗く（「この画面を直す」）、受け取った人が分け方から考え直す

## 2. 束にする

**いつ使う:** 差分の一覧ができたとき。

**やること:**

- **人ごと・ファイルの持ち主ごと**に束を切る。同じファイルを触る件は、同じ束に入れる（別の人に分けるとぶつかる）
- 束ごとに、件数・件の識別子・**触るファイルと、そのファイルを触る件**を書き出す
- ほかの束と同じファイルを触る件は、束の一覧に「ほかの束と重なる」と印を付け、重なる相手を書く
- 重なるファイルは、表にまとめる（ファイル・かぶる束と件・扱い）。表は目で拾わず、**機械で突き合わせて作る**
  （各件の触るファイルの一覧を突き合わせる）。扱いは「先に入れる側」と「後から入れる側が rebase で解く」
  を決めておく
- 担当の決まらない件（特に D）は、「担当未定」の束に置く。無理に誰かへ割り当てない

**決めるときの観点:**

- 共通の部品を直す人を 1 人決め、その人に「部品を足す」役を寄せる。画面の側の人は、部品を呼ぶだけにする
- すべての画面に当たる道具（置き換えのスクリプトなど）は、**道具の決まりの表を直す件**と、**画面のファイルに道具を当てる件**を
  分ける。画面全体を 1 人が一度に触らない

**よくある失敗:**

- 「全画面に道具を当てる」件を 1 人の束に入れ、ほかの人の画面のファイルまで触らせる
- 重なるファイルの扱いを書かず、各人の AI が同じファイルを同時に書き換えて衝突する

## 3. 分担ボードの issue を立てる

**いつ使う:** 束が決まったとき。製品のリポ（実装の側）に 1 本立てる。分担と進み具合の**正はこの issue**。差分の一覧の文書は
「元の一覧」として issue から指す。

**やること:** 次の節立てで書く。中身は、そのリポの事情に合わせて埋める。

```markdown
# <画面の範囲> の残りの差分（Figma と main）の分担ボード

<何と何を比べた一覧か、1〜2 文>。分けて実装するための共有ボード。各自の AI はこの issue を読んで動く。

- 元の一覧（違いの詳細・Figma の場所・当たる仕組み・絵）: <差分の一覧へのリンク>
- Figma の決まり（色・字・すき間・部品）: <決まりの文書へのリンク>
- 識別子の頭の意味: L＝一覧の画面、C＝共通の部品、…（束と合わせる）

## 並行で進めるための決まり

- ファイルの持ち主を決めてある。各節の件は、その人の画面のファイルだけを触る。ほかの人の節のファイルは、
  触る前にこの issue にコメントで聞く
- 共通の部品は「足す PR」と「置き換える PR」に分ける。足す人が、部品だけの PR を最初に出す
- 道具の決まりの表を直す PR は、画面のファイルを触らず最初に出す。各自は自分の画面のファイルにだけ道具を当てる
- 「〜の後に測る」と書いた件も待たない。Figma の値で作り、土台が入った後にずれたら各自の PR で直す
- 全員が触るファイル（翻訳ファイルなど）は、別のキーなら同時でよい。後から入れる人が rebase で解く
- 待つのは、部品を足す PR と道具の表の PR の 2 つだけ

## AI への進め方（この issue を読んだ AI が守ること）

1. 自分の担当の節の、チェックの付いていない件から選ぶ。並行の決まりを守る
2. 1 つの PR には、同じファイルを触る件をまとめてよい（目安 1〜5 件）。PR の題に件の識別子を入れる
3. 実装の前に、元の一覧の行を読み、Figma の該当の枠を撮って確かめる。実装後は、実装の画面を撮って突き合わせる
4. 着手したら、この issue の本文の自分の行の末尾に PR の番号を書く。マージされたら、その行のチェックを付ける
5. 決めが要る件・ほかの人の節のファイルとかぶる件は、始める前にこの issue にコメントで聞く
6. すでに開いている別の PR と同じファイルを触る件は、その PR の扱い（先か後か）を先に確かめる

## かぶるファイル

| ファイル | 触る件 | 扱い |
|---|---|---|
| <共通の部品のファイル> | <作る人>（部品側）・<各自>（呼ぶ側） | 部品を足す PR が先 |
| <翻訳ファイル> | 全員 | 別のキーなら同時。後から入れる人が rebase |

## <人 A> の束｜<持ち主の範囲>

- [ ] **C-01** <件の 1 行の説明>。<当たるファイル> — <Figma と実装の違い>。PR:
- [ ] **C-02** …

## <人 B> の束｜<持ち主の範囲>

- [ ] **L-01** …

## 担当未定

- [ ] **D-01** …（決めか機能が先に要る）
```

- **チェックは、マージされた件だけ**に付ける。進み具合の正をこの issue 1 本にする
- 表の中のチェックは画面で押せない。**件は 1 件 1 行の並び**（上の雛形）にする
- issue の本文を書き換えるのは、自分の行だけにする（`gh issue edit` で本文を取って、自分の行だけ直して戻す）。
  人の行を巻き込まないように、書き換えの直前に最新の本文を取り直す
- 本文をスクリプトで作り直すと、人が手で足した節が消える。作り直す前に、今の本文との差を見る
- 人が増えたら、その人の**今の持ち仕事を数えてから**割る

**よくある失敗:**

- issue の本文が長く、読んだ AI が「並行の決まり」と「進め方」を読み飛ばす。この 2 節は、件の一覧より前に置く
- 分担と進み具合を、issue と差分の一覧の文書の 2 か所で持つ（食い違う）。正を issue に決め、文書側には「正は issue」と書く

## 4. 各人の AI へプロンプトを渡す

**いつ使う:** issue ができたとき。

**やること:**

- チャット（人が使う場）で、**人ごとに 1 本のプロンプト**を渡す。各人が、自分の AI の会話に貼る
- プロンプトに入れるのは、次の短い指示だけ。**件の中身は issue に任せる**（プロンプトに写すと、issue と食い違う）
  - issue の場所と、自分の束の名前
  - 「issue の『並行で進めるための決まり』と『AI への進め方』を読んで、自分の束のチェックの付いていない件から進める」
  - 最初に出す PR があるなら（部品を足す人）、それを最初にやること
- 渡す前に、**人の名前と束の対応が合っているか**を、人間（ユーザー）に確かめる

**よくある失敗:**

- プロンプトに件の詳細を書き、issue を読ませない
- 束の持ち主を取り違えて、ほかの人のファイルを触る AI ができる

## 5. issue のコメントで動きを合わせる

**いつ使う:** 各人の AI が動き出した後、実装が進んでいる間ずっと。

**やること:**

- 各 AI は、**決めが要る件・ほかの人の節のファイルとかぶる件は、始める前に issue へコメントで聞く**。聞く相手は、
  ファイルの持ち主か、決まりの持ち主（下の「実装の側から決めを聞かれたとき」）
- 着手と完了は、自分の行（PR の番号・チェック）で見せる。コメントは、決めと取り決めに使う。区切りごとに、
  コメントで進み具合を知らせる。**着手の前に、最新のコメントを読む**
- ほかの人の PR のブランチには触らない。ぶつかったら、**後からマージされる側**が rebase で解く
- ほかの人の PR とファイルがぶつかっても、待たずに進める

**順序の依存は「部品を足すだけの PR を最初にメインのブランチへ」で切る。**

- 部品（共通の枠・見出し・ボタン）を足す・直す PR は、画面の置き換えを含めず、最初に出して入れる。
  順序の依存を切る最初の小さい PR（部品を足すだけ・置き換えの決まりの表だけ）は、**傘ではなく既定のブランチへ直接**出す
  （傘に入れると、ほかの人の作業に届かない）
- 画面の側の置き換えは、部品が入った後に、各人が自分の画面のファイルで行う
- 部品を待たずに進めたい件は、Figma の値で作り、後でずれたら直す（待つ件を最小にする）
- 待つ依存が増えてきたら、束の切り方が悪い。ファイルの持ち主を切り直す
- 値の書き方で検査（直書きの検出など）をすり抜ける形が見つかったら、書き方を止めさせ、**検査の側に足す**
- 実装の規模が傘になるときは、`umbrella-handoff` で実装の傘へ渡す。Figma の傘の司令官の担当に、製品のリポを直接書かせない

**よくある失敗:**

- 部品を足す PR に、画面の置き換えまで含め、PR が大きくなって入るのが遅れる（全員が待つ）
- 聞かずに、ほかの人の節のファイルを書き換える

## 実装の側から Figma の決めを聞かれたとき

**いつ使う:** 実装を進める AI や人から、「Figma のこの部分は、どちらに合わせるのか」「Figma に無い状態はどうするのか」と
聞かれたとき。

**やること:**

- **決まり（色・字・すき間などの決め）の持ち主は、Figma の傘の司令官。** 実装の側で決めずに、司令官へ聞く
  （[SKILL.md](../SKILL.md)「誰が何を決めるか」）。司令官は、決めて、答えを聞いた人（実装の司令官か issue のコメント）へ返す
- 答えの前に、司令官が**今の Figma を自分で読んで**確かめる（記録や記憶だけで答えない）
- **Figma の方が誤りなら、実装を Figma に合わせるのではなく、Figma を実装に合わせて直す。** 直す作業は、通常の件の流れ
  （[SKILL.md](../SKILL.md)「1 件の流れ」）で担当へ出す。直した後で、決めを答えた相手へ知らせる
- 決めが、見た目が目に見えて変わる物・意味が変わる物なら、司令官が決める前にユーザーへ聞く（同じ「誰が何を決めるか」）
- Figma 側で決まった事・実装で気を付けることが見つかったときは、聞かれなくても、**その都度**実装の傘の司令官へ知らせる

**決めるときの観点:**

- 実装でしか起きない事情（描画のずれ・フォントの違い）なのか、Figma の誤りなのかを分ける。前者は実装の側の調整、
  後者は Figma を直す
- 答えは 1 件ずつ、それだけで分かる文で書く（場所・今の見え方・決めた内容と理由）

**よくある失敗:**

- 実装の側が、Figma を見ずに近い値で決めてしまい、Figma との差分が増える
- Figma の誤りに気づいたのに、実装を Figma に合わせて残し、Figma を直さない（次の差分洗いで同じ件が出る）
