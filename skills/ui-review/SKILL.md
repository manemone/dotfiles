# ui-review — 画面を触る PR の確認

画面の PR を、**作った人（実装役）とは別の目**で確認する。実装役の自己チェックの代わりであり、
全部のボタンを 1 つずつ押す確認の代わりではない。芯は次の 2 つ。

- **別の目で見る。** 確認項目を実装役に書かせない。リポ側の入口に書かれた流れと原則から、レビュー役が決める
- **安く見る。** 幅は 1 つ、流れは 1 本、30 分以内。スマホ・タブレット幅とアクセシビリティの全面確認はしない
  （ラベルの無いアイコンのボタンだけは見る）

下敷きは design-review（MIT）と Playwright スクリプト式の webapp-testing。使ったもの・削ったものと理由は
ADR DOC-2611040233 にある。

## いつ回すか

次の 2 つが両方そろうときだけ。どちらかが欠けたら、このスキルは回さない（今までどおりコードだけのレビュー）。

1. `.claude/pr-review.yml` に `ui_review:`（入口ファイルのパス）がある
2. PR の変更ファイルが、入口ファイルの `screen_paths`（グロブ）のどれかに当たる

入口ファイルの形は [references/entry-format.md](references/entry-format.md)。

## 順番（崩さない）

### 1. 機械チェックを回して結果を読む

入口の `machine_checks`（コマンドの一覧）を回し、数字と一覧を読む。**同じことを目で数え直さない**
（用語・はみ出し・並びのずれなど、機械が数えるものは機械に任せる）。出力が長ければ一時ファイル
（`mktemp -d`）へ書いて、件数と該当行だけ見る。コマンドが無い・失敗したら、その旨を結果に書いて先へ進む。

### 2. 画面の字を、読み物より先に読む

**計画書・PR の説明・コード・ADR を開く前に**、画面に出ている字だけを読む。中の名前や計画書の言い回しに
慣れたあとでは、不自然な字に気づけない。見方は 1 つ:
「初めて開いた人が、その字だけで何が起きるか分かるか」。

- ボタン・見出し・列の名前・数だけの字（「受け入れる 2」のような、数の意味が字から分からないもの）・
  中の名前や ID がそのまま出ていないか
- ここで気になったことは、**このあとの読み物で理由が分かっても指摘から消さない**（読めば分かる字は、
  初めての人には分からない字である）

### 3. 流れを 1 本通す

入口の `flows` から、PR が触った画面を通る流れを 1 本選び、最後まで通す。見るのは次の 4 点:

- 押したら変化が見えるか（押しても何も起きない・結果が別の場所にしか出ない）
- 無意味なボタン（押さないと中身が見えないのに、押すことを求めるもの）
- 部品の置き場所（その操作が効く範囲のすぐそばにあるか）
- 押せないとき、理由が見えるか

危ない操作（書き込む・消す・外へ送るボタン）は**押さない**。入口の `danger_marker` が見分ける印を
持つなら、それに当たるものは押さずに「押さなかった」と書く。

### 4. 原則と用語表に突き合わせる

ここで初めて、入口の `principles_docs` と `glossary_docs` を読み、2・3 で気づいたことと、見落としを
突き合わせる。読み物が長いので、見出しを `grep -n '^#'` で引いて要る節だけ読む。

## 手を動かす人（確認役）

画面を触る作業は、高いモデルのレビュー役が自分でやるより、確認役のペイン（`ocw checker`。既定は Sonnet）に
任せるほうが安い。`ocw checker` はレビュー役のペインからも呼べる（レビュー役専用の確認役ペインが立ち、
実装役の確認役とは文脈を共有しない）。レビュー役が依頼ディレクトリ（`mktemp -d`）に次の 2 つを書く:

- `shoot.sh`: 入口の `serve_cmd` で小さいコピーの画面を立てる（または `url` が生きているか確認する）だけの
  スクリプト。**確認役に立て方を探させない**。ヘッドレスのブラウザは音を消す（`--mute-audio`）
- `checklist.md`: 手順 2 → 3 の順の確認項目。流れは入口から**レビュー役が選んで**書く。実装役が書いた確認項目は使わない。
  スクショの保存先（リポジトリの外）、1 つの幅（入口の `viewport`。無ければ 1920×1080）、押してはいけないもの、
  結果に書く 4 段（下記）を含める。スクショは流れの要所の数枚だけ

```bash
ocw checker "$REQ_DIR" --wait 540   # ツールのタイムアウトは 600000 ms
```

確認役は Playwright のスクリプト（Python か Node。入っている方）を書いて画面を触る。MCP は入れない
（入れると道具の説明文だけで毎回の文脈が増える）。`ocw checker` が使えない環境（ペインの外など）では、
レビュー役が自分で同じ手順を回す。

## 結果の形

指摘は **Blocker / High / Medium / Nitpick** の 4 段。1 件につき 1 行で、次を並べる:

```
[High] <画面> / <部品> / <見えたもの> / <スクショのパス>
```

スクショのパスはリポジトリの外。見つからなければ「指摘なし」と書き、**押した流れと押さなかったもの**を添える。
結果の末尾に、**かかった時間とおおよそのトークン**を書く（30 分を超えそうなら、そこで止めて、通せた範囲を書く）。

GitHub への投稿は、`pr-review-loop` の普段のレビューと同じ形・同じ手順で行う（このスキルの指摘は
普段の指摘の 1 部であり、別の投稿先を作らない）。Blocker / High は `pr-review-loop` の指摘の基準に照らして
変更要求にするか決める。

## やらないこと

- 全部のボタンを 1 つずつ押す確認、複数の幅、本物の規模のデータでの確認
- アクセシビリティの全面確認
- 入口に無いリポでの先回り（入口の項目が無ければ何もしない）
- 本物のデータ・本物のサービスに向ける（小さいコピーだけ）
