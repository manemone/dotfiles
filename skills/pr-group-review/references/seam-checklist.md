# リポ間の継ぎ目チェックリスト

PR 群を「PR ごと」ではなく「PR と PR の継ぎ目」で見るための項目。`pr-group-review`（レビュワー用）は
レビューの 1 観点として、`pr-group-request`（依頼者用）はレビューを頼む前の自己チェックとして使う。

**このファイルの名前は `pr-group-request` から相対パス
（`../pr-group-review/references/seam-checklist.md`）で参照される。リネームしないこと。**

## 最初に読む注意: 事故の種は、照合より「順序と手作業」の側にあった

実際に 9 リポ 18 本の PR 群をレビューしたとき（ADR DOC-2609270420 §1）、重大な指摘 8 件のうち
**6 件はコードではなく順序と手作業**だった（スキーマ管理ツールの適用順、submodule が古い系統を
指していた、デプロイツールの前提、ブランチから先に apply 済みのインフラ）。一方で、リポ間の照合
（payload ↔ スキーマ ↔ 受信、API 契約 ↔ 実装、インフラ名 ↔ ENV など）は**全部一致していた**。

照合は目に見えやすく、作者も念入りに確かめている。**時間の配分は順序と手作業（§2.6・§2.7）を
厚くする。** 照合の項目は「一致を確かめたら次へ」でよい。

## 1. 使い方

- 各項目について、PR 群の中に該当する契約・前提を列挙し、地図の「リポ間の照合表」
  （`group-map.md`）に 1 行ずつ起こす
- 該当が無い項目は「該当なし」と記録する（確認していないのと区別するため）
- 単体 PR（1 本だけの PR 群）では、§2.6〜§2.9 を見る（PR 群の中に相手がいないため、リポをまたぐ
  継ぎ目は §2.9 にしか無い。§2.1〜§2.5 は、PR 群の外との継ぎ目として見る余裕があれば見る）
- 不一致・未確認は指摘にする（`category: seam` / `order` / `manual`）。順序と手作業の指摘は
  投稿の 1 段目に入る（`state-format.md` §4.1）

依存の種類は次の 5 つで呼ぶ（地図の `dependencies[].kind` と揃える）:
**code**（ライブラリ・共有コード）/ **service**（API 呼び出し）/ **data**（テーブル・バケット・
キュー）/ **pipeline**（CI・デプロイ・マイグレーション）/ **docs**（仕様書・ADR）。

## 2. 項目

### 2.1 payload ↔ スキーマ ↔ 受信側（data / service）

- 送る側が組み立てる payload のフィールド名・型・必須性と、スキーマ定義（あれば）と、受ける側が
  読むフィールドが一致しているか
- 送る側が先にデプロイされたとき、古い受信側が新しい payload を受けて壊れないか（逆も）
- 確かめ方: 各 worktree でフィールド名を横断検索する

  ```sh
  grep -rn "<フィールド名>" "$WT_ROOT"/*/
  ```

### 2.2 API 契約（OAS 等）↔ 実装（service / docs）

- 契約ファイルの変更と、提供側の実装・利用側のクライアントが同じ PR 群の中で揃っているか
- 契約だけ変わって実装が無い、実装だけ変わって契約が古い、を探す

### 2.3 インフラの名前 ↔ ENV ↔ アプリの設定（data / pipeline）

- インフラ側で作るリソース名（バケット・キュー・テーブル・シークレット名）と、ENV に渡す値と、
  アプリが読む ENV キー名が一致しているか
- ENV を足した PR で、全環境（開発・検証・本番）の設定に入っているか

### 2.4 DB の列 ↔ コード（data）

- マイグレーションで足す・消す・改名する列と、それを読み書きするコードが揃っているか
- 列を消す／改名するとき、古いコードが動いている間に列が無くなる順序になっていないか（§2.6）
- outbox やイベントテーブルの列と、それを読む relay・consumer が揃っているか

### 2.5 submodule や依存のバージョン（code）

- submodule・共有ライブラリの参照先が、PR 群の中の**新しい方の系統**を指しているか
  （古い系統のコミットを指したまま、という事故が実際にあった）
- lock ファイルの更新漏れ

### 2.6 デプロイとマイグレーションの順序（pipeline）★厚く見る

- 地図の「マージと適用の順序」が、依存の向きと矛盾しないか
- スキーマ・インフラの適用が、それを使うコードのデプロイより先になっているか
- 「マージ = デプロイ」のリポと「マージ後に手動で apply」のリポが混ざっていないか。混ざっていれば
  その区別が地図に書かれているか
- ブランチから先に apply 済み（マージ前にインフラへ反映済み）のものが無いか。あればその事実と、
  マージ後の差分がどうなるかが書かれているか
- stack の下の PR だけがマージされた状態で壊れないか

### 2.7 手作業の前提（pipeline）★厚く見る

- 差分から読み取れる「人がやらないと動かない」作業を全部拾う: 新しいシークレットの登録、
  管理画面での設定、手動の apply、サービスの新規作成、権限の付与、外部サービスの設定
- それぞれに「いつ（順序の何番の前後）」「誰が」があるか
- デプロイツールがサービスの存在を前提にしていないか（新規サービスは誰が作るのか）

### 2.8 ロールバック（pipeline / data）

- 順序の各段で戻す方法があるか
- 戻せない段（データの移行・削除、外部への通知の送信）が明示されているか。その前で止める判断が
  できるか
- 片方のリポだけ戻したときに、もう片方が壊れないか

### 2.9 PR 群に入っていない利用者（全種類）

- 変更した契約（API・payload・テーブル・ENV・共有ライブラリ）を、**PR 群の外で**使っているコード・
  サービスが無いか。影響は両方向に追う: 「変更に依存しているもの」と「PR の中で他とぶつかるもの」
  （Qodo の cross-repo code review の考え方）
- 確かめ方の例（組織横断のコード検索が使える場合）:

  ```sh
  gh search code "<変更した識別子>" --owner <org> --limit 50
  ```

- 見つかった利用者は地図の照合表に「群外: <名前>」として載せ、影響を確かめられなければ
  `question` の指摘にする
