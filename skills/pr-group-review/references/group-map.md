# PR 群の地図

複数の PR（複数リポにまたがることが多い）が、どういう順番で、どんな前提で、何と噛み合って
本番に届くのかを 1 枚にまとめたもの。`pr-group-review`（レビュワー用）は作者の地図を検証するか
自分で作り、`pr-group-request`（依頼者用）は自分で作る。決定の経緯は ADR DOC-2609270420 を参照。

**このファイルの名前は `pr-group-request` から相対パス
（`../pr-group-review/references/group-map.md`）で参照される。リネームしないこと。**

- 地図の正典は状態ファイル（`state-format.md` §3.4 の `map`）。本書は各項目の意味と書き方を定める
- 人に見せる形は 2 つ: まとめの HTML（`summary-template.html`）と、PR 本文や依頼文に貼る
  Markdown（本書 §4）

## 1. 地図の項目

| 項目 | 何を書くか | 書けていないと何が起きるか |
|---|---|---|
| グループ | 目的が同じ PR のまとまり（例: 「受信側の API」「スキーマ」「インフラ」）。1 PR は 1 グループに属する | レビュワーが全体像をつかめず、PR を 1 本ずつ読むことになる |
| PR 間の依存 | 「A が無いと B が動かない」関係。種類（code / service / data / pipeline / docs）を付ける | マージ順を誤る |
| 積んでいる PR（stack） | base が別の PR のブランチになっている連なり。main に近い側から並べる | 下の PR の変更が上の PR の差分に混ざって見える／下だけマージされる |
| マージと適用の順序 | マージ・インフラやスキーマの適用・デプロイ・手作業を 1 本の手順に並べたもの | **事故の種の大半はここにある**（`seam-checklist.md` 冒頭） |
| 手作業の工程 | 人がやる作業（管理画面での設定、秘密情報の登録、手動の apply 等）。いつ・誰が・何を | 「マージしたのに動かない」「ブランチから apply 済みで差分が合わない」 |
| 未決の ADR | この PR 群が前提にしている、まだ確定していない設計判断 | 前提が覆ると PR 群ごと作り直しになる |
| リポ間の照合表 | 1 つの契約（payload・API・テーブル・ENV 名など）について、作る側と使う側の PR を並べ、一致しているか | 片側だけ直してずれる |
| ロールバック | 順序の各段で問題が起きたときの戻し方。戻せない段（データ移行など）を明示する | 途中で止めたときに戻せない |

**単体 PR（1 本だけの PR 群）のとき**は、グループ・依存・stack を省き、「マージと適用の順序」
「手作業の工程」「ロールバック」だけを 1 本の表にしてよい。該当が無い項目は「なし」と書き、
空欄にしない（「確認して、無かった」と「確認していない」を区別するため）。

## 2. 作るとき

1. 対象 PR の一覧を確定させる（複数の情報源を突き合わせる。`state-format.md` §3.2）
2. stack を上下の両方向にたどって組む。下へは、base が default branch 以外ならその base を head に持つ
   PR を探す。上へは、その PR の head ブランチを base にしている PR を探す
   （`gh pr list -R <owner>/<repo> --base <その PR の headRefName>`）
3. 各 PR の本文・差分から、依存（何を前提にしているか）と手作業（本文の「マージ後に〜」「事前に〜」）を拾う
4. マージ・適用・デプロイ・手作業を 1 本の順序に並べる。依存の向きと矛盾しないことを確かめる
5. リポ間の照合表は `seam-checklist.md` の項目ごとに、契約を 1 行ずつ起こす
6. 各段のロールバックを書く。戻せない段があれば、その前で止める判断ができるように明記する

傘ブランチの計画書（`umbrella-orchestrator` 形式）から作るときは、進捗テーブルの孫の並びと
依存の記述がそのまま「グループ」「依存」「順序」の材料になる（手順は `pr-group-request` を参照）。

## 3. 作者の地図を検証するとき（レビュワー用）

作者が地図を出していれば、それを出発点にして次を確かめる。食い違いは状態ファイルの
`map.discrepancies` に残し、指摘（`category: structure` / `order` / `manual`）にする。

- 地図に載っている PR と、他の情報源で見つかった PR が一致するか（**地図にだけある PR、地図に
  無い PR の両方**を探す）
- 各 PR の base と、地図の stack が一致するか
- 順序が依存の向きと矛盾しないか（使う側が作る側より先にマージ・デプロイされていないか）
- 手作業の工程に「いつ」「誰が」があるか。差分から読み取れる手作業（新しい ENV、新しい
  バケット、手動の apply など）が地図から漏れていないか
- 照合表の「一致」が実物で本当に一致しているか（**作者が一致と書いていても、差分で確かめる**）
- ロールバックが、戻せない段を戻せると書いていないか

## 4. Markdown テンプレート（PR 本文・依頼文・メモに貼る用）

```markdown
## PR 群の地図: <テーマ>

### グループと PR

| グループ | PR | 役割 | base |
|---|---|---|---|
| G1 <名前> | <owner>/<repo>#<番号> | <一言> | <base ブランチ> |

### 依存

- <owner>/<repo>#<番号> → <owner>/<repo>#<番号>（<code/service/data/pipeline/docs>）: <理由>

### マージと適用の順序

| # | 種類 | 対象 | 前提・メモ |
|---|---|---|---|
| 1 | merge / apply / deploy / manual | <PR または作業> | <何が済んでいる必要があるか> |

### 手作業の工程

| ID | いつ | 何を | 誰が |
|---|---|---|---|
| M1 | <順序の何番の前後> | <作業> | <担当> |

### 未決の ADR

- <PR または文書>: <何が決まっていないか>。影響する PR: <…>（なければ「なし」）

### リポ間の照合表

| 契約 | 作る側 | 使う側 | 状態 | メモ |
|---|---|---|---|---|
| <payload / API / テーブル / ENV 名 など> | <PR> | <PR（PR 群の外なら「群外: 名前」）> | 一致 / 不一致 / 未確認 | <…> |

### ロールバック

| 対象の段 | 戻し方 | 戻せるか |
|---|---|---|
| <順序の何番> | <手順> | 可 / 不可（不可なら理由） |
```
