# 工程 4: 実装への申し送りの文書の組

Figma の画面の構成が固まり、実装の担当へ渡すときに読む。読み手は、Figma の傘の司令官と担当。
差分の洗い出し・分担ボードの issue・各人の AI へのプロンプトは、`figma-design-workflow` の `references/handoff-to-impl.md` が持つ。ここが持つのは、**その前に置く文書の組**。

## 書き始める時期

**画面の構成が決まってから書く。** 構成が決まる前に書くと、構成が変わるたびに全面に近く書き直す使い捨てになる。
見た目の決めの一覧と対応表は、画面の決まりが固まるまで書けない面もある。ただし画面を作っている間にも、色などの食い違いを
差分の洗い出しの段で初めて見つけることになるので、作り込みの終盤から下書きを始める。

## 文書の組

| 文書 | 何のためか | 中身 |
|---|---|---|
| 入口（`handoff/README.md` など） | 実装の担当が迷わず読み始める1枚 | 読む順・Figma の場所と正・実装の現在地・画面ごとの差分・言葉の置き換え・データの穴・未決事項 |
| 対応表 | Figma の画面・部品が、実装のどの画面・部品に当たるか | 1行1件。**共通にする候補**の列を持つ（実装側の部品づくりの材料になる） |
| 見た目の決めの一覧 | 色・字の段・すき間と角丸の段・影の実装との対応 | 実装のトークンの定義と、Figma の変数を対応させる |
| Figma の id の対応 | Figma のフレーム・部品の識別子 | 古い対応は `archive/` へ移す |
| 言葉の置き換え表 | 画面に出す言葉と、実装内の言葉 | 外へ出す文書の用語ルールと整合させる |
| データの穴の一覧 | Figma にあって実装のデータに無い物 | 別の件として扱う（表示の置き換えでは直らない） |

1本にまとまる規模なら、分けずに入口の中の節にする。分けるのは、更新の頻度や読み手が違うときだけ。

## 書き方

- **入口を1か所に決める。** ほかの文書の頭からそこを指す。各文書の頭に「読む順」を書く
- **実装の現在地は、実装リポの既定ブランチを読んで書く。** 時点（日付とコミット）を書く。実装は触らず、読むだけで対応表を作れる
- 置き換え済みの申し送りは削除せず `archive/` へ移し、本文の頭に移した先を書く
- 実装リポに書き込まない。分担ボードの issue を立てるときだけ `figma-design-workflow` の手順に従う
- 実装への申し送りも、会議やレビューの発言を逐語で書かず、決定と指摘だけを書く

## 差分の洗い出しと分担ボードで足すこと

`figma-design-workflow` の `references/handoff-to-impl.md` に加えて、次を守る。

- **かぶる件の本文を書き換えたら、コメントで知らせる。** 本文の書き換えはコメントの流れに出ないので、別の担当の AI が見落とし、同じ件を重ねて出すことがある。かぶる件は、先に着手を宣言してから作る
- **2回目の洗い直しを予定に入れる。** 1回目の件がほぼ入った後に洗い直すと、新しい差分と1回目の取りこぼしが見つかる
- 実装の側から決めを聞かれたら、決まりの持ち主（司令官）が決めて issue に書き、Figma が誤りなら Figma を直し、記録として PR にする

## 出口

- 実装の担当が、入口の1枚から読み始められる
- 対応表の「共通にする候補」が、実装側の部品づくりの材料になっている
- 実装の現在地に時点が書かれている
- ここまで済んだら、差分の洗い出し（工程 5）へ進み、`figma-design-workflow` の `references/handoff-to-impl.md` に従う。実装の傘を立てるときは `task-intake` → `umbrella-handoff`

## よくある失敗

- 構成が決まる前に申し送りを書き、後で全面に書き直す
- 見た目の決めの一覧を渡す直前に初めて作り、色の食い違いが差分の洗い出しで初めて見つかる
- 入口が複数あり、実装の担当が古い文書から読み始める
- 実装の現在地に時点が無く、いつの状態か分からない
