# screen-design-lifecycle — 画面デザインの工程の全体と始め方

新しい画面（または既存画面の次の版）のデザインを、傘ブランチ（司令官1人＋担当の会話）で進めるときの、**工程の順番と、各工程で作る文書**。
Figma の作り込みそのものの手順は `figma-design-workflow` が持つ。このスキルは、その前（準備・FB の取り込み・決め）と
後（申し送り・分担ボード・デモ後の受け口）をつなぐ入口になる。

主な読み手は、画面の設計を始める人と、傘の**司令官**。

別のスキルにした理由と却下案は ADR DOC-2611271321（本文は `docs/adr/` の `screen-design-lifecycle-skill`）にある。

## いつ使うか・使わないか

使う: 新しい画面や次の版の設計を始めるとき。進行中の画面で「次にどの文書を作るか」「番号をどう振るか」「この工程はどこへ渡すか」を迷ったとき。

使わない:

| 場面 | 向かう先 |
|---|---|
| Figma を書く作業（体制・1件の流れ・控え・点検・記録の書き方） | `figma-design-workflow` |
| Figma と実装の差分の洗い出しと分担ボードの issue の雛形 | `figma-design-workflow` の `references/handoff-to-impl.md` |
| 作業の振り分け（傘にするか・どこへ引き継ぐか） | `task-intake` |
| 孫の spawn・マージ・巡回 | `umbrella-orchestrator` |
| PR のレビューの往復 | `pr-review-loop` |
| 実装した画面の確認 | `ui-review` |

## 用語

| 用語 | 意味 |
|---|---|
| 司令官・担当・ユーザー | `figma-design-workflow` の用語と同じ。ユーザーは決めをする人間 |
| 決めの文書 | 「何をどうする」と「なぜ」を1枚にまとめた、決まっていることの正。決定が変わったら、まずこれを直す |
| 定義の文書 | 数字の分母・状態の言葉・外部の決まりを1枚にまとめた物。画面の案を作る前に読む |
| 記録 | 見た目の決めを変える件を、1件1ファイル1PR で残した文書（`figma-design-workflow` の `references/record.md`） |
| 申し送り | 実装の担当へ渡す文書の組 |
| 受け口 | デモを触った人の気づきが集まる場所（issue のコメント） |
| ボード | 受け口から仕分けた件を、状態つきで並べた表（同じ issue の本文） |

## 工程の全体図

| 工程 | 主な成果物 | 入口の条件 | 出口の条件 | 手順の持ち主 |
|---|---|---|---|---|
| 0 準備 | 画面のディレクトリ・現状の把握・共通方針の引き継ぎ・番号の凡例 | 画面を作ると決まった | 骨組みと凡例が置かれ、Figma より前に置く文書が揃っている | [references/start.md](references/start.md) |
| 1 FB の取り込み | 会議の要約・FB の一覧（`FB-` の番号） | FB の元（会議・レビュー）がある | 画面で対応が要る点が、決めの候補として並んでいる | [references/intake-to-decisions.md](references/intake-to-decisions.md) |
| 2 決めと記録 | 決めの文書・定義の文書・記録（`DEC-` の番号） | 決めの候補がある | 決めの文書に書かれ、ユーザーが確認した | 同上 |
| 3 Figma の作り込み | Figma の画面・記録・点検の結果 | 決めの文書と定義の文書がある | 点検が0件で、記録が PR で承認された | `figma-design-workflow` |
| 4 実装への申し送り | 申し送りの文書の組 | 画面の構成が固まった | 実装の担当が、入口の1枚から読み始められる | [references/handoff-docs.md](references/handoff-docs.md) |
| 5 差分の洗い出しと分担ボード | 差分の表（`GAP-` の番号。束の頭文字つき）・分担ボードの issue | 申し送りがある | 差分が束になり、取る人が名乗れる | `figma-design-workflow` の `references/handoff-to-impl.md` |
| 6 デモ後の受け口 | 受け口とボードを兼ねた issue（`BD-` の番号） | 実装がデモできる状態 | ボードの行が「済み」になる | [references/after-demo.md](references/after-demo.md) |

工程は一方通行ではない。デモ後の気づきが決めの変更になれば、工程 2・3 へ戻る。ただし戻り先でも、同じ手順（決めの文書を先に直す、記録を1件1PR で残す）を使う。

## 新しい画面を始める人の最初の一手

1. [references/start.md](references/start.md) を読み、画面のディレクトリを作る
2. 番号の凡例（出どころごとの接頭辞）を、文書の置き場の入口に書く
3. **Figma を作り始める前に**、次の3種を置く: 現状の把握・ページの役割と定義・決めの文書
4. 置けたら、工程 1（FB の取り込み）と工程 2（決め）を回し、決めの文書がユーザーに確認されてから `figma-design-workflow` を起動する

この順を守る理由: 決めの文書と定義の文書を後から作ると、傘の始めの決まりが計画書の本文に散り、担当が代わるたびに前提が揃わなくなる。
数字の分母や状態の言葉の食い違いも、画面を作った後の議論で初めて出て、作り直しになる。

## 誰が何を決めるか

- **ユーザー**: 見た目が目に見えて変わる物・意味が変わる物・決めの文書や記録で決められない物
- **司令官**: 数pxの余白など細かい不揃い、番号の配布、決めの文書の更新、仕分け
- **担当**: 割り当てられた範囲の作業。決めの文書と食い違ったら、自分で決めず司令官へ聞く

判断をユーザーに仰ぐのは、FB・記録・決めの文書のどれでも決められない物だけにする。小さな確認でユーザーを止めない。

## 文書を書くときの共通ルール

- 各文書の頭に「読む順」か「この文書の位置づけ」を書く。入口は1か所に決め、ほかの文書の頭からそこを指す
- 今の状態の正は、計画書の進捗テーブルと決めの文書。引き継ぎ文書は経緯の記録なので、時点（日付と参照したコミット）を書く
- 置き換わった文書は、本文を直さず、頭に「移した先」と印を書いて `archive/` へ移す。削除しない
- 会議やレビューの発言を逐語で書かない。決定と指摘だけを書き、人は役割（ユーザー・司令官・担当・レビュワー）で書く
- 画面の構成が決まる前に、実装への申し送りを書かない（使い捨てになる）
- 文章の言葉の基準は、このリポジトリの「AI が書く文章の言葉」に従う

## 渡す先のスキル

| 渡す場面 | スキル |
|---|---|
| 工程 3（Figma を書く） | `figma-design-workflow` |
| 工程 5（差分の洗い出し・分担ボード・実装の側からの質問への答え） | `figma-design-workflow`（`references/handoff-to-impl.md`） |
| 実装の傘を立てる | `task-intake` → `umbrella-handoff` |
| 孫の進行 | `umbrella-orchestrator` |
| 記録や申し送りの PR | `pr-review-loop` |
| 実装した画面の確認 | `ui-review` |
