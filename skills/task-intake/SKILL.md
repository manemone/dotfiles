# task-intake — 作業の入口（判断と振り分け）

**AI 不問。** 「こういうことをやりたい」を相談されていた側（以下「相談AI」）が
このスキルを読んで振る舞う。YAML frontmatter を除き自然言語のみで完結する。

## 1. 位置づけ

思いついた件を専用の会話（herdr のペイン）へ引き継ぎ、個別のトピックは孫にやらせる——
この流れを毎回迷わずに進めるための入口。毎回迷っていた次の3つの判断を肩代わりする。

- どのリポにまたがるか
- PR 1本か複数か
- 司令官をどのリポに置くか

```
「こういうことをやりたい」が固まる
  → 判断の3軸（§3）で判断する
  → 判断結果と根拠を人間に1回見せて確認を取る（§4）
  → 振り分ける
       1リポ × 1本  → 軽いハンドオフ（§5。このスキルの中で行う）
       それ以外     → umbrella-handoff（§6）
  → 引き継ぎ先への到達を確認して手を引く
```

**起動のしかた**: 人間が `/task-intake` で起動するか、相談AIが「この件は
`task-intake` で振り分けませんか」と提案し、人間が同意したら使う。勝手に発動しない。

## 2. 線引き（最重要）

`umbrella-handoff` §2 と同じ線引きを守る。このスキルを実行している間、相談AIは次を
**行わない**。

- 相談していた会話で実装を始めない
- 相談していた会話で計画書（`docs/planning/DOC-*_計画.md`）を書かない
- 1本規模の件でも、ブリーフを書く以上のこと（調査の深掘り・コードの試し書き）をしない。
  分からないことはブリーフの「先に潰すべき前提」に未確認と書いて実装AIに渡す

## 3. 判断の3軸

次の順で判断する。

### 3.1 どのリポにまたがるか

製品だけ／分析だけ／両方。製品リポ・分析リポ以外のリポも同じ扱いで数える。
「**ツール本体を変えるか**」「**実行履歴を残すか**」を、次のリポ間の役割分担表に
当てて決める。

| 何を | どこに |
|---|---|
| ツール本体（プロンプト・推論コード） | 製品リポ（`kenko` 等）。分析リポにコピーしない |
| 実行履歴（どの版で・何に・どう流して・何が出たか） | 分析リポ。製品リポのコミット SHA・PR 番号・実行コマンドを残す |
| 結論・意思決定 | Notion（分析リポの既存規約どおり） |

この表が問題にするのは、散らばること自体ではなく、**同じものが2か所にあることと、
片方から辿れないこと**である。

- ツール本体を変える → 製品リポが入る
- 実行履歴を残す → 分析リポが入る
- 製品リポのツールを**変えずに**使って分析するだけなら、製品リポは入らない（分析だけ）。
  使った版は分析リポの記録に残す
- 製品リポのツールを分析の都合で変えたくなったら、分析リポにコピーして直すのではなく
  製品リポに PR を出す（→ 両方）。その PR 本文から分析リポの分析ディレクトリへリンクを
  貼り、分析側の記録からは製品リポのコミット SHA・PR 番号を辿れるようにする（双方向）

分析リポ側で何をどう記録するか（`README.md` 等に残す項目）の正典は、分析リポの
`adhoc-analysis` スキルの `references/` にある「他リポのツールで回した実験の記録」の
規約である。このスキルには書かない。

### 3.2 規模: PR 1本か複数か

次のどれかに当てはまれば複数とみなす。

- 変更が、独立してレビュー・マージできる複数の単位に自然に分かれる
- 変更の関心事が複数に分離できる（例: 設定変更・テスト追加・ドキュメント更新が
  それぞれ別の判断を要する規模になっている）
- 完了までに複数セッション・複数日にまたがる見込みがある

**両リポにまたがる時点で PR は最低2本**（リポごとに1本）になる。

人間が「これは1本で済む」と言ったら、それに従う。

### 3.3 司令官をどのリポに置くか（複数のときだけ）

**「問いと結論が載るほうのリポ」に置く。**

- 評価が目的なら分析リポ
- 製品の変更が主目的で、評価が確認にすぎないなら製品リポ

1リポで複数の場合は、そのリポに置くだけなので判断は要らない。

### 3.4 振り分け

| リポ | 規模 | 行き先 |
|---|---|---|
| 1つ | 1本 | 軽いハンドオフ（§5） |
| 1つ | 複数 | `umbrella-handoff`（従来どおり） |
| 両方 | 各リポ1本ずつ程度 | `umbrella-handoff`。司令官を 3.3 で決めたリポに置き、もう一方のリポの PR を「他リポの孫」とする |
| 両方 | 複数 | 同上 |

**両リポにまたがるのに、軽いハンドオフを2本別々に立てない。** 各リポ1本ずつなら傘は
大げさに見えるが、2本を別々の会話に渡すと互いを知る場所が無くなり、片方から辿れなく
なる。3.1 の役割分担が問題にしているのはまさにこの状態である。

### 3.5 当てはめの例

**例1: 1つのリポ × 1本 → 軽いハンドオフ。** 直前に分析リポで回した栄養推定の実験と
同じ推定を、別の食事写真データに当てて結果を見せたい。分析リポのスキルでスライドに
まとめるところまでを「まずトライ」としてクイックにやりたい。

1. リポ: 分析だけ。推定に使うプロンプトやスクリプトは既存のものを使い、ツール本体は
   変えない。実行履歴は分析リポに残る
2. 規模: 1本。分析ディレクトリ1つとスライドで閉じ、独立にマージしたい単位に分かれない
3. 司令官: 要らない（1本）

→ 軽いハンドオフ。ブリーフを書き、分析リポに2ペインのワークスペースを立てて渡す。

**例2: 製品のモデル乗り換え評価 → `umbrella-handoff`、司令官は分析リポ。** 製品の
AI 解析で使っている旧モデルが近く廃止されるため、新しいモデルに乗り換えた場合の評価を
したい。

1. リポ: 両方。製品リポでモデルを差し替え（ツール本体の変更）、分析リポで評価結果を
   残す（実行履歴）
2. 規模: 最低2本（製品側の差し替え PR と、分析側の評価・記録 PR）
3. 司令官: 目的は「新モデルに乗り換えてよいか」の判断＝評価なので、分析リポ

→ `umbrella-handoff`。傘・計画書・司令官は分析リポに置き、製品リポの差し替え PR は
他リポの孫として製品リポの既定ブランチから切る。その PR のマージは人間が行い、PR 本文から
分析リポの分析ディレクトリへリンクを貼る。

## 4. 人間への確認（1回）

振り分ける前に、判断結果と根拠を**1回だけ**まとめて見せ、確認を取る。軸ごとに
小分けに聞かない。

```
この件の振り分け案です。

- リポ: <製品だけ／分析だけ／両方（リポ名）>。根拠: <ツール本体を変えるか・実行履歴を残すか>
- 規模: <1本／複数（おおよその本数）>。根拠: <どの目安に当たるか>
- 司令官: <リポ名／要らない>。根拠: <問いと結論が載るのはどちらか>
- 行き先: <軽いハンドオフ／umbrella-handoff>

この方針で引き継いでよいですか。
```

人間が判断を変えたら、それに従って振り分け直す（もう一度全体を見せ直す必要は無い）。

## 5. 軽いハンドオフ（1リポ × 1本）

別スキルにせず、このスキルの中で行う。判断の直後にしか使わず、単独で起動する場面が
無いため。

### 5.1 ブリーフを書く

雛形は [`references/brief-template.md`](references/brief-template.md)。節立ては
依頼（原文）／位置づけ／再利用できる資産／先に潰すべき前提／作業の骨子／
成果物の文体・用語で毎回指摘される点／引き継ぎ元に残っている未処理。

**置き場は、これから作るワークツリーの外**、対象リポの `{repo_parent}`（メイン
ワークツリーの親ディレクトリ）の直下に `handoff_<slug>.md` として置く。Pattern A なら
`~/work/<repo>/handoff_<slug>.md`。ワークツリーの中に置くと誤ってコミットされる。
scratchpad にも置かない（実装AIは別のセッションで動くため、読めないか消えている）。

`{repo_parent}` は対象リポのメインワークツリーで次を叩いて求める（1行目がメイン
ワークツリー）:

```bash
dirname "$(git worktree list --porcelain | sed -n '1s/^worktree //p')"
```

### 5.2 ワークスペースを作る

対象リポの**メインワークツリーに `cd` して**次を叩く（`ocw` は対象リポをカレント
ディレクトリから解決する。相談の会話が別のリポにいるまま叩くと、別のリポに
ワークツリーができる）:

```bash
cd <対象リポのメインワークツリーの絶対パス>
git fetch origin
ocw -H --no-commander <ブランチ名> origin/<既定ブランチ>
```

- **`git fetch origin` を省かない。** `ocw` は自分では fetch しないので、省くと
  `origin/<既定ブランチ>` はメインワークツリーで最後に fetch したときのまま使われる。
  メインワークツリーは人間が普段使う作業場所で、何日も fetch されていないことがある。
  古い土台から切ると、ブリーフの「再利用できる資産」に書いた最近のマージが実装AIの
  ワークツリーに無く、実装AIが迷うか同じものを作り直す
- `git fetch origin` は作業ツリーを触らない（`origin/*` を更新するだけ）ので、人間の
  メインワークツリーで叩いてよい。**`git checkout` / `git merge` / `git pull` は叩かない**
- `--no-commander` を付けて2ペイン（implementer / reviewer）にする。1本規模に司令官は
  要らない
- base-ref（`origin/<既定ブランチ>`）は省略しない。既定ブランチは対象リポで
  `gh repo view --json defaultBranchRef -q .defaultBranchRef.name` で確かめる
- ブランチ名は対象リポの規約に従う（例: 分析リポの単発分析なら
  `adhoc/<YYYY-MM>_<スラッグ>`）。規約が無ければ短い英語スラグにする

出力例:

```
workspace:   w0
implementer: w0:p1
reviewer:    w0:p2
```

**Herdr が使えない環境**（`HERDR_ENV` が立っていない）では、`-H` と
`--no-commander` を外して（`--no-commander` は `-H` 無しでは `ocw` がエラーで止まる）
（上と同じく `git fetch origin` を先に叩いてから）
`ocw <ブランチ名> origin/<既定ブランチ>` でワークツリーだけを作り
（`git worktree add` を直書きしない。`ocw.worktreeDir` の設定を迂回するため）、人間に
「新しい会話でこのワークツリーを開き、ブリーフ `<ブリーフの絶対パス>` を読んで
実装するよう指示してください」と案内して終える。§5.3・§5.4 は Herdr がある場合のみ。

### 5.3 日本語ラベルへ改名する

出力の `workspace:` の ID を、`umbrella-orchestrator` §5「ワークスペースラベル」の
書式（`<repo_name> :: <日本語の説明>`）で改名する。説明は全角16文字以内を目安に、
ブリーフのテーマから起こす。

```bash
herdr workspace rename <workspace_id> "<repo_name> :: <日本語の説明>"
```

**rename が失敗しても警告のみで続行する**（表示上の都合であり、引き継ぎを止める
理由にならない）。

### 5.4 implementer へ送る

送信手順・到達確認は `umbrella-orchestrator` §5「AI間送信手順（二段構え）」に従う。
正典はそちらにあり、このスキルは参照するだけで全文をコピーしない。宛先は §5.2 の
出力の `implementer:` 行のペイン。

送るのは**ブリーフの絶対パスと、次の1文だけ**。ブリーフの中身を打ち込まない。
「〜とだけ返事してください」のようなメタ指示も付けない（受け手がそれを実行して
返事だけして停止する）。

```
ブリーフ <ブリーフの絶対パス> を読んで実装してください。PR 作成後は /pr-review-loop を回してください。マージは人間が行います。
```

### 5.5 手を引く

到達を確認できたら、相談AIはここで手を引く。人間には「`<repo_name>` の
`<ブランチ名>` へ引き継ぎました（ブリーフ: `<ブリーフの絶対パス>`）」とだけ報告する。

ブリーフは一時ファイルである。実装AIが PR 本文に必要な内容を転記したあとは消してよいが、
**消すのは人間か相談AIであり、実装AIではない**。勝手に消さない（実装AIがまだ読み返す
可能性がある）。

## 6. 複数のとき: `umbrella-handoff` へ引き渡す

`umbrella-handoff` を起動し、その手順に従う。このスキルで決めたことを次のように
引き継ぐ。

- **傘を立てるリポ**: 3.3 で決めた司令官のリポ。`umbrella-handoff` §5 の手順（`ocw -H`、
  ブリーフの配置）は、すべてそのリポのワークツリーの中で叩く。もう一方のリポには
  傘を立てない
- **ブリーフの「関係するリポ」節**: 司令官のリポを1行目にして、関係する全リポの名前・
  メインワークツリーの絶対パス・`owner/name`・既定ブランチ・そのリポで守るべき規約の
  在処を書く。司令官はこれを計画書の `## 関係するリポ` 節へ転記し、他リポの孫を扱う
  （`umbrella-orchestrator` §2.1・§3.2「他リポの孫の spawn」）
- **ブリーフの「司令官をこのリポに置く理由」節**: §4 で人間に見せた 3.3 の根拠を書く
- 1リポで複数の場合は、「関係するリポ」節に「傘のリポのみ」と1行書けばよい

孫の分割・順序・他リポの孫をどう切るかは司令官の仕事であり、相談AIは決めない
（`umbrella-handoff` §2）。

## 7. 採らなかった案

- **軽いハンドオフを別スキルにする**: 判断の直後にしか使わず、単独で起動する場面が無い
- **両リポにまたがる件で軽いハンドオフを2本別々に立てる**: 片方から辿れなくなる（3.4）
- **このスキルを分析リポに置く**: 分析リポで開いた会話でしか読み込まれない。思いつく
  会話は製品リポで作業中かもしれないし雑談かもしれない。土台（`umbrella-handoff` /
  `umbrella-orchestrator` / `ocw` / herdr 前提の道具）もすべて dotfiles にある

決定の経緯は ADR DOC-2610081412 を参照。この ADR は dotfiles リポジトリの `docs/adr/`
配下にあり、配布された本スキル単体からは参照できない。
