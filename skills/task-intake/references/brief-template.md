# 軽いハンドオフのブリーフ雛形

`task-intake` §5「軽いハンドオフ」で、相談AIが実装AIへ渡すブリーフの雛形。
PR 1本規模（1リポ × 1本）の件にだけ使う。複数 PR 規模の件は `umbrella-handoff` §3 の
雛形を使う（こちらは計画書の material であり、節立てが違う）。

節立ては、実際に1本規模の分析を別の会話へ引き継いだときのブリーフを一般化したもの。
各節の書き方の注意:

- **依頼の原文を要約に置き換えない。** 実装AIは人間と直接話していないので、要約すると
  人間が本当に求めている条件（「クイックに」「まずトライ」等）が落ちる
- **分からないことは分からないと書く。** 「先に潰すべき前提」に未確認と書いておけば、
  実装AIは着手時に人間へ確認する。推測で埋めると、実装AIはそれを事実として扱う
- **書くことが無い節は「なし」と1行書く。** 節ごと消すと、書き忘れたのか無いのかが
  実装AIに区別できない

```markdown
# 引き継ぎ: <一言テーマ>

作成 <YYYY-MM-DD> / 引き継ぎ元の会話: <どの相談の途中で出てきた件か>

**これは一時ファイルである。** PR 本文に残すべき内容（依頼の原文・位置づけ・前提の
確認結果）は PR 本文へ転記すること。このファイルは転記後に人間か引き継ぎ元が消す
（実装AIは消さない）。

---

## 1. 依頼（原文）

> （人間の発言をそのまま引用する。要約しない。複数回に分かれていれば全部引用する）

読み取り:
- **目的**: （何のためにやるのか。本番の成果物か、先行して手応えを見るトライか）
- **成果物**: （何を作れば終わりか。形式・置き場）
- **条件**: （「クイックに」など、やり方を縛る条件。何を繰り返さなくてよいか）

## 2. 位置づけ

（既存の分析・機能・過去の PR のどれの延長にあたるか。関係する README や問いの木の
該当箇所をパスで示す。対象リポの規約が置き場の判断を人間に確認せよと定めているなら、
「置き場は着手時に人間に確認すること」と書き、有力案だけを添える）

## 3. 再利用できる資産

（すべて既定ブランチにあるか、未マージの PR にあるかを明記する）

| ファイル | 役割 | 差し替えが要る箇所 |
|---|---|---|
| （パス） | （何をするものか） | （そのまま使える／何を変えるか） |

（**変えてはいけない前提**があれば、理由とともにここに書く。
例: 「この実行方法を使うのは本番への影響を避けるため。ここは変えないこと」）

（他リポのツールをそのまま使う場合は、そのリポの名前・使う版（コミット SHA や
タグ）の決め方をここに書く。ツール本体を変える必要が出たら、この1本の範囲を超える
ので人間に相談すること、と添える）

## 4. 先に潰すべき前提

**着手の最初に確認すること。** 結果次第で設計が分かれるものは、分岐ごとに
どうなるかを書き、「人間に確認してから設計を決めること」と明記する。

### 4.1 外部依存が生きているか

（使うモデル・API・外部サービスの提供終了日、廃止の予定など。確認方法があれば書く）

### 4.2 認証

（必要な認証と、切れていたら人間に何を頼むか）

### 4.3 データの所在・件数・取り扱い範囲

（どこにあるか、どう抽出するか、何件か。個人情報やセンシングデータを含むなら、
対象リポのコミットしてよいものの規約を引く）

### 4.4 設計が分かれる分岐点

（例: 正解値があるか無いかで評価指標が変わる、など。分岐ごとの行き先を書く）

## 5. 作業の骨子

1. （対象リポのどのスキル・どの工程から始めるか）
2. （重複確認: 既定ブランチと open PR の両方で既出でないことを確かめる）
3. （4 の前提をどの工程で潰すか）
4. ...
5. PR を作成したら `/pr-review-loop` を回す。マージは人間

## 6. 成果物の文体・用語で毎回指摘される点

（このリポ・この種類の成果物で、人間が過去に繰り返し直してきた点。成果物の質に
直接効くので、思い当たるものは全部書く。無ければ「なし」）

## 7. 引き継ぎ元に残っている未処理

**この引き継ぎとは独立。新しい会話では触らなくてよい。**

（引き継ぎ元の会話に残っている未コミットの作業・未決の論点など。実装AIが同じ
ワークツリーやブランチに出くわしたときに誤って触らないよう、場所と状態を書く。
無ければ「なし」）
```
