# pr-group-request — 自分の PR 群のレビューを他人に頼む準備をする

**AI 不問。** このスキルを読んでいる AI（以下「依頼者AI」）が、人間（PR 群の作者本人）の
代わりにレビュー依頼の準備をする。YAML frontmatter を除き自然言語のみで完結する。実行可能な
スクリプトは同梱しない（手順中のコマンドは例であり、そのまま使っても書き換えてもよい）。

決定の経緯と却下案は ADR DOC-2609270420 を参照。

## 0. 線引き

- 対象は**自分の PR** だけ。他人の PR をレビューするのは `pr-group-review` の担当
  （他人の PR の本文は書き換えない）
- 外部への書き込みは**自分の PR の本文の更新だけ**で、それも**人間の確認後**に行う（§4）
- **チャット（Slack 等）へ投稿しない。** 依頼文は下書きを人間に渡し、まとめの HTML の添付と
  投稿は人間が行う（§5）
- 返ってきた指摘への対応はこのスキルの担当ではない。PR ごとに `pr-review-loop` で回す（§7）

## 呼び出し

```
/pr-group-request [PR の URL / 一覧 / 傘ブランチの計画書のパス / テーマ名 など]
```

- 引数は自由形式。PR の URL の列挙、傘ブランチの計画書、作業メモなどを受け取る
- 既存の状態ディレクトリのテーマ名が与えられたら、その `state.json`（`role` が `requester`）を
  読み込んで続きから行う（PR が増えた、本文を直したい、依頼文を作り直したい、など）
- 何も与えられなかったら、人間に対象（PR 群の手がかり）を尋ねる

## 参照文書

地図のテンプレート・継ぎ目チェックリスト・状態ファイルの形式・まとめの HTML の雛形は、
レビュワー用スキル `pr-group-review` の `references/` にあるものを**そのまま使う**
（このスキルには写しを持たない）。スキルは兄弟ディレクトリとして配られるので、このファイルからの
相対パスで届く。

| ファイル | このスキルでの使い道 |
|---|---|
| `../pr-group-review/references/state-format.md` | 状態ディレクトリの置き場所・構成、`state.json` の形式（§3.7 が依頼者用のキー） |
| `../pr-group-review/references/group-map.md` | 地図の項目定義と作り方（§2）、PR 本文・依頼文に貼る Markdown テンプレート（§4） |
| `../pr-group-review/references/seam-checklist.md` | 継ぎ目の自己チェック（冒頭の注意を必ず読む） |
| `../pr-group-review/references/summary-template.html` | まとめの HTML の雛形（依頼者用での読み替えは雛形の先頭コメント） |

## 1. PR 群を列挙する

### 1.1 状態ディレクトリを作る

状態ディレクトリのベースは `${PR_GROUP_REVIEW_DIR:-$HOME/work/reviews}`（`state-format.md` §1）。
レビュワー用と同じ置き場を使い、`role` で区別する。

テーマ名を人間に確認して決め、`$PR_GROUP_REVIEW_DIR/<今日の YYYY-MM-DD>-<テーマ>/` を作って
`git init` する。`state.json` を `role: "requester"`・`format_version: 1` で作る。
このスキルが状態ディレクトリに足すファイルは次のとおり（`state-format.md` §2 の `drafts/` は使わない）。

```
<YYYY-MM-DD>-<テーマ>/
├── state.json      # 正典。role: "requester"
├── summary.html    # まとめの HTML（§5 で依頼文に添付してもらう）
├── request.md      # チャット用の依頼文の下書き（§5。state.json の requester.request_draft）
└── notes/          # 任意。PR 本文の更新前の写し（§4）など
```

### 1.2 複数の情報源から列挙して突き合わせる

自分の PR でも、**1 つの情報源だけで列挙しない**（ADR DOC-2609270420 §3.8。レビュワー側で、
リストに無い PR が別の文書にだけ載っていたことがある。依頼する側が漏らせば、レビュワーは
その PR を見ずに終わる）。手に入るものを全部当たる。

- 人間が示したリスト、作業メモ
- 傘ブランチの計画書（§1.3）
- 各 PR の本文に書いた関連 PR のリンク
- 自分の PR の検索。ブランチ名は `--head` で探す

  ```sh
  gh search prs --author @me --state open --created ">=<日付>"
  gh search prs --author @me --state open --head "<ブランチ名>"
  gh search prs --author @me --state open "<チケット番号>"
  ```

- 積んでいる PR を上下の両方向にたどって見つかる PR（`group-map.md` §2 手順 2）

情報源ごとに見つかった PR を `state.json` の `sources` に記録し、**どれかにだけある PR を人間に
示して**一覧を確定してもらう。各 PR が自分のものであることも確かめる（`author` が
`gh api user --jq .login` と一致するか）。一致しない PR があれば、その PR は対象から外して人間に
伝える（他人の PR の本文は更新しない）。

確定したら `prs` を書く。`clone` には自分の作業場所（その PR のブランチがある worktree）のパスを
入れる。`heads` の 1 件目に、依頼する時点の head SHA と base の SHA を記録する（依頼後に何が
変わったかを後で説明できるようにするため）。

```sh
gh pr view <N> -R <owner>/<repo> --json headRefOid,baseRefName,baseRefOid,state,title,author
```

### 1.3 傘ブランチの計画書から列挙する

`umbrella-orchestrator` 形式の計画書（`umbrella-orchestrator` の SKILL.md §2）があれば、PR 群の
骨格はそこから作れる。計画書は `sources` に `kind: "umbrella_plan"`・`ref: <計画書のパス>` で残す。

- **進捗テーブル**（`| 孫 | ブランチ | 内容 | 状況 |`）の 1 行が孫 1 本に当たる
  - 「状況」列が `✅ PR #XX マージ済` の行は、その `#XX` が孫の PR（base は傘ブランチ。既に
    傘ブランチへマージ済み）
  - `🔄 実装中` / `⬜ 待機中` の行は、まだ PR が無いか未完成。`gh pr list --head <ブランチ列の値>` で
    PR の有無を確かめ、無ければ地図に「未作成」として載せる（レビュー対象からは外すかを人間に確認する）
  - 「孫」列の番号と、表の下の「依存:」の記述が、地図の「依存」と「マージと適用の順序」の材料になる
  - 「内容」列がグループ・役割の材料になる
- **傘ブランチ → 既定ブランチの PR**（`umbrella-orchestrator` §3.4 の `/finalize` で作るもの）が
  あれば、それも列挙に入れる。地図の順序の最後の段は「傘 → 既定ブランチのマージ（人間）」になる
- 他人に頼むのが「孫の PR を 1 本ずつ」なのか「傘 → 既定ブランチの PR を、孫の PR を読む順の
  案内付きで」なのかは、人間に確認して決める。孫が既に傘ブランチへマージ済みなら、後者のほうが
  レビュワーのコメントの置き場が 1 つにまとまる
- 計画書の「決定的な制約」「スコープ外」、ADR の孫があればその ADR が、地図の「未決の ADR」と
  依頼文の「前提」の材料になる
- 複数のリポにそれぞれ傘がある場合は、計画書ごとに `sources` を 1 件ずつ足して突き合わせる

計画書の内容のうち、公開してよくないもの（社内の名前・URL など）を PR 本文や依頼文へ写さない。
依頼先の範囲（社内か社外か）を人間に確認してから書く。

## 2. 地図を作る

`../pr-group-review/references/group-map.md` を読んで、§2「作るとき」に従って地図を作る。
`map.source` は `requester`。地図は `state.json` の `map` に書く。

- 自分の PR なので、依存・手作業・ロールバックは差分を読み直すだけでなく、**自分が知っている
  前提を書き出す**（レビュワーが差分から読み取れない前提ほど、地図に書く価値がある）
- 手作業の工程の「誰が」は、自分・チームの誰か・インフラ担当など、実際にやる人を書く。
  決まっていなければ「未定」と書き、依頼文の確認事項にする
- 単体 PR（1 本だけの PR 群）では、`group-map.md` §1 末尾のとおり「1 本だけの表」に縮退させてよい

## 3. 継ぎ目を自分でチェックする

`../pr-group-review/references/seam-checklist.md` の全項目を、頼む前に自分で見る。
**冒頭の注意（事故の種は照合より順序と手作業の側にあった）を読み、§2.6〜§2.8 を厚く見る。**

- 各項目の結果を地図の「リポ間の照合表」に起こし、`状態` を `一致` / `不一致` / `未確認` で埋める
- 見つけた問題は `state.json` の `findings` に記録する（形式は `state-format.md` §3.6。依頼者用では
  「自己チェックの結果」として使う。`thread` は使わない）
- 自分で直せるものは、**依頼を出す前に**直す。直したら `status` を `resolved` にし、`history` に
  直したコミットを残す。依頼前なら履歴を整えるための force-push をしてもよいが、依頼を出した後は
  しない（§6）
- 直さずに残すもの（別の PR で直す、判断をレビュワーに仰ぐ）は、依頼文と PR 本文の
  「マージ前の前提」または確認事項に載せる
- `未確認` が残る項目は、隠さずに依頼文で「ここは未確認なので見てほしい」と頼む

## 4. 各 PR の本文を更新する（人間の確認後）

各 PR の本文に、次の 2 つを書き足す。

- **PR 群の中での位置**: どのグループか、どの PR に依存し、どの PR から依存されているか、
  地図の順序の何番か。stack なら上下の PR
- **マージ前の前提**: この PR をマージ・適用する前に済んでいる必要があること（他の PR のマージ、
  スキーマ・インフラの適用、手作業の工程、未決の ADR）

書き方:

- 既存の本文は消さず、**区切りのコメントで囲んだ節を足す**。2 回目以降の更新ではこの節だけを
  差し替える

  ```markdown
  <!-- pr-group-request: begin -->
  ## PR 群の中での位置
  …
  ## マージ前の前提
  …
  <!-- pr-group-request: end -->
  ```

- 地図の全体は代表の 1 本（順序の先頭の PR、または傘 → 既定ブランチの PR）にだけ
  `group-map.md` §4 のテンプレートで貼り、他の PR からはその PR へリンクする（同じ表を全 PR に
  貼らない。どれかを直したときにずれる）
- 投稿先のリポに PR 本文のテンプレートや規約（`.github/pull_request_template.md`、AGENTS.md、
  `docs/` 配下の PR の作法など）があれば、それに従って節の置き場所・見出しを合わせる

手順:

1. 各 PR の現在の本文を `notes/pr-body-<repo>-<N>.before.md` に保存する

   ```sh
   gh pr view <N> -R <owner>/<repo> --json body --jq .body > "notes/pr-body-<repo>-<N>.before.md"
   ```

2. 更新後の本文を作り、**PR ごとに差分を人間に見せて、更新してよいかの明示的な了承を得る**
3. 了承を得た PR だけ更新する

   ```sh
   gh pr edit <N> -R <owner>/<repo> --body-file "notes/pr-body-<repo>-<N>.after.md"
   ```

4. `state.json` の `requester.pr_bodies` に更新した PR と日付を記録する

権限の仕組み（auto mode の分類器など）に更新を止められたら、コマンドを人間に渡して
「自分で実行してください」とはしない。止められたことと理由を人間に伝え、許可を得たうえで
依頼者AI自身が更新する（ADR DOC-2609270420 §2.5）。

## 5. 依頼文の下書きとまとめの HTML を作る

### 5.1 まとめの HTML

`../pr-group-review/references/summary-template.html` を状態ディレクトリへ `summary.html` として
コピーし、`state.json` の内容で埋める。雛形の先頭コメントの使い方に従う。依頼者用では、
「指摘」節を「自己チェックの結果」と読み替え、「投稿の記録」節は消してよい（雛形の先頭コメント）。
自己完結した 1 ファイルにし、外部の CSS / JS / フォント / 画像を読み込まない。

### 5.2 依頼文の下書き

`request.md` に、チャット（Slack 等）に貼る依頼文を書く。**まとめの HTML を添付する前提**で書き、
依頼文の本体は短くする（詳細は HTML と PR 本文に任せる）。含めるもの:

1. 何の PR 群か（目的を 1〜2 文）と、PR の本数・リポ数
2. PR の一覧（URL）と、**読む順**（地図の順序、または stack の下から）
3. 特に見てほしいこと。構造・順序・手作業を先に見てほしい、と書く（設計の手戻りは大きいため。
   ADR DOC-2609270420 §2.5）。自己チェックで `未確認` が残った項目もここに挙げる
4. マージ前の前提の要約と、判断を仰ぎたい点（未決の ADR、未定の担当など）
5. レビュー中の作者側の運用の宣言（§6。レビュワーへのお願いではない）
6. 返信の期限や、急ぎかどうか（人間に確認して書く。決まっていなければ書かない）

「まとめの HTML を添付してください」と人間に伝える場所（ファイルのパス）も、下書きの外で添える。

### 5.3 人間に渡す

`request.md` の内容と `summary.html` のパスを人間に示す。**投稿と添付は人間が行う。** AI は
チャットへ投稿しない。Notion へのアップロードは、人間が求めたときだけ行う（任意の追加手段）。

渡したら、状態ディレクトリで `git add -A && git commit -m "request: drafted"` のようにコミットする。
`state.json` の `requester.request_draft` に `request.md` を記録しておく。

## 6. レビュー中の作者側の運用を依頼文で宣言する

依頼文（§5.2 の 5）に、**作者（依頼する側）がレビュー中にどう振る舞うか**を宣言として書く。
レビュワーへのお願いではない（レビュワーは相手の PR に push する立場ではない）。レビュワーが
知りたいのは「前回のレビュー以降の変更で差分を追ってよいか」であり、それに答えるためである。

- **指摘への修正は追加のコミット（fixup コミット）で積み、force-push や rebase をしない。**
  force-push / rebase をすると、GitHub の「前回のレビュー以降の変更」が壊れ、レビュワーは
  `git range-diff` で差分を取り直すことになる（ADR DOC-2609270420 §2.8）
- 履歴を整える（fixup を潰す）のは、承認をもらってからマージの直前に行う。base の更新などで
  やむを得ず途中で rebase するときは、その旨を PR のコメントで知らせる
- 指摘への返事は、各スレッドに書く

依頼文での書き方の例:「指摘への修正は追加のコミットで積み、force-push はしません。base の更新で
やむを得ず rebase するときは PR のコメントでお知らせします。返事は各スレッドに書きます。」

依頼者AI自身がこの宣言を守る。依頼を出した後に自分の PR を直すときは、追加のコミットで直し、
force-push しない。

## 7. 返ってきた指摘への対応

返ってきた指摘への対応（修正・返信）は、このスキルでは行わない。**PR ごとに `pr-review-loop` で
回す。** その PR の作業場所で `/pr-review-loop <PR 番号または URL>` を起動する。修正を通常の push
（force push 禁止）で積む点は §6 の宣言と合う。

**ただし `pr-review-loop` の止まり方とマージの挙動に注意する。** `pr-review-loop` は Herdr の
reviewer ペインにいる**手元の AI レビュワー**との往復で回り、その AI の承認でループを抜ける。
さらに base が傘ブランチで、リポの AGENTS.md が傘ブランチ方式を明記していれば、承認後にそのまま
`gh pr merge --squash --delete-branch` まで進む（`pr-review-loop` の SKILL.md の Phase 7）。
依頼先のレビュワー（他人）の再レビューや承認は待たない。そのまま使うと、依頼先が修正を見直す
前に PR がマージされ、他人に頼んだ意味が失われる。

- 他人にレビューを頼んだ PR で `pr-review-loop` を起動するときは、**「マージしない。依頼先の
  レビュワーの承認を待ち、マージは人間が判断する」と明示して起動する**（例:
  `/pr-review-loop <PR> マージはしないこと。承認後は報告で止まる`）。手元の AI の承認が出ても、
  そこで報告して止まらせる
- 依頼先の再レビュー・承認を確かめるのは人間（または依頼者AIが `gh pr view` でレビューの状態を
  読んで人間に伝える）であり、マージするかどうかは人間が決める
- 複数の PR にかかる指摘（順序・手作業・継ぎ目）は、直す PR を決めてから、その PR で回す。
  地図の順序や前提が変わったら、このスキルを再起動して地図・PR 本文（§4）・`summary.html` を
  更新する
- `pr-review-loop` が使えない環境（Herdr の外など）では、同じ作法（追加のコミットで直す、
  force-push しない、スレッドへ返信する）で対応し、マージは人間に任せる

状態ディレクトリは、PR 群がマージされるまで残しておく（再起動時に地図と前提を読み直すため）。
