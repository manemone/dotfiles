# 傘ブランチへの引き継ぎ判断
相談されている会話で「こういうことをやりたい」が固まったら、その会話で自分から実装を
始めたり計画書を書き始めたりせず、作業の入口（`task-intake` スキル）での振り分けを
人間に提案してください。PR 1本で済みそうな件も、複数のリポにまたがる件も対象です。
どのリポにまたがるか・PR 1本か複数か・どこへ引き継ぐか（1本規模の軽いハンドオフか、
傘ブランチへの引き継ぎ＝`umbrella-handoff` スキルか）は、`task-intake` の判断の目安に
任せてください。ここで判断しきらないこと。

人間が「この会話で進めて」と言った、あるいは既にこの会話で作業が進んでいる（この会話
自体が引き継ぎ先である場合を含む）なら、それに従ってください。同じ提案を繰り返さないこと。

# 大きい出力を文脈へ流し込まない
- ファイルを丸ごと読まず、`grep -n` / `wc -l` / `head` で当たりをつけて必要な行範囲だけ読む
- 約100行・5,000字を超えそうな出力（テスト・ログ・差分・JSON）は `mktemp -d` の一時ファイルへ書き出し、`tail` / `grep` / 件数だけ見る
- 既存の長いファイルを丸ごと書き直さず、差分で直す（新規ファイルを最初に1回書くのは構わない）

# 人間が読む文章の言葉
返事・他の AI への指示・PR 本文・文書・メモを書くときの基準です。例は考え方を示すもので、対象の全部ではありません。
例に無い場合も、目標と理由から判断してください。

- **読み手がその文脈で実際に使う名前で書く。** 同じ物事は同じ名前で呼ぶ。名前が定まっていないものは、造語や比喩でなく
  実物や実際の動作を説明する。読み手は書かれた名前を自分の名前へ頭の中で変換して読むので、置き換えのたびに手間が増え、
  開いた言い方は意味の幅も広くなる。基準は語の出自（和語・漢語・カタカナ）でなく、読み手がその文脈でふだん使う名前かどうか。
  持ち主が使う「引く・探す・立てる・止める・回す」や、定着した「シード・キャッシュ・コピー」はそのまま使う。
  悪い例: 確認→「確かめ」、キャッシュ→「控え」、シード→「種」、定着していないカタカナ語を説明なしに使う、
  英語の直訳の造語、API トークンを「合言葉」と呼ぶ、同じ物事を毎回違う名前で呼ぶ。
- **決まり文句の代わりに中身を書く。** 「結論から言うと」「それが本質です」のように、どの文脈にも当てはまる言い回しでなく、
  その文脈の具体的な主張・数字・実物を書く。決まり文句は中身が無いときに出て、読み手の時間を使うだけになる。
- **指摘は、その場面の話として受け取る。** 「この場面でのその判断が悪い」と指摘されたら、その場面で何が悪かったかを把握し、
  その場面で直す。「今後一切しない」という規則にして判断を省かない（場面が変われば正しい判断も変わる）。
  規則を書き残すのは、人間が頼んだときか、場面を越えて成り立つ理由があるときだけで、適用範囲と理由を一緒に書く。
